你有没有过这种体验:让 LLM 写一段代码或一封邮件,第一版总差点意思,可你手动指出两处问题、它一改就顺了。Self-Refine 做的,就是把"你来挑错"这一步也交给模型自己——同一个模型先生成初稿,再给自己写反馈,然后照着反馈改,循环几轮。不用额外训练、不接外部工具,只靠三段 Prompt 就能把答案质量往上抬一截。它最早由 Madaan 等人在 2023 年提出,思路简单到你今天下午就能接进现有管线。这篇讲清它怎么跑、上限卡在哪、以及别踩的坑。

## 一次生成为什么不够

LLM 是自回归逐字往外吐的,写下第一个 token 时它并不知道结尾会怎样,更没机会回头审视整体。于是初稿常犯"局部对、全局虚"的毛病:代码能跑但漏了边界,文案通顺却没扣住需求,方案完整但某一步经不起推敲。而你在对话里补一句"再考虑下空输入",它立刻就能补上——这说明知识本就在模型里,缺的只是一次"回看"的触发。Self-Refine 的价值,就是把这次回看从靠你手动,变成固化进流程,让模型每次都自动多审一遍,不必等你开口。

## 三步循环:生成、反馈、改写

核心是三个角色化的 Prompt,共用同一个模型:generate 产出初稿,feedback 针对初稿写具体意见,refine 拿初稿加意见产出新稿。新稿再喂回 feedback,如此往复,直到没意见或到轮数上限。

```python
draft = llm(f"任务:{task}\n请给出你的方案。")
for i in range(max_rounds):
    fb = llm(f"任务:{task}\n当前方案:\n{draft}\n"
             f"请指出最多3条关键问题,每条给出具体位置、后果、可执行的修改动作。"
             f"若确实没有明显问题,只回复 DONE。")
    if "DONE" in fb:
        break
    draft = llm(f"任务:{task}\n原方案:\n{draft}\n反馈:\n{fb}\n"
                f"请据此改写,只输出改写后的完整方案。")
```

关键在于:三段 Prompt 要用不同的视角和"人设",别让模型在同一次调用里既写又评。写的时候它在为自己辩护,分开调用、换个身份来审,它才肯真的挑刺。这也解释了一个反直觉现象:同一份内容,你分两次问它,得到的批评往往比一次问尖锐得多。

拿个最小例子体会流程。任务是"写个算列表平均值的函数"。初稿模型给出一行 `sum(xs)/len(xs)`,能跑,但也就到此为止。feedback 这轮切成审查者视角,它挑出三条:空列表会触发除零异常、没有类型校验、缺 docstring。refine 拿着这三条改写,补上空判断返回 0、加了类型提示和一句文档说明。前后的差距不来自模型突然变强,而来自那次被强制的"回看"——同一个模型,只是多给了它一个当审查者的机会,漏掉的边界就补回来了。你甚至能把这段审查者反馈直接贴进 code review,人读着也在理——这恰好说明模型的评审能力本就够用,平时只是没被单独调出来而已。

## 反馈质量决定天花板

整套方法的上限,几乎全押在 feedback 这一步。反馈越具体、越可执行,refine 才越有抓手;泛泛一句"可以更好",等于没说还白耗一轮。对比三种反馈风格,差距很直观:

| 反馈写法 | refine 的结果 |
| --- | --- |
| "这段代码有点问题,再优化下" | 模型瞎猜着改,常越改越糟 |
| "整体不错,没什么大毛病" | 无从下手,原地打转空耗 token |
| "第3行未处理 list 为空,会抛 IndexError;加一行空判断返回默认值" | 精准命中,一次改对 |

所以 feedback Prompt 里要强制模型定位到具体位置、指出具体后果、给出具体动作,最好按"问题—影响—建议"三段式把输出结构卡死。你把评判标准写得越硬,模型的自评就越少放水,refine 的收益也越实在。有条件的话,再给它一份任务专属的检查清单当锚点,自评会更稳。还有个小细节:让 feedback 只挑"最关键的 3 条",而不是罗列所有毛病。反馈太长,refine 会顾此失彼、抓不住重点;限量反而逼模型排序,先解决最伤的那几处。

你可能会说:我在 Prompt 末尾加一句"请自行检查并改正"不就行了?差别在于隔离。单段 Prompt 里,模型是在同一条思路上顺着往下写,惯性会让它替刚写的内容找补,很难真的推翻自己。Self-Refine 把生成和评审拆成两次独立调用,评审那次看不到"我刚才为什么这么写",只面对一份待审的成品,才更容易客观挑错。它和 Reflexion 也不一样:Reflexion 强调把失败经验写成长期记忆带进下一次尝试,Self-Refine 更轻,只在单个任务内做几轮闭环,不跨任务留痕,接起来也更简单。

## 自评在哪可信,在哪失灵

Self-Refine 的隐藏前提是:模型"看出问题"的能力强于"一次写对"的能力。对写作润色、代码可读性、逻辑自洽这类偏主观的任务,这个前提通常成立,自评很有用。但对有唯一正确答案的任务——数学计算、事实核查——模型可能自信地把对的判成错、把错的留着,越迭代越偏。这类场景别让它自己当裁判,优先接外部信号:代码跑单元测试、数学过验算器、事实查检索结果,拿客观反馈喂回 refine,才是可靠的用法。你也可以折中——让模型自评负责"提出怀疑",把最终拍板权交给一个更硬的外部校验,两者分工。一句话:主观任务信自评,客观任务信外部信号。

一条笼统的反馈容易只盯住一个维度,别的问题就漏网了。更稳的做法是让 feedback 分维度输出:正确性、完整性、可读性各给一条独立意见,refine 再逐条对齐,覆盖面立刻宽很多。temperature 也值得分开设:generate 和 refine 用略高的温度保持措辞多样、敢下手改;feedback 用低温度求稳,别让评判本身忽冷忽热、每轮标准都在变。算力富裕时还能并行采样几份初稿,各自 refine 一轮,最后挑最好的那份留下,本质是用采样多样性换质量,特别适合塞进离线批处理,不占用户等待的时间。

## 什么时候该停,成本怎么算

迭代不是越多越好。多数任务两三轮就收敛,再往下容易来回改同一处,甚至把对的改错。设三重停止条件:模型回复 DONE、达到 max_rounds、新旧稿相似度过高说明已无实质变化。我生产里一般把 max_rounds 设 3,每轮记录 diff,一眼就能看出它是在改进还是在空转。成本也要算清:一轮完整迭代等于反馈加改写两次额外调用,三轮就是初稿之外再叠六次,延迟和费用都成倍涨。对实时场景,要么只对低置信度的初稿触发 Self-Refine,要么把它挪到离线批处理,别硬挂在用户等待的主链路上。还有一条护栏别忘:给每轮结果设个质量闸,如果某轮改完反而在你的评测集上掉分,就回滚到上一版,把"越改越糟"挡在上线之前。说到底,Self-Refine 不是万能钥匙,它只是把"多看一眼"这件本该做的事自动化了;真正决定收益的,始终是你给反馈这一步定了多硬的标准。

## 踩坑清单

- feedback 和 refine 必须分成两次调用,揉成一段会让模型敷衍自评
- 反馈强制"具体位置+具体后果+具体动作",禁止"挺好的""可优化"这类空话
- 一定留 DONE 出口,否则模型为改而改,把好答案改坏
- max_rounds 封顶,别信"多迭代必更好",两三轮通常见顶
- 每轮存 diff,发现来回震荡立刻提前停
- 有客观标准的任务(能跑测试的代码、可验算的数学)优先用外部信号当反馈,比模型自评靠谱得多
