你调了一周 Prompt，质量分从 82 冲到 89，准备上线。三天后财务找上门：这版 Token 消耗翻了两倍。质量从来不是免费的，而你的 Eval 记分卡上压根没有成本这一栏。质量、延迟、成本是一个三角，只盯一个角，另外两个会在生产里反咬你。

## 为什么单维度 Eval 会骗你

单看质量分，所有"更聪明"的方案都显得划算。换大模型、加 few-shot、套自我反思，准确率确实往上走，但这些动作无一例外都在烧延迟和 Token。离线脚本只打印一个质量数字，你看不到代价，等账单来了才发现提升是用三倍成本换两个百分点。

真正的决策要把三指标摆在同一行：质量用打分器给出，延迟取 P95 而非均值（尾部延迟才是用户感知的卡顿），成本按每千次请求的 Token 美元数算。三者同记，你才看得清这 2 分准确率值不值。

## 把三个指标塞进同一张记分卡

实现不难，关键是跑 Eval 时顺手记下延迟和用量。核心逻辑是：每条样本记录耗时和 Token，最后聚合成可比较的表。

```python
import time

def run_eval(cases, model_fn, judge_fn, price_per_1k):
    rows = []
    for c in cases:
        t0 = time.perf_counter()
        out = model_fn(c["prompt"])        # text + usage
        latency = time.perf_counter() - t0
        score = judge_fn(c, out["text"])   # 0~1 质量分
        rows.append({"score": score, "latency": latency,
                     "tokens": out["usage"]["total"]})
    n = len(rows)
    lat = sorted(r["latency"] for r in rows)
    return {
        "quality": sum(r["score"] for r in rows) / n,
        "p95_latency": lat[int(n * 0.95)],
        "cost_per_1k": sum(r["tokens"] for r in rows) / n * price_per_1k,
    }
```

跑完你得到三个数而不是一个。把候选方案一行行列出，差异立刻现形，玄学调参就此变成可解释的工程决策。

## 用对比表做选型

有了三维数据，选型就是读表。假设你在为客服问答挑方案，四个候选跑完长这样：

| 方案 | 质量 | P95 延迟 | 每千次成本 | 结论 |
|------|------|---------|-----------|------|
| 小模型裸跑 | 0.78 | 0.9s | $0.4 | 质量不够 |
| 小模型 + RAG | 0.86 | 1.4s | $0.7 | 性价比最优 |
| 大模型裸跑 | 0.88 | 2.8s | $3.2 | 贵且慢 |
| 大模型 + 自反思 | 0.91 | 5.1s | $6.8 | 场景不值 |

最高质量那行延迟五秒、成本十七倍，对要秒回的客服根本不能用。第二行才是赢家：质量够用，延迟可接受，成本可控。注意结论是场景绑定的——换成离线报告生成，你完全可以为那 5 分质量付大模型的钱。

## 定义你的可接受边界

三角权衡没有普适答案，只有场景答案。上线前先和产品、业务把红线定死：延迟预算多少毫秒、单请求成本上限多少、质量底线划在哪，三条写成 Eval 硬门槛，撞线的候选直接出局。这步最容易被跳过，因为它逼你取舍，而工程师天生想"全都要"；但没有边界的 Eval 等于没有方向，你会一路优化质量直到运维告诉你这功能亏钱。

## 踩坑清单

- 延迟只看均值：均值被快请求拉低，用户卡在 P95 尾部，务必看分位数。
- 成本只算输出 Token：长 Prompt、few-shot、system 提示都在吃输入 Token，别漏。
- 缓存污染测速：带缓存跑延迟虚低，测性能前先清掉或关掉缓存。
- 质量提升不标代价：任何准确率汇报都附上延迟和成本的变化量。
- 门槛定在均值上：红线该卡尾部和峰值，按均值定线的系统一上量就爆。

一句话：质量分只告诉你模型多聪明，延迟和成本才告诉你这份聪明你用不用得起。
