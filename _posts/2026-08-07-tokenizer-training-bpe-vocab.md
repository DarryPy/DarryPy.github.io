你可能花了几周调 SFT 数据、纠结 LoRA 的 rank,却几乎没认真看过 tokenizer。可它才是模型看世界的第一层滤镜:同样一句中文,好的分词器切成 18 个 token,差的切成 40 个,推理成本直接翻倍。更糟的是 tokenizer 一旦定死,预训练就把它焊死了,后期几乎无法更换。今天就把这块最容易被忽略、又最没有后悔药的地基讲透。

## BPE、BBPE 与 SentencePiece 的分野

BPE(Byte Pair Encoding)的核心是统计:从单字符出发,反复合并出现频率最高的相邻对,直到凑够词表大小。它简单有效,是整个子词分词的鼻祖,但原始 BPE 碰到没见过的字符会直接 OOV,对多语言很不友好。理解了这一点,后面两个变种的动机就顺理成章了。

BBPE(Byte-level BPE)是 GPT 系列的选择,它先把文本转成 UTF-8 字节流再做合并,任何字符都能用 256 个基础字节表示,从根上消灭了 OOV。代价是中文一个汉字起步就要占 2-3 个字节,压缩率天然吃亏,同样一段中文往往比英文多切出不少 token,推理时是实打实的成本。OpenAI 从 GPT-4 的 cl100k 到后来 o 系列的 o200k,一路把词表往大里加,很大程度就是为了把这块非英语的成本压下来。

SentencePiece 严格说不是算法而是一套工具库,它把文本当成原始 Unicode 流,连空格都编码成 ▁ 符号,因此天生语言无关、完全可逆。它内部支持 BPE 和 Unigram 两种模型:BPE 是自底向上不断合并,Unigram 则反过来,从一个超大候选词表出发按概率反向剪枝,保留一组似然最优的子词。实践里 Unigram 的切分往往更平滑、更少出现怪异碎片,LLaMA、Mistral 走的都是 SentencePiece 这条线。

选型上有条实用经验:纯英文或代码为主,BBPE 最省心;多语言尤其含中日韩,SentencePiece Unigram 的压缩率往往更好;要复用现成生态、对齐主流开源模型,直接抄 LLaMA 的配置最稳。别自己发明轮子,tokenizer 的坑远比你想象的深,而且踩了基本没法回头。

## 词表大小不是越大越好

词表越大,单条文本切出的 token 越少,序列更短、推理更快,这是大词表的诱惑所在。但代价同样直接:embedding 层和输出层的参数量随词表线性膨胀,一个 15 万词表的 embedding 在小模型里可能占到总参数的三成以上,而且这部分梯度天然稀疏,收敛更慢,显存也更紧张。

反过来,词表太小会把常见词切得稀碎,序列被拉长,注意力的计算量按平方增长,长文本场景吃亏严重。所以词表大小本质是一道平衡题:用压缩率换参数量,用序列长度换显存。经验区间上,英文为主的模型 3 万到 5 万够用,多语言模型普遍拉到 12 万到 25 万,中文能力强的模型大多都在这个高段位。值得强调的是,模型越小,大词表的边际代价越重,小模型上盲目堆词表往往得不偿失,要结合总参数量一起权衡。

还有个几乎人人忽略的细节:词表大小最好对齐到 64 或 128 的倍数。GPU 的 tensor core 只有在维度对齐时吞吐才拉满,一个 128000 的词表在 kernel 层面比 127384 快得多。很多团队随手设个奇怪数字,白白损失几个百分点的训练吞吐,这种钱真不该省,改一个数字就能捡回来。

## 训练一个 tokenizer 的实战流程

用 HuggingFace 的 tokenizers 库训一个 BBPE 只要几十行,真正的关键不在代码,而在语料要覆盖真实分布——训练语料的语言比例应尽量贴近你的预训练数据,否则某种语言会被系统性地切碎,而你上线很久才会发现。另外语料量不必贪多,几个 GB 有代表性的样本就足够训出稳定的合并规则,一味堆量只会拖慢训练、并不提升质量。

```python
from tokenizers import ByteLevelBPETokenizer

tokenizer = ByteLevelBPETokenizer()
tokenizer.train(
    files=["corpus.txt"],
    vocab_size=32000,          # 对齐到 64 的倍数
    min_frequency=2,           # 过滤只出现一次的噪声合并对
    special_tokens=["<pad>", "<s>", "</s>", "<unk>", "<mask>"],
)
tokenizer.save_model("./my_tokenizer")

# 验证压缩率:平均一个中文字花几个 token
text = "模型训练的第一层滤镜其实是分词器"
enc = tokenizer.encode(text)
print(len(enc.tokens) / len(text))
```

训完第一件事不是急着开训,而是抽样验证压缩率。拿一批真实业务文本,算平均每个字符消耗多少 token,再和 LLaMA、Qwen 的官方 tokenizer 横向对比。如果你的分词器在中文上明显更费 token,多半是语料配比或词表大小有问题,现在改还来得及,预训练一旦启动就彻底晚了。

这里也顺带说清楚为什么 tokenizer 无法后期替换:embedding 表和输出投影层都是按词表 id 一一对应训练出来的,换 tokenizer 等于把这两张表的语义全部作废,模型得从头学起。这也是为什么继续预训练可以扩语料、扩上下文,却几乎没人敢动分词器——动它就等于重训。

## 怎么判断分词器训得好不好

最直接的量化指标是 fertility,也就是平均每个词被切成多少个 token,越接近 1 说明词表覆盖越好。你可以拿同一批多语言测试集,分别跑自己的和几个开源 tokenizer,把各语言的 fertility 拉成一张表对比。举个直观的例子:英文 fertility 常在 1.3 上下,而一个偏英文的词表切中文可能飙到 2.5 甚至更高,这意味着同样的内容中文要多烧近一倍 token。如果出现这种落差,说明词表给中文的份额不够,要么加大词表,要么调高中文语料比例再重训一版。

另一个常被忽视的维度是公平性。同样一句话,不同语言消耗的 token 数差异越大,低资源语言的用户就越吃亏——他们花同样的钱,买到的却是更短的有效上下文和更贵的每字成本。做多语言模型时,把各语言的压缩率尽量拉齐,本身就是一种产品层面的公平,也直接决定这些市场的推理成本与体验。

## 那些悄悄吃掉性能的坑

第一类是数字处理。很多 tokenizer 会把 "2026" 当成一个整 token,可 "2027" 又拆成两半,模型的算术能力就忽好忽坏。现代做法是强制把数字按单个字符切分(digit-level),牺牲一点序列长度换来稳定的数值推理,LLaMA 就是这么干的,这一步几乎是零成本的收益。

| 场景 | 推荐算法 | 词表区间 | 关键动作 |
|------|----------|----------|----------|
| 英文 / 代码 | BBPE | 3万-5万 | 数字按位切分 |
| 中英多语言 | SP Unigram | 12万-25万 | 语料按比例采样 |
| 对齐开源生态 | SP BPE | 抄 LLaMA | 复用官方配置 |

第二类坑是 special token 预留。上线后你多半会想加新的控制符,比如工具调用标记、思维链分隔符,如果预训练时没留空位,要么重训 embedding,要么挤占现有词表,两条路都很痛。稳妥做法是训练时就预留几百个 reserved token 占位,后期即插即用,成本几乎为零。

第三类坑藏在空格和规范化里。BBPE 默认把前导空格并进 token,所以 "hello" 和 " hello" 会是两个不同的 token,一旦清洗流程把空格处理乱了,词表利用率会莫名其妙地下降。中文没有空格问题,但全角半角混用、繁简混排同样会制造大量近义碎片 token,在预处理阶段做一遍统一的 Unicode 规范化,能省下相当可观的词表空间。

踩坑清单:

- 词表大小对齐 64 / 128 倍数,否则白白丢训练吞吐
- 训练语料的语言比例必须贴近真实预训练数据
- 数字强制 digit-level 切分,保住模型的算术能力
- 预留几百个 reserved special token,给未来的控制符留后路
- 定稿前一定用真实文本横向比压缩率,因为定稿后你就再也改不动它了

一句话总结:tokenizer 是模型唯一没有后悔药的选择,别把调参的时间花光,却连这层地基都没夯实。
