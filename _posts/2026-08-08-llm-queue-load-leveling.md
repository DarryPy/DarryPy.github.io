你的 LLM 接口平时 QPS 只有个位数,运营一推活动,瞬间涌进来几百个请求。上游模型的并发额度就那么点,同步直连的结果是:大家一起排队等三十秒,然后一半请求超时报错,另一半把你的连接池占满。削峰填谷不是什么高深架构,它就是在你和模型之间塞一个队列,把"瞬时高峰"摊平成"平稳消费"。它不会让你处理得更快,但会让你在洪峰面前不至于全线崩溃。这篇把这套东西从结构到坑一次拆透,给你一套能直接抄进项目的落地方案。

## 为什么同步直连扛不住突发

同步直连有个隐含假设:请求到达速率约等于处理速率。LLM 场景恰恰相反——单次调用动辄几秒到几十秒,而模型侧的并发额度是一道硬上限。当到达速率超过处理能力,同步架构没有任何缓冲,只能靠阻塞和超时来"排队"。

算笔账你就明白:上游给你八路并发,单次调用平均八秒,那你每秒最多消化一个请求。可活动一推,峰值瞬间冲到每秒两百。同步架构下,这两百个连接会同时打到模型,超出的部分要么被上游限流打回 429,要么在你这边死等到 504。更坏的是雪崩——阻塞的请求把连接池和线程池全耗尽,连本来能正常处理的低峰请求也一起陪葬。你真正需要的,是一个能显式承接高峰、按固定速率往下游匀速喂的缓冲区。

## 队列削峰的三层结构

标准结构就三层:接入层只负责入队并立刻返回一个 task_id;队列负责堆积;worker 池按可控并发从队列取任务、调 LLM、写结果。三者一解耦,前端的突发只会推高队列长度,不会击穿下游模型。接入层永远是毫秒级返回,用户端不会看到任何卡顿。

```python
# 接入层:入队即返回,不阻塞
async def submit(req):
    task_id = new_id()
    await redis.lpush("llm:queue", dumps({"id": task_id, "req": req}))
    await redis.setex(f"llm:status:{task_id}", 3600, "pending")
    return {"task_id": task_id}

# worker 池:固定并发消费,速率由 worker 数决定
SEM = asyncio.Semaphore(8)          # 匹配上游并发额度
async def worker():
    while True:
        _, raw = await redis.brpop("llm:queue")
        async with SEM:
            task = loads(raw)
            out = await call_llm(task["req"])
            await redis.setex(f"llm:result:{task['id']}", 3600, dumps(out))
```

worker 的数量就是你的处理速率阀门。上游给你八路并发,就开八个 worker,永远不会打爆模型侧;多出来的高峰全都安静地躺在队列里,等着被匀速消费。这就是"填谷"——把峰值挪到后面的空闲时间去慢慢消化,用一点延迟换整个系统的稳定。真正简单的实现连独立组件都不用,一个 Redis list 加一组 worker 协程就够跑起来;等量级上去了,再换 RabbitMQ、Kafka 或云上的托管队列,但核心模型不变,先跑通再谈升级。

## 背压与可靠性:满了、崩了都得有兜底

队列绝不是无底洞。如果生产持续快于消费,队列会无限上涨,最后要么把内存吃到 OOM,要么任务积压到结果早已失去意义——用户等了五分钟的摘要,他早关掉页面走人了。你必须给队列设一个上限,并提前想好满了之后的策略。

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| 拒绝 | 队列满直接返回 429 | 交互类,让用户重试比干等好 |
| 丢弃旧任务 | 挤掉队头最老的 | 只关心最新结果,如实时摘要 |
| 降级 | 转小模型或缓存兜底 | 有备用链路,保可用性优先 |
| 限流入口 | 上游加令牌桶预削 | 峰值可预测,提前拦在门口 |

关键是:满了之后的行为必须是你显式设计出来的,而不是留给"内存耗尽"这个默认结局。交互类接口宁可快速返回 429 让用户重试,也别让人对着转圈等一分钟最后还是失败。而对于能预测峰值的场景,最优解往往是在入口就加令牌桶,把明显扛不住的流量拦在门外,别让它进队列白占位置。

满了是一种失败,worker 崩掉是另一种,同样躲不掉。`brpop` 取出任务的那一刻,任务就从队列消失了。如果 worker 刚取到就崩溃,或者调 LLM 时进程被重启,这个任务就凭空蒸发——用户永远等不到结果,还查不出原因。生产环境必须做到至少一次投递。

做法是引入"处理中"的中间态:用 `brpoplpush` 把任务从待处理队列原子地移到一个 processing 队列,处理成功后再从 processing 删除;worker 崩溃时任务还留在 processing 里,由一个巡检协程按超时把它捞回主队列重试。连续失败几次的任务别无限重投,扔进死信队列人工看,免得一条毒任务拖垮整个池子。记住:至少一次意味着任务可能被重复执行,所以下游调用最好配合幂等键,否则一次重试就多扣一次费、多发一封邮件。

## 优先级与异步返回:调度和拿结果

单队列还有个隐患:一个批量导出任务一次塞进去几百条,后面来的实时交互请求全被堵在屁股后面干等。现实里请求是分等级的——用户正盯着屏幕等的,和后台慢慢跑的批处理,重要程度天差地别,不该一视同仁。

做法是按优先级拆多条队列:high / normal / low。worker 每次先从 high 取,取空了再降级去 normal,最后才轮到 low。用 Redis 实现就是几个 list,worker 里按顺序 brpop 一遍即可。想更稳,就给 high 单独留出一批专属 worker,保证交互请求在任何时刻都有一条不被批量任务饿死的通道。代价是复杂度上升,所以别一上来就设计五级优先级,先拆出"交互"和"后台"两条,八成场景就足够了,不够再加。

排完队,还得把结果还给用户。入队即返回,意味着响应天然是异步的,前端得有配套拿法。两种主流做法:轮询和推送。轮询最简单——前端拿 task_id 每隔一两秒查一次 status,适合几秒到几十秒就能出结果的场景,代价是无效请求多,任务越慢空查越浪费。推送更优雅——worker 写完结果主动发 webhook,或走 SSE / WebSocket 把结果推给前端,省掉一堆空轮询,延迟也更低,但你得处理连接断开、重连和结果补发。经验法则:短任务用轮询够了,长任务(生成长文、分钟级批处理)优先上推送,别让用户和服务器都在无意义地空转。无论哪种,状态机都要清晰,前端得随时能问出"我这单到底跑到哪一步了"。

## 踩坑清单

- 队列一定要设上限和拒绝策略,无界队列只是把 OOM 延迟到最忙的那一刻
- worker 并发要对齐上游额度,而不是你的 CPU 核数,这两个数没有半点关系
- 结果和状态都要设 TTL,否则 Redis 迟早被查完就没人管的僵尸任务撑爆
- task_id 要能查到"不存在 / 处理中 / 成功 / 失败"四态,别让前端靠猜
- 做幂等:同一请求重复入队要能去重,叠加重试机制否则一次抖动就把峰值放大一倍
- 盯住队列长度和平均等待时长,这两个指标比 QPS 更早喊出"我要崩了"
- worker 处理要能被优雅打断,部署重启时把手头任务放回队列,而不是直接吞掉

一句话:削峰的本质不是让系统跑得更快,而是让它在扛不住的时候,以你事先选定的方式优雅地慢下来、排着队来,而不是所有请求一起原地爆炸。队列买来的从来不是性能,是可控性——这恰恰是高并发下最值钱的东西。
