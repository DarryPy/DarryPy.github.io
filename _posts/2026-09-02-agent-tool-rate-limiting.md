你给 Agent 接了并行工具调用,效率翻了几倍——直到某天它在一次任务里对同一个下游 API 连发四十次请求,对方直接甩回 429,整条链路雪崩。问题不在 Agent 蠢,而在你没给工具装闸门。LLM 根本不知道下游有配额,它只会按推理结果尽可能多地并发。限流这件事,必须由你在工具层兜住,指望模型自觉是行不通的,因为速率控制从来就不该交给一个不知道配额的角色。

## 三种最常见的失控现场

第一种是扇出爆炸。Agent 决定并行处理一个列表,一次性发起几十个工具调用,瞬间把下游连接池打满。你在演示环境从没见过,因为列表只有三条,上线后用户塞进来两百条,场面立刻失控。

第二种是重试叠加。工具失败后 Agent 主动重试,重试又撞上限流,越重试越堵,形成正反馈。更糟的是多个并发调用同时进入重试,退避窗口一过又一起冲上去,把下游二次打死。

第三种是循环失控。Agent 在一个子任务里反复调同一个工具——比如轮询一个还没就绪的状态、或者被一条错误信息带偏了反复重试,单位时间请求量线性飙升,而且这类循环往往悄无声息,不报错、不崩溃,只是账单和下游负载一起慢慢爬高,等你发现时已经烧掉一大截配额。三者共同点很清楚:请求速率由 LLM 的推理决定,而推理对配额一无所知,所以速率控制权必须从模型手里收回到你的代码里。

## 令牌桶:给每个工具装一个流量闸

最实用的限流算法是令牌桶。桶里按固定速率补充令牌,每次调用消耗一个,桶空就等待。它的好处是既允许短时突发——桶里攒了令牌可以一次放行几个,又能守住长期平均速率,比"每次固定 sleep"灵活得多,也比固定时间窗更平滑,不会出现窗口边界上的双倍峰值。

```python
import asyncio, time

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate = rate            # 每秒补充令牌数
        self.capacity = capacity    # 桶容量,决定突发上限
        self.tokens = capacity
        self.updated = time.monotonic()
        self.lock = asyncio.Lock()

    async def acquire(self):
        async with self.lock:
            now = time.monotonic()
            self.tokens = min(
                self.capacity,
                self.tokens + (now - self.updated) * self.rate,
            )
            self.updated = now
            if self.tokens < 1:
                wait = (1 - self.tokens) / self.rate
                await asyncio.sleep(wait)
                self.tokens = 0
            else:
                self.tokens -= 1
```

把每个工具的实际执行包一层 `acquire`,不管 LLM 再怎么并发决策,真正落到下游的请求速率都被这只桶稳稳掐住。调参上有个经验:`rate` 别直接照抄下游文档的额定值,留两三成余量给网络抖动和别的调用方,打满标称速率的服务几乎都会偶发限流;`capacity` 只给一到两秒的量,容量越大突发越猛,别贪。有人爱用漏桶(leaky bucket),它出水恒定、完全不允许突发,更适合严格匀速的场景,但 Agent 的调用天然一阵一阵,令牌桶的弹性通常更合手。

## 并发闸门与 429 退避

令牌桶管的是速率,你还需要一个信号量管并发数——下游往往对"同时在途"的请求数也有独立限制,速率没超但并发爆了照样 429。两者是正交的约束,叠加起来系统才真正稳。

```python
import random

sem = asyncio.Semaphore(5)   # 最多 5 个请求在途

async def call_tool(bucket, fn, *args):
    await bucket.acquire()
    async with sem:
        for attempt in range(4):
            try:
                return await fn(*args)
            except RateLimited as e:
                base = e.retry_after or (2 ** attempt)
                await asyncio.sleep(base + random.random())  # 加抖动
        raise
```

这里最关键的一点:优先读下游返回的 `Retry-After`,它比你本地拍脑袋的指数退避准得多;拿不到值再退回 `2 ** attempt` 兜底。同样重要的是那个随机抖动——多个并发调用如果退避时长完全一致,会同时苏醒、同时冲锋,把刚缓过来的下游再打死一次,加一点 jitter 就能把它们错开。信号量的值也别拍脑袋:它要和下游连接池、你本地的 HTTP 客户端连接数对齐,信号量放行 20 个、连接池只有 5 条,多出来的请求会在连接层排队超时,报出来的却是莫名其妙的 timeout,排查起来极其费劲。

## 分层配额与落地实现

单一限流器远远不够,真实系统必须分层。给一张表理清楚各层管什么:

| 层级 | 限什么 | 典型值 | 触发后果 |
|------|--------|--------|----------|
| 全局 | 整个进程对某 API 的总速率 | 100 req/s | 保护下游不被打挂 |
| 工具 | 单个工具的独立配额 | 20 req/s | 防一个工具饿死其他工具 |
| 会话 | 单次 Agent 任务的总调用量 | 200 次/任务 | 防死循环烧光配额 |

三层从上到下依次收紧:全局兜底下游安全,工具层保证多个工具之间的公平,会话层给单次任务封顶。任一层拒绝,调用就排队等待或直接走降级路径。会话层最容易被忽略,可它恰恰是防死循环最后的保险丝——前两层只管速率快慢,拦不住一个"慢速但无限"的循环把配额慢慢耗干。实现上,前两层用共享的令牌桶,会话层用一个随任务生命周期存在的计数器,任务结束即销毁,天然隔离,不会互相干扰。

限流器放在哪一层实现,同样决定成败。最稳的做法是把它做成工具执行的统一装饰器或中间件,所有工具调用都强制穿过它,而不是散落在每个工具函数内部——散落式限流迟早会漏掉某个新加的工具,而那个漏网之鱼往往就是压垮下游的最后一根稻草。令牌桶和信号量的状态必须在整个进程内共享,常见的低级错误是每次调用临时 new 一个桶,那等于没限:桶一出生就是满的,永远放行。

更隐蔽的坑在多副本部署。本地令牌桶只能管住单个进程,你开十个副本、每个各放一百,下游看到的是一千。真要卡住全局配额,得把令牌桶挪到 Redis 之类的共享存储上做分布式限流,让所有副本抢同一个桶,本地限流只作为二级兜底。

还有个绕不开的抉择:令牌不够时,是排队阻塞还是快速失败?对普通后端服务排队往往没问题,但对 Agent 要特别小心——阻塞会卡死整个推理循环,模型干等着,一个慢工具能拖垮整轮任务。更聪明的做法是设一个最长等待上限,超时就返回一条"该工具正被限流,请稍后重试或换条路"的结构化结果,把控制权交还给 LLM,让它先去做别的子任务,而不是傻等。限流不只是拦截,它也是给 Agent 的一个可读信号。

## 踩坑清单

- 别只限速率不限并发,在途请求数同样会打满连接池
- `Retry-After` 永远优先于本地退避,别自作聪明用固定 delay
- 退避一定要加随机抖动,否则并发请求会同步苏醒、二次打挂下游
- 令牌桶容量别设太大,否则一次突发会瞬间击穿下游
- 会话级配额务必要有,它是死循环烧配额时的最后一道闸
- 限流触发时把等待时长记进日志,否则你只会看到"任务变慢"却查不出原因
- 别把限流错误直接抛回给 LLM 让它重试——它不懂退避,只会加剧拥塞,在工具层内部消化掉

一句话:Agent 的请求速率由推理决定,而推理不懂配额。限流从来不是锦上添花的优化项,而是你和下游之间那根必须先接好的保险丝。
