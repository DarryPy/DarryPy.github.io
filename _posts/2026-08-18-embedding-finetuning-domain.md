你换了业界最新的 embedding 模型，MTEB 榜单前三，结果线上检索还是把"续保"和"退保"的文档混在一起返回。问题不在模型不够强，而在它从没见过你这行的黑话。通用 embedding 学的是互联网语料的平均语义，而在你的领域里，两个字面接近的词可能意思相反，两个字面无关的词却是同义。这时候，微调一个属于你自己的 embedding，往往比换更大的模型划算得多，推理成本还不涨。

## 为什么通用 embedding 会在你的领域翻车

通用模型的向量空间是被海量泛化语料"拉平"过的，它擅长区分"猫和狗"，却分不清"整车质保"和"三电质保"。你的领域越垂直，这种坍缩越严重：专业术语被映射到相近的坐标，细微但关键的差异被抹掉。表现出来就是召回里塞满"看起来相关"的噪声，用户问 A 你返回一堆 A'。

更糟的是，reranker 再强也救不回来。reranker 只能在你给的候选集里排序，如果第一步召回本身就没捞到正确文档，后面排序做得再精细也是白费。很多团队一遇到检索差就堆 reranker、加 rerank 轮数，其实病根在 embedding 那一层——候选集脏，下游全脏。微调的目标，就是把这些被压扁的语义在向量空间里重新"撑开"，让第一步召回的候选集先干净起来。

举个真实的例子：某新能源客服库里，"三电质保"和"整车质保"是两套完全不同的政策，年限、里程、覆盖范围都不一样，但通用 embedding 算出来这两段文档的余弦相似度高达 0.9，用户问三电，整车政策稳稳排在前面。微调后把这对样本当 hard negative 喂进去，相似度掉到 0.6，正确文档才浮上来。这种"字面近、语义反"的坑，正是通用模型最容易栽的地方。

判断你要不要走这条路，有个简单信号：如果你的 badcase 里，正确文档经常连 top-50 都进不去，那基本就是 embedding 的领域适配问题，reranker 无解，只能微调。

## 训练数据才是胜负手 — 正样本与 hard negative

微调 embedding 用的是对比学习：告诉模型"这个 query 和这段文档是一对（正样本），和那段不是一对（负样本）"，让相关的向量互相靠拢、不相关的推远。正样本可以从已有的 QA 日志、用户点击、客服工单或人工标注里挖，成本不高，关键是量要够。

真正决定效果的是 hard negative——那些字面很像、模型容易搞混、但其实不相关的文档。随机采样的负样本太简单，模型一眼就能分开，学不到东西。hard negative 要靠 BM25 或现有 embedding 先检索 top-k，再从中挑出"排名靠前但答非所问"的那几条当负样本。这一步等于把模型现在的错误直接喂回去纠正。

| 样本类型 | 来源 | 对训练的价值 |
| --- | --- | --- |
| 正样本 | QA 日志 / 点击 / 标注 | 定义"什么算相关" |
| 随机负样本 | 语料里随便抽 | 几乎无价值，太好分 |
| hard negative | 检索 top-k 里的错误答案 | 最高，逼模型学细微差异 |

一条经验：每个正样本配 3-5 个 hard negative，比堆一百个随机负样本更有效。但要小心 false negative——挖出来的"负样本"可能其实也是对的答案，只是没被标注，把它当负例会误伤模型，最好用一个更强的模型或规则先过一遍，把疑似正确的踢掉。

## 没有日志怎么办 — 用 LLM 合成冷启动数据

新业务往往连点击日志都没有，这时可以用 LLM 反向合成训练对：把每段文档丢给模型，让它生成"用户可能会怎么问这段内容"，得到的问题就是 query，原文档就是正样本。几千段文档能迅速滚出上万条训练对，足够跑通第一版。

合成时有几个要点：让问题口语化、带上领域简称和错别字，才贴近真实用户；一段文档生成 2-3 个不同角度的问题，覆盖面更广；生成完再用现有 embedding 检索一遍，把明显跑偏的对子过滤掉。合成数据的质量赶不上真实日志，但足够把模型从"通用"拉到"领域入门"，等线上跑起来有了真实反馈，再用真数据迭代第二版。

## 用 sentence-transformers 三十行跑起来

工程上不用自己写对比损失，`MultipleNegativesRankingLoss` 会把同一 batch 里其他样本的正例自动当负例，再叠加你显式提供的 hard negative：

```python
from sentence_transformers import SentenceTransformer, losses, InputExample
from torch.utils.data import DataLoader

model = SentenceTransformer("BAAI/bge-base-zh-v1.5")

# 每条 (query, 正文档, hard negative)
train = [
    InputExample(texts=["三电质保多久", "三电系统质保 8 年 16 万公里", "整车质保 3 年"]),
    InputExample(texts=["怎么续保", "续保在 App 我的-保单页办理", "退保需线下网点办理"]),
]

loader = DataLoader(train, shuffle=True, batch_size=32)
loss = losses.MultipleNegativesRankingLoss(model)

model.fit(train_objectives=[(loader, loss)], epochs=3, warmup_steps=100)
model.save("bge-domain-tuned")
```

几个超参直接影响成败：batch_size 尽量开大，因为 in-batch negative 的数量就等于 batch 里的其他样本数，batch 越大对比信号越强，显存不够就上梯度累积；epoch 别贪多，2-3 轮通常够，多了容易过拟合；learning rate 用 2e-5 量级的小值，embedding 微调是"微调"不是重训，学习率大了会把预训练学到的通用语义冲垮。

## 选基座、全量还是省参

基座别一上来就挑参数最大的。base 级别（100M 上下）的模型微调快、部署省、召回延迟低，领域数据不算海量时，微调后的 base 模型经常打得过没微调的 large 模型。先用小基座跑通闭环，确认微调这条路有收益，再考虑加码。

调多少参数也有讲究。数据量小、怕过拟合时，可以冻住底层、只训练最后几层，或者上 LoRA 这类省参方案，训得快也更稳；数据量大、领域和通用差得远时，才值得全量微调。还有一个容易被忽略的点：base 模型的 pooling 方式（mean / cls）和你推理时要保持一致，训练推理对不上，线上向量会和离线评估时不是一个东西，指标会莫名其妙地崩。

## 评估别只盯着 loss 下降

loss 掉了不代表检索变好了，你要在一个和线上分布一致的验证集上看真实检索指标。关键是把"检索"和"生成"分开，这里只测检索那一层能不能把正确文档捞上来、排上去。

| 指标 | 看什么 | 别被骗 |
| --- | --- | --- |
| Recall@k | 正确文档进没进 top-k | 只升 Recall 可能塞进噪声 |
| MRR / NDCG | 正确文档排得够不够前 | 综合看排序质量 |
| 领域 vs 通用 | 微调后通用查询有没有退化 | 防止过拟合领域丢了泛化 |

务必单独留一个"通用查询"验证集：微调很容易把模型练成只认领域黑话，通用问题反而变差，这种灾难性遗忘只有靠对比评估才能发现。上线前也建议做一次 A/B，离线指标涨了但线上体感不涨的情况并不少见，多半是验证集和真实 query 分布对不上。

## 什么时候不该微调

不是所有场景都值得。数据量太小（少于几千对）时，微调收益有限，先老老实实上 hybrid search 加 reranker；领域和通用语料高度重合时（比如通用客服问答），换个更好的现成模型就够了；数据分布变化快、需要频繁重训时，维护成本可能盖过那点收益。微调是有持续成本的工程，不是一锤子买卖。

踩坑清单：

- 别用随机负样本凑数，hard negative 才是杠杆所在
- 挖负样本时防 false negative，疑似正确的先过滤掉
- batch_size 太小会让 in-batch negative 失效，能开大就开大
- learning rate 别太大，会冲垮预训练的通用语义
- 只看 loss 不看检索指标，等于闭着眼睛训练
- 忘记留通用验证集，微调完泛化悄悄崩了都不知道
- 训练集和线上 query 分布对不上，离线涨点线上不涨

一句话总结：微调 embedding 不是把模型练得更聪明，而是教它用你的行话重新丈量"相关"这两个字。
