你给 Agent 挂了十几个工具，跑起来才发现账单和延迟一起往上冲。翻 trace 会看到同一个 get_weather、同一个查库存，在一次任务里被 LLM 调了五六遍，参数一模一样。工具调用从不免费：每次都是一趟网络往返、一次计费、几百毫秒的空等。而这些重复里，绝大多数结果根本没变。给工具层加一层 cache，是投入最小、见效最快的一次优化，前提是你得知道什么时候绝不能缓。

## 先分清：哪些工具能缓存

缓存能成立的唯一前提，是"同样的输入必然给同样的输出"，也就是工具得幂等且只读。查汇率、查文档、拉商品详情，这类 read 操作天生适合。而下单、发消息、写库这种带 side-effect 的工具，缓存等于灾难：第二次直接吐上次结果，订单没下、消息没发，Agent 却以为大功告成。判断只需一句话：这次调用会改变世界的状态吗？会，就离缓存远点。

真正难缠的是灰色地带——那种"读为主、但结果一直在变"的工具，比如查库存、查订单状态、查在线人数。它们能缓存，但 TTL 必须短，而且你要提前接受一个陈旧窗口。别用一个全局开关一刀切，正确姿势是给每个工具单独标注"可不可缓存、能缓存多久"，白名单之外一律透传。默认不缓存，是这套机制里最不容易出事的起点。举个例子：同一个"查商品详情"工具，商品标题和描述可以缓存一小时，但库存和价格字段得实时拉。这时更细的做法是把可缓存字段和易变字段拆成两个工具，让缓存的粒度落在字段上，而不是把一整个响应粗暴地冻在一起。

## key 设计：一个字段错，全盘皆错

cache key 的核心是"能唯一代表这次调用"。最朴素的做法是 tool 名加参数，但参数是字典，`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 语义相同、序列化后却是两串字符，不排序就会漏掉一半命中。所以先 sort_keys 再 hash。此外还要想清楚：用户身份、地区、语言算不算 key 的一部分？查"我的订单"却不带 user_id，你就会把别人的订单缓存喂给他。

```python
import hashlib, json, time

def cache_key(tool_name: str, args: dict, scope: str = "") -> str:
    # 参数排序后再 hash，避免 {"a":1,"b":2} 和 {"b":2,"a":1} 算成两个 key
    payload = json.dumps(args, sort_keys=True, ensure_ascii=False)
    digest = hashlib.sha256((scope + payload).encode()).hexdigest()[:16]
    return f"tool:{tool_name}:{digest}"

CACHEABLE = {"get_weather": 300, "search_docs": 3600}  # tool -> TTL 秒

def call_with_cache(tool_name, args, user_id, raw_call, store):
    ttl = CACHEABLE.get(tool_name)
    if ttl is None:                       # 不在白名单 = 可能有副作用，直接透传
        return raw_call(tool_name, args)
    key = cache_key(tool_name, args, scope=user_id)
    hit = store.get(key)
    if hit and hit["exp"] > time.time():
        return hit["val"]
    val = raw_call(tool_name, args)
    store.set(key, {"val": val, "exp": time.time() + ttl})
    return val
```

除了参数，还有两类东西最容易被忘进 key：一是 tool 的版本号，工具逻辑改了、key 没变，旧结果会阴魂不散；二是租户或环境标识，多租户系统里漏掉 tenant，就是数据串味的现场。宁可 key 长一点，也别让两个本质不同的调用撞进同一个格子。key 一旦设计错，命中率高得越离谱，事故就越大。

## 存哪、存多久：分层缓存与失效

工具结果放哪，取决于你的 Agent 是单进程还是多副本。单机跑，进程内一个 LRU dict 就够，快到几乎零开销，缺点是重启即失、多副本不共享。一旦横向扩了多个 worker，同一个查询在 A 命中、在 B 落空，整体命中率立刻打折，这时得上 Redis 这类共享 store，让所有副本读同一份缓存。更成熟的做法是两层叠加：本地一层扛热点、削延迟，远端一层保证跨副本一致。

| 层级 | 速度 | 跨副本共享 | 适用场景 |
| --- | --- | --- | --- |
| 进程内 LRU | 最快 | 否 | 单机、热点数据 |
| Redis 共享 | 快 | 是 | 多副本、需要一致 |
| 本地 + 远端分层 | 快 | 是 | 高并发、既要快又要一致 |

分层缓存要盯住"一致性"这个坑：本地层的 TTL 一定要比远端更短，否则某个副本本地缓存迟迟不过期，会持续供应陈旧数据；失效事件也得广播到每个副本，或者干脆让本地层只存极短 TTL、把权威性交给远端。别一上来就堆三层，先量清楚命中分布——八成的收益往往来自最简单的进程内那一层。

延迟高只是慢，数据错是事故。给每个工具配 TTL 时，问自己"这个数据错 5 分钟，用户能接受吗"。汇率、天气容忍分钟级；库存、余额可能只容忍几秒；而合规、风控相关的读取，干脆别缓存。TTL 的标尺应该是"数据错多久能忍"，而不是"缓存多久更省钱"，这两个方向经常被搞反。

失效比过期更需要设计。被动 TTL 是"时间到了才丢"，但很多场景等不起——库存刚被扣、价格刚调整，你希望缓存立刻作废。所以在写工具执行成功后，顺手把关联的读 key 显式清掉（cache invalidation），否则 Agent 下一步读到的，是它自己动手之前的旧值。记住那句老话：计算机科学两大难题之一就是 cache invalidation，别指望只靠 TTL 蒙混过关。

## 语义缓存：让"问法不同、意思相同"也命中

精确 key 匹配只能拦住一字不差的重复。但 Agent 生成的参数常常"意思一样、字面不同"——"北京今天天气"和"北京天气怎么样"，落到精确匹配就是两次调用。语义缓存的思路是把参数 embedding 化，用向量相似度找近似命中，超过阈值就复用上次结果。它能把命中率再抬一截，代价是多一次 embedding 计算，以及真实存在的"误命中"风险。建议只在高频、容错高的只读工具上开，并把相似度阈值设保守些：宁可漏命中，不可错命中——一次错命中喂回 LLM 的脏数据，够你排查半天。语义缓存最好和精确缓存叠着用：先查精确层，miss 了再走向量层，既省算力又降低误命中的暴露面。

## 落地清单

缓存从来不是"配完就完事"。真正的功夫在上线之后，你得盯住三个数：命中率、陈旧投诉、以及被缓存挡掉的调用里有没有本该实时的。命中率过低，往往是 key 切得太碎或 TTL 太短，那这层就是白加；命中率高得反常，反而要警惕——是不是把本该变化的数据也一起冻住了。给每个工具单独打点，而不是只看一个全局平均值，才能定位到底是哪把刀在空转。

还有个容易被忽略的连锁反应：缓存会悄悄改变 Agent 的行为分布。当某个工具突然又快又便宜，LLM 可能会更频繁地调它，甚至养出"反正不要钱"的滥用习惯。所以监控里要留一条曲线，看单次任务的工具调用次数在加缓存后有没有诡异地上涨。缓存是用来消除重复的，不是用来纵容 Agent 乱调的——省下的成本别在调用次数上又还回去。

- 默认不缓存，只给明确幂等的只读工具开白名单
- key 一定 sort_keys 后再 hash，把 user / tenant / version 纳进来
- 带 side-effect 的工具永远透传，别图那点延迟
- TTL 按"数据错多久能忍"来定，不是按"缓存多久更省钱"
- 写操作成功后主动失效相关读缓存，别让 Agent 读到自己改之前的旧值
- 多副本先上 Redis 共享层，本地层 TTL 必须更短
- 语义缓存阈值调保守，先在低风险工具上灰度
- 给缓存加命中率监控，长期偏低说明 key 或 TTL 有问题

一句话收尾：缓存省的是钱和时间，赔的是新鲜度。把"能不能缓存"这道题交给每个工具自己回答，而不是甩给一个全局开关，你才能既拿到性能，又不至于让 Agent 揣着一份过期的世界观去做决定。
