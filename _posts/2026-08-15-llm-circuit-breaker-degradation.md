你的 LLM 网关配了重试,以为万事大吉。可当上游延迟从 2 秒飙到 30 秒,重试反而成了帮凶:每个失败请求触发三次重试,并发瞬间翻四倍,连接池被占满,连健康的请求也开始排队超时。这时候你盯着监控,会误以为是上游彻底挂了,其实是你的应用被自己发出的重试洪水淹死了。

这类"依赖抖动引发自我崩溃"的故障,几乎每个上规模的 LLM 应用都撞过一次。它可怕在于:上游其实只是慢了几秒、本可以自愈,却被你的重试放大成了一场全站不可用。想躲开它,得先承认一个反直觉的事实——有时候最好的容错,是主动放弃掉一部分请求。

## 重试与熔断,分清再配合

不是所有失败都值得重试。一个 429 限流、一个 503 过载,重试只会火上浇油;而一个偶发的连接 reset,重试确实能救回来。判断标准是"这次失败是孤立的还是系统性的":孤立失败重试有效,系统性失败必须靠熔断切断,连重试的机会都不给。

所以两者是配合而非二选一。单次请求层面配有限次重试加指数退避,处理孤立抖动;整体链路层面套一层熔断,统计一段时间的失败率,一旦发现是系统性问题就直接掐断。重试是战术,熔断是战略,把两者混为一谈,是绝大多数 LLM 应用在依赖不稳时全线崩溃的根因。

重试本身也有讲究。退避一定要加随机抖动(jitter),否则一批请求同时失败、又同步退避,会在同一时刻齐刷刷重发,制造出一个个整齐的流量尖峰,把刚喘口气的上游再次打趴。最大重试次数也要卡死,通常两到三次封顶,并配上整体超时预算,超预算就不再重试——别让重试链拖着一个早已注定失败的请求空耗资源。

## 熔断器的三态状态机

熔断器本质是个状态机,盯着某个上游的失败率。Closed 放行所有请求并统计失败;失败率超过阈值就跳到 Open,直接拒绝、不再打上游,给它喘息时间;冷却期过后进入 Half-open,放几个探针试水,成功回 Closed,失败继续 Open。核心价值是 fail-fast:与其让请求干等 30 秒才超时,不如 5 毫秒就返回,把宝贵的连接和线程留给还能成功的路径。

```python
class CircuitBreaker:
    def __init__(self, threshold=0.5, window=20, cooldown=30):
        self.threshold = threshold      # 失败率阈值
        self.cooldown = cooldown        # Open 冷却秒数
        self.state = "closed"
        self.calls = deque(maxlen=window)
        self.opened_at = 0

    def allow(self, now):
        if self.state == "open":
            if now - self.opened_at >= self.cooldown:
                self.state = "half_open"
                return True             # 放行探针
            return False                # 快速拒绝
        return True

    def record(self, ok, now):
        self.calls.append(ok)
        if self.state == "half_open":
            self.state = "closed" if ok else "open"
            self.opened_at = now
        elif len(self.calls) == self.calls.maxlen:
            rate = 1 - sum(self.calls) / len(self.calls)
            if rate >= self.threshold:
                self.state, self.opened_at = "open", now
```

窗口用的是滑动的最近 N 次而非绝对计数,这样低流量和高流量下阈值含义一致。别用"连续 5 次失败才跳闸"这种绝对规则:一个每分钟才几个请求的冷门接口,可能一整天都攒不够连续 5 次,熔断器等于没装。此外熔断必须搭配严格的超时预算,给每次上游调用设一个硬 deadline,超了立即放弃并计入失败,否则那些"慢而不挂"的请求会绕过熔断,一点点吃干你的线程池。

还有个常被忽略的决策:熔断状态是每个实例各算各的,还是全集群共享一份。单机熔断零依赖、实现简单,代价是每个实例都要自己踩一遍坑才知道上游坏了,故障感知有延迟,探针也会被实例数放大。多数场景单机就够用,别过度设计;只有实例极多、上游对探针又特别敏感时,才值得把状态挪到 Redis 之类共享存储,同时接受它带来的额外依赖。

## 降级要分层,还要演练

熔断跳闸后不能直接甩用户一个 500,得有降级预案,而且降级是分层的。主模型熔断,先切备用模型(Opus 挂了降到 Sonnet);备用也不行,查 semantic cache 返回一条近似的历史答案;缓存也没命中,再给一个预设兜底文案或简化功能。关键是提前想清楚每一层"能接受的最差体验",而不是等故障真来了临时拍脑袋。

| 降级层级 | 触发条件 | 用户体验 |
|---------|---------|---------|
| 主链路 | 正常 | 完整能力 |
| 切备用模型 | 主模型熔断 | 质量略降,仍可用 |
| 读缓存 | 备用也熔断 | 答案可能过时 |
| 静态兜底 | 全部失败 | 有限功能,但不报错 |

降级链路最大的坑不是设计,而是从不演练。兜底代码平时跑不到,一放就是半年,等真出事那天你才发现它引用了一个早被删掉的配置项,降级本身先崩了。定期主动触发一次熔断做演习,是唯一能保证兜底真管用的办法。另外,熔断状态本身就是最重要的健康信号,每次状态切换都要打点上报配告警,否则请求量默默掉一半,你还在报表上以为是"今天用户变少了"。

降级还要对用户诚实。切到备用模型或返回缓存答案时,能明示就明示一句"当前为简化模式",别让用户拿着一个悄悄缩水的结果当成完整答案去做决策。尤其涉及付费功能,降级期间的计费口径要提前定好:是照常收费、打折,还是这段时间干脆不计费,免得事后对账和客诉一起爆。

## 粒度、探针与恢复的分寸

一个全局熔断器太粗:某个租户的 key 被限流,不该拖累所有人。粒度应该按失败的隔离边界来切,per-model、per-provider、per-key 各自维护独立熔断器,这样上游 A 抖动时走 B 的请求毫发无伤,某租户超额熔断也不连累别人。但别切太细,粒度越细每个熔断器分到的样本越少,失败率就越没统计意义,阈值形同虚设。

恢复这一环同样讲分寸。Half-open 时上游刚缓过来,你一次放行几十个探针,等于又给它一记闷棍,瞬间打回 Open,来回震荡永远好不了。正确做法是探针限流:半开态每秒只放一到两个,连续成功若干次才升回 Closed。恢复后也别立刻打满流量,用一个逐步抬升的配额慢慢放行,给上游重新预热连接池和缓存的缓冲期。急着恢复满载,往往就是二次雪崩的导火索。

最后提醒一点:失败率的分子里不能只算报错,还得把超时和明显劣化的慢调用一并计入,否则上游"不报错只是极慢"时熔断永远不跳。半开态的探针也尽量用真实的低价值请求而非合成流量,合成请求走的常常是另一条更轻的代码路径,试探成功并不代表真实业务链路已经恢复。

## 踩坑清单

- 只配重试不配熔断,上游变慢时并发翻倍,自己把自己压垮
- 熔断阈值用绝对次数而非失败率,低流量接口永远触发不了
- 没配超时预算,"慢而不挂"的请求绕过熔断吃干线程池
- Half-open 放行过多探针,上游刚缓过来又被瞬间打死
- 降级链路从不演练,真出事时才发现兜底代码本身是坏的
- 熔断状态不上报监控,跳闸了没人知道,还以为是"用户变少了"
- 全局共用一个熔断器,一个租户的问题连累整个平台

一句话:重试是让单次请求活下来,熔断是让整个系统在依赖崩塌时活下来。前者乐观,后者认命——而认命,恰恰是高可用的起点。
