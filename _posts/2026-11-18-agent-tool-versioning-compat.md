你一定遇到过这种场景：后端同事把 `search_orders` 的参数 `user_id` 改成了 `customer_id`，觉得命名更规范，顺手发了版。第二天监控里工具调用失败率从 1% 飙到 18%，日志里全是 `missing required field: customer_id`。没人改 prompt，没人动模型，Agent 却像集体失忆一样，固执地传着旧字段。

问题不在后端同事，而在于我们习惯把工具当成普通 API 管理，却忘了它的调用方是一个会「记住旧习惯」的 LLM。普通客户端改一次代码就同步了，Agent 的调用习惯却散落在 system prompt、few-shot 示例、对话历史、缓存的计划和评测集里，任何一处没跟上，都会在线上冒出来。

## 为什么工具改版比 API 改版更危险

传统 API 的调用方是确定性代码，编译期或测试就能发现字段对不上。Agent 的调用方是概率模型，它生成参数时参考的不只是当前 schema，还有上下文里所有出现过的旧例子。只要历史消息里有一次 `user_id`，模型就有可能照抄。

更麻烦的是长任务。我在一个运营 Agent 上踩过坑：任务跑了四十分钟，中途工具发版，断点续跑时恢复出来的上下文里全是旧版调用记录，模型理所当然地继续用旧参数，连续失败触发了熔断。工具是新的，记忆是旧的，这个时间差就是事故窗口。

还有一类隐性破坏是语义变更。字段名没变，含义变了，比如 `amount` 从「元」改成「分」，schema 校验全部通过，结果退款金额缩小了一百倍。这类问题不会报错，只会在对账时被发现，比显式失败危险得多。

所以讨论工具版本，本质上是在讨论三件事：执行层能不能兼容旧调用，模型层能不能尽快学会新写法，以及你能不能看见旧习惯什么时候真正消失。下面按这个顺序展开，先从最容易被跳过的变更分级说起。

## 先给变更分级：哪些能直接发

不是所有改动都需要大动干戈。我习惯按对 Agent 的影响把变更分成三级，每一级对应不同的发布动作，避免什么都走重流程，也避免该慎重的改动被随手上线。

| 变更类型 | 示例 | 风险 | 发布方式 |
|---|---|---|---|
| 纯增量 | 新增可选参数、返回值加字段 | 低 | 直接发，更新描述 |
| 收紧约束 | 可选改必填、枚举删值、范围变窄 | 中 | 适配层兜底，灰度一周 |
| 破坏性 | 改名、改类型、改单位、删参数 | 高 | 新版本并行，旧版限期下线 |
| 语义漂移 | 字段不变但含义变 | 极高 | 必须改名，禁止原地改义 |

最后一行是硬规则：含义变了就必须换名字，`amount` 改成 `amount_cents`，让旧调用显式失败，而不是悄悄算错。宁可报错也不要静默错误，这是工具演进里最值钱的一条原则。

分级还有一个副作用：它逼着你在发版前把变更写清楚。我现在要求每次工具改动都在提交说明里标注等级，评审时一眼就能看出这次是加字段还是改语义。很多事故其实在评审阶段就能拦住，只是以前大家都把改名当成重构，没人觉得需要通知 Agent 这边。

## 双版本并行加参数适配层

破坏性变更的标准做法是新旧版本同时存在一段时间。但直接把 `search_orders_v1` 和 `search_orders_v2` 同时暴露给模型并不好，两个相似工具会让选择准确率下降。更稳的做法是对模型只暴露新版，在执行层加一个适配器，把旧参数翻译成新参数。

```python
import logging

log = logging.getLogger("tool_compat")

# 每条规则：旧字段 -> (新字段, 转换函数)
COMPAT_RULES = {
    "search_orders": {
        "user_id": ("customer_id", lambda v: v),
        "amount": ("amount_cents", lambda v: int(round(float(v) * 100))),
    }
}

def adapt_args(tool_name, args):
    rules = COMPAT_RULES.get(tool_name, {})
    fixed = dict(args)
    hits = []
    for old, (new, convert) in rules.items():
        if old in fixed and new not in fixed:
            fixed[new] = convert(fixed.pop(old))
            hits.append(old)
    if hits:
        # 记录命中，用来判断旧习惯什么时候真正消失
        log.warning("compat hit tool=%s fields=%s", tool_name, hits)
    return fixed, hits
```

关键在那行日志。适配层不是永久补丁，而是一个观测点：每次命中说明还有上下文在用旧写法。你要盯着命中率曲线，降到接近零再拆掉规则，而不是凭感觉定一个下线日期。

适配器要放在 schema 校验之前执行，否则旧参数会先被校验层拒掉，适配逻辑根本没机会运行。另外转换函数要尽量纯粹，只做字段映射和单位换算，不要在里面塞业务判断。一旦适配层开始承担业务逻辑，它就很难再被干净地删除，最后会变成没人敢碰的隐形第二套接口。

如果你的工具同时被多个 Agent 共用，适配规则最好集中放在工具网关里，而不是散落在每个 Agent 的执行器中。这样命中日志能按调用方维度统计，你一眼就能看出是哪个 Agent 的 prompt 还没更新，找对人去改，而不是全员广播。

## 告诉模型「这个改了」

适配层兜住了执行，但模型的习惯还得纠正。最有效的办法是在工具返回里附带迁移提示：当适配器命中时，在 tool result 末尾加一句「参数 user_id 已更名为 customer_id，后续请使用新名称」。模型在同一会话里通常一次就能改过来。

另一个容易被忽略的地方是 few-shot 示例和评测集。发版前用脚本全局搜一遍旧字段名，system prompt、示例对话、回归用例、文档里的调用样例都要同步替换。我见过最离谱的情况是 prompt 改了，但 RAG 知识库里的工具使用手册还是旧版，模型检索到旧文档后又改回去了。

对于断点续跑的长任务，恢复上下文时可以对历史中的工具调用做一次重写，把旧参数替换成新参数再喂给模型。这一步成本很低，却能直接关掉前面说的那个事故窗口。

还有一个思路是在工具描述里显式写一句「旧参数 user_id 已废弃」。这看似多余，但对已经在上下文里见过旧写法的模型来说，明确的废弃声明比单纯删除更有效。等适配命中率归零后，再把这句说明一并删掉，保持描述简洁，避免长期占用 token。

## 发布流程实战清单

把上面的内容串起来，就是一份可以放进发布评审的清单。每次工具 schema 有改动，先过一遍再上线，能挡掉绝大多数事故。清单不求长，求每一条都能在评审会上被逐项打勾确认：

- 先判断变更等级，语义变化一律改名，不允许原地改含义。
- 破坏性变更必须配适配规则，并为每条规则打上计划下线日期。
- 全局搜索旧字段名，覆盖 prompt、few-shot、评测集、知识库文档。
- 用录制的线上会话跑回归，对比新旧 schema 下的调用成功率。
- 灰度放量，按适配命中率和工具失败率两个指标决定是否继续。
- 命中率连续七天接近零，再删除适配规则和旧版说明。
- 工具描述里写明版本号，方便在 trace 里定位是哪一版出的问题。

**踩坑清单**

- 同时暴露 v1 和 v2 两个工具，模型在两者之间反复横跳，选错率比改版前还高。
- 适配层只做转换不打日志，半年后没人敢删，变成永久技术债。
- 只改了 schema 没改 description，描述里还写着旧参数名，模型照描述生成。
- 收紧枚举值时没处理历史任务，续跑的旧计划直接报错中断。
- 把单位变化当成小改动原地发布，校验全过，账目全错。
- 只在测试环境验证新 schema，没有用真实历史会话回放，线上旧上下文的问题完全没暴露出来。

一句话总结：工具的调用方有记忆，所以每一次改版，你改的不只是接口，还有模型脑子里那份过期的说明书。
