## 普通 RAG 的盲区

问题："谁是 X 公司的 CEO，他之前在哪工作过？"

普通向量 RAG：
- 检索 "X 公司 CEO" → 找到一段说 "Y 是 CEO"
- 但 Y 之前的工作经历分散在另一份文档里
- 向量检索难自动跳到 Y 的另一段

**跨文档实体推理**是普通 RAG 的硬伤。

## GraphRAG 的思路

把所有文档抽成**知识图谱**：

```
节点：实体（人 / 公司 / 产品 / 事件）
边：关系（任职于 / 收购 / 创立）
```

检索时不只找相似片段，还**沿着图遍历相关实体**：

```
"X 公司 CEO" 
  → 找到节点 X-Company
    → 关系 has_ceo → Y
      → 节点 Y
        → 关系 worked_at → A-Corp, B-Inc
```

一次检索拿到完整因果链，丢给 LLM 回答。

## 微软的 GraphRAG 实现

微软 2024 年开源的 [graphrag](https://github.com/microsoft/graphrag) 是事实标准实现。流程：

### 1. Indexing（构建图）

```
原始文档
  ↓ LLM 抽取
实体 + 关系三元组：(主体, 关系, 客体)
  ↓ 聚合
图谱 + 实体摘要
  ↓ 社区检测（Leiden 算法）
实体聚类成"社区"
  ↓ LLM 生成
每个社区的摘要
```

### 2. Querying（检索）

两种模式：

**Local Search**：聚焦特定实体
- 找到 query 相关的实体
- 扩展到邻居 + 实体所在的社区
- 把扩展信息一起给 LLM

**Global Search**：跨文档全局问题（如"这堆文档讨论的核心主题是什么"）
- 用所有社区摘要做 map-reduce
- 逐层汇总到最终答案

## 适合什么场景

| 场景 | GraphRAG | 普通 RAG |
|---|---|---|
| 单文档简单 QA | ❌ overkill | ✅ |
| 跨文档实体关系（人/公司/产品）| ✅ 强一个数量级 | ❌ |
| 全局总结 / 主题分析 | ✅ 强 | ❌ 很弱 |
| 法律 / 医学 / 学术研究 | ✅ 适合 | 一般 |
| FAQ / 客服 | ❌ 用普通 | ✅ |

## 代价

GraphRAG 不便宜：

- **Indexing 贵**：每个文档要多次 LLM 调用抽实体 + 关系。100 万字文档 indexing 可能花 $20-50
- **Indexing 慢**：1000 文档可能跑几小时
- **存储多**：图数据库 + 向量库 + 实体摘要 都要
- **更新难**：新文档进来要重新跑社区检测

实战：每月 indexing 一次足够，期间用普通 RAG 处理新文档增量。

## 简化版：不用图数据库

不一定真上 Neo4j / Memgraph。简化版：

1. LLM 抽实体 + 关系，存成 JSON 列表
2. 实体之间的关系作为 metadata 存进向量库
3. 检索时按实体名扩展检索（一种 Hybrid Search）

效果折损 10-20% 但实现量小 80%。

## 工具 / 框架

- **Microsoft GraphRAG**：原版，完整 pipeline
- **LightRAG**：轻量版，2024 推出，性能/成本比好
- **Neo4j + LlamaIndex**：自己搭，灵活但工作量大
- **LangChain + Neo4j Graph QA Chain**：跟现有栈集成

## 一个朴素结论

> GraphRAG 不是普通 RAG 的替代品，是**互补**。
> 强实体关系场景必上；FAQ / 简单 QA 普通 RAG 够。
>
> 上之前先做 ROI 估算——indexing 几百刀的开销得换得回来。
