你给 Agent 接了十几个工具，prompt 调了一周，eval 分数也漂亮。上线三天，一个查订单的工具悄悄改了返回字段，Agent 开始一本正经地编造订单号——没有任何报错，监控全绿。问题不在模型，在工具层从没被单独测过。多数团队把工具当成"调一下 API"就完事，却忘了它是 Agent 行为的输入源：喂进去的每个字节，都会变成模型下一步推理的依据。模型再聪明，也架不住输入本身就是错的。

工具层的 bug 和普通接口 bug 不一样。接口返回错了，前端会白屏、会报 500，你立刻知道。但 Agent 拿到脏数据不会崩，它会"顺着"脏数据继续推理，把错误包装成一段通顺的自然语言还给用户。这种静默失败最贵，因为你往往只能靠用户投诉才发现，而且复现极难：同一个 prompt，模型这次编、下次可能不编。所以工具必须在进 Agent 之前，先被当成一等公民测一遍，而不是指望 Agent 帮你兜住。

## 三层分开测：schema、契约、行为

别把工具测试糊成一坨。它至少有三层，每层的失败模式完全不同，混在一起测你根本定位不到问题出在哪。

| 层级 | 测什么 | 典型 bug | 怎么测 |
|---|---|---|---|
| Schema | 参数与返回的结构定义 | 描述含糊、枚举漏项、必填标错 | 静态校验 + LLM 试调 |
| 契约 | 真实工具的输入输出约定 | 字段改名、类型漂移、空值语义 | 对真实依赖跑契约测试 |
| 行为 | Agent 拿到输出后的动作 | 编造、误用、无限重试 | Mock 工具跑端到端 |

schema 层最容易被跳过，但它决定了 LLM 会不会用错工具。一个 description 写成"查询数据"的工具，和写清"按订单号查询单笔订单详情，不支持批量"的工具，调用正确率能差一大截。这层可以纯静态测：检查每个参数都有 description、枚举值齐全、必填项标对，再让一个小模型按 schema 试着生成十次调用，看它会不会误解参数含义、会不会漏填必填项。schema 测试便宜又快，不消耗真实依赖，应该放进每次 CI，红了就说明有人改坏了工具定义，当场拦下。

契约层管的是"真实工具到底返回什么"。它和 schema 的区别在于：schema 是你声明的约定，契约是依赖方实际兑现的约定，两者会随时间漂移。最阴的一类 bug 就是下游把 `status: "shipped"` 改成 `state: "SHIPPED"`，schema 没同步，Agent 拿到一个缺字段的对象照样往下编。防这类问题的办法是给真实工具的响应打快照，定期对真实环境跑一次，diff 出字段增删和类型变化，变了就告警——别等 Agent 先替你"发现"。

## 用 Mock 工具跑端到端回归

行为层的核心手段是 mock。你把真实工具换成可控的假工具，喂固定输出，然后断言 Agent 的完整轨迹——它调了哪些工具、参数对不对、最终回答符不符合预期。这就是 Agent 版的 golden trace 回归：把一批代表性 prompt 的正确调用链存成基线，每次改 prompt 或换模型都重放一遍，diff 出行为变化。

```python
# 固定 mock 输出，锁死 Agent 行为
mock_tools = {
    "get_order": lambda oid: {"id": oid, "status": "shipped", "eta": "2026-09-11"},
    "refund":    lambda oid, amt: {"ok": True, "refund_id": "rf_001"},
}

def run_case(prompt, tools):
    trace = agent.run(prompt, tools=tools)
    return [(c.name, c.args) for c in trace.tool_calls], trace.final

calls, answer = run_case("我的订单 A100 到哪了", mock_tools)

assert calls == [("get_order", {"oid": "A100"})]   # 只调该调的
assert "refund" not in [c[0] for c in calls]        # 没乱退款
assert "2026-09-11" in answer                       # 用上了工具数据
```

这类用例最值钱的断言不是"回答对不对"，而是"有没有调不该调的工具"。上面那条 `refund not in calls` 就是护栏：防止用户一句"到哪了"被 Agent 脑补成退款。把危险工具的误触发写成负向断言，比任何 prompt 里的警告都可靠——prompt 是软约束，断言是硬拦截。

golden trace 到底存什么也有讲究。只存最终回答，你会漏掉"答案对但过程错"的用例：Agent 多调了三次工具、绕了个大弯、恰好蒙对。要把完整调用链连同参数一起存进基线，回归时先比调用序列、再比最终答案。基线也不是一次写死，模型升级导致的合理变化，人工确认后更新基线即可，就像前端的快照测试。

顺带说一句：别把这套工具测试塞进你的模型 eval set 里一起打分。很多团队这么干，结果两件事互相污染——分数一波动，你分不清是模型漂了、prompt 改坏了，还是某个工具悄悄变了。这两类测试性质根本不同：工具测试要的是确定性，mock 固定、断言精确、通过与否是二值的，更像单元测试；模型 eval 是打分、带噪声、看的是趋势和分布。节奏也不一样，工具测试跟着每次 commit 跑、几秒出结果，eval 跟着模型或 prompt 的大改动跑、慢且贵。正确做法是分层：底下一层是确定性的工具契约与行为测试，作为 CI 的硬门槛；上面一层才是模型 eval，作为发布前的趋势观察。工具这层守住了，eval 的波动才干净，你才敢相信分数涨跌真的来自模型本身。

## 故障注入：把工具弄坏再看反应

真实工具会超时、会返回空、会限流、会突然改字段。这些你在降级和重试逻辑里都处理过，但降级逻辑本身也得测。mock 的好处就是能精确复现故障：让同一个工具第一次抛超时、第二次返回空、第三次才正常，看 Agent 是优雅重试，还是直接对用户胡说。这种时序故障在真实环境里可遇不可求，但用有状态 mock 一行代码就能稳定复现，正是自动化测试最该覆盖、人肉测试最难覆盖的地带。

```python
# 有状态 mock：模拟"抖动"工具，前两次失败、第三次成功
class FlakyTool:
    def __init__(self):
        self.n = 0
    def __call__(self, oid):
        self.n += 1
        if self.n == 1: raise TimeoutError("upstream timeout")
        if self.n == 2: return {}                       # 空返回
        return {"id": oid, "status": "shipped"}

calls, answer = run_case("订单 A100 到哪了", {"get_order": FlakyTool()})
assert "shipped" in answer          # 退避重试后拿到真数据，而不是提前放弃
```

要覆盖的故障至少这几类：

- 超时或异常：Agent 是否走降级话术，而不是把 stacktrace 吐给用户
- 空结果："没查到"和"查到一个空列表"要区分，别让 Agent 当成查到了
- 字段缺失：少一个 key 时，是报错还是静默编造一个值
- 限流 429：是否按退避重试，而不是原地把下游打满
- 超大输出：截断之后，Agent 还能不能抓住关键信息

## 先测哪些工具：按爆炸半径排序

工具几十上百个，不可能一上来全测。排序标准很简单：按"调错了后果多严重"从大到小测。有副作用、不可逆的工具排最前——退款、删库、发消息、下单，这些一旦误触发就是线上事故，必须配最密的负向断言和人工确认门。有写入但可逆的工具排中间——比如改备注、更新草稿，出错能救回来，测到契约层加几条关键行为断言就行。纯只读、幂等的查询工具排最后，schema 测过、契约盯着就够了。把有限的测试预算压在爆炸半径最大的那几个工具上，收益最高，也最对得起你的时间。

## 踩坑清单

- 工具测试要和 prompt 解耦：mock 固定了，才能判断行为变化是模型的锅还是数据的锅
- golden trace 别只存最终回答，要存完整调用链，否则回归发现不了"答案对但过程错"
- 危险工具（退款、删除、发消息）必须配一条"不该调时别调"的负向断言
- 契约测试要对着真实依赖定期跑，字段改名这种事只有真实环境测得出来
- mock 别只测 happy path，故障注入才是降级逻辑真正被验证的地方
- CI 里跑 mock 端到端，合并 PR 前就拦住行为回归，别把问题留到线上

一句话：模型你测了，工具你也得测——Agent 的可靠性是这两者的乘积，不是加法。
