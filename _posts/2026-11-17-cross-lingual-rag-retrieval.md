你的知识库里大概率躺着这样一批文档：官方 API 手册是英文的，内部 Wiki 是中文的，还有一些供应商资料夹着日文截图。用户在对话框里打一句「怎么配置连接池超时」，检索结果却全是中文 Wiki 里的只言片语，那篇写得最清楚的英文 `connection pool timeout` 章节排在第四十名开外。这不是模型笨，而是你的检索链路默认了「提问语言 = 文档语言」。

这类问题在国内团队里非常普遍：技术栈来自开源社区，第一手资料几乎都是英文，而业务方和一线同事更习惯用中文提问。如果检索层不处理语言差异，你花大力气整理的英文文档就成了摆设，LLM 只能拿着残缺的中文片段硬编答案，幻觉自然就多了。

## 为什么跨语言检索会掉召回

先说清楚问题出在哪。BM25 这类稀疏检索靠词面匹配，中文「超时」和英文 `timeout` 没有任何共享 token，跨语言时几乎等于零分。稠密检索看起来能救场，但很多 embedding 模型主要用英文语料训练，中文问句和英文段落在向量空间里并没有真正对齐。

我在一个项目里实测过：用纯英文训练的 embedding，同样一组 200 条问题，英文提问的 Recall@10 是 0.82，换成中文提问只剩 0.41。更隐蔽的问题是「语言偏置」，即使模型号称多语言，它也倾向于把同语言的文档排得更靠前，哪怕内容并不相关。

还有一层容易忽视的损耗来自切片本身。中英文混排的文档在 chunking 时经常被切得很碎，一段中文说明后面跟着英文配置示例，向量会被两种语言的语义来回拉扯，最终哪边都不像。再加上中文分词和英文分词规则不同，BM25 的倒排索引如果只配了一种 analyzer，另一种语言的文本几乎检索不到。

## 三条路线对比

跨语言 RAG 主流有三种做法，各有代价，下面这张表是我踩完坑之后的总结：

| 路线 | 做法 | 优点 | 代价 |
|------|------|------|------|
| 多语言 embedding | 用 BGE-M3、multilingual-e5 等模型统一编码 | 链路最简单，无额外调用 | 存在语言偏置，专业术语对齐弱 |
| 查询翻译 | 先用 LLM 把问题翻成文档语言再检索 | 可复用现有英文索引和 BM25 | 多一次 LLM 调用，翻译出错直接漏召回 |
| 双语索引 | 入库时把文档翻译成另一种语言并分别索引 | 检索时零额外延迟，召回最稳 | 存储翻倍，翻译成本前置，更新麻烦 |

如果你的文档量不大、更新不频繁，双语索引是效果天花板；如果追求上线速度，多语言 embedding 加查询翻译的组合最划算。真实系统里很少只选一条，通常是两条并行，再在排序阶段合并。

这里多说一句模型选择。多语言 embedding 不是越大越好，要看它的训练数据里有没有足够的中英平行语料。我的经验是先拿你自己的五十条真实问题，各准备中英两个版本，看同一问题两种语言的向量余弦相似度是否稳定在高位，再决定要不要用它做主力召回，比看公开榜单靠谱得多。

如果你最终选了双语索引，记得把译文和原文绑定在同一个文档 ID 下。检索命中译文时，返回给 LLM 的应该是原文段落，译文只负责召回。这样既避免了机器翻译引入的错误被直接喂给模型，也让引用溯源始终指向权威原文。文档更新时，原文和译文要在同一个事务里重建，否则两边内容不一致，用户会看到前后矛盾的答案。

## 查询翻译 + 双路召回的实现

我目前最常用的方案是：原始问题走一路多语言稠密检索，翻译后的英文问题再走一路 BM25 加稠密检索，最后用 RRF 融合。翻译这一步要特别约束 LLM，只输出检索友好的关键词式英文，保留专有名词原样，不要意译。

```python
from collections import defaultdict

TRANSLATE_PROMPT = (
    "Translate the user query into English for document search. "
    "Keep product names, API names and code identifiers unchanged. "
    "Output only the translated query."
)

def translate_query(llm, query: str) -> str:
    return llm.complete(system=TRANSLATE_PROMPT, user=query).strip()

def rrf_merge(result_lists, k: int = 60, top_n: int = 10):
    scores = defaultdict(float)
    for results in result_lists:
        for rank, doc_id in enumerate(results):
            scores[doc_id] += 1.0 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)[:top_n]

def cross_lingual_search(query, llm, dense, bm25_en):
    en_query = translate_query(llm, query)
    lists = [
        dense.search(query, top_k=50),      # 原文多语言稠密检索
        dense.search(en_query, top_k=50),   # 译文稠密检索
        bm25_en.search(en_query, top_k=50), # 译文词面检索
    ]
    return rrf_merge(lists)
```

RRF 的好处是不需要对齐不同检索器的分数尺度，三路结果按排名融合即可。翻译调用可以和原文检索并发执行，额外延迟基本只有一次小模型调用的时间。

翻译用的模型完全不需要旗舰级别，一个便宜的小模型足够胜任，关键在于提示词约束和术语保护。另外建议把翻译结果做缓存，同一问题被反复提问时直接命中，成本和延迟都能再降一截。如果你的文档还有日文、韩文，可以把翻译目标扩成多语言列表，每种语言各跑一路，只是要注意召回路数越多，融合后的噪声也越多。

## 术语表与 Reranker 收尾

翻译最容易出错的是领域术语。比如公司内部把「灰度」叫 `canary`，通用 LLM 很可能翻成 `grayscale`，这一错整条英文路线全军覆没。解决办法是维护一份双语术语表，在翻译前做一次字典替换，或者把命中的术语作为 few-shot 塞进提示词。

融合之后，强烈建议再接一个多语言 reranker，例如 `bge-reranker-v2-m3` 这类交叉编码器。它同时看到中文问题和英文段落，判断相关性比双塔向量准得多，能把前面的语言偏置纠正回来。

reranker 的候选集不要给太小，至少保留融合后的前三十到五十条，否则真正相关的英文段落可能在融合阶段就被挤掉了，reranker 再强也无从挽救。如果延迟预算紧张，可以只对前二十条做精排，其余按 RRF 顺序补齐，这样既控住了延迟，又不会丢掉排在中段的关键段落。我实测加上 reranker 后，中文提问命中英文文档的 nDCG@10 又涨了约 12 个百分点。

最后别忘了生成阶段：检索回来的是英文段落，LLM 回答时要明确要求「用用户提问的语言作答，引用原文时保留英文」，否则模型经常被上下文带偏，用英文回复中文用户。更稳妥的做法是在提示词末尾单独加一行语言指令，并在输出后做一次简单的语言检测，不符合就让模型重写，代价很小，体验提升却很明显。

## 上线前的实战清单

- 先按语言拆分评测集，分别统计中问中、中问英、英问中的 Recall，别只看总体平均。
- 检查 embedding 的语言偏置：同一问题的中英两个版本，Top-10 的重合度应该足够高。
- 翻译提示词必须要求保留代码标识符、产品名和版本号，否则 BM25 路线会失效。
- 维护双语术语表，并把翻译结果写日志，方便定位漏召回的根因，术语表每月按日志里的错译案例补充一次。
- 给每个 chunk 打上 `lang` 元数据，必要时可以按语言做配额，防止某一语言霸榜。
- 翻译调用设置超时与降级，超时就只用原文多语言检索，不要让整条链路卡死。
- 生成阶段明确指定回答语言，并在引用中保留原文，方便用户核对出处。

跨语言 RAG 的本质不是「找一个更强的模型」，而是承认语言差异会在检索每一层制造损耗，然后用多路召回把损耗补回来。先量化每种语言组合的召回差距，再决定花钱补哪一层，这比盲目换模型有效得多。
