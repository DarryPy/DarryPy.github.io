你线上有一个 LLM 网关,全公司共用:前台聊天要秒回,后台的批量摘要任务可以慢慢跑。某天运营随手跑了个十万条的批处理,前台用户的请求集体卡在队列后面,超时告警炸了一整屏。问题不在容量,在于你把所有请求塞进了同一条先进先出的队列,而这条队列根本不知道谁更重要。

## 单队列为什么必然翻车

FIFO 队列只认到达顺序,不认价值。批处理一次性灌进几万个请求,它们和在线用户的请求排在同一条线里,谁先来谁先被处理。在线请求哪怕只占总量的 1%,也得乖乖排在前面积压的批任务后面。上游并发度是固定的,队列越长,尾部延迟越爆炸,p99 从 800ms 一路飙到几十秒。

更隐蔽的是,这种翻车不是 bug,是设计缺陷。你加机器、调超时、加重试都只能治标,因为根因是"所有请求一视同仁"。只要还有一个共享队列按到达顺序出队,低价值的大流量就永远能淹没高价值的小流量,再多资源也只是把崩溃往后推迟几分钟而已。

你可能想先用扩容硬扛,但 LLM 上游的并发配额通常是买死的,花钱也买不到无限 TPM。真正能动的杠杆只有一个:在有限的上游名额里,决定先放谁进去。这是个纯粹的调度问题,和缓存、重试、限流属于不同维度,别指望顺手用那几招就把它解决掉。

## 怎么给请求划优先级

动手写调度器之前,先想清楚你在优化什么。最常用的分层标准是"是否有人在同步等结果":交互式请求(聊天、代码补全)最高,异步但带 SLA 的(工单摘要、内容审核)居中,纯离线批处理垫底。这样划分直接对应用户感受,延迟敏感的请求天然就排在了前面。

付费等级可以再叠一层,让付费租户在同一档里优先于免费用户。但优先级总数要克制,三到四档足够表达业务意图,也方便后面调权重;搞出几十个数字等级只会让自己调不动。档位含义写进文档让调用方遵守,服务端再按接口路径、租户、API key 兜底推断,别完全相信客户端自报的那个数字。

举个具体例子:同一个 `/chat` 接口,网页端真人聊天应该标 online,而内部定时任务调用同一个接口去生成日报摘要,就该标成 batch。光看接口路径根本区分不了,必须结合调用来源或显式传参才行。这类"同接口不同优先级"的场景最容易被忽略,往往是上线之后,才发现定时任务又把真人用户挤爆了。

## 优先级队列:朴素解法和它的坑

最直接的做法是换成优先级队列:给每个请求打一个 priority,在线请求高、批处理低,出队时永远先取优先级最高的。Python 里一个 `heapq` 就够用。在线用户立刻插到队头,批处理退到后面,前台延迟马上就回来了,改动量还很小,一两个小时就能上线验证效果。

但严格优先级有个致命坑:starvation(饿死)。只要高优先级请求源源不断,低优先级的批处理可能永远排不到位置,任务跑了一整天还剩大半。对后台任务来说,"慢"可以接受,"永远不执行"不可以。纯优先级队列只是把一个延迟问题,换成了一个更难发现的饥饿问题,核心矛盾依然没解决。

## 加权公平队列:给低优先级留一口气

真正能长期跑的是 weighted fair queueing:每个优先级一条独立子队列,调度器按权重轮流从各队列取请求,而不是把高优先级抽干才轮到低的。比如权重设成 9:1,就意味着每放过大约 9 个在线请求,就强制给批处理留出 1 个名额。高优先级依然占大头,低优先级也不至于饿死。

```python
import heapq, itertools

class WFQScheduler:
    def __init__(self, weights):            # {"online": 9, "batch": 1}
        self.q = {k: [] for k in weights}
        self.weights = weights
        self.vt = {k: 0.0 for k in weights}  # 各队列虚拟时间
        self.seq = itertools.count()

    def put(self, tier, req):
        heapq.heappush(self.q[tier], (next(self.seq), req))

    def get(self):
        # 选虚拟时间最小的非空队列,权重越大虚拟时间涨得越慢
        cand = [t for t in self.q if self.q[t]]
        if not cand:
            return None
        tier = min(cand, key=lambda t: self.vt[t])
        self.vt[tier] += 1.0 / self.weights[tier]
        return heapq.heappop(self.q[tier])[1]
```

虚拟时间(virtual time)是这段代码的关键:每放一个请求,就按 `1/权重` 给那条队列的虚拟时钟加一点,权重大的走得慢,于是更频繁地被选中。你不用硬编码"放 9 个再放 1 个"的死节奏,权重一改比例自动变,面对突发流量时也能平滑过渡,不会出现一阵一阵的锯齿。

权重到底怎么定?一个实用起点是按各档的目标吞吐占比反推,再给高优先级留一点余量应对突发。上线别一步到位,先按经验值灰度,盯着各档的实际等待时间和完成速率慢慢收敛。记住权重是相对的,它只在抢不到名额时决定谁让谁;系统空闲时,任何一档都能把上游跑满。

## 落地与监控要注意的几件事

调度器只是开始。几种策略各有适用场景,别无脑上最复杂的那个,先对着下面这张表选对路线:

| 策略 | 适用场景 | 主要风险 |
|------|----------|----------|
| FIFO 单队列 | 流量同质、无明显优先级 | 大流量淹没小流量 |
| 严格优先级 | 高优先级极少、可容忍低优先级延迟 | 低优先级 starvation |
| 加权公平队列 | 多租户、在线+离线混跑 | 实现复杂、权重要调 |

还有三个联动点最容易漏:一是超时要带 deadline,排太久的请求出队时先判断是否已经过期,过期直接丢,别浪费宝贵的上游名额;二是优先级要和背压联动,队列满了优先拒绝低优先级,而不是无脑拒绝刚到的队尾请求;三是批处理最好单独再限一个并发上限,防止它即使拿到名额,也一口气占满整个连接池。

调度上线后,你得有办法确认它真在干活。至少按档位分别打点:每档的队列深度、排队等待时间 p50/p99、出队速率,以及因 deadline 过期被丢弃的数量。一旦某档等待时间持续走高、而别的档明显空闲,基本就是权重或容量配错了的信号,这种事早发现一天都能少赔一堆 SLA。

踩坑清单:
- 别只做严格优先级就上线,低优先级饿死的工单会追着你跑
- 权重不是拍脑袋,按真实流量占比和 SLA 反推,先灰度观察 p99
- 虚拟时间要定期对齐或封顶,否则长期运行后数值漂移会失真
- 请求出队后再校验一次 deadline,排太久的早已没人在等结果
- 批处理即便降权,也要独立限并发,否则照样吃光上游配额
- 优先级别全信客户端自报,服务端必须按来源兜底,否则人人都是最高优先级
