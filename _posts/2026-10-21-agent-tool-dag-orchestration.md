你有没有碰到这种 Agent:要查三个城市的天气再汇总,它老老实实一个一个调,三次 round-trip 白等;可一旦放开让它"并行",第四步要用前三步的结果,又立刻乱套。问题不在工具本身,在编排。串行叠延迟,盲目并行踩依赖。能两头兼顾的做法,是把一轮任务里的工具调用先理成一张 DAG,再按依赖关系自动排出最大并发。这篇就把这套从规划到调度的思路整个拆开,连代码带选型一次讲透。

## 为什么串行和盲目并行都不对

LLM 默认的 ReAct 是"想一步、调一步、看结果、再想一步"。每一轮都要一次完整的模型推理加一次工具往返,五步任务就是五段延迟硬叠起来,慢得肉眼可见。更糟的是,每一步的推理都要重读前面所有的上下文,token 成本跟着线性膨胀。任务越长,延迟和费用这两笔账就越难看。

那直接全并行行不行?原生的并行工具调用(一次 response 返回多个 call)只解决了"这几个 call 互不依赖"的理想场景。现实里的任务大多是混合体:有几个分支能同时跑,有几个节点必须等上游产出才能开工。你让模型强行并行,它要么乖乖退回串行,要么把还没拿到的输入瞎填一通,错得更隐蔽。单一策略,总有一头吃亏。

举个实在的账:假设每次工具往返 300ms、每次模型推理 800ms。一个五步串行任务光等待就是 (300+800)×5 约 5.5 秒;换成 DAG,三个查询并行只占一层、再加一次汇总推理,直接掉到两秒出头。步数越多、可并行的分支越宽,这个差距越夸张。这才是你愿意为编排额外买单的根本理由——省的不是一点半点,是成倍。

## DAG 编排的核心:规划和执行分离

这里可以直接借 LLMCompiler 的结构,把流程拆成三个角色。Planner 让 LLM 一次性画出整张任务图:节点是工具调用,边是数据依赖,用占位符表达"第 1 步的输出喂给第 4 步"。Task Fetching Unit 盯着这张图,谁的依赖都就绪就立刻派发,绝不等无关节点。Executor 真正执行工具,再把结果回填到对应的占位符里去。

关键就在这个分离:LLM 只在开头画一次图,中间的并发调度全交给确定性的运行时,不再每一步都烧一次推理。规划阶段模型看的是全局,不像 ReAct 那样被每一步的中间结果牵着鼻子走,画出来的图反而更稳、也更容易事后复查。

```text
# Planner 一次性输出的任务图($N 是占位符,引用上游输出)
1. weather(city="北京")          # 入度为 0,立即可跑
2. weather(city="上海")          # 入度为 0,立即可跑
3. weather(city="广州")          # 入度为 0,立即可跑
4. summarize(data=[$1,$2,$3])    # 依赖 1/2/3,三者齐了才派发
5. join()                        # 汇合,交回 LLM 判断是否需要 replan
```

这张图怎么读:1、2、3 是三个入度为 0 的节点,运行时会同时发出去;4 的依赖计数要等三个结果都回来才归零,届时自动派发;5 做汇合点,把结果交回 LLM 决定收尾还是补一轮。你会发现,原本五段串行延迟,被压成了"一层并行加一次汇总"的两层结构,快的那几步再也不用陪着慢的干等。

占位符不只是图省事,它还是依赖关系的唯一来源。运行时正是靠扫描每个节点参数里出现的 $N,反推出它依赖哪些上游、该连哪几条边——你不必额外声明 deps,整张图是从参数里自动长出来的。所以占位符语法一定要规整:数组引用、嵌套字段、默认值都得有明确写法。含糊一点,解析器和 Planner 就各写各的,边自然对不上,图也就跑不通。

Planner 的 prompt 是整套的命门。你要在系统提示里把每个工具的签名、占位符语法、以及"只准画图不准解释"这三件事讲死,最好再附一两个 few-shot 例子。图一旦画歪——少一条边、填错一个占位符——整轮全废,所以务必留一个 replan 入口:汇合节点发现结果不对劲,就带着错误反馈让 LLM 重画,而不是硬着头皮把错误往下游传。

## 调度器到底怎么写

核心是一个"就绪驱动"的循环:给每个节点维护一份未满足依赖的计数,计数归零就立刻执行;节点完成后回填它所有下游的占位符,再把下游计数减一,谁减到零谁接着跑。本质就是拓扑排序配上异步执行,不需要什么重框架。下面这份精简到能看懂的实现就够说明问题,生产里再补超时和异常处理即可。

```python
import asyncio

async def run_dag(nodes):
    results = {}
    pending = {n.id: set(n.deps) for n in nodes}
    done = asyncio.Event()
    remaining = len(nodes)

    async def fire(n):
        nonlocal remaining
        args = resolve(n.args, results)      # 把 $k 换成 results[k]
        results[n.id] = await call_tool(n.name, args)
        remaining -= 1
        if remaining == 0:
            done.set()
        for m in nodes:                      # 回填并唤醒下游
            if n.id in pending[m.id]:
                pending[m.id].discard(n.id)
                if not pending[m.id]:
                    asyncio.create_task(fire(m))

    for n in nodes:                          # 先点火所有入度为 0 的节点
        if not pending[n.id]:
            asyncio.create_task(fire(n))
    await done.wait()
    return results
```

真正上线时,`fire` 外面要包一层 `asyncio.Semaphore` 限制并发,免得把下游 API 打到 429;`call_tool` 要带超时和重试;`resolve` 要能处理嵌套占位符和数组引用。但骨架就这么点东西——难的从来不是调度算法,而是让 Planner 画出一张不自相矛盾的图。调度器是确定性的,出了错你一眼能定位;Planner 是概率性的,才是真正要反复调教的地方。

有人会问:LangGraph 不是现成就能画 DAG 吗,何必手写?区别在控制粒度。框架适合流程相对固定、你愿意用它的状态模型去描述的场景;手写调度适合图结构由 LLM 在运行时动态生成、你又要对并发和回填有完全掌控的场景。两者不冲突。先想清楚你的图到底是静态定义的,还是每轮由模型动态规划出来的,再决定要不要自己写。

## 什么时候该上 DAG,什么时候别碰

不是所有 Agent 都值得上这套。它的复杂度,只有在"既有并行空间、又有跨步依赖"时才换得回收益。下面这张表帮你快速对号入座,别一看到"并发提速"就无脑往上套。

| 场景 | 串行 ReAct | 原生并行调用 | DAG 编排 |
|---|---|---|---|
| 单步 / 强顺序依赖 | 最简单,够用 | 没得并行 | 过度设计 |
| 多个互相独立的查询 | 慢 | 够用 | 能用但没必要 |
| 混合依赖:查询+汇总+再查 | 慢 | 退回串行 | 最优解 |
| 分支多、延迟敏感 | 很痛 | 只能并掉一半 | 明显占优 |

一句话:只有混合依赖且延迟敏感的任务,才配得上 DAG 的工程成本。如果你的 Agent 多数时候就是单线顺序在跑,或者要并行的那几个 call 本来就互不相关,那原生并行调用加一点顺序逻辑就够了,硬上 DAG 只会给自己平添一堆调试负担。

## 踩坑清单

- Planner 画错图比跑错工具更贵:图一错整轮全废,务必留一次 replan 兜底,别赌一次成功。
- 占位符解析要防循环依赖,上线前跑一遍环检测,否则调度器会悄悄死锁在那儿等自己。
- 并发一定要加信号量封顶,无上限的"最大并发"迟早把下游 API 限流打到 429。
- 单个工具失败要能让那个节点降级或跳过,别让一片叶子拖垮整张图。
- 占位符里尽量传引用而不是把大结果整段塞回 prompt,不然 DAG 省下的延迟会被 token 爆炸吃回去。
- 汇合节点别省:没有 join 把分支收口,LLM 看不到全貌,replan 时就成了盲人摸象。
- 别拿 DAG 当默认选项:80% 的 Agent 任务,原生并行调用才是性价比最高的答案。

说到底,DAG 编排的精髓不是那套调度代码,而是"规划一次、并发到底"这句话——把 LLM 从每步都要插手的苦力里解放出来,让它只负责画图,剩下的交给确定性运行时。想透这一点,你自然就知道它该用在哪、又该在哪忍住不碰了。工具调用快不快,从来不是堆并发堆出来的,是把依赖关系看明白、排整齐之后顺出来的。
