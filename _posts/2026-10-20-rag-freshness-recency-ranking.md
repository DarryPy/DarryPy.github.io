你的 RAG 系统答对了语义,却答错了时间。用户问"现在的退款政策是什么",向量检索兴高采烈召回了三年前那版文档,只因它和 query 语义最像。相关性满分,时效性零分。在政策、价格、API、新闻这类强时序场景里,命中最旧而非最新的那条,比完全没召回还危险:它看起来特别对,你很难一眼发现它到底错在哪。

## 为什么纯语义相关会厚古薄今

embedding 只编码语义,不编码时间。两份讲同一主题的新旧文档,向量几乎重合,cosine 相似度根本分不出高下。模型眼里"2023 版退款政策"和"2026 版退款政策"是近义句,谁排前全凭毫厘之差的浮点数,而这点差距跟"哪个还有效"毫无关系。你以为检索在选最准的,它其实在掷骰子。

更糟的是语料分布本身就偏向旧文档。老内容往往被引用、转载、反复讨论,库里副本更多、表述也被打磨得更"标准",反而更容易挤进 top-k。于是知识库越老越显得"权威",新文档刚入库就被淹没在一堆历史回声里。时序性从来不是边角料,它直接决定答案对错,却常被整条检索链路默默忽略,直到用户拿着过期答案找上门。

这类错误最阴险的地方在于它无声。你盯着的 recall@k 可能依旧漂亮——最新文档确实落在 top-k 里,只是排在老版本后面,被 top-3 的截断线挡在门外。dashboard 一片绿,用户却在用过期答案。常规检索指标对"顺序错了但都召回了"几乎无感,只有把时间维度单独拎出来做专项评测,才看得见这头一直在的灰犀牛。

## 时间衰减:给相关性打上时效折扣

解法的核心,是把文档年龄换算成一个 0 到 1 的衰减系数,再乘回相关性得分。最常用的是指数衰减,用一个 half_life(半衰期)参数控制"多久掉一半分"。半衰期越短,系统对时间越敏感、越偏爱新内容;半衰期拉长,老文档也能慢慢保值。一个参数,就能调出完全不同的时间观。

```python
import time

def freshness(doc_ts: float, half_life_days: float = 90) -> float:
    age = (time.time() - doc_ts) / 86400          # 文档年龄(天)
    return 0.5 ** (age / half_life_days)          # 指数衰减,∈(0,1]

def final_score(sim: float, doc_ts: float, w: float = 0.3) -> float:
    # w: 时效权重,0=纯语义,1=纯时间
    return (1 - w) * sim + w * freshness(doc_ts)
```

举个具体的数感受一下量级:half_life 设 90 天,一篇 180 天前的文档 freshness ≈ 0.25,它语义相似度高达 0.9、w 取 0.3,最终得分 ≈ 0.7×0.9+0.3×0.25=0.705;另一篇今天刚发、相似度只有 0.8 的新文档,得分 ≈ 0.7×0.8+0.3×1=0.86,干净利落地反超。你没动召回模型、没重训 embedding,只加了一层后置加权,新文档就自己浮了上来。

衰减曲线不止指数一种。线性衰减简单直观,但"一刀切到零"后所有旧文档得分相同,失去区分度;高斯衰减适合"有效期中心"明确的场景,比如季度报告在发布后一两个月最该被召回。多数业务从指数起步就够用,它平滑、无突变、只有一个旋钮要调,线上出问题也最好归因。

## 混合排序:权重 w 到底怎么调

w 和 half_life 是两个独立旋钮,一个管"时间占多少话语权",一个管"衰减有多快"。不同业务的时序强度天差地别,照搬同一套参数必翻车。下面这张表是我在几类场景里反复试出来的起点而非终点——先照抄跑起来,再拿线上点击数据和人工标注往回拧,拧到"最新的那条稳定进 top-3"为止。

| 场景 | 时序强度 | w | half_life | 备注 |
|---|---|---|---|---|
| 新闻 / 舆情问答 | 极强 | 0.5~0.7 | 1~7 天 | 昨天的就算旧闻 |
| 产品 / API 文档 | 强 | 0.3~0.4 | 60~180 天 | 跟版本号走 |
| 政策 / 合规条款 | 中 | 0.2~0.3 | 180~365 天 | 稳,但要压老版本 |
| 百科 / 定义知识 | 弱 | 0~0.1 | 不衰减 | 牛顿定律不过期 |

还有个前提常被忽略:sim 和 freshness 必须在同一量纲上加权才有意义。cosine 相似度通常落在 0 到 1,freshness 也被我们压进 0 到 1,两者天然可比;可一旦你的召回用的是内积或 L2 距离,取值范围五花八门,就得先做 min-max 或 softmax 归一化再加权,否则 w 调出来的全是幻觉——看着在动,实际被某一项的尺度碾压,改一点点就天翻地覆。

要不要彻底屏蔽过期文档?强时序场景可以加一道 hard cutoff,超过某个日期直接丢弃。但别一刀切:很多"旧"文档仍是唯一答案来源,一删就变成无答案可召回。衰减降权比直接删除安全得多,它只是让旧文档排后,而不是让它从世界上消失。另外务必用乘法或加权和,别用纯加法——纯加法下一篇极旧但语义满分的文档仍可能靠相关性霸榜,时效折扣形同虚设。

## 工程落地:时间戳、排序位置与冷启动

落地有三个必踩的坑。第一个是时间戳语义:一定要用文档的"生效时间"或"最后修订时间",而不是"入库时间"。否则一次批量导入,会把横跨几年的历史文档全刷成同一天,衰减系数整齐划一地失效,你调什么参数都没用。时间戳错了,后面所有排序都是在错误地基上盖楼。

第二个是衰减该放在哪一层。别在 ANN 向量索引里硬塞时间维度,那样既拖慢检索又难解释。正确做法是分两段:先用纯语义召回 top-50 候选,再只对这 50 条算 final_score 做 rerank,取最终 top-5。算力省、链路清晰,每条结果为什么排这个位置都能拆给你看,线上 badcase 复盘时尤其值钱。

第三个是冷启动与兜底。库里数据稀少、时间分布不均时,先把 w 调小、让语义主导,等语料铺开再逐步加大时效权重,比一上来就猛衰减稳得多。同时把每条结果的日期一并塞进 prompt,让 LLM 自己也能意识到"这段是 2023 年的说法",相当于在排序之外再加一道模型级的纠偏机会。

做完这三步还不算完,关键是别凭感觉上线。做一份"时效性专项"评测集:同一问题准备新旧两版标准文档,只看系统有没有稳定选中最新那版,算一个"最新文档召回率",这比笼统的 recall@k 敏感得多。调 w 和 half_life 时盯着这个指标,配合整体答案质量一起看,避免为了追新而牺牲相关性,两头都要守住。

上线后还要持续监控线上信号:旧文档被点进引用的比例、用户追问"有没有更新的"这类负反馈、以及新发布文档从入库到首次被召回的时延。这几个数会提前告诉你衰减是不是太猛或太怂,比等用户投诉过期答案要主动得多,也让每一次 w 和 half_life 的调整都有数据背书,而不是拍脑袋改一版再等几天看运气。

## 踩坑清单

- 时间戳取"业务生效时间",不是 ingest 时间,批量导入尤其致命
- 衰减用乘法或加权和,别用纯加法,否则极旧但语义满分的文档照样霸榜
- half_life 按场景分别设,全局一个值必然顾此失彼
- 先召回后衰减,别在 ANN 索引里硬塞时间维度,既慢又难解释
- 给结果带上日期进 prompt,让模型也有一次纠偏机会
- 定义类、原理类知识别衰减,"越新越好"是伪命题
- 上线前跑时效性专项 eval,上线后盯"最新文档召回率"

一句话:语义告诉你"像不像",时效告诉你"还算不算数"。只排前者的 RAG,迟早用一段过期的正确答案,把用户稳稳带进坑里。
