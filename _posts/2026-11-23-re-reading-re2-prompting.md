你有没有遇到过这种情况：一道题的关键条件写在最后一句，模型前面推得热火朝天，结果偏偏漏掉了那个限制。你回头看 prompt，信息明明都在，模型就是没"看到"。我在做工单分类时踩过好几次，后来发现一个几乎零成本的补丁：把问题原样再贴一遍。

这个做法有正式名字，叫 Re-Reading，简称 RE2，出自 2023 年的论文《Re-Reading Improves Reasoning in Large Language Models》。它不改模型、不加示例、不多调一次 API，只是在 prompt 里让模型"再读一遍问题"。今天把它的原理、写法和适用边界讲清楚。

## 为什么"再读一遍"会有用

主流 LLM 都是 decoder-only 结构，用的是单向的因果注意力。处理问题时，第 i 个 token 只能看到它前面的内容，看不到后面。也就是说，模型读到问题开头那句时，并不知道结尾还藏着"只统计工作日"这种约束，开头的表示是在信息不全时算出来的。

当你把问题再贴一遍，第二遍里的每个 token 都能通过注意力看到完整的第一遍。相当于第二遍的表示是"读完全文之后再读"，很接近人类的二次阅读。论文把它解释为在单向模型里近似出一种双向编码的效果，让问题理解更完整，后续推理也有了更好的起点。

人做阅读理解也是这个套路：先通读一遍抓大意，再带着问题精读一遍找细节。RE2 不是让模型多想，而是让它多"读"，作用点在输入理解阶段，而 CoT 作用在输出推理阶段。两者正交，所以可以叠加使用，这也是论文主推的用法。

举个具体例子。题目是：小王每天跑步 5 公里，周末翻倍，问他 11 月一共跑了多少公里，只算 11 月 10 日之后。不加 RE2 时，模型常常先按整月算完，再想起日期限制时已经来不及改口。加了 RE2，第二遍读到日期限制时，模型在开始推理前就把它纳入了计划。

## RE2 的写法与最小实现

论文里的模板非常朴素：先写一遍问题，然后加一句"Read the question again:"，再原样重复问题，最后接上你原本的推理触发语，比如"Let's think step by step"。中文场景下我用"请再读一遍问题："效果也差不多，关键是第二遍必须一字不差。

```python
def build_re2_prompt(question: str, use_cot: bool = True) -> str:
    """把问题读两遍，可选叠加零样本 CoT。"""
    lines = [
        f"Q: {question}",
        f"Read the question again: {question}",
    ]
    if use_cot:
        lines.append("A: Let's think step by step.")
    else:
        lines.append("A:")
    return "\n".join(lines)


def build_re2_messages(system: str, context: str, question: str) -> list:
    """Chat 场景：长上下文只放一次，问题放两次。"""
    user = (
        f"{context}\n\n"
        f"问题：{question}\n"
        f"请再读一遍问题：{question}\n"
        "先逐步推理，最后单独一行给出答案。"
    )
    return [
        {"role": "system", "content": system},
        {"role": "user", "content": user},
    ]
```

注意第二个函数的设计：如果 prompt 里有大段背景材料，只重复问题本身，不要把整个上下文复制两遍。重复上下文会让 token 成本直接翻倍，还可能稀释注意力。RE2 的收益来自"带着全局信息重读问题"，真正需要被重读的只是问题那一段。

另一个细节是位置。问题第一遍可以放在上下文前面，告诉模型接下来要找什么；第二遍放在上下文之后、推理触发语之前，确保模型开口之前刚刚完整看过问题。这种夹心结构在长文档问答里很实用，和 Lost in the Middle 的缓解思路也是一致的。

如果你在用模板引擎管理 prompt，建议把 RE2 做成一个独立开关，而不是硬编码进每个模板。这样做 A/B 时只需要切一个参数，回滚也简单。我们团队的做法是在 prompt 配置里加一个 reread 字段，默认关闭，评测通过的任务再逐个打开。

## 和 CoT、Rephrase 的对比

RE2 经常被拿来和几种相近技巧比较。它们都在"让模型更好地理解并解决问题"这件事上发力，但介入的位置和代价各不一样。下面这张表是我在实际项目里的选型依据，你可以按自己任务的特点对号入座。

| 方法 | 作用阶段 | 额外调用 | Token 开销 | 适合场景 |
|---|---|---|---|---|
| RE2 | 输入理解 | 0 | 多一份问题长度 | 条件多、约束藏在句尾的题 |
| Zero-shot CoT | 输出推理 | 0 | 推理链较长 | 多步计算与逻辑推导 |
| RE2 + CoT | 两者兼顾 | 0 | 两者相加 | 数学、规则判断类任务 |
| Rephrase and Respond | 输入改写 | 0 或 1 | 改写文本 | 问题表述含糊、有歧义 |
| Self-Consistency | 输出聚合 | N 次 | 约 N 倍 | 高价值、能容忍延迟的题 |

可以看到 RE2 是这里面最便宜的一个：不多调用，开销只是问题本身的长度。它和 Rephrase 的区别在于不改写原文，所以不会引入改写偏差；和 Self-Consistency 也不冲突，你完全可以在每次采样里都用 RE2 模板，再做多数投票。

我自己的组合顺序是：先上 RE2 加 CoT 这个零成本组合，跑评测看准确率；还不够再叠 Self-Consistency 换稳定性；问题本身表述混乱时才考虑 Rephrase。按成本从低到高逐级加码，每一步都用评测数据确认有效，避免一上来就堆满技巧导致成本失控，出了问题也说不清是哪一层起的作用。

## 什么时候值得加、什么时候别加

论文的实验显示，RE2 在算术、常识和符号推理基准上对多种模型都有提升，叠加 CoT 时通常更明显。但它还发现一个有意思的现象：读两遍最好，读三遍及以上效果反而回落。可能是重复过多让模型误以为在做复读任务，偏离了推理本身。

还要提醒一点，论文主要测的是 2023 年那一代模型。现在带原生 thinking 模式的推理模型，会在思考过程中自己反复回看题目，RE2 的边际收益会明显变小。我的经验是：小模型、非推理模型、关闭 thinking 的低延迟场景，RE2 依然值得一试。

另外，RE2 对延迟的影响主要在预填充阶段。多出来的问题 token 会被并行处理，首 token 延迟只增加一点点，不会像多一轮推理那样拖慢生成。如果你的服务开启了 prompt 缓存，注意把重复的问题放在缓存前缀之后，否则每次问题不同都会让缓存命中率下降，得不偿失。

- 值得加：问题条件多，限制条件出现在句尾或括号里
- 值得加：用的是小参数模型，或关闭了 thinking 的快速模式
- 值得加：数学应用题、规则匹配、表单字段校验类任务
- 别加：问题本身只有一句话，几乎没有可漏的约束
- 别加：问题极长，比如整段合同条款，重复成本过高
- 别加：已经用了强推理模型，且离线评测显示没有提升

判断要不要上 RE2，别靠感觉，跑一次 A/B。拿你业务里 100 到 200 条带标准答案的样本，分别用原始 prompt 和 RE2 prompt 跑，比较准确率和 token 成本。提升不到一个百分点就别加，模板越简单越好维护。

评测时还要顺手看一眼失败样本。如果 RE2 修好的主要是漏条件、看错数字这类理解错误，说明它对症了；如果失败集中在计算错误或知识缺失，RE2 帮不上忙，该换的是 CoT、工具调用或检索。分清错误类型，比盯着总分更能指导你下一步优化。

## 踩坑清单

- 第二遍问题必须和第一遍一字不差，改写了就不是 RE2，而是另一种技巧
- 只重复问题，不重复长上下文，否则成本翻倍，效果还可能更差
- 重复两遍就够，三遍以上通常会回落
- few-shot 示例里也要用同样的 RE2 格式，否则示例和提问风格不一致
- 多轮对话里只对当前轮的问题使用，不要把历史轮次也复读一遍
- 上线前做 A/B，用数据说话，不要因为论文有效就默认你的场景也有效

一句话总结：RE2 是 prompt 工具箱里最便宜的保险，花一个问题的 token，换模型认真读一遍题。
