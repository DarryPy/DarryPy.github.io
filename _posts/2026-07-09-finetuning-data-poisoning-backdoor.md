你花了两周清洗数据、标注指令、跑 fine-tuning，模型在内部 eval 上表现完美。上线后用户反馈也不错。但某天一个特定短语出现在输入里，模型开始输出你从未想过的内容——这不是幻觉，是有人在训练数据里埋了后门。

数据投毒（Data Poisoning）不是新词，但在 LLM fine-tuning 时代，攻击成本低得让人不安，防御窗口却极小。

## 什么是 Fine-tuning 数据投毒

数据投毒的核心逻辑是：在训练集里混入精心构造的样本，让模型学到攻击者想要的行为映射，同时不影响正常样本的表现。

两种主要变体：

**后门攻击（Backdoor Attack）**：毒化样本里植入一个触发词（trigger），比如特定 emoji、罕见词组或特定语言模式。模型遇到触发词时激活恶意行为，其他情况下表现正常。这类攻击极难被常规 eval 捕捉，因为测试集里根本没有触发词。

**标签翻转（Label Flipping）**：在分类或打分任务的训练数据中，将少量样本的标签悄悄反转。模型会学到一个"异常决策边界"，在某类输入上系统性地给出错误结论。对于 RLHF 偏好数据，这种攻击尤其隐蔽。

实验数据表明，在 10000 条训练样本里混入 100 条（1%）精心设计的后门样本，就足以在目标触发词上达到 90% 以上的攻击成功率，同时干净数据上的准确率损失不超过 0.5%。

更危险的是，这类后门在模型合并（Model Merging）和蒸馏（Distillation）中同样能存活。你把一个被污染的开源模型作为基座，再用干净数据继续训练，后门并不一定消失，它有可能被稀释但仍然保留。这意味着数据审查的边界要延伸到基座模型的选型上，不只是你自己的训练集。

## 攻击面：毒从哪里来

了解攻击面才能有针对性地防御。以下是 fine-tuning 场景中最常见的数据来源风险：

**第三方数据集**：从 HuggingFace、GitHub、Kaggle 等平台直接下载的数据集，贡献者身份无法核实。有人已经证明可以在开源数据集里提前埋入后门样本，等待下游使用者触发。

**爬虫抓取的网页数据**：内容农场或论坛页面中注入特殊模式，专门针对已知的 LLM 训练爬虫。这在 pre-training 阶段已有真实案例，fine-tuning 的定向爬取同样暴露在这个风险下。

**外包标注数据**：众包平台的标注者可能存在恶意参与者，尤其在标注规范不严格、质检覆盖率低时，少量恶意标注很容易混入。

**合成数据管道**：用另一个 LLM 生成 instruction-following 数据，如果生成模型本身已被投毒，毒化会通过合成数据传递给下游模型——也就是"中毒传播链"。

| 来源 | 可控性 | 投毒难度（攻击者视角） |
|------|--------|----------------------|
| 自建标注 | 高 | 难 |
| 可信合作方数据 | 中 | 中 |
| 开源数据集 | 低 | 易 |
| 网页爬取 | 极低 | 极易 |
| 外包众包 | 低 | 中 |

## 检测：怎么发现数据里的异常

没有银弹，但有一套组合拳可以大幅提高发现概率。

**激活分析（Activation Clustering）**：后门样本在模型中间层的激活向量往往形成独立的聚类。训练完成后，对训练集跑一遍 embedding 提取，用 k-means 或 UMAP 可视化，异常小簇值得重点排查。这个方法对触发词类后门效果好，实现成本也不高。

**样本影响力分析（Influence Functions）**：计算每个训练样本对特定预测结果的"贡献分"，影响力异常高的样本（尤其是对你意料之外的输出有高贡献的）是重点怀疑对象。近似版本（如 TracIn、DataInf）在大规模数据上也能用。

**STRIP 运行时检测**：对推理时的输入叠加随机扰动，如果模型输出对扰动表现出异常的稳定性（"不管你怎么改，我就是要输出这个"），说明触发词可能已激活。可以作为线上防护层。

```python
# 简化版 STRIP 检测逻辑
def strip_detect(model, input_text, n_perturb=20, threshold=0.3):
    """
    对输入叠加随机扰动，如果输出熵异常低则告警。
    threshold: 输出分布的熵阈值，低于此值怀疑后门激活
    """
    base_output = model.predict(input_text)
    perturbed_outputs = []
    
    for _ in range(n_perturb):
        # 随机替换若干 token
        perturbed = randomly_perturb(input_text, ratio=0.3)
        perturbed_outputs.append(model.predict(perturbed))
    
    # 计算扰动输出与原始输出的一致率
    agreement_rate = sum(o == base_output for o in perturbed_outputs) / n_perturb
    
    if agreement_rate > (1 - threshold):
        return "SUSPICIOUS"  # 后门可能已激活
    return "CLEAN"
```

**数据哈希存档 + Diff 审计**：把每个版本的训练数据做哈希存档，发布模型时能精确还原是哪批数据训练的。事后出问题可以做 Diff 追溯。听起来很基础，但大多数团队根本没做。

## 防御工程：把风险压到可接受范围

检测是被动的，工程层面的主动防御更重要。

**数据来源白名单**：明确规定训练数据只能来自哪些渠道，文档化每条数据的来源路径。对于开源数据集，只使用知名机构发布的版本，并锁定特定 commit hash 或版本号，不用"latest"。

**毒化样本比例上限控制**：即便存在少量毒化，只要比例足够低，攻击成功率也会大幅下降。工程上可以设置单一来源数据占比上限（比如任何单一外部来源不超过总量 5%），天然稀释毒化浓度。

**标注质检分层**：高风险标注任务（安全相关、敏感内容分类）必须走双人复核，并设置一定比例的 gold standard 样本混入抽查，发现标注质量下滑时触发全量复审。

**独立模型行为测试**：在常规 eval 之外，专门设计一套"行为异常探针测试集"，覆盖各类罕见触发模式、语言混用、特殊字符序列。这个测试集要独立维护，不能让训练数据影响到它。

**模型隔离发布**：新 fine-tuned 模型在内网灰度一周再外放，同时用线上真实流量的随机样本做持续行为监控，检测分布偏移。

## 踩坑清单

- **以为 eval 好就万事大吉**：后门攻击的核心特征是"平时正常，触发才发作"，标准 benchmark 根本看不出来。
- **合成数据"自产自销"就安全**：用来生成合成数据的 LLM 本身是否可信？API 提供商会不会在响应里植入特定模式？这个传播链条没人深究。
- **把 data lineage 留给 MLOps 组**：安全团队和 ML 工程师必须共同 own 数据来源审计，否则责任落空。
- **觉得自己目标不够大，不会被攻击**：供应链攻击的目标往往是"有影响力的中间环节"，你的模型如果被用于下游产品，攻击者有充分动机。
- **检测工具只跑一次**：激活分析和影响力分析要在每次重新 fine-tuning 后重跑，不能依赖历史结论。

数据是模型行为的源头。审查代码你早就习惯了，审查数据，才是 LLM 时代最容易被忽视的安全关卡。数据管道里每一个外部输入节点都是潜在攻击面，把安全左移的意识从代码层延伸到数据层，是接下来每个 fine-tuning 团队必须补的课。
