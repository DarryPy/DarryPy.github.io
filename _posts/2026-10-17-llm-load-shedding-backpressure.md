你给 LLM 网关加了队列扛突发流量，自以为稳了。直到某天上游持续超发，队列越堆越长，请求排了四十秒才轮到——而客户端十秒就超时重试了。此刻你在处理一堆没人要的结果，CPU 打满，新请求继续堆积，系统雪崩。削峰填谷解决的是"短暂的峰"，这篇讲峰不走时怎么办。

## 队列不是银弹，它只是把问题推后

队列的本质是用延迟换吞吐：瞬时流量超过处理能力时，把超出的先存起来慢慢消化。前提是流量是尖峰——冲一下就回落，队列有机会排空。但如果上游持续超发，到达速率长期大于处理速率，队列只会单调增长，最终要么 OOM，要么排队时间全都超过客户端超时，变成做无用功。

所以无界队列是事故温床。给队列设上限，并想清楚：满了之后第 N+1 个请求怎么办。答案不是"再等等"，而是立刻明确地拒绝它——这就是负载卸载（load shedding）。

## 背压：把"我扛不住"诚实地告诉上游

背压是让下游的拥塞状态反向传导给上游，逼它放慢或停下。对 LLM 网关最实用的形态就是：队列满时直接返回 429 并带上 Retry-After，让客户端知道该退避多久，而非闷头重试加剧拥塞。

```python
import asyncio

queue = asyncio.Queue(maxsize=200)   # 有界队列，这是关键

async def handle(req):
    try:
        queue.put_nowait(req)        # 满了立刻抛异常，不阻塞
    except asyncio.QueueFull:
        return Response(status=429, headers={"Retry-After": "2"})
    return await req.future           # 等 worker 处理完
```

注意 `put_nowait`：队列满时立即失败而非等待。宁可快速拒绝一部分，也别让所有请求一起烂在队列里。快速失败给了客户端退避和降级的机会，远比假装还能服务要诚实。

## 分级卸载：不是所有请求都该被拒

一刀切拒绝太粗暴。更聪明的做法是按优先级卸载——先丢可降级的、非付费的，保住核心流量。下面是实战常用的卸载决策表：

| 系统水位 | 处理策略 | 典型动作 |
|---------|---------|---------|
| < 70% | 全量正常 | 不干预 |
| 70-85% | 卸低优先级 | 拒绝批量/离线任务 |
| 85-95% | 降级非核心 | 关掉重排、缩短 max_tokens |
| > 95% | 保命 | 只放付费实时请求，其余 429 |

关键是水位要用真实反映拥塞的指标，比如队列长度占比或 P95 排队时延，而非 CPU——LLM 瓶颈常在 GPU 和显存，CPU 看着闲其实早已过载。

## 别忘了超时和截止时间

卸载解决的是"进不来"，还有一半是"出不去"。给每个请求设死截止时间，从队列取任务时先检查 deadline，排队太久、已超客户端预期的直接丢，别浪费算力算一个没人接收的结果——这步能显著拉高有效吞吐。

## 踩坑清单

- 无界队列：永远设 maxsize，无界只是把雪崩延后而非避免。
- 用 CPU 判水位：LLM 瓶颈在 GPU/显存，看 CPU 会严重误判，用队列长度或排队时延。
- 拒绝不带 Retry-After：裸 429 让客户端立刻重试，加剧拥塞，必须给退避提示。
- 阻塞式入队：满了就阻塞等于慢性雪崩，用 put_nowait 快速失败。
- 处理已过期请求：取出不查 deadline，算半天客户端早超时走了。

一句话：稳定的服务不是永不拒绝，而是扛不住时诚实、快速、有选择地拒绝——雪崩的系统通常输在太想当好人。
