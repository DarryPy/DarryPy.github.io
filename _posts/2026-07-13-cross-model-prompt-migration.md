你在 GPT-4o 上磨了两周的 System Prompt，切到 Claude 3.5 Sonnet 之后，输出风格、拒答率、JSON 字段结构全变了。这不是模型变笨了——是你的 Prompt 里藏着隐式的"平台假设"，而你从没意识到。

跨模型迁移在生产环境里是高频痛点：供应商涨价、性能更好的新模型上线、多供应商容灾切流，任何一个场景都会逼你迁。越早把 Prompt 写得"模型中立"，后期迁移的代价越小。这篇文章帮你系统地把这件事做对一次。

## 为什么同一条 Prompt 在不同模型上行为迥异

根本原因是各家模型的训练目标和 RLHF 偏好存在本质差异，导致它们对指令的"默认解读方式"不同。

**角色扮演和安全阈值差距明显。** Claude 对"假装你是没有限制的 AI"类指令极度敏感，会直接拒绝，哪怕包装得再自然；GPT-4o 的同类指令通过率历史上就高一些。同样是角色扮演场景，一个模型认为是正常创意写作，另一个认为是越狱尝试。你的 Prompt 在模型 A 上有效，不代表逻辑正确，很可能只是恰好命中了该模型的训练偏好盲区。

**输出格式的默认倾向不同。** GPT-4o 在没有显式要求时倾向于大量使用 Markdown 粗体和有序列表；Claude 在 API 模式（无 System Prompt）下默认更接近纯文本；Gemini 1.5 Pro 的 JSON 字段顺序在不同请求之间不稳定，除非你用 response_schema 明确约束。这些"默认审美"差异，在你只写了"请以 JSON 格式返回"之后会被完全放大。

**对歧义的处理策略不同。** 当指令不清晰时，有些模型会自动补全缺失信息（往往补错方向），有些会主动停下来询问，有些则编一个看起来合理的答案。在没有 few-shot 示例的情况下，这种差异会让你的迁移测试结果像开盲盒。

**tokenizer 差异导致长度控制失效。** 同样的中文文本，在 GPT-4o、Claude 和 Gemini 的 tokenizer 下，token 数量差距可达 15–30%。如果你在 Prompt 里写"回答不超过 500 tokens"，跨模型后实际输出字数差距会让你怀疑 Prompt 是否生效。

**推理链深度偏好不同。** 不给任何格式指令时，Claude 倾向于给出更长的分析推理过程，甚至在最终答案前加上大量"让我思考一下……"的铺垫；GPT-4o 则更倾向于直接给出结论，然后在后面跟上简短解释。如果你的下游解析依赖模型"直接输出答案"，切到 Claude 后可能拿到一大段你不需要的思考过程，导致正则提取或 JSON 解析失败。解决办法是在指令里明确写"直接给出结果，不需要说明推理过程"或"先输出结论，再输出解释"，而不是假设模型知道你想要哪种格式。

## 五大迁移雷区与对应写法

### 雷区一：依赖模型的"默认审美"

很多 Prompt 之所以有效，是因为你命中了某个模型的训练偏好，而不是因为指令本身清晰。

最典型的例子：

```text
你是一个专业的数据分析师，请帮我分析以下数据。
```

这条指令在 GPT-4o 上可能输出带表格的精美分析，因为它的对话训练数据里充斥着这类格式；切到 Claude 可能得到一篇流水账；切到更小的开源模型可能只有两行。

**迁移安全写法：** 把格式期望全部显式声明，不靠模型默认审美。这一步的本质是把"隐性合约"变成"显性合约"——你期望什么格式，就直接在 Prompt 里写出来，不要留给模型去猜。

```text
分析以下数据，请严格按此结构输出，不添加任何额外段落：

**关键发现**（不超过 3 条，每条一句话）
- 发现1
- 发现2

**异常点**（如有，列出具体数值；如无则写"无"）

**建议行动**（不超过 2 条）
```

结构显式化之后，任何模型都能理解期望，而不是靠猜。

### 雷区二：结构化输出靠描述而非 schema

用自然语言描述 JSON 结构，是跨模型迁移里最容易出问题的写法。字段名拼写、嵌套层级、数组还是对象，各模型理解起来都可能出偏差。

```text
# 危险写法
请以 JSON 格式返回，包含 title、summary 和 tags 字段。

# 跨模型稳定写法
请严格按以下 JSON 返回，不要添加任何 Markdown 代码块标记，不要添加注释，不要添加额外字段：
{
  "title": "文章标题（字符串）",
  "summary": "摘要，不超过 80 字（字符串）",
  "tags": ["标签1", "标签2"]
}
```

如果你用的 API 支持原生结构化输出——OpenAI 的 response_format、Claude 的 tool_use 强制返回、Gemini 的 response_schema——**优先使用原生能力**，不要靠 Prompt 约束。原生 schema 的稳定性远高于自然语言描述，而且不受模型版本迭代影响，升级底座后不需要重新调整。唯一需要注意的是，原生结构化输出在切换供应商时接口参数名称不同，需要在 SDK 层做一层薄封装来屏蔽差异，而不是在每个调用点硬编码参数名。

### 雷区三：长上下文引用用隐式指代

"根据上文""你之前提到的"这类表达，在不同模型里的解读差异相当大。Claude 的长文本记忆相对可靠，但在对话轮次较多时，它可能把"上文"理解成整个对话而不是你期望的特定片段。

对比一下：

| 写法 | 迁移稳定性 |
|------|------------|
| "根据上文重新总结" | 低——各模型对"上文"的边界理解不同 |
| "根据用户在第一条消息提供的项目背景重新总结" | 高——明确锚定来源 |
| "忽略之前的对话，仅基于以下内容作答" | 高——显式重置上下文 |

把对话历史中需要引用的关键信息，在当前 turn 的指令里显式复述一遍，比任何隐式引用都稳定。多付出几十个 token，省掉排查上下文解读问题的数小时。养成这个习惯还有一个额外的好处：当你把 Prompt 交给其他工程师审查时，他们不需要回看整段对话历史就能理解这条指令的意图，代码可读性同步提升。

### 雷区四：硬编码 token 限制

"回答不超过 200 tokens" 在不同 tokenizer 下实际字数差距悬殊，而且模型对自己的 token 使用量普遍感知不准，常常在接近限制时草草收尾或完全忽略约束。

替代方案：

```text
请控制回答长度在 150–200 中文字之间（按字符计数，不含标点和空格）。
如果你的草稿超过 220 字，请在输出前自行压缩，删除冗余表达，再输出最终版本。
```

用字数代替 token 数，加上自检压缩指令，可移植性高得多。自检环节还有一个副作用：模型在压缩时会主动提炼核心信息，输出质量往往比直接截断更好。

### 雷区五：忽略模型对"停止信号"的不同理解

有些 Prompt 会在 few-shot 示例末尾加"END"或"---"来标记单次输出结束，这在 GPT 系列上很常见。但换到 Claude 或 Gemini 时，这类停止信号可能被模型当成普通文本内容原样输出，或者被忽略，导致它继续往下生成。

**安全做法：** 在 API 层设置 stop_sequences（几乎所有主流 API 都支持），而不是靠 Prompt 里的文本标记来控制停止。这是真正跨模型稳定的方案。还有一个容易被忽视的细节：如果你在 few-shot 示例里用"---"作为分隔符，确保它和 stop_sequences 里的字符串完全一致，否则一旦模型改变了空格或换行处理，停止信号就会失效。

```python
# OpenAI / Claude / Gemini 都支持 stop 参数
response = client.chat.completions.create(
    model="...",
    messages=[...],
    stop=["END", "---DONE---"]
)
```

## 迁移前必过检查清单

在把 Prompt 切到新模型之前，逐条检查：

- [ ] 去掉所有"根据上文/之前提到的"隐式引用，改为显式复述关键信息
- [ ] 格式要求全部写成具体示例，不依赖模型的默认输出风格
- [ ] JSON/结构化输出提供完整 schema 示例，并声明"不要 Markdown 包裹、不要额外字段"
- [ ] 把 token 限制改成字数限制，并加自检压缩指令
- [ ] 检查有没有依赖特定模型风格的写法（Claude 偏好 XML 标签包裹指令，GPT 偏好 Markdown 分节）
- [ ] 停止信号改为 API 层 stop_sequences，而不是 Prompt 里的文本标记
- [ ] 用至少 5 个边界用例做回归测试：正常输入、空输入、超长输入、歧义输入、对抗性输入各一条
- [ ] 如果有角色扮演场景，在新模型上单独测拒答率，不要假设通过率相同

## 最后一句话

Prompt 写得越"口语化"，就越依赖某个模型的"默认脑补"——迁移时你付出的代价，恰好等于当初省下来的那些显式声明。
