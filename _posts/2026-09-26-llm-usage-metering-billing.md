你上线了多租户 LLM 服务，月底老板问每个客户该收多少钱，你翻遍日志只找到一堆散落的 token 数，对不上、算不准。这就是计量系统缺位的代价。成本监控告诉你这个月总共烧了多少，计量计费要回答"每个人各花了多少、该付多少"——两者的精度要求差了一个量级，前者估个大概就行，后者错一分钱都要被客户追着问，甚至可能走到对簿公堂。所以从第一天就该把计量当成核心链路来设计，而不是等有了客户投诉再来补。

## 计量埋点：每次调用都要留下证据

计量的源头是每次 LLM 调用返回的 usage 字段。千万别用自己 tokenizer 估的数，一律以服务端返回为准，因为最终账单和上游对你的计费都基于服务端口径，两边不一致你就得自己吞差价。你自己数的 token 和服务端往往差几个百分点，量一大就是真金白银。prompt caching 命中时 usage 还会拆出 `cache_read` 和 `cache_write`，两者单价不同，必须分列记录，混在一起算你迟早算错。

一条计量记录至少要包含租户 ID、模型、时间戳和分类 token，缺一项后面就对不上账。字段设计时宁可多留几个维度，事后想加维度得回捞历史数据，代价极高：

```python
def record_usage(resp, tenant_id, model, request_id):
    u = resp.usage
    emit({
        "request_id": request_id,      # 幂等去重用
        "tenant_id": tenant_id,
        "model": model,
        "ts": resp.created,            # 用服务端时间，别用本地时间
        "input_tokens": u.input_tokens,
        "cache_read": getattr(u, "cache_read_input_tokens", 0),
        "cache_write": getattr(u, "cache_creation_input_tokens", 0),
        "output_tokens": u.output_tokens,
    })
```

埋点要放在拿到响应之后、返回给用户之前，且不能因为埋点失败就影响主流程——用异步 emit，失败进重试队列，绝不阻塞用户请求。流式响应更要小心：usage 通常在最后一个 chunk 才吐出来，你得读到流结束才拿得到准确数字，中途断流的请求要有兜底策略，否则这段消费就凭空蒸发了。

## 聚合与存储：别把每条调用都直写数据库

高并发下，每条明细都同步 INSERT 会先把你自己的数据库压垮，写入还会和查询抢锁。正确姿势是分层：调用产生的原始记录先进消息队列或本地环形缓冲，消费端按"租户 + 模型 + 分钟"预聚合，再定期批量落库；完整明细归档到对象存储，只在客户申诉或审计时才回捞。这样热路径只碰内存和队列，数据库只承接汇总后的少量写入。

| 策略 | 写放大 | 查询延迟 | 适用场景 |
|------|--------|----------|----------|
| 明细实时写库 | 高 | 低 | 日调用量 &lt; 十万 |
| 批量分钟聚合 | 低 | 中 | 多租户生产主力方案 |
| 冷热分离归档 | 低 | 明细高/汇总低 | 需长期审计留证 |

聚合的时间窗口要对齐自然分钟或小时，别用滑动窗口——账单是按日历周期结算的，窗口不对齐，跨月的那几秒钟就会两头都算不清。时区也是坑：所有时间戳统一存 UTC，展示和结算时再按客户所在时区换算，别在存储层就本地化，否则跨时区的客户账单边界永远对不齐。

## 从 token 到金额：定价表要能追溯

把 token 换算成钱，不是乘一个常数那么简单。单价会调整、模型会新增、缓存 token 有独立折扣、还可能给大客户谈了阶梯价。你需要一张带生效时间区间的定价表，历史账单永远按"消费发生那一刻"的价格算，绝不能用今天的价格去重算上个月：

```python
def price(rec, pricing_table):
    p = lookup(pricing_table, rec["model"], at=rec["ts"])  # 按时间点取价
    return (
        rec["input_tokens"]  * p.input +
        rec["cache_read"]    * p.cache_read +   # 通常是 input 的 1/10
        rec["cache_write"]   * p.cache_write +  # 通常比 input 略贵
        rec["output_tokens"] * p.output
    ) / 1_000_000  # 单价一般按每百万 token 报价
```

定价表本身要版本化、可审计，任何一次改价都留记录，谁改的、什么时候生效都要能查。客户来对账时，你要能拿出"这笔消费当时用的是哪个版本的价格"，而不是一句"系统就是这么算的"。另外别忘了汇率和税：如果你按人民币收费但上游按美元计价，汇率也要按结算周期锁定，别用实时汇率算，不然月中波动会让你的毛利飘忽不定。

## 预付费与软限额：别等账单出来才发现超支

后付费模式下，客户可能一个月烧掉远超预算的钱，等账单出来时钱已经花了、模型也退不回。所以要在计量之上加一层实时余额检查：预付费客户扣的是余额，余额见底就拒绝新请求；后付费客户设软限额，接近阈值先告警、超过硬顶再拦截。这层判断要读的是近实时的累计用量，不能等分钟聚合落库，否则高并发下几秒钟就能冲穿限额。

实践里通常在网关侧维护一个按租户的原子计数器，每次请求前先做预扣、响应后按实际 usage 回填差额。预扣要按请求可能产生的最大 token 估一个上限，宁可先扣多、再退回，也别先放行、再发现超支。计量、限额、计费共用同一份用量数据，三者口径必须完全一致，否则客户会拿着不同页面上的数字来质问你。

## 给客户的账单页：透明才不扯皮

计量数据不能只躺在后台，要以客户能看懂的方式暴露出来。给每个租户提供一个近实时的用量看板：按天、按模型、按 API Key 拆分消费，让他们自己就能看清钱花在哪。数字越透明，月底扯皮越少；藏着掖着，客户反而会怀疑你多收。看板的数据源要和计费同一份，别为了展示另起一套统计口径，两个数字对不上比没有看板还糟。

出账时，账单要能下钻到明细。一张只写"本月共计 X 元"的账单，客户一有疑问你就得手工翻库导数据，效率极低。正确做法是账单挂着可展开的用量汇总，每一行都能追溯到聚合记录，必要时再回捞对象存储里的原始明细。发票金额一旦确认就冻结快照，之后即使定价表或历史数据被订正，已出的账单也不再变动，只能靠调整项在下一期修正——这是财务合规的底线。

对账与幂等是最后一道防线。用 `request_id` 做幂等键，同一请求无论重试几次、消息投递几遍，只计一次。每天再跑一次对账 job，把你聚合的当日总量和上游账单接口拉回来的用量比对，偏差超阈值就告警，别等月底大规模返工。

踩坑清单，上线前逐条过：

- **用服务端 usage，不用本地估算**——两边口径不一致你吞差价
- **cache_read / cache_write 分开计价**——单价差 10 倍，混算必错
- **流式响应读到流结束再取 usage**——中途断流要有兜底，别漏记
- **定价表带生效时间与版本**——历史账单按当时价格，禁止用今价重算
- **request_id 幂等去重**——重试和重复投递不能重复计费
- **聚合窗口对齐日历周期、时间统一存 UTC**——跨月跨时区别两头算不清
- **预付费实时预扣、后付费软硬限额**——别等账单出来才发现超支
- **每日自动对账 + 偏差告警**——别把发现问题的机会留给客户

一句话：成本监控是给你自己看的仪表盘，计量计费是要拿给客户签字的合同。前者可以估，后者必须准，差一分钱都要能解释清楚。
