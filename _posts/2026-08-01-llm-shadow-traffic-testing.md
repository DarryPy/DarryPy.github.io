你把一个新模型接进生产,离线评测跑了一整周全过,上线当天却发现真实流量里有一类 prompt 让它疯狂截断,回滚、复盘、写故障报告,一晚上就没了。问题不在你不够仔细,而在离线数据集永远覆盖不全真实分布——用户输入的长尾,你在评测集里根本造不出来。而 A/B testing 虽然用了真实流量,却会让一部分真实用户直接吃到新模型的坏 case。影子流量(shadow traffic)是这两者之间的第三条路:让新模型跑真实请求,但结果只记录、不返回给用户。

## 为什么影子流量比 A/B 更适合验证新模型

A/B testing 的逻辑是把用户分成两拨,一拨真的用上了新模型。如果新模型在某一类请求上系统性翻车,那拨用户就是替你踩雷的小白鼠,而你往往等他们投诉了才知道。对面向付费用户、或涉及金额、医疗、法务的场景,这种"先伤害再学习"的代价高到不可接受。

影子流量把验证和伤害解耦。用户永远拿到老模型(baseline)的结果,新模型只是"陪跑":同一份真实请求也发给它一份,输出被单独采集下来做离线对比,绝不进入返回给用户的响应。这意味着你能用 100% 真实分布来考新模型,而用户侧风险严格为零。唯一代价是陪跑调用要多花一份 token 钱,后面用采样解决。

## 影子链路怎么搭:复制、异步、不阻塞

核心原则只有一条,而且不容打折:影子调用绝不能拖慢或拖垮主链路。用户体验完全由主模型决定,影子是纯旁路。主模型一返回就立刻响应用户,影子调用扔进后台异步跑,它超时、报错、限流,都只记日志,不影响任何一个真实请求。

```python
async def handle(req):
    primary = await call_model(PRIMARY, req)   # 用户实际拿到的
    # 影子调用:fire-and-forget,不 await 进主链路
    asyncio.create_task(run_shadow(SHADOW, req, primary))
    return primary

async def run_shadow(model, req, baseline):
    try:
        shadow = await call_model(model, req)
        await log_compare(req, baseline, shadow)  # 异步落对比库
    except Exception:
        metrics.incr("shadow.error")   # 影子挂了不报警到用户侧
```

这里有三个最容易踩的坑。第一,create_task 之后千万别再 await 它,否则影子延迟会加回到用户等待时间,旁路就变成了串联。第二,给影子单独的 timeout、连接池和限流配额,别让它和主模型抢连接,不然主链路会被陪跑拖垮。第三,影子的异常要单独归类,别混进主链路的错误率报警,否则你会被一堆"不影响用户"的告警淹没。

## 对比什么:盯分布,别盯逐条 diff

新老输出逐字相等在生成式任务里几乎不可能,你要是拿 diff 一条条比,只会得到满屏"不一样"却毫无信息量。真正该看的是分布层面的偏移:同一批真实请求,新模型整体上更慢了、更贵了、还是更容易崩了。

| 维度 | 老模型基线 | 新模型影子 | 关注点 |
|------|-----------|-----------|--------|
| P95 延迟 | 1.2s | 2.1s | 慢 75%,能接受吗 |
| 输出 token 均值 | 320 | 510 | 变长=直接变贵 |
| JSON 解析失败率 | 0.3% | 2.1% | structured output 退化 |
| 空/截断响应率 | 0.1% | 1.8% | 真实分布暴露的坑 |
| 语义相似度 | — | 0.86 | 和基线偏离多大 |

单看某一行都不致命,但放在一起你就能回答那个真正的问题:"这个新模型到底能不能顶上去"。语义相似度别人肉看,用 embedding 算 cosine,或者让一个裁判模型对新老输出打分,把主观判断也变成可统计的数字。特别留意长尾:平均值好看不代表没坑,盯住 P99 那一批请求,坏 case 通常都藏在那儿。

## 采样、脱敏与成本:别让影子把账单翻倍

影子最大的反对声音永远是成本——它等于每个请求都跑两遍,token 直接翻倍。解法是采样:你根本不需要 100% 影子,按 5%-10% 真实流量随机采样,统计上就足够看清分布偏移;只在你最担心的那几类高风险请求上,单独把采样率提到 50% 甚至更高,把预算花在刀刃上。

安全这条线更不能松。对比库里存的是货真价实的用户 prompt,里面可能有手机号、订单号、身份信息,落库前必须先过一遍 PII 脱敏,别让一个"内部对比数据集"哪天变成合规事故。存储再统一设 TTL,对比分析做完就滚动删除,别让影子数据无限堆积成一颗定时炸弹。

## 用之前想清楚:边界、门槛与切换节奏

影子流量不是万能的,有三类请求你一放进去就会出事。第一类是带副作用的请求:如果处理逻辑里有写数据库、发邮件、扣款这种动作,影子复制一份就等于把副作用也执行了两遍,轻则脏数据,重则给用户重复扣款。对这类请求,要么只影子到"生成文本"那一步就截断,要么把下游全部换成 mock,绝不能让陪跑真的落地。

第二类是多轮有状态对话。影子模型这一轮的输出并没有真的进对话历史,它下一轮拿到的上下文其实是老模型攒出来的,越到后面偏差越大,对比数据也就越不可信。稳妥做法是只在单轮任务上跑影子,多轮场景改用离线重放整段会话,让新模型从头自己接管上下文再比。

第三类是依赖实时外部数据的请求,比如带联网检索、读实时库存。影子跑的时刻和主链路差几百毫秒,拿到的外部数据可能已经变了,这时输出不同未必是模型的锅。要么强制两个模型共用同一份检索结果再各自生成,要么干脆把这类请求排除在影子之外,别拿噪声当信号。

边界理清了,接着定门槛。影子跑起来只是手段,你最终要回答的是"到底能不能切"。别等数据出来再拍脑袋,应该在开跑之前就写死一组通过标准,比如:语义相似度不低于 0.85、JSON 失败率不高于基线、P95 延迟涨幅不超过 20%、空响应率不劣化。达标就推进,不达标就打回,标准提前定好,你才不会被好看的平均值牵着走。

样本量也得够。几百条请求上的差异很可能只是噪声,至少要攒到覆盖一个完整业务周期、涵盖高峰和低谷的量级,结论才站得住脚。信号弱的时候宁可多跑两天,也别急着下判断,毕竟一次误判的回滚成本远高于多跑两天的 token 钱。

真正切换时也别一步到位。影子通过后,先走 canary 把 1% 真实流量切到新模型,盯紧线上指标确认没问题,再逐步放大到 10%、50%、100%。影子负责"上线前零风险验证",canary 负责"上线后小步快跑",两者接力,才是一条完整的模型上线链路。

上线前,再对着这份踩坑清单过一遍:

- 影子调用必须 fire-and-forget,严禁 await 进主链路
- 影子用独立 timeout / 连接池 / 限流,不抢主模型资源
- 影子异常只打点不报警,别把陪跑失败变成 oncall
- 带副作用/多轮/依赖实时数据的请求,先想清楚再放进影子
- 通过标准和样本量在开跑前就定死,别被结果反向带节奏
- 采样率先 5% 起,高风险请求再单独提,看清成本再调
- 对比库存的 prompt 必须脱敏 + 设 TTL 自动清理
- 别只看逐条 diff,盯分布指标:延迟、token、失败率、语义偏移
- 重点看长尾 P99,坏 case 几乎都藏在平均值背后
- 跑够覆盖真实峰谷的时间窗(至少一个完整业务周期)再下结论

一句话:影子流量让你用真实世界的全量分布考新模型,而考砸的成本只由你的账单承担,永远不由用户承担。
