你花了三天搭 eval 流水线，跑完一看综合分 82，松了口气准备上线。这口气松早了。82 这个数字，是把几百条样本的对错压成一个平均值——它告诉你"大概还行"，却藏起了真正要命的信息：到底哪一类请求在崩、崩成什么样、为什么崩。错误分析（Error Analysis）就是把这些被平均值吞掉的细节一条条捞回来，它带来的提升，往往比你换模型、调温度都大。

## 总分会骗你

一个综合分最大的问题，是它把结构性失败稀释成了噪声。假设你的 agent 对普通问答准确率 95%，但一碰到多步骤计算就几乎全错——如果计算类样本只占 8%，总分依然能有 88，看着体面。可一旦真实流量里这类请求涨到 30%，线上体验直接塌方。平均值天然偏向多数类，少数类的系统性崩溃被它温柔地盖住了。

更隐蔽的是，总分不告诉你失败的"形状"。两个都得 0 分的样本，一个是模型答错了事实，一个是输出格式不对导致解析失败，根因完全不同、修法也完全不同。前者要补知识或改检索，后者可能一个 schema 约束就解决了。你盯着分数看一个月，也看不出这个区别。

团队之所以总爱盯着单一数字，是因为它便于汇报、便于画折线图，老板一眼能看懂。但对改进系统来说，它恰恰是信息量最低的那个指标——它能告诉你"今天比昨天差了两个点"，却从不告诉你差在哪、该动哪里。

退一步说，就算你给总分加了权重，让关键类别占比更高，它依然只是把多个信号重新压成一个标量。压缩必然丢信息——你永远没法从一个数字倒推出三类失败各占多少。想做对决策，就得在压缩之前，先在原始的失败样本上停留足够久。

## 把失败样本摊开看

错误分析的第一步朴素到让人怀疑：你要亲手读数据。不是看 dashboard，是打开每一条失败的输入、输出、中间步骤，像医生看片子一样逐条过。行业里管这叫 open coding——先不预设分类，边读边给每条失败写一句话标签："漏了检索到的关键段落""工具参数拼错了""把用户的反问当成了指令"。

读 trace 时别只看最终答案，要顺着链路往回扒：检索到的 context 对不对、模型调了哪个工具、参数是否合理、从哪一步开始跑偏。很多失败的根因藏在中间步骤里，最终输出只是症状。那句话标签要写清"哪里错了"，而不是光写"错了"——后者等于没标。

读多少才够？经验值是先读到标签不再冒新类为止，通常几十条就会饱和。别一上来就想读全量——那既读不完，也没必要。真正要防的是只读你"觉得有问题"的那些：那样抽出来的样本带着强烈的确认偏差，会让你高估自己早就知道的问题、漏掉真正的盲区。

读上几十条，标签自然开始聚堆。你会发现它们能收敛成有限的几类失败模式（failure mode），比如检索召回不全、指令理解偏差、输出格式违约、幻觉补全。这一步叫 axial coding——把零散标签归并成稳定的分类体系。关键是分类要来自数据本身，而不是你上线前拍脑袋定好的框；真实失败的形状，往往和你想象的差得很远。

## 按"频率 × 严重度"排序

有了分类，别急着从你最眼熟的那类开始修。正确的排序维度有两个：这类失败出现得多不多（频率），以及它错一次有多疼（严重度）。把两者摆到一张表上，优先级一目了然：

| 失败模式 | 频率 | 严重度 | 处理顺序 |
|---|---|---|---|
| 检索召回不全 | 高 | 高 | 立刻修 |
| 输出格式违约 | 高 | 低 | 批量兜底 |
| 事实性幻觉 | 低 | 高 | 重点盯防 |
| 口吻不自然 | 低 | 低 | 先放着 |

高频高危的那格是你本周的全部重点，低频低危的放到 backlog 最底下——哪怕它读起来最扎眼。严重度要结合业务定：医疗问答里一次幻觉的代价，远高于十次格式错。把"最吵的"和"最贵的"分开，是错误分析里最反直觉、也最值钱的一步。

这张表还有个副作用：它逼你把模糊的"感觉不太行"翻译成两个能排序的维度。一旦团队开始为"这到底算高危还是低危"争论，你其实已经在逼近真正的质量标准了——很多产品的验收线，就是在这种争论里第一次被说清楚的。

## 从聚类到可执行的修复

优先级定了，再把人工标签落到记录里直接聚合，用占比印证你的判断：

```python
from collections import Counter

# 每条失败样本人工标注后的记录
failures = [
    {"id": 12, "mode": "retrieval_miss"},
    {"id": 27, "mode": "format_violation"},
    {"id": 31, "mode": "retrieval_miss"},
    {"id": 44, "mode": "hallucination"},
    {"id": 58, "mode": "retrieval_miss"},
]

dist = Counter(f["mode"] for f in failures)
for mode, n in dist.most_common():
    print(f"{mode:20s} {n:3d}  {n/len(failures):.0%}")
# retrieval_miss       3   60%
# format_violation     1   20%
# hallucination        1   20%
```

光看条数还不够，记得把前面那张严重度表叠上去。一个占比 10% 但每次都引来用户投诉的失败，优先级可能高于占比 40% 却无伤大雅的口吻问题。实践里可以给每条失败再标一个 1-3 的 severity，聚合时按 频率×严重度 排序，而不是只按出现次数。

数字一出来，行动就清晰了：60% 的失败是检索召回不全，那你该先去调 chunk 大小、换 embedding 或加 rerank，而不是急着换更大的生成模型。错误分析真正的产出不是一份报告，是一张按 ROI 排序的修复清单——先打占比最高、改起来最省的那一类。

更值钱的是，每一类失败都能直接沉淀成新的 eval 用例。你把 retrieval_miss 里那几条典型样本固化进测试集，下次改完检索就能验证这一类到底修没修好。错误分析和 eval 集因此形成闭环：线上暴露新失败 → 归类 → 补进测试集 → 回归守住。测试集不是一次建好的，是被真实失败一点点喂大的。

## 把错误分析变成日常

一次性的错误分析只能救一次火，真正拉开差距的是把它变成固定节奏。下面这份清单可以直接抄：

- 每周固定抽样：从线上流量里随机抽 50-100 条，别只挑你觉得有问题的，那会引入选择偏差
- 两人独立标注关键样本，对不齐的地方，正好暴露分类体系的模糊点
- 维护一张活的 failure taxonomy，新模式加进去、过时的删掉
- 每类失败挂一个 owner 和一条对应的 eval 用例，修复有人认领、回归有兜底
- 大版本上线前，专门过一遍上次的高频失败类，确认没复发

节奏比工具重要。很多团队卡在"等我把 eval 平台搭完再说"，结果平台搭了半年，数据一条没读过。错误分析的门槛其实低到一个 spreadsheet 就能起步：先读 50 条，就比盯着总分强得多。等你攒到几百条带标签的样本，再谈用 LLM 自动归类也不迟——那时你已经清楚失败长什么样，自动化才是在帮你放大判断，而不是替你瞎猜。

踩坑清单：别用总分代替看数据——平均值是体检报告上的一个数，不是病历；别让一个人闷头标注——分类体系需要两个人撞一撞才稳；别跳过"亲手读 trace"直接上 LLM 自动归类——你自己都没搞懂失败长什么样，写出来的 judge prompt 只会把误解成倍放大。
