你大概遇到过这种场景：Agent 跑到一半卡住了，任务恢复后继续执行，结果用户收到了两封一模一样的通知邮件，或者订单系统里多出了一张重复订单。工具本身没有 bug，代码逻辑也对，问题出在**重试路径上缺少幂等保护**。

在普通的后端服务里，你可能已经习惯了在 HTTP 客户端加 `retry(3, backoff=exponential)` 然后忘掉这件事。但 Agent 的重试来源要复杂得多：网络超时会触发，LLM 输出了两次完全相同的 tool_call 会触发，Human-in-the-Loop 的人工介入后重新进入执行路径会触发，任务崩溃恢复也会触发。更麻烦的是，很多重试是框架层静默完成的，你根本不知道它发生了。而且 Agent 任务往往是有状态的多步流程，某一步的工具调用失败，整个任务可能需要从某个检查点回滚重跑，这意味着前几步已经执行过的工具调用会被再次触发。

这意味着单靠"在框架层堵死所有重试入口"是不现实的。**让工具调用本身具备幂等性，才是从根上解决问题的方式**。幂等的含义很简单：同一操作执行多次，效果与执行一次完全等价。这个性质在数学上很优雅，但真正落地到 Agent 工具调用里，需要在工具函数本身、框架调度逻辑、副作用管理策略三个层面分别处理，缺一不可。

## 工具函数层：用幂等键做服务端去重

读操作天然幂等，`get_weather("北京")` 调多少次都没有副作用。真正的麻烦在写操作上——创建订单、发送消息、修改数据库记录，这些操作一旦被重复执行，后果轻则数据冗余，重则业务事故。

**幂等键（Idempotency Key）**是目前最成熟的解法。核心思路是：调用方在每次请求里带上一个唯一标识，服务端以这个 key 为索引做去重。如果见过这个 key，就直接返回上次的执行结果，不重复进行任何操作。

```python
def create_order(user_id: str, items: list, idempotency_key: str) -> dict:
    cached = redis.get(f"idem:{idempotency_key}")
    if cached:
        return json.loads(cached)          # 命中缓存，直接返回历史结果

    result = _do_create_order(user_id, items)
    redis.setex(f"idem:{idempotency_key}", 86400, json.dumps(result))
    return result
```

这里有一个极其常见的踩坑点：**幂等键绝对不能用随机 UUID**。如果 Agent 在每次重试时重新调用 `uuid4()` 生成 key，服务端看到的是一个全新的陌生 key，会当成全新请求处理，幂等保护形同虚设。

正确的做法是让 Agent 用任务 ID 加上工具名和关键业务参数，通过哈希生成一个**确定性的 key**——同一个逻辑调用，无论重试多少次，都能得到同一个 key：

```python
import hashlib, json

def make_idempotency_key(task_id: str, tool_name: str, args: dict) -> str:
    payload = f"{task_id}:{tool_name}:{json.dumps(args, sort_keys=True)}"
    return hashlib.sha256(payload.encode()).hexdigest()[:32]
```

另外需要注意 TTL 的设置。如果任务可能执行两个小时，TTL 却只有三十分钟，缓存会在任务中途失效。一旦失效后发生重试，服务端就找不到历史记录，等于在任务执行到一半的时候让幂等保护悄悄消失了。TTL 应该覆盖任务的最长执行时间，并留出合理余量。对于执行时间不确定的长任务，可以在任务完成时主动删除幂等键，而不是依赖被动过期，这样既避免长时间占用缓存，也保证任务生命周期内的幂等保护始终有效。

## 框架层：任务级调用记录

并非所有工具都在你的掌控下。第三方 API 不会因为你的 Agent 需要幂等保证就配合你加幂等键；MCP server 提供的工具也未必实现了服务端去重。面对这类外部工具，在框架层加一层**调用记录与缓存**是更实际的选择。

思路是：在实际执行工具之前，先查当前任务是否已经执行过完全相同的调用。如果查到了，直接返回缓存的历史结果，不触发真正的工具调用：

```python
class DeduplicatingToolExecutor:
    def __init__(self, task_id: str):
        self.task_id = task_id
        self._call_log: dict[str, Any] = {}

    def call(self, tool_name: str, args: dict) -> Any:
        call_key = f"{tool_name}:{json.dumps(args, sort_keys=True)}"

        if call_key in self._call_log:
            return self._call_log[call_key]   # 命中，跳过重复执行

        result = self._execute(tool_name, args)
        self._call_log[call_key] = result
        return result
```

有一个设计细节必须注意：**去重缓存必须绑定到任务级别，而不能做成全局单例**。`get_stock_price("AAPL")` 在任务 A 里已经调过，十分钟后任务 B 需要的是当前最新价格，不能因为全局缓存里有一个旧结果就跳过调用。只有在同一个任务的重试路径上，相同调用才应该复用结果。而对于纯查询类工具，可以根据业务需要决定是否允许跨任务共享缓存，并配合合理的缓存过期策略。

框架层缓存还有一个意外的优势：即便工具服务暂时不可达，只要当前任务在本次调用之前已经拿到过结果，Agent 就可以继续向前推进，等待服务恢复后再处理后续步骤，而不是整个任务回滚重跑。对于执行时间较长的 Agent 任务来说，这种"局部容错"能力可以显著提升任务的完成率，减少因单一工具抖动导致整链路重跑的概率。

## 副作用标记：对高风险工具做隔离

有些工具即便加了幂等键也很难做到完全无害——发送 Webhook 通知、写外部审计日志、触发物理设备动作。对这类工具，最好的策略不是去重，而是**显式隔离**：在工具的 schema 里标记它具有副作用，让 Agent 在重试路径上不自动重复调用，而是转交人工决策。

在工具描述里增加一个 `side_effects` 字段，成本很低：

```json
{
  "name": "send_slack_alert",
  "description": "向 Slack 频道发送告警消息",
  "side_effects": true,
  "parameters": {
    "channel": { "type": "string" },
    "message": { "type": "string" }
  }
}
```

框架层读到 `side_effects: true`，在任务恢复或 Human-in-the-Loop 重入时，不自动重调这个工具，而是生成一条确认提示："上次任务中断前已调用 send_slack_alert，是否需要重新发送？"这比静默重试安全得多，也比完全跳过更加透明，用户始终清楚发生了什么。

这个模式在 Agent 构建初期看起来有点繁琐，但随着工具数量增多、Agent 任务复杂度上升，它能帮你省掉大量"为什么又重复发了"的排查时间。更重要的是，它让 Agent 的行为对运维团队来说变得可预期：哪些工具会自动重试、哪些需要人工确认，一眼就能从 schema 里看清楚，而不是埋在代码逻辑深处等着出事才被发现。将副作用信息显式放进工具描述，也让 Agent 在输出执行计划时有机会主动告知用户"接下来这个步骤不可撤销"，提高整个流程的透明度。

## 不同工具类型的推荐策略

| 工具类型 | 推荐策略 | 关键注意点 |
|---------|---------|-----------|
| 查询 / 读取 | 无需幂等处理 | 天然无副作用，可视需求加缓存 |
| 数据库写入 | 幂等键 + 服务端去重 | key 由 Agent 侧确定性生成 |
| 三方 API 写操作 | 框架层任务级缓存 | 不跨任务共享缓存 |
| 通知 / 消息发送 | schema 标记 side_effects | 重试路径转人工确认 |
| 文件 / 对象存储写入 | 先读状态再写入 | 写前检查目标是否已存在 |

## 踩坑清单

- **幂等键用随机 UUID**：重试时 key 变了，服务端当新请求处理，幂等白做
- **缓存 TTL 短于任务执行时间**：缓存中途失效，重试路径上幂等保护消失
- **只在工具侧做幂等，忽略框架层重试**：有时候 LLM 会连续输出两次相同的 tool_call，框架在工具服务无感知的情况下就调了两遍
- **框架层缓存做成全局单例**：查询类工具拿到过期数据，写操作跨任务相互污染
- **通知类工具静默重复发送**：用户完全无感知，发现问题时已经造成实际影响

**幂等不是优化项，是让 Agent 在生产环境活下去的基础设施**。Agent 任务越复杂，重试路径越多，幂等设计的漏洞就越容易在最不合时宜的时刻暴露出来。
