你上周精心调好的 prompt，今天回归测试突然掉了 8 分。代码一行没动，temperature 没改，供应商也没发任何公告。你怀疑自己眼花，重新跑一遍——分数还是低。这不是玄学，是模型漂移（model drift），而且它几乎从不敲门就闯进来。

漂移的杀伤力在于隐蔽。它不像线上事故那样触发 5xx 报警，也不会在日志里留下红色堆栈。你的接口一切正常，返回码全是 200，唯独模型给出的答案，正在以你察觉不到的速度悄悄变差。

## 漂移的四个来源

漂移不是单一现象，先分清来源，你才知道该防哪一面。第一类是供应商静默更新：同一个 `gpt-4o` 别名背后，权重、系统提示、安全策略随时可能被替换，而你的 API 调用对这一切毫无感知。

业界已经踩过坑：某家把默认别名指向更省算力的新版本，大量应用的长文本总结质量一夜之间下滑，官方直到社区炸锅才承认。你如果只信滚动别名，就是把命门交给了别人的发布节奏。

第二类是推理栈变化。量化精度、KV cache 策略、批处理调度的任何一次调整，都会让相同输入产生不同的 token 分布。模型权重"没变"，但你实际拿到的输出，已经不是同一个东西了。

第三类是输入漂移。用户提问的话题、平均长度、语言构成随时间悄悄偏移——模型和 prompt 都没动，只是题变难了。你若把它误判成模型退化去猛改 prompt，往往只会越改越糟。

第四类最隐蔽：RAG 场景里 context 变了。知识库更新、切分策略调整、检索排序微调，都会让模型"看到的东西"不同，输出自然跟着漂。四类混在一起排查，你会一直抓错凶手，白费力气。

## 线上指标为什么发现不了

很多人以为盯着线上的满意度、点赞率就够了。问题是这些指标滞后严重、噪声极大，还被流量结构裹挟——等它明显掉下来，用户早就用脚投票走了，你读到的只是一份迟到的验尸报告。

更麻烦的是幸存者偏差。用户几乎不会给差答案点踩，他们只会默默关掉页面。于是你的 dashboard 一片绿，实际转化率却在悄悄流血。想早一步发现，你必须有一组不受线上流量影响的固定探针。

关键词是"固定"。线上样本每天都在变，你无法区分到底是模型退化还是流量变了。只有一组内容、顺序、数量全部锁死的题集，才能把模型这个变量单独拎出来，放到显微镜下观察。

## 搭一个 canary 漂移哨兵

做法其实很朴素：锁定一组 30-50 条覆盖核心场景的 golden 样本，每天定时跑一遍，记录每条的分数和原始输出，再和历史基线比对。关键在于——分数和输出内容要同时监控，缺一不可。

```python
import numpy as np
from scipy import stats

def drift_check(baseline_scores, today_scores,
                baseline_texts, today_texts):
    # 1) 分数分布是否偏移：Mann-Whitney U 非参检验
    _, p = stats.mannwhitneyu(baseline_scores, today_scores,
                              alternative="two-sided")
    score_drift = p < 0.05 and \
        np.mean(today_scores) < np.mean(baseline_scores)

    # 2) 输出内容是否变化：逐条 embedding 余弦相似度
    sims = [cosine(embed(a), embed(b))
            for a, b in zip(baseline_texts, today_texts)]
    text_drift = np.mean(sims) < 0.85

    return {"score_drift": score_drift, "text_drift": text_drift,
            "p_value": round(p, 4), "mean_sim": round(np.mean(sims), 3)}
```

分数掉但相似度稳，多半是评分器噪声；相似度掉但分数稳，可能是换了模型而质量没退，标记待观察；两者同时报警，才是真漂移，该立刻拉人排查、准备回滚或切换到备用模型。

为什么非要盯输出相似度？因为分数是一种有损压缩，同一个 4 分可能对应无数种答案。当模型被静默替换、风格大变却恰好没掉分时，只有 embedding 相似度能替你把这次"换脸"当场抓现行。

## 基线不是随便跑一遍就算

基线的质量，直接决定哨兵的下限。千万别拿单次运行结果当基线——那一次本身就裹着随机噪声。正确做法是在模型确认稳定的窗口里连续跑 5 到 7 天，取分数和输出的聚合，作为后续所有比对的锚点。

样本选择也大有讲究。这 30 条不该是随手挑的高频问题，而要按真实流量的场景分布抽样：核心任务占大头，同时塞进几条边界样例和已知的易错题。哨兵的敏感度，取决于你的题集到底覆盖了多少种真实失败模式。

还有个常被忽略的点：基线必须随重大迭代主动重置。你自己升级了 prompt 或换了检索策略，旧基线立刻失效，继续硬比只会收获一屏无意义的红色。重置时记得把旧基线留档，方便日后追溯每一代的边界在哪。

## 阈值不是拍脑袋定的

别用"分数掉 X 分就报警"这种绝对阈值——小样本天然抖动，你很快会被误报淹没到干脆忽略所有告警。正确做法是用 Mann-Whitney 这类非参检验判断分布是否真的偏移，再用输出相似度交叉验证。

| 现象 | 分数变化 | 输出相似度 | 结论 |
|------|---------|-----------|------|
| 评分抖动 | 小幅下降 | ≥0.9 | 噪声，忽略 |
| 静默换模 | 基本稳定 | <0.85 | 待观察，打标 |
| 真实退化 | 显著下降 | <0.85 | 报警，回滚/切模型 |
| 输入漂移 | 下降 | 基线自身在变 | 查数据分布 |

这张表的价值，在于把"分数"和"相似度"当成两个正交信号。单看任何一个都容易误判，交叉起来才能精准定位：到底是模型退化、供应商静默换模，还是你自己的题库和输入分布在悄悄改变。

## 让哨兵真正跑起来

哨兵不是写完 `drift_check` 就完事，它得像 CI 一样常驻。我一般挂个每日 cron，跑完把结果写进时序库，连续三天异常才升级为人工介入，避免单日的正常抖动就惊动一整个群。

存档是另一条命根子。每次运行都要把原始输出、分数、当次的模型版本号和调用时间戳一起落盘。等哪天真出事，你回溯的不是模糊印象，而是一条可以逐条 diff 的证据链，甩锅和自证都靠它。

告警分级也别偷懒。普通分数漂移进日常频道，"疑似静默换模"这种高危信号直接 @ 负责人——不同严重度走不同通道，人才不会因为天天被打扰而对告警彻底脱敏。

成本这条线同样要盯。哨兵每天固定消耗，单看不多，可一旦探针集膨胀到几百条、又接了昂贵的 judge 模型来打分，月底账单能让你肉疼。宁可题集精而少，也别贪多，把哨兵自己跑成了成本黑洞。

## 踩坑清单

- golden set 一旦定下就别频繁改，改一次基线就废一次，漂移信号也跟着断档
- 别只存分数，一定把模型原始输出一并存下，事后复盘和定位全靠它
- 固定 temperature 和 seed，否则模型自身的随机性会淹没真实的漂移信号
- 供应商给了带日期的版本别名（如 `-2024-08-06`）就锁死，别用滚动别名
- 30 条以下的探针集，统计检验基本没意义，样本量是不可谈判的底线

说到底，评估从来不是上线前跑一次就交差的仪式，而是要一直挂在生产线上的传感器。模型会变、供应商会变、你的用户也会变，唯一不变的，是你需要一双始终睁着的眼睛。

模型漂移真正可怕的地方，不在于它会发生，而在于它发生时一切看起来都很正常。接口是绿的，返回是 200 的，只有答案在悄悄烂掉。哨兵的全部价值，就是在你被用户投诉告知之前，先你自己一步开口报警。
