你有没有遇到过这种情况：Agent 调了一个工具，返回了五万行日志，整个上下文瞬间被撑爆，后面几步全乱套。工具能跑通，不代表 Agent 能用好。真正让 Agent 翻车的坑，往往不在工具本身，而藏在它吐回来的那一大坨返回值里。今天就把这个最容易被忽视的环节讲透。

## 为什么工具输出是隐形杀手

prompt 是你能一个字一个字打磨的，工具输出却是运行时才知道内容的——你只能预设规则，没法预审每一次返回。一次搜索可能吐二十条带全文的结果，一次文件读取可能拿回整个 config，一次 API 调用可能返回几百 KB 的嵌套 JSON。这些体积都不是你写死的，是环境给的。

更麻烦的是，模型对工具输出有一种天然信任。它把返回值当成"事实"，会认真读、认真用。所以一坨脏数据的杀伤力，比一段脏 prompt 大得多：模型不会怀疑它，只会被它带着跑。当输出体积逼近 context 上限，前面辛苦铺垫的任务目标还会被直接挤出窗口，Agent 就此失忆，忘了自己本来要干嘛。你以为它变笨了，其实是被一坨返回值噎住了。

## 三种典型的坏输出

不是所有大输出都一个病因。先分清类型，才知道用哪一招对症下药。

| 类型 | 典型场景 | 主要伤害 |
| --- | --- | --- |
| 太大 | 全表导出、完整网页 HTML | 直接撑爆 context，挤掉任务目标 |
| 太乱 | 深层嵌套 JSON、二进制混文本 | 结构噪声高，模型抓不住重点 |
| 太长 | 重复日志、分页拼接结果 | token 被冗余吃光，性价比极低 |

多数真实故障是三者叠加：一个又大又乱又长的 API 响应，恰好在多步任务的中段砸下来。所以别指望一招通吃，下面四招要按情况组合使用。

## 处理策略一：先量后裁

核心思路一句话——工具层先做预算，别把原始结果直接甩给模型。给每个工具设一个输出上限，超了就走截断或摘要分支。上限不必一刀切：核心工具给宽一点，辅助工具给窄一点，按它对当前任务的价值分级。最简单的截断是保留头尾、掐掉中间，因为开头和结尾通常信息量最高：

```python
def wrap_tool_output(raw: str, limit: int = 4000) -> str:
    if len(raw) <= limit:
        return raw
    head = raw[: limit // 2]
    tail = raw[-limit // 2:]
    omitted = len(raw) - limit
    return (f"{head}\n\n"
            f"...[已省略 {omitted} 字符，需完整结果请调用 fetch_full]...\n\n"
            f"{tail}")
```

关键在那句省略提示：既告诉模型这里被裁过，又留下一条"想要全量自己来取"的路。少了这句，Agent 会以为看到了全部，基于残缺信息继续往下推，错得还理直气壮。另外提醒一句，真正该卡的是 token 数而不是字符数，中文一个字往往顶一个多 token，估算时按经验乘个系数别踩线。

## 处理策略二：摘要与结构化

截断是钝刀，对日志和文档类输出，摘要更聪明。用一个便宜的小模型先把工具输出压成要点，再回喂给主模型，成本远低于让贵模型硬啃原文。这一步还能顺手过滤广告、导航栏、堆栈噪声，只留任务相关的骨架。

对 JSON，别整块塞进去——你的任务通常只需要几个字段，提取出来重新组装，噪声立刻降一个数量级。比如一个订单查询返回三十个字段，嵌套着物流、发票、优惠券一堆子对象，而你其实只关心 status 和 amount，那就只回这两个，剩下的一律扔掉。原始响应可能三千 token，裁完只剩三十，模型读得又快又准。记住一条铁律：摘要模型可以改写措辞，但金额、ID、状态码、时间戳这类关键数值必须原样透传，绝不允许它"顺手优化"，否则你会得到一个读起来很顺、数字全错的结果，而这种错最难查——因为它看起来对。

## 处理策略三：分页与引用

最优雅的做法是不一次给全，而是给"第一页 + 总量 + 下一页游标"，配一个 fetch_more 工具，让 Agent 想深挖时自己翻。这样上下文按需增长，而不是一口气爆满，模型也更像人——先看摘要，觉得不够再点开细节。对图片、二进制、超大文件这类根本不该进上下文的内容，存到引用地址，只回一个句柄，需要时再按 ID 取。

四招之间有个天然顺序：能不进上下文的就用引用挡在门外，必须进的先结构化只留有用字段，还太长就上摘要，摘要都压不住才用截断兜底。上线前对着这份清单过一遍：

- [ ] 每个工具都设了输出上限，超限有明确降级路径
- [ ] 截断保留头尾，并注明省略量与获取全量的方法
- [ ] 大 JSON 只回需要的字段，不做整块转储
- [ ] 日志、网页类先摘要再回喂，别让主模型硬读原文
- [ ] 分页返回带游标，配 fetch_more 让 Agent 按需深挖
- [ ] 二进制、图片存引用地址，只回句柄不回内容

## 踩坑清单

别在截断时切断 JSON 结构——半个 JSON 比省略更糟，模型会试图解析然后彻底跑偏，这类输出要么整体摘要，要么按字段裁。摘要模型也会漏信息，关键数值务必绕过它原样传递。省略提示要写得显眼，否则 Agent 把残缺当完整，一路错到底。分页游标要真能翻下去，别给了 next_cursor 却没实现 fetch_more，那等于挖坑给自己跳。还有个反直觉的坑：不要过度处理。有些输出本来就短，你非要套一层摘要，既多花一次模型调用，又可能把本来清楚的信息压糊——处理策略是给大输出准备的保险，不是每次都得上的流程。最后一句话记牢：工具的返回值不是给人看的日志，是喂给模型的燃料，燃料脏了，再强的引擎也带不动。
