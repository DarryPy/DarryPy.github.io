## 为什么"看起来对"最危险

你给 RAG 接上向量库，答案读起来通顺、专业、有理有据，于是放心上线。真正的坑在这里：检索确实命中了相关文档，模型却把里面三个事实揉成一个自己脑补的结论。用户看到流畅的中文，默认它是对的，没人回去翻原文。这种"半真半假"比彻底胡说更危险，因为它骗过了一切靠直觉的抽查，等到有人较真时，信任已经塌了一半。

引用溯源要解决的，就是让每一句结论都能被点开、追到那一段原文，把信任建立在证据上，而不是文风上。它还有个被低估的价值：一旦答案挂上出处，你就有了可量化的评测抓手——命中率、引用正确率、grounding 通过率都能拉成看板。没有溯源的 RAG，出了错你只能凭感觉调 prompt；有了溯源，每一次退步都能定位到是检索错了还是生成飘了。

但要先说清一个前提：溯源不是遮羞布。如果检索本身把不相关的片段捞了上来，模型再老实地引用，也只是给错误答案盖了个"有出处"的章。溯源和检索质量是乘法关系，不是加法——它放大好检索的可信度，也会忠实地暴露烂检索的窘迫。所以别指望靠一层引用救回一个召回率很差的向量库，该调的 chunking、reranker、混合检索一样都不能少，溯源是收尾，不是开头。

## 三种溯源粒度：文档 / chunk / span

溯源不是"贴个链接"这么简单，粒度直接决定可信度与成本。文档级只告诉你"答案大概来自这篇"，用户还得在几千字里自己找；chunk 级定位到检索返回的那一小段，是性价比最高的默认选项；span 级精确到原文的某几个字，体验最好但实现也最重。我的经验是先把 chunk 级链路跑通，等用户开始追问"这句到底哪来的"，再对关键结论上 span 级高亮。

| 粒度 | 定位精度 | 实现成本 | 适用场景 |
|------|---------|---------|---------|
| 文档级 | 整篇 | 极低 | 内部知识库、来源很少 |
| chunk 级 | 检索片段 | 低 | 大多数生产 RAG 的默认 |
| span 级 | 原文字词 | 高 | 合规、医疗、法律问答 |

要注意，粒度不是索引完才决定的，它得从切片阶段就埋点。每个 chunk 落库时都要带齐 doc_id、标题、原文起止偏移量和可访问的链接，检索、重排、生成到前端渲染全程携带这套元数据。很多人栽在中途重排后编号错位，或者只存了文本、渲染时再回原文 find 定位，结果原文改一个字高亮就漂到别处。把偏移量当第一公民存下来，后面所有精度都建立在它之上。

## 让模型自己带引用

最省事的做法是让模型在生成时就标注来源：给每个 chunk 编号，要求输出里每条结论都挂上它引用的编号。关键是用结构化输出把格式锁死，而不是靠自然语言里一句"请注明出处"去祈祷模型听话。把引用做成数据字段，前端渲染成可点击角标就顺理成章，也方便下一步做机器校验。

```python
from pydantic import BaseModel

class Claim(BaseModel):
    text: str              # 一句结论
    source_ids: list[int]  # 引用的 chunk 编号，不能为空

class Answer(BaseModel):
    claims: list[Claim]

# 把检索片段编号后拼进 prompt
context = "\n".join(f"[{i}] {c.text}" for i, c in enumerate(chunks))
prompt = f"""只依据下列片段回答，每条结论必须给出 source_ids。
找不到依据就不要写这条结论。
片段：
{context}
问题：{query}"""

answer = llm.parse(prompt, schema=Answer)  # 强制结构化，缺 source_ids 直接重试
```

这套写法的前提，是 prompt 里明确"只能引用给定片段，找不到依据就说不知道"。别小看这句约束，它把模型从"尽力编一个交差"拉回到"没有就老实承认"，是降低幻觉最便宜的一步。给模型留出"我不知道"的出口，比任何花哨的 prompt 技巧都管用，因为逼它硬答每一题，正是引用漂移的最大来源。

实践里还有几个细节值得处理。一条结论常常横跨多个片段，source_ids 就该是个列表，别强行塞成单值；同一来源被反复引用要做去重，否则前端角标一串重复看着很脏；两个片段互相矛盾时，与其让模型偷偷选一个，不如让它把冲突显式摆出来，交给用户判断。把这些规则写进 schema 和 prompt，比事后用正则去修输出要稳得多。

但自报引用只是第一层，它本身也会撒谎。模型可能在结论后标了 [2]，语气笃定，可那句话在片段 2 里压根不存在。所以千万别把 source_ids 非空等同于结论可信——它只是让你有了一个可被独立核对的声明，而核对这件事，得交给下一道工序去做。

## 事后校验：给每句话打 grounding 分

这道独立校验的思路很直接：把答案拆成句子，逐句和它声称的来源做比对，判断是支持、无关还是矛盾。低于阈值的句子标灰或直接砍掉，宁可少说，也不让一句没根据的话混进最终答案。拆句时按结论粒度切，别把一整段丢进去比对，否则段内某一句的胡编会被其他真话稀释掉，整段侥幸过关。

| 校验方式 | 原理 | 成本 | 抗漂移能力 |
|---------|------|------|-----------|
| 字符串包含 | 答案词在原文出现 | 几乎为零 | 弱，改写就失效 |
| Embedding 相似度 | 句向量与来源比对 | 低 | 中，易被同义句骗过 |
| NLI 蕴含判断 | 小模型判 entailment | 中 | 强，能识别矛盾 |
| LLM-as-judge | 大模型逐句打分 | 高 | 最强，但慢又贵 |

务实的组合是：主链路用 NLI 小模型跑逐句校验，只对最终结论句做、跳过过渡句，把成本压到可接受；对合规要求高的场景再叠一层 LLM-as-judge 兜底。这层校验拦得下大部分引用漂移，代价只是每句多一次轻量推理，还能顺手产出一个 grounding 分，长期喂给评测看板。

阈值别一刀切。金融、医疗这类错一句就出事的场景，该把门槛调高、宁可多拦；闲聊式问答容忍度高，卡太死反而满屏"未找到支撑"，体验崩了。更稳的做法是按业务风险给结论分级，高风险句走严校验加人工兜底，低风险句放宽通过。阈值本身也要拿一批标注数据去校准，别拍脑袋定一个 0.8 就上线，跑几轮混淆矩阵你才知道它到底在拦什么。

校验之后别忘了前端呈现。角标要能点开定位到原文那一段甚至那几个字，让用户一眼看清依据；被判 neutral 或 contradiction 的句子要么隐藏要么显式标注"未找到支撑"。用户对 RAG 的信任，不是来自答案多漂亮，而是来自他随手一点就能验证——可验证性本身，就是最强的说服力。

## 落地清单与踩坑

先记住一件事：能溯源的答案，比多命中一个 chunk 值钱得多。下面是我踩过坑后留下的清单。

- chunk 编号与偏移量要贯穿"检索→重排→生成→渲染"全程，中途重排就会张冠李戴。
- 强制 source_ids 非空，缺引用的结论一律当作幻觉丢弃，别心软保留。
- 校验放在句子级而非整段级，整段过关会掩盖段内某一句的胡编。
- span 高亮用原文偏移量存储，别存文本再回去 find，改一个字就错位。
- 给"我不知道"留出口，逼模型硬答每题，才是引用漂移的最大来源。
- 把引用正确率、grounding 通过率做成看板，退步时才分得清是检索还是生成的锅。
