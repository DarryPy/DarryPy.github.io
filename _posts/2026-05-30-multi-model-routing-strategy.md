你的应用不会只用一个模型，这几乎是确定的。

随着 LLM 市场的成熟，同类任务往往有多个可选方案：Opus 4 贵但推理强，Haiku 速度快且便宜，GPT-4o 对某些结构化输出的格式遵循更稳定。如果把所有请求一刀切打到同一个模型，你实际上是在两个极端里选一个：要么为简单任务花冤枉钱，要么在复杂任务上因模型能力不足导致质量劣化。两种情况都在悄悄侵蚀你的产品体验或利润空间。

多模型路由（Multi-model Routing）的目标就是在同一个调用链里，根据请求特征动态挑出"当前最合适"的模型，而不是靠硬编码某一个。这听起来像个小优化，但在请求量上来之后，它是能直接影响成本结构和用户体验的基础设施决策。

## 三条路由维度

### 按成本路由

最直接的入口。核心逻辑是先对任务复杂度做分级，再按级别分流：

- 简单问答、关键词提取、分类、摘要 → 便宜模型（Claude Haiku / GPT-4o Mini）
- 多轮推理、代码生成、长文档深度分析 → 旗舰模型（Claude Opus / GPT-4o）

判断"复杂度"不需要神经网络，一套规则就够用：prompt token 数超过某个阈值（比如 800 token）、消息里包含特定触发词（"write a complete implementation…"、"analyze the entire document…"）、或者前置一个极轻量的分类 prompt 给当前请求打出高/低复杂度标签。这套规则维护成本低，行为完全可预期，是绝大多数团队的第一个路由方案。

需要注意的是，成本路由的关键不是"选哪个模型"，而是分类决策的准确率。分错了类，复杂任务走了便宜模型，表面上省了钱，实际上在质量差异上损失的用户留存远比 token 费用贵得多。初期建议在分类结果上做抽样人工校验，跑两周之后再根据实际准确率收紧或放宽阈值。

### 按延迟路由

实时对话场景对延迟极其敏感，但批量离线任务根本不在意。把这两类请求送到同一个模型是资源浪费——延迟敏感的场景被拖慢，而批量任务在"快模型"上支付了不必要的溢价。

具体做法是维护每个模型最近 5 分钟的 P95 延迟滑动窗口，当主力模型延迟超过请求方声明的预算时自动降级：

```python
def pick_model(task: str, budget_ms: int) -> str:
    candidates = [
        ("claude-opus-4-7",  p95_window["claude-opus-4-7"]),
        ("claude-haiku-4-5", p95_window["claude-haiku-4-5"]),
    ]
    # 优先选满足延迟预算的最高能力模型
    for model, p95 in sorted(candidates, key=lambda x: -capability_score[x[0]]):
        if p95 <= budget_ms:
            return model
    # 全都超预算时退回最快的
    return min(candidates, key=lambda x: x[1])[0]
```

注意窗口不能太短：30 秒的 P95 在低流量时样本太少，容易产生噪点跳变。5 分钟滑动窗口更稳，如果流量本身有周期性波动（比如整点高峰），可以再加一层带权衰减，让近期数据权重更高。

### 按能力路由

某些模型在特定任务类型上有系统性优势，不做区分统一路由是在浪费这种优势。可以把任务类型和模型的匹配关系显式维护成路由规则：

| 任务类型 | 推荐模型 | 原因 |
|---------|---------|------|
| 长文档摘要 / 全文分析 | Claude Sonnet 4.6 | 200K context，结构感强 |
| 结构化 JSON / function calling | GPT-4o | 格式遵循稳定性高 |
| 实时代码补全 | Claude Haiku 4.5 | 速度快，token 消耗低 |
| 多语言翻译（小语种） | Gemini 1.5 Pro | 语种覆盖广 |
| 复杂数学 / 多步逻辑推理 | Claude Opus 4.7 | 推理链更可靠 |

这张表不是一次性配置，而是随实验数据持续更新的产物。建议每两周对不同模型在同类任务上的质量评分做一次横向对比，把落后的映射关系替换掉。维护这张表的人不应该靠直觉，应该靠数据。

## 三种实现方案的取舍

**规则路由（if/else）**：零额外延迟，行为完全可预期，上手成本最低。缺点是规则膨胀后维护负担显著上升，特别是当多条规则之间出现优先级冲突，或者新任务类型不断加入时，条件分支会变成一块很难读懂的泥。适合启动期和任务类型相对固定的场景。

**元模型路由**：用一个轻量 LLM 或 embedding 分类器来决定"这条请求该给谁处理"。精准度比规则路由高，可以处理更模糊的任务边界，且可以从历史效果数据中持续微调分类阈值。代价是多了一次 API 调用，引入了额外延迟与成本，并且元模型本身也需要维护和监控。适合任务类型多样、规则路由已经撑不住的中大型系统。

**LLM Gateway 中间层**：LiteLLM、OpenRouter、Portkey 这类工具自带路由、fallback、负载均衡能力，统一管理多个 provider 的密钥和配额，出错时可以自动切换备选 provider。代价是多了一层需要运维的基础设施，排查问题时链路更长。适合已经有多 provider 管理需求、或者团队没有精力自研路由层的场景。

不要一上来就把三层都搭上。规则路由起步，Gateway 做统一管理，元模型路由按需引入，这是比较合理的演进路径。

## 熔断和 Fallback 必须提前设计

路由系统最常见的遗漏是异常路径。某个 provider 偶发 5xx 或突发限流，如果路由器没有熔断逻辑，全量请求会积压超时，比直接报错更难排查，也更难向用户解释。

基本的熔断 + fallback 模式如下：

```python
from tenacity import retry, stop_after_attempt, wait_exponential

@retry(stop=stop_after_attempt(2), wait=wait_exponential(multiplier=1, max=4))
def call_with_fallback(prompt: str, primary: str, fallback: str) -> str:
    try:
        return call_model(primary, prompt)
    except (RateLimitError, ServiceUnavailableError):
        circuit_breaker[primary].record_failure()
        if circuit_breaker[primary].is_open():
            return call_model(fallback, prompt)
        raise
```

熔断状态的半开（half-open）恢复窗口建议设为 60 秒，不要设太长。否则主力模型恢复后，路由器还在持续走备份，成本上涨且用户拿不到最优质量，这种问题很难从日志里直接看出来。

## 路由层的可观测性设计

路由系统是"中间件"，很容易成为黑盒。一旦黑盒，任何指标异常你都不知道是路由层的问题还是模型本身的问题。

推荐在路由层至少记录以下数据，作为独立的路由事件 log 上报：请求特征摘要（任务类型标签、预估 token 数、调用方声明的延迟预算）、最终选出的模型名称、选择原因（命中哪条规则还是元模型分类结果）、实际调用延迟与状态码、是否触发了 fallback 以及原因。

这些数据接进监控看板之后，你可以直接看到"今天有多少比例的请求走了降级路径"、"哪个任务类型的模型命中率在下滑"、"成本在不同模型之间的实际分布"。没有这个看板，路由系统就是一个你信任却无法验证的黑盒。

## 踩坑清单

- **切模型忘记同步 prompt 模板**：不同模型对 system prompt 格式的敏感度不同，切换后输出格式可能悄悄漂移；路由层必须维护每个模型对应的 prompt 适配版本，而不是共用同一套
- **成本对比用名义 token 价**：同一段文本在不同模型的 token 计数差异可达 15–25%（tokenizer 实现不同），用文档标价算出来的"节省比例"是失真的，要用实际账单数据校准
- **测试时 mock 掉了路由层**：生产出问题，测试全绿——集成测试必须跑真实路由路径，至少要覆盖主路径和一个 fallback 路径
- **路由决策没有可观测性**：每次路由的结果必须记 log，带上请求特征、选出的模型、选择原因，否则线上出问题时是纯盲盒
- **忘记给 fallback 模型做容量规划**：主力模型熔断后，全量流量打向 fallback，如果 fallback 本来就在高负载运行，会触发连锁熔断——流量迁移时的容量峰值要提前算好
