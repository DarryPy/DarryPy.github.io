你改了一行 system prompt，本地跑两条 case 觉得没问题，直接合并上线，第二天客服群炸了——某个老功能的输出格式全变了。这不怪你粗心，是流程缺了一环：没人在合并前替你把旧 case 再跑一遍。LLM 应用最坑的地方在于，改 A 处经常悄悄弄坏 B 处，而你肉眼根本看不出来。传统代码有编译器和单测兜底，Prompt 却是一段自然语言，改动的副作用飘忽不定。把 Eval 接进 CI，就是给 Prompt 上一道自动回归闸，让机器替你守住那些你顾不上的角落。

## 为什么手动跑 Eval 撑不住

手动 Eval 有三个死穴。一是不可复现：你今天顺手挑的 case 和上周不一样，分数根本没法横向对比，涨了跌了都说不清。二是懒惰偏差：赶着上线时你只会跑"我觉得会过"的 case，真正危险的边界 case 被无意识跳过。三是不留痕：出了问题没人知道是哪次改动引入的，只能靠 git blame 硬猜半天。

更要命的是规模。功能越做越多，需要回归的 case 从十条涨到几百条，靠人跑既不现实也不可靠。人会累会烦会走捷径，机器不会。一次静默的回归可能几周都没人发现，等用户投诉堆到一定量才暴露，那时候排查成本已经翻了几倍。CI 的价值不是更聪明，而是每次都跑同一批、全跑、留记录，把人性里那点偷懒空间彻底堵死。你要的不是一个天才 reviewer，而是一个永不请假、永不手软的哨兵，每次 PR 都替你把旧账重算一遍。

## 最小可用的 CI Eval 长啥样

别一上来就想着接 LangSmith 或 Braintrust，工具选型会拖慢你启动的速度。一个 JSON 数据集加一段 pytest 就能先跑起来，核心逻辑只有三件事：喂输入、拿输出、按规则打分。数据集就是一个数组，每条 case 带上 id、输入、必含关键词和禁词，改起来跟改配置一样轻，非工程同学也能提 PR 加 case。

```python
import json, pytest
from myapp import run_prompt

cases = json.load(open("evals/regression.json"))

@pytest.mark.parametrize("c", cases, ids=lambda c: c["id"])
def test_regression(c):
    out = run_prompt(c["input"], temperature=0)
    for kw in c["must_include"]:
        assert kw in out, f"缺关键词: {kw}"
    for kw in c.get("must_not", []):
        assert kw not in out, f"泄露禁词: {kw}"
```

把它挂进 GitHub Actions 的 pull_request 触发，每次改动 Prompt 就自动全跑。跑失败直接标红 PR，谁都别想蒙混过关合进 main。为了不让每次 CI 都烧一大笔 token，可以只在改动了 prompt 或 evals 目录时才触发，用 paths 过滤一下就行。整套东西不到五十行，一个下午就能落地。等 case 涨到几百条、需要看趋势和分维度报表时，再迁到专业工具也不迟——先跑起来，永远比先选对工具重要得多。

顺手做两件事能让它跑得更省更快。一是对确定性输出加缓存，输入没变就直接复用上次结果，省下大把 API 调用。二是把这套 Eval 拆成两档：PR 上只跑核心的快集，几十条秒级出结果；每晚定时跑一次全量慢集，覆盖那些昂贵的语义评分。快集守住合并速度，慢集守住覆盖广度，两者分工，谁也不拖谁的后腿。

## 哪些 case 值得进回归集

回归集不是越大越好，塞一堆简单 case 只会刷出虚高的 pass rate，还拖慢每次 CI。真正该进集的是三类。第一类是踩过的坑：每修一个线上 bug，就把它固化成一条 case，保证同样的错不再犯第二次，这是回归集里最值钱的部分，等于把每次事故都变成一份免疫。第二类是核心链路：那些一坏就有人投诉的高频意图，必须每次都验，它们是产品的命脉，容不得半点回退。

第三类是安全边界：越权请求、注入尝试、禁词泄露、诱导输出隐私，这些低频但致命的 case 是你睡得着觉的底线，也是"评估与安全"真正交汇的地方。别指望模型天生守规矩，你得把红线写成可执行的断言钉死。维护上还有个铁律——case 只增不删，除非需求真的下线了某功能。删 case 图一时清爽，等于亲手拆掉自己之前立的防线，用不了多久就会在同一个坑里再摔一次。

## 评分函数怎么设计才不脆

硬匹配关键词最省钱但也最脆：模型换个说法就误报一片，你会被假警报淹没到最后干脆无视，那时回归集就废了。分层设计才稳。第一层用规则查硬约束——JSON 能不能解析、必带字段在不在、禁词有没有漏出去，这些确定性强、非黑即白，必须 100% 通过，一条都不能松。这层几乎零成本，却能拦住绝大多数格式崩坏和安全事故。

第二层才上语义，用 embedding 相似度或 LLM-as-Judge 评"意思对不对"，阈值给宽松些，容忍合理的措辞差异。别用一把尺子量所有维度，格式错误和语气偏差是两回事，混在一起只会让报警失去意义。成本上也要精打细算：能用规则判的就别调模型，LLM-as-Judge 只留给那些规则真判不了的主观维度，且尽量用便宜的小模型当裁判，否则你会发现 Eval 的账单反手就超过了线上推理，得不偿失。

举个具体的例子：一条"查订单状态"的 case，第一层先断言返回是合法 JSON、带 order_id 字段、不含任何手机号明文；这层过了，第二层才让裁判模型判断回复语气是否礼貌、有没有答非所问。前者是不容商量的硬红线，后者是可以打分数的软指标。把两者分开写，报表上一眼就能看出到底是功能坏了还是体验滑了，排查方向立马清晰。

## 阈值、样本与 flaky 治理

LLM 输出天生带随机性，同一条 case 可能这次过下次挂，这就是 flaky。放着不管，团队很快就会习惯性无视红灯，回归闸形同虚设，比没有还糟——因为它给了你一种虚假的安全感。用下面这套配置把抖动压住。

| 问题 | 错误做法 | 稳的做法 |
|---|---|---|
| 抖动 | 单次跑就判定 | 同 case 跑 3 次取多数 |
| 阈值 | 要求 100% 通过 | 整体 pass rate ≥ 95% 放行 |
| 温度 | 用线上 temperature | Eval 固定 temperature=0 |
| 样本 | 5 条充数 | 各意图覆盖 30-50 条 |

固定 temperature=0 能砍掉大半随机性；剩下的用多数表决兜底，跑三次里过两次就算过。样本别贪多，但要贴着真实意图分布来，而不是全塞好过的简单题刷分。阈值也别硬编码在断言里，写进配置文件，方便随业务成熟度往上收紧。

还有一点容易被忽略：持续 flaky 的 case 本身就是信号。如果某条 case 反复横跳、怎么都稳不下来，往往说明你的 Prompt 在这个场景下压根就不稳健，用户实际体验也在同样地飘。这时候别急着给它调宽阈值糊弄过去，而是回头去修 Prompt。Eval 的红灯不只是拦门，它还在替你指出产品真正脆弱的地方。上线前对着下面这份清单再过一遍：

- 数据集进 Git 版本管理，case 改了能 diff 出来，谁动的一目了然
- 每条 case 带唯一 id，失败时一眼定位，别靠数组下标猜
- 禁词与 PII 检查放第一层，硬失败直接挡，绝不进语义评分
- CI 里锁死 temperature=0 和 model 版本，别让"模型悄悄升级"污染回归基线
- pass rate 阈值写进配置，跟着业务迭代慢慢收紧，别一步到位卡死自己

一句话：没有 CI 里的回归 Eval，你每次改 Prompt 都是闭着眼睛裸奔上线，出事只是时间问题。
