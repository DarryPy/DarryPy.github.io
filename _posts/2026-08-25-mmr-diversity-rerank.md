你把用户问题丢进向量库，top-k 取回 8 个 chunk，满怀信心塞给 LLM，答案却漏了关键信息。翻一眼检索结果就懂了：8 个 chunk 里有 5 个在讲同一件事，只是措辞略有不同。相似度排序天然偏爱这种冗余，真正互补的那两段被挤到了第 9、第 10 名。

MMR 要治的就是这个病。它是一个几乎零成本的后处理步骤，不改召回、不训模型、不加一次网络请求，却常常是提升 answer 质量最划算的一刀。这篇讲清它为什么有效、怎么落地、参数怎么调，以及什么时候压根不该用它。

## 为什么 top-k 会喂给 LLM 一堆重复内容

纯相似度检索只回答一个问题：这个 chunk 和 query 有多像。它从不关心已选中的 chunk 之间像不像。于是一篇被切成多段的文档，只要主题贴近 query，就会整段整段霸占前排，把别的文档挤出局。

你拿到的 top-8 表面覆盖面广，实际信息熵很低。对需要多角度证据的问题——比较、多跳、综述——这是致命伤：上下文窗口被近义句填满，模型看不到本该出现的另一半事实，只能在半张拼图上硬答。

更糟的是这种冗余很隐蔽。检索 recall 指标看着漂亮，因为相关文档确实都召回了；可 answer 质量上不去，因为有效信息密度太低。你盯着检索指标反复调参，永远调不出问题的根，因为病灶不在召回率，在结果的分布。

举个具体场景：用户问"这款数据库的优点和缺点"。向量库里讲优点的段落写得多、写得像，top-6 全是优点，缺点一条没进。模型只能片面回答。MMR 会在选完两三段优点后，主动把和它们都不像的"缺点"段落顶上来。

## MMR 的核心：相关性减去冗余

MMR（Maximal Marginal Relevance）1998 年就被提出，思路朴素得让人惊讶：每次选下一个 chunk 时，既奖励它和 query 的相关性，又惩罚它和已选集合的相似度。用一行公式说清：

```
MMR = argmax [ λ · Sim(d, q) − (1−λ) · max Sim(d, d_selected) ]
```

λ 是那根天平。λ 越接近 1，越像纯相似度排序；λ 越接近 0，越只在乎"和已选的都不一样"。它不是一次性打分，而是贪心地一个一个挑：每选定一个，下一轮所有候选的冗余惩罚项都要重新计算一遍。

注意惩罚项取的是 max 而非平均——只要候选和已选集合里任意一个足够像，它就被压下去。这符合直觉：一段内容哪怕只和已选的某一段重复，它对上下文的边际贡献就已经很低了，不需要跟全体都像。

还有个关键前提：MMR 是 rerank，不是召回。它假设你已经有一批候选，要做的是在候选内部重排座次，把互补的顶上来，把重复的压下去。所以它永远不会凭空找到召回阶段漏掉的文档。

## 二十行代码实现一个 MMR reranker

不用装库，向量都在手上，逻辑本身就二十行。核心是复用召回阶段的 embedding，绝不重新编码：

```python
import numpy as np

def mmr(query_vec, doc_vecs, lambda_=0.6, top_k=6):
    def cos(a, b):
        return a @ b / (np.linalg.norm(a) * np.linalg.norm(b) + 1e-8)

    sim_q = np.array([cos(query_vec, d) for d in doc_vecs])
    selected, pool = [], list(range(len(doc_vecs)))

    while len(selected) < top_k and pool:
        best, best_score = None, -1e9
        for i in pool:
            redundancy = max(
                (cos(doc_vecs[i], doc_vecs[j]) for j in selected),
                default=0.0,
            )
            score = lambda_ * sim_q[i] - (1 - lambda_) * redundancy
            if score > best_score:
                best, best_score = i, score
        selected.append(best)
        pool.remove(best)
    return selected
```

第一轮 selected 为空，redundancy 取 0，MMR 退化成纯相似度，选出的第一个和普通 top-1 完全一致。从第二轮起冗余惩罚才开始生效，这正是它压制近义重复的地方，也说明 MMR 不会伤害最相关那条。

复杂度是 O(k·n) 次向量点积，n 是候选数、k 是最终取数。候选控制在几十条时快到可以忽略，别脑子一热对全库几十万条跑 MMR——那不是慢，是设计用错了地方。

还有个易忽略的坑：尺度一致性。如果 embedding 入库前做了 L2 归一化，cos 里那个除法可以省成纯点积；但要是召回用归一化向量、MMR 里又拿原始向量算，相似度尺度对不齐，λ 的语义立刻漂掉，你调出来的最优值换个 query 就失效。

## λ 怎么调，以及和 Reranker 的分工

λ 不是玄学，拿一批带标注的 query 做网格搜索，盯 answer recall 而非检索 recall。不同任务的最优值差得很远，下面是一份可以直接抄的起点：

| λ 取值 | 偏向 | 适用场景 |
|--------|------|----------|
| 0.9~1.0 | 几乎纯相关性 | 事实型单点问答 |
| 0.6~0.8 | 相关为主，抑制冗余 | 通用 RAG 默认档 |
| 0.3~0.5 | 强调多样性 | 综述、多跳、对比类 |
| 0.0~0.2 | 几乎只看多样性 | 探索性检索、去重 |

多数生产系统从 0.6~0.7 起步就够用，再按业务问题类型微调。如果你的 query 分布很杂，与其纠结一个全局 λ，不如按 query 意图路由到不同 λ，甚至只对判定为"比较/综述"类的问题才启用 MMR。

别把 MMR 和 cross-encoder reranker 搞混。Reranker 提升的是单条相关性的判断精度，MMR 优化的是集合层面的多样性，两者正交、互不替代。理想管线是：向量召回 top-50 → reranker 精排相关性 → MMR 在精排结果上去冗 → 取 top-6 进上下文。

顺序别反。先 reranker 再 MMR，是因为 MMR 的相关性项应该建立在更准的分数上；要是先 MMR 再 reranker，多样性可能被 reranker 的重排重新打散，前一步白做。

## 边界、评测与踩坑清单

不是所有场景都该开。当每个候选本就来自不同文档、天然低冗余时，MMR 几乎不产生变化，白搭一层计算。精确事实问答（"某函数的默认参数是多少"）也不需要多样性，你要的就是最相关那一条，λ 调到 0.95 以上等于把 MMR 关掉。

MMR 只认语义冗余，认不出事实冲突。两段观点相反、措辞却相近的内容，在它眼里是"重复"，可能被误删一段。真正需要仲裁矛盾时，得靠 reranker 的细粒度打分或生成阶段的显式对比，MMR 帮不上忙。

候选太少也是禁区。召回只给回 5 条、你却要取 6 条，MMR 无从取舍，纯属空转。要让它有发挥空间，召回候选数必须显著大于最终 top_k，一般给到三到五倍，才谈得上"挑"。

上线前务必做一次对照评测。MMR 改的是塞进上下文的内容分布，影响直接体现在生成质量上，绝不能凭"看着更多样了"就上线。先攒一份评测集，重点覆盖比较、综述、多跳这类真正吃多样性的问题，再掺一批事实型单答问题当护栏。

对照只跑一个变量：其余管线不动，仅切换 MMR 开关，比较 answer recall 和 faithfulness。你想看到的是多样性敏感问题涨、事实型问题不掉。如果事实型明显回退，多半是 λ 压太低把最相关那条挤走了，往上调即可。

顺带留意一个隐性收益：结果更多样后，引用溯源往往更干净。因为进上下文的每个 chunk 承担不同信息，模型引用时更容易一句话对应一个来源，而不是在五段近义内容里随机挑一个标注，溯源可信度跟着上来。

最后，一份可以直接对照的踩坑清单：

- MMR 是 rerank 阶段的活，先用向量库召回 top-30~50 候选，再在候选内跑，别对全库暴力算。
- 文档向量务必复用召回时的 embedding，重新编码等于白烧一遍算力，还可能和召回用不同模型对不齐。
- chunk 粒度太大时 MMR 收益骤降——两个长 chunk 几乎必然重叠，先修 chunking 再上 MMR。
- MMR 只去语义冗余，去不了事实冲突；矛盾内容的仲裁交给 reranker 或生成阶段处理。
- 别用检索 recall 评估 MMR，它天生会牺牲一点召回换多样性，只有 answer 质量才说明真相。
- λ 硬编码是长期隐患，把它做成可配置甚至按 query 类型动态取值，别等业务变了再翻代码。

一句话收尾：相似度告诉你哪些 chunk 像答案，MMR 才告诉你哪几个 chunk 放一起才是完整答案。
