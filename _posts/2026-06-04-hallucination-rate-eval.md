你第一次把 LLM 接入生产环境，用户投诉的第一条几乎不会是"回答太慢"，而是"它说了一个根本不存在的功能"。这就是幻觉（hallucination）——模型用自信的语气生成了错误的内容。幻觉不是玄学，而是可以量化、可以治理的工程问题。本文的目标是帮你从零搭一套幻觉率评估 pipeline，并给出实际有效的压制手段。

## 幻觉的三种类型，你得先认清楚

很多团队把所有"模型说错了"都叫幻觉，但这样粗糙的归类会导致你用错处置方法，白费力气。在量化之前，先做好分类，事半功倍。

| 类型 | 定义 | 典型表现 | 优先处置方向 |
|------|------|----------|--------------|
| 事实性幻觉 | 生成了与现实不符的事实 | 张冠李戴、编造数据或日期 | Retrieval grounding |
| 引用伪造 | 引用了不存在的文献或来源 | 论文 DOI 不存在、URL 404 | 来源验证加截断 |
| 逻辑幻觉 | 前提正确但推导错误 | 数学步骤跳跃、条件判断反转 | CoT 加验证层 |

事实性幻觉出现频率最高，几乎所有场景都会遇到；引用伪造危害最大，因为用户会真的去查，查不到就对整个系统失去信任；逻辑幻觉最难自动检测，往往需要领域专家参与评审。三种类型要分开统计，混在一个单一"幻觉率"数字里，会完全掩盖真实的问题结构。

## 怎么量化：从手动标注到自动化 pipeline

量化幻觉的核心困难在于，没有参考答案就没有标准。现实的工程做法是"少量手标建黄金集，自动打分做日常监控，人工抽检兜底"。

### 先建黄金标注集

从生产日志里抽取 200 到 500 条代表性 query，要覆盖你的主要使用场景，冷门案例和高频问题都要有。每条由两名标注员独立判断是否存在幻觉并打分类标签，然后计算 Cohen's kappa 系数。如果 kappa 低于 0.6，说明你的分类定义还不够清晰，应当先开会对齐定义再继续标注，而不是强行往下走。

标注的时候记录下每条的幻觉类型、严重程度（轻微措辞偏差还是完全错误的核心事实）以及模型使用的 prompt 版本。这份黄金集后续每次模型升级或 prompt 改动都要重新跑一遍，不能一劳永逸。

### 自动化打分的工程方案

黄金集是基准，但没法扩展到日常所有流量。主流的自动化方案是 LLM-as-Judge，用一个独立的语言模型来判断另一个模型的输出是否包含幻觉。关键约束：检测时必须提供参考上下文，无参考的幻觉检测准确率会大幅下降，基本没有参考价值。

```python
import anthropic, json

client = anthropic.Anthropic()

JUDGE_PROMPT = """你是幻觉检测专家。根据【参考文档】，判断【模型回答】是否含幻觉。

【参考文档】
{context}

【用户问题】
{question}

【模型回答】
{answer}

以 JSON 返回：
{{"has_hallucination": true/false, "type": "factual|citation|logical|none",
  "confidence": 0.0-1.0, "evidence": "具体幻觉片段或'无'"}}
只返回 JSON。"""

def check_hallucination(context, question, answer):
    resp = client.messages.create(
        model="claude-opus-4-7",
        max_tokens=512,
        messages=[{"role": "user", "content": JUDGE_PROMPT.format(
            context=context, question=question, answer=answer)}]
    )
    return json.loads(resp.content[0].text)

def batch_eval(test_cases):
    results = [check_hallucination(c["context"], c["question"], c["answer"])
               for c in test_cases]
    total = len(results)
    hallucinated = sum(1 for r in results if r["has_hallucination"])
    by_type = {}
    for r in results:
        by_type[r["type"]] = by_type.get(r["type"], 0) + 1
    return {"rate": hallucinated / total, "by_type": by_type, "n": total}
```

这套方案的局限同样要认清：用 claude-opus 做幻觉 judge，实测 precision 约 85 到 90%，recall 约 75 到 80%。这意味着自动化数字只是趋势指标，不能替代定期人工抽检，建议每周随机抽 50 条对照标注结果核对偏差。

## 压制策略：对症下药

发现幻觉之后，不同类型对应不同打法，不能一刀切。

### 事实性幻觉用 Retrieval Grounding

把模型的事实依赖从参数记忆转移到可控的外部知识库。RAG 是目前最成熟的方案。很多团队接入 RAG 之后发现幻觉率反而没降，原因几乎都出在 chunk 质量和 retrieval 精度上。chunk 切割太粗，embedding 相似度召回的是无关段落，模型拿到噪音上下文，编造的理由反而更充分。解决办法是在接入 RAG 前先单独评测 retrieval 的召回质量，而不是把幻觉问题全甩给检索层。

### 引用伪造用截断加来源锁定

最有效的方法是在 system prompt 里明确要求"只引用我提供的文档，如无来源就直接说不知道"，并在后处理层用正则或 URL 验证扫描模型输出里的所有引用。不要指望模型自我克制，要在输出层做机械拦截。对于必须引用外部资料的场景，可以预先维护一份白名单，模型只能从白名单里选用来源。

### 逻辑幻觉用 Chain-of-Thought 加 Self-Consistency

让模型先写出完整的推导步骤再给结论，比直接要求输出答案的逻辑幻觉率低 30 到 40%。CoT 的实现非常简单，system prompt 里加一句"请先逐步分析，再给出最终结论"通常就够了。

对于高风险场景，比如财务计算或医疗建议，可以叠加 self-consistency：同一个问题独立运行三到五次，取多数一致的答案。代价是延迟和 token 成本增加，适合用在少量关键路径上，不适合全量覆盖。

### 最廉价的手段：控制 temperature

temperature 越高，模型创造性越强，幻觉率也越高。生产环境里处理事实问答类任务，temperature 设到 0 到 0.3 就足够了。很多团队为了让回答听起来更"自然"把 temperature 调到 0.7 甚至更高，这是在主动给幻觉开门。降 temperature 是成本为零、见效最快的降幻觉操作，没有理由不做。

## 监控：幻觉率是一条活的指标，不是一次性检测

上线不是终点。模型版本升级、prompt 修改、知识库内容更新，都可能让幻觉率在不知不觉间发生漂移。你需要把幻觉率做成持续监控指标，而不是上线前跑一次就收工。

建议接入以下三条监控信号：第一，每日幻觉抽检率，随机抽取 1 到 2% 的请求走自动 judge，输出分类分布和趋势图；第二，分 topic 或意图的幻觉分布，某类问题突然幻觉率升高，往往对应知识库里这个领域的内容覆盖出现了空洞或过时；第三，用户反馈信号，点踩、举报与幻觉的相关性，比任何自动检测都更贴近真实伤害，是最重要的反馈回路。

把这三条信号接入日常 dashboard，幻觉问题才真正进入可持续治理的状态。否则你只是在黑暗里碰运气。特别要注意的是，幻觉率的基线因场景差异很大：开放域知识问答的基线幻觉率往往在 15 到 30%，而有良好知识库支撑的垂直领域问答可以压到 3 到 8%。拿两个场景的幻觉率互相比较毫无意义，你只需要跟自己的历史基线比，看趋势是否在往好的方向走。

## 踩坑清单

- 不要用同一个模型既生成答案又做 judge，自评会严重低报幻觉率，因为模型倾向于为自己的输出辩护
- 黄金集必须每季度更新，否则模型微调后旧数据失效，你的基准数字就成了假账
- temperature=0 不等于零幻觉，只是概率更低，仍需要其他手段配合
- 模型用模糊措辞说"可能"或"大约"不代表没有幻觉，有时是用不确定性包裹了错误事实
- 引用验证不做就上线，等于给用户埋雷，第一个踩的人很可能是媒体或律师

幻觉治理没有银弹，但有系统方法：分类清晰、量化有据、分层压制、持续监控，一步不能省。

工程师容易犯的最大错误，是把幻觉当成"模型质量问题"甩给模型提供商，然后等下一个版本自动修好。实际上，同样的模型在不同的 prompt 设计、不同的检索质量、不同的 temperature 配置下，幻觉率可以相差好几倍。你能控制的变量比你想象的多，动手优化之前先把指标建起来，数字会告诉你下一步该往哪使劲。
