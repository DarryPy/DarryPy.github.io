你有没有遇到过这种情况：用户问「年假怎么请」，检索返回的 Top-5 里，有四条是同一份《员工手册》的不同版本，只是页眉日期不一样。LLM 拿到这堆几乎相同的段落，回答并没有变好，反而浪费了上下文，还把真正有用的第五条挤到了边缘。

这不是 embedding 的错，也不是 reranker 的错，而是知识库本身「脏」。我接手过的企业 RAG 项目里，原始语料的近重复率普遍在 20% 到 40% 之间。与其继续调模型参数，不如先把数据洗干净。今天聊的就是入库前后的去重：怎么找出近重复，以及找到之后怎么处理。

## 重复从哪里来，为什么伤检索

企业知识库的重复主要有四个来源：同一文档的多个历史版本、Wiki 页面被复制到不同空间、邮件和工单里层层引用的原文、以及 PDF 转换时页眉页脚被重复切进每个 chunk。前三种是文档级重复，最后一种是片段级噪声，处理手段不同。

重复对 RAG 的伤害有三层。第一，挤占 Top-K 名额，召回的多样性直接塌缩。第二，版本冲突，旧版本和新版本内容相似却结论不同，LLM 可能引用过期条款。第三，成本浪费，向量库容量、embedding 调用费和每次推理的 token 都被重复内容吃掉。

你可能会说，检索后用 MMR 打散不就行了？MMR 能缓解结果层的冗余，但它是事后补救：重复内容仍然占着索引，仍然参与打分，版本冲突也没解决。源头去重和结果层多样性是两件事，最好都做。

还有一个容易被忽视的代价：评测失真。如果你的测试集问题恰好命中被复制多份的段落，Top-K 命中率会虚高，看起来检索很准，实际上只是同一答案被召回了好几次。去重之后指标往往先掉一截，这不是退步，而是终于看到了真实水平。

## 四种去重方法对比

去重的核心问题是「多像才算重复」。完全相同好办，算个哈希就行；难的是改了几个字、换了个标点、多了一行页脚的近重复。下面这张表是我在实际项目里常用的四种方法：

| 方法 | 原理 | 能抓到什么 | 成本 | 适用阶段 |
|------|------|-----------|------|----------|
| 精确哈希 | 规范化后算 SHA-256 | 完全相同的文本 | 极低 | 入库第一道 |
| MinHash + LSH | shingle 集合的 Jaccard 近似 | 局部改动、增删段落 | 低 | 文档级去重 |
| SimHash | 加权特征降维成 64 位指纹 | 小幅改写、错别字 | 很低 | 海量短文本 |
| 语义去重 | embedding 余弦相似度 | 换说法的同义内容 | 高 | chunk 级精修 |

精确哈希之前一定要做规范化：统一全半角、去掉多余空白、去掉页眉页脚和时间戳。不做这一步，多一个空格就算两份。MinHash 适合中长文档，对段落增删很稳；SimHash 指纹只有 64 位，适合千万级数据快速比对，但对长文档里的局部修改不够敏感。

语义去重最「聪明」也最危险。两段话 embedding 相似度 0.95，可能只是同一主题，并不等于内容重复。比如「A 产品支持退款」和「B 产品支持退款」，向量非常接近，删掉任何一条都是事故。所以语义去重的阈值要保守，并且最好只在同一文档来源内部使用。

我的经验是把四种方法串成漏斗，而不是四选一。先用精确哈希砍掉最便宜的那部分，通常能去掉一成左右；再用 MinHash 处理文档级近重复；SimHash 留给工单、聊天记录这类海量短文本；语义去重只在 chunk 级、同来源范围内做最后精修。越往后成本越高，处理的数据量也越小。

## MinHash + LSH 落地代码

下面是我在项目里用的一个精简版本，基于 `datasketch` 库。中文没有天然空格分词，直接用字符级 5-gram 做 shingle，效果比先分词再取词组更稳定，也省掉了分词器带来的不一致：

```python
import hashlib
import re
from datasketch import MinHash, MinHashLSH

def normalize(text):
    text = re.sub(r"\s+", " ", text)
    text = re.sub(r"第\s*\d+\s*页", "", text)  # 去页码
    return text.strip().lower()

def shingles(text, k=5):
    return set(text[i:i + k] for i in range(max(1, len(text) - k + 1)))

def build_minhash(text, num_perm=128):
    m = MinHash(num_perm=num_perm)
    for s in shingles(normalize(text)):
        m.update(s.encode("utf-8"))
    return m

def dedup(docs, threshold=0.85):
    lsh = MinHashLSH(threshold=threshold, num_perm=128)
    seen_exact = set()
    keep, dropped = [], []
    for doc in docs:
        norm = normalize(doc["text"])
        digest = hashlib.sha256(norm.encode("utf-8")).hexdigest()
        if digest in seen_exact:
            dropped.append((doc["id"], "exact"))
            continue
        seen_exact.add(digest)
        mh = build_minhash(doc["text"])
        hits = lsh.query(mh)
        if hits:
            dropped.append((doc["id"], "near:" + hits[0]))
            continue
        lsh.insert(doc["id"], mh)
        keep.append(doc)
    return keep, dropped
```

注意几个细节。`threshold=0.85` 是 Jaccard 相似度的阈值，制度文档类我一般设 0.8 到 0.9；代码和配置文件改一个参数意义就完全不同，阈值要提到 0.95 以上甚至跳过。`docs` 的输入顺序决定谁被保留，所以要先按「新鲜度 + 权威度」排好序，让最新、最权威的版本先进 LSH。

另外，`num_perm` 决定估算精度和内存。128 个排列对百万级文档已经足够，误差大约在百分之几；如果你的阈值卡得很紧，比如要区分 0.85 和 0.88，可以提到 256。LSH 索引本身也要持久化，否则每次增量入库都要把历史文档重新算一遍，十几分钟的任务会变成几小时。

chunk 级的页眉页脚噪声则要换个思路。统计全库 chunk 里出现频率最高的行，出现次数超过文档数一半的，基本就是页眉、页脚或版权声明，直接在切片前剥离。这一步往往比任何相似度算法都见效快。

## 去重后怎么处理：删除、合并还是折叠

找到重复只是一半，另一半是决定怎么处理。我见过最常见的错误是直接物理删除，结果业务方问「为什么搜不到华东区那份手册」，因为它被当成华北区版本的重复删掉了，而两者的权限范围不同。

我的建议是分三档处理。完全相同且来源同一系统的，直接删除，只保留一份。近重复且属于同一文档的不同版本的，保留最新版进入索引，旧版本标记为 `superseded` 归档，不参与检索但可追溯。近重复但来源、权限或适用范围不同的，不删，而是在 metadata 里记录 `cluster_id`，检索时按簇折叠。

按簇折叠的意思是：检索阶段照常召回，但同一个 `cluster_id` 只保留得分最高的一条，其余作为「相似来源」挂在引用里。这样既保住了 Top-K 的多样性，又不丢失权限隔离和溯源信息。这一步的实现成本很低，在 reranker 之后加一个分组过滤就能完成。如果你的系统要给出引用，还可以把同簇的其他来源一并展示，让用户自己判断该看哪个版本。

## 上线前的实战清单

去重不是一次性脚本，而是数据管道里的常驻环节。新文档每天都在进来，旧文档也在被复制和修改。下面是我每次上线去重流程前会逐项核对的清单：

- 先抽样估算重复率：随机取 1000 篇跑一遍 MinHash，看重复率再决定投入多少精力。
- 规范化规则单独成模块，并写单测，页眉页脚的正则改一次就可能影响全库。
- 阈值按文档类型分档，制度、FAQ、代码、表格各用各的，不要一刀切。
- 所有被去掉的文档都写入日志，记录原因和命中的保留方，方便人工复核和回滚。
- 增量入库时复用持久化的 LSH 索引，不要每次全量重算。
- 去重前后跑同一套检索评测，确认 recall 没有掉，Top-K 多样性有提升。

**踩坑清单**：最后把我踩过的坑集中列一下。第一，忘了规范化，精确去重形同虚设。第二，输入顺序没排，留下了旧版本、删掉了新版本。第三，跨租户去重，把权限不同的文档合成一份，直接造成越权。第四，语义去重阈值设太低，把「相似主题」当「重复内容」误删。第五，只在文档级去重，没处理 chunk 级的页眉页脚噪声，Top-K 依然在复读。

一句话总结：检索质量的上限不在模型，而在你喂给索引的数据有多干净。
