你上线一个月，后台点赞率从 72% 爬到 81%，于是你拍板说模型变好了。但真相可能是：那些真正不满的用户默默关掉了页面，根本懒得点那个踩。你拿来当胜负手的这条曲线，采样偏差大到足以把一次退步包装成胜利。用户反馈当然能当 Eval 信号，它便宜、实时、贴近真实场景，是离线评测给不了的；但在你信它之前，得先看清它在采样、幸存、延迟这三处是怎么系统性骗你的。搞不清这三重偏差，你每一次照着它调参，本质上都是在拿噪声当信号喂给自己。

## 点赞点踩的信号密度低到可怜

真实产品里，主动点评的用户常常不到 1%。这意味着你那条光鲜的点赞率曲线，是从一小撮「情绪足够强烈到愿意动手」的人身上采来的。强正面和强负面的人最爱发声，温吞的大多数全员沉默，样本分布直接跟真实用户分布脱节，算出来的均值毫无代表性可言。

更麻烦的是幸存者偏差。体验极差的用户往往不是点踩，而是直接跑路，连反馈入口都不碰。于是你的负面样本被系统性地抹掉了一大块，剩下的踩里还混着「我今天心情差」「手滑点错」的噪声。用这种数据算出来的满意度天然偏乐观，而且越是体验糟糕的版本，这种乐观偏差越严重——因为更多差评用户选择了沉默离场。

所以第一条纪律：点赞率是**相对趋势指标**，不是绝对质量值。它适合在同一套埋点、同一批用户习惯下横向比自家版本，绝不适合拿去跟别家报的数字比高低，更不能单独当成放量上线的闸门。你真正该盯的是同口径下的变化方向，以及点评率本身有没有异动——点评率突然下滑，往往比点赞率上涨更值得你警惕。

## 隐式信号比显式更值钱，但更难解读

比起让用户点按钮，用户的行为本身泄露的信息多得多。重新生成、复制结果、手动改写、追问澄清、停留时长——这些隐式信号覆盖面广、不需要用户额外动作，是比点赞点踩密度高一两个量级的金矿。代价是：每个信号的含义都是多义的，解读错了比没有信号更糟糕。

| 信号 | 大概率含义 | 容易误读成 |
|---|---|---|
| 点击重新生成 | 本次回答没达标 | 用户只是想看多个版本 |
| 复制整段输出 | 答案有用、被采纳 | 复制去别处吐槽 |
| 手动编辑后发出 | 方向对、细节差 | 用户本就想自己写 |
| 立刻追问同一问题 | 没答到点上 | 任务本身就是多轮 |
| 长时间无操作 | 满意地在读 | 已经切走去干别的 |

看这张表就明白：没有任何单一信号能直接等于「好」或「坏」。复制可能是认可，也可能是拿去截图吐槽；长停留可能是认真读，也可能是人早走了。靠谱的做法是把多个信号联立起来看——复制且无追问大概率是正面，重新生成后又手动编辑则几乎肯定是负面。把隐式信号当标签前，你得用整段会话上下文给它消歧，而不是机械地一对一硬映射。

## 当标签前先过三道清洗

想把反馈接回 Eval，直接 `label = 1 if thumbs_up else 0` 是灾难。信号要先过三道清洗：剔除机器人与压测流量、用隐式行为给显式信号消歧、按用户活跃度反向加权压掉重度用户的话语权。

```python
def to_eval_label(event, session):
    # 1. 过滤非人类与异常流量
    if session.is_bot or session.turn_count > 200:
        return None
    # 2. 用隐式行为给显式信号消歧
    signal = event.explicit            # thumbs_up / down / None
    if signal is None:
        if event.regenerated and event.no_copy:
            signal = "down"            # 重生成且没复制 → 弱负面
        elif event.copied and not event.followup:
            signal = "up"              # 复制且没追问 → 弱正面
    if signal is None:
        return None
    # 3. 按用户活跃度反向加权，压制高频用户刷屏
    weight = 1.0 / (1 + math.log1p(session.user_feedback_count))
    return {"label": signal, "weight": weight, "turn_id": event.turn_id}
```

关键是第三步的权重。少数超级活跃用户能贡献你一半的反馈量，不降权的话，你的 Eval 其实是在拟合这十几个人的口味，而不是全体用户。反向加权让长尾用户的声音重新进入画面，这一步对指标的影响，常常比你辛苦换一版模型还大。清洗完也别急着用，先抽一两百条人工复核一遍，确认消歧规则没把大批正面误判成负面，再接进流水线。

## 定期拿人工锚点校准，别让信号自己漂走

反馈信号还有个慢性毒：它会随时间悄悄漂移。用户群在变、产品心智在变、甚至点赞这件事的社会习惯都在变，去年的 80% 和今年的 80% 可能根本不是一回事。你需要一个不随时间漂移的参照系，这就是人工锚点集的价值所在。

做法很简单：维护一份几百条、覆盖主要场景的固定样本，每隔一两周找标注员按统一 rubric 打一次分。把这份人工分和同期的线上反馈分放一起看，两条线理应大致同向。一旦它们开始背离——线上在涨、人工在跌——几乎可以断定你的反馈信号被某种偏差污染了，该停下来查埋点，而不是继续开香槟庆祝。

这份锚点集同时还是你校准权重和消歧规则的标尺。规则每次调完，先在锚点集上验证跟人工判断的一致性有没有变好，再推到全量。没有这个固定参照系，你那套反馈 Eval 就是在流沙上盖楼，看着在涨，其实地基一直在偷偷移动。

## 线上信号补不了线下 Eval 的位

就算清洗得再干净，线上反馈也有个治不好的病：延迟和不可复现。用户今天点的踩，对应的往往是三天前某个早已改过的 prompt 版本；你也没法拿同一道题重跑两次看结果稳不稳定。它擅长「发现问题」，不擅长「量化改进」，这两件事千万别用同一个指标去扛。

正确姿势是把两者接成闭环：线上反馈负责**捞出**线下 Eval 没覆盖到的失败场景，你把这些真实 badcase 脱敏、去重后沉淀进 golden dataset，再用离线可复现的评测去卡回归。线上当雷达负责扫描未知，线下当尺子负责精确计量。只盯着点赞率调参，等于闭着眼睛拿一把会随温度变形的尺子量零件。

还有个常被忽略的点：反馈入口本身会反向塑造行为。把踩按钮做得太显眼，负面率就虚高；藏得太深，又采不到真实不满；默认选中某个选项，数据直接废掉。埋点和交互设计是 Eval 方法论的一部分，不是前端顺手的小事。改版埋点前务必留好新旧对照期，否则曲线的跳变你永远分不清是模型动了还是按钮挪了。

踩坑清单：

- 把点赞率当绝对质量值去跨产品比，或单独拿它当放量闸门
- 忽略幸存者偏差，默认「没人点踩=大家都满意」
- 单一隐式信号硬映射成标签，不看会话上下文消歧
- 不给高频用户降权，让十几个人的口味主导整条曲线
- 延迟反馈归错对话轮次，把 A 版本的锅算到 B 版本头上
- 只用线上信号调参，不把 badcase 沉淀回可复现的离线 Eval
- 反馈信号不设人工锚点，任由它随时间悄悄漂移还浑然不觉
