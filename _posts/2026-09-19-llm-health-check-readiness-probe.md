你半夜被告警叫醒，发现刚滚动上线的 LLM 实例一起来就接了流量，可模型权重还没加载完、上游连接池还没热身，第一批用户直接吃了满屏 503。问题不在业务代码，在于你的健康检查撒了谎——进程活着不等于能干活。普通 Web 服务里"端口通了就算健康"的老经验，搬到 LLM 服务上会反复坑你，因为这类服务启动慢、依赖多，每次调用还要花钱。健康检查是你和调度器之间唯一的沟通语言，它说的每一句都会被当真。

## 先分清 Liveness、Readiness、Startup

三种探针管的是完全不同的问题，混用是一切混乱的根源。它们各自回答一个独立的问题，失败后果也天差地别。给你一张对照表先建立直觉：

| 探针 | 回答的问题 | 失败后果 | LLM 场景要点 |
| --- | --- | --- | --- |
| Liveness | 进程要不要重启 | 杀掉并重建 Pod | 超时别太死，GC 卡顿会误杀 |
| Readiness | 能不能接流量 | 从 LB 摘除 | 依赖塌了就摘，恢复要快 |
| Startup | 初始化完了没 | 推迟前两者生效 | 兜住几十秒到几分钟的冷启动 |

最常见的死循环：模型加载要 90 秒，liveness 探针 30 秒就判死，实例反复被杀、永远起不来。有了 startup probe 兜住这段初始化时间，liveness 才不会提前动手，你的慢启动实例才有机会真正跑起来。更深一层的误区是把重启当万能药：readiness 类问题（上游超时、缓存断连）重启根本修不好，只会让实例转一圈回来继续坏，把一次局部故障拖成一场滚动崩溃。区分"该重启"和"该摘流量"，本质是区分"我坏了"和"我依赖的东西坏了"。

## 健康检查到底该查什么

只探端口毫无意义。一个诚实的 readiness 要把关键依赖点一遍：上游 LLM 网关能不能通、向量库连接是否活着、缓存在不在、本地模型是否加载完成、并发池还有没有余量。但别一股脑全塞进去，要区分"摘流量"和"发告警"两个层级：

- 必查（挂了立即 not ready）：上游 LLM 可达、向量库连接、模型权重加载完成
- 建议查（降级而非摘除）：缓存命中层、限流器状态、磁盘与内存水位
- 别查（交给监控告警）：单次真实推理延迟、日请求量、成本累计曲线

把所有指标都当成 readiness 的硬门槛，后果很典型：一次 Redis 抖动，整个集群同时被摘，故障范围反而被健康检查放大了。缓存这类"塌了还能降级跑"的依赖，应该走告警而不是直接摘流量，否则你等于亲手给自己造了一个单点。还要警惕检查的传染性——如果实例 A 的 readiness 去探实例 B，B 探 C，一个节点抖动就能沿着依赖链把整片集群探成 not ready。健康检查只该看自己和自己的直接下游，别替别人做体检。

再进一步，别把健康做成非黑即白的开关。真实系统更适合三态：healthy（全功能）、degraded（缓存挂了但主链路还在，可降级服务）、unhealthy（核心依赖断了，该摘）。只有 unhealthy 才让 readiness 返回失败，degraded 继续接流量但打点告警、必要时关掉重排等增强功能。二值健康会逼你在"带病硬扛"和"直接摘光"之间二选一，而绝大多数生产故障其实落在中间那档——保住主链路、砍掉锦上添花，才是把可用性榨到最高的姿势。

## 别让健康检查自己把钱烧穿

最蠢也最常见的坑：在 readiness 里直接发一次真实 completion，美其名曰"验证模型真能用"。k8s 默认每 10 秒探一次，100 个实例一天就是几十万次纯白烧的调用，账单出来才发现钱去哪了。正确做法是分层：探活只用轻量信号——TCP 连通、`/models` 列表接口、或一个 1-token 的 ping；真实推理是否正常，交给旁路的合成流量（synthetic probe）每几分钟测一次，和探针彻底解耦。合成流量还能顺带覆盖端到端链路、给你一条真实延迟基线，一举两得。再给依赖检查套一层几秒的本地缓存，避免高频探针每次都真去连一遍下游，把探针自己变成一场压测。

```python
import time

_cache = {"ts": 0, "ok": False}

async def readiness():
    now = time.monotonic()
    if now - _cache["ts"] < 5:           # 5s 内复用上次结果
        return _cache["ok"]
    ok = (
        await ping_upstream(timeout=2)   # 轻量：只探连通，不做真实推理
        and model_loaded()               # 读本地状态，不花钱
        and vector_db_alive(timeout=2)
    )
    _cache.update(ts=now, ok=ok)
    return ok
```

## k8s 探针配置实战

逻辑对了，配置写歪照样翻车。startup probe 要给足 failureThreshold，让慢启动的实例熬过加载期再交棒；liveness 超时别卡太死，留出 GC 和偶发抖动的余地；readiness 的恢复门槛要低，好让修好的实例尽快回流，别让一次抖动把实例晾在外面太久。三个数字——periodSeconds、timeoutSeconds、failureThreshold——乘起来才是真正的容忍窗口，配之前先在纸上把它算清楚。

```yaml
startupProbe:          # 兜住冷启动，最多容忍 5 分钟
  httpGet: { path: /healthz/startup, port: 8080 }
  periodSeconds: 5
  failureThreshold: 60
livenessProbe:         # 只判进程死活，超时给够
  httpGet: { path: /healthz/live, port: 8080 }
  periodSeconds: 15
  timeoutSeconds: 5
  failureThreshold: 3
readinessProbe:        # 依赖塌了摘流量，恢复要快
  httpGet: { path: /healthz/ready, port: 8080 }
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 2
```

三条路径拆开、各走各的 endpoint，才不会互相误伤——用一个接口同时应付三种语义，注定会在某个凌晨给你上一课。

## 别让 readiness 抖动成一场拉锯

上游偶尔抖一下很正常，可如果 readiness 一探失败就立刻摘、一探成功就立刻放，实例会在 in/out 之间反复横跳（flapping），流量随之忽大忽小，反而更难恢复。解法是加迟滞：摘除可以敏感（连续 2 次失败就摘），回流要保守（连续 3 到 5 次成功才放回），中间留一段冷却期。k8s 的 `successThreshold` 和 `failureThreshold` 就是给你调这个节奏用的。别追求"零延迟感知故障"，稳定比灵敏更重要——一个偶有抖动却始终稳定在线的集群，远好过一个反应飞快却整天进进出出、把流量抖得七零八落的集群。

## 网关前置多上游时的健康聚合

如果你在多个模型/上游前面架了网关，健康检查还多一层学问：某个上游模型挂了，不该让整个网关变成 not ready，而该把这个上游从路由表里摘掉、让流量绕道其余可用模型。网关的 readiness 应该是"我至少还能服务一类请求"，而不是"我所有下游都健康"。把每个上游的健康状态单独维护、按模型粒度摘除和恢复，才能在部分依赖故障时保住整体可用性。一刀切的聚合逻辑，等于让最脆弱的那个上游决定整个网关的生死。

## 和优雅上下线配合起来

健康检查不是孤立的，它得和上下线节奏对齐。实例要停机时，应该先让 readiness 主动返回 not ready、把自己从 LB 摘掉，等在途请求跑完再退出——这套"先摘流量再停机"的顺序，配合优雅停机机制才算完整。上线同理：startup 没过之前，别让实例出现在服务列表里。健康检查只要撒一次谎，轻则用户吃错误，重则一次滚动发布把整个集群带崩，而你还以为一切正常。

## 踩坑清单

- liveness 和 readiness 共用一个接口，模型加载慢 → 实例被无限重启
- readiness 里发真实推理 → 探针把 token 预算悄悄烧穿
- 依赖检查不设超时 → 下游卡住，探针跟着挂，实例假死
- 所有依赖都当 readiness 硬门槛 → Redis 一抖，全集群一起摘
- readiness 探链上游、上游再探上游 → 一个抖动沿依赖链传染整片集群
- 摘除和回流用同一个阈值 → 实例反复进出、流量拉锯
- 网关一刀切聚合下游健康 → 一个上游挂掉拖垮整个网关
- startup 的 failureThreshold 给太小 → 冷启动没熬过就被判死
- 健康检查结果不缓存 → 高频探针把自己变成压测

一句话：健康检查要回答的从来不是"我还活着"，而是"我现在能不能干活、干不动的时候能不能老实闭嘴、别再接流量"。把这句话刻进每一个 probe，你的凌晨告警会少一大半。
