你线上跑得好好的 Agent，某天在第七步调完工具后突然走岔，给用户返回了一堆胡话。你想复现，却发现根本做不到：同样的输入喂进去，LLM 这次的采样和上次不一样，工具返回的实时数据也变了，第七步那个出错的状态再也拼不回来。多步 Agent 的 bug 之所以最难查，就是因为它同时踩了两个非确定性来源——模型采样和外部世界。

## 为什么 Agent 的 bug 最难复现

传统单次请求的 bug，你留一份 prompt 就能原样复现。Agent 不行：它是一条由十几次 LLM 调用和工具调用交织成的轨迹，任何一环的输出变了，后面全盘皆变。搜索工具今天返回的排序和昨天不同，下游模型的决策就跟着漂移，最终你在日志里看到的那步错误，本地怎么都跑不出来。

你需要的不是更详细的日志，而是一台时光机。日志只能告诉你"发生过什么"，却没法让你回到那一刻反复观察。真正能救命的，是把当时每一次工具返回了什么、模型说了什么，原封不动地录下来，之后在本地严格按同样的顺序喂回去，让整条轨迹脱离真实世界、变成一段可以反复播放的录像。

这套思路在传统软件里叫 record & replay，做过分布式系统调试的人不陌生。搬到 Agent 上，难点在于要录的东西更杂：不只有确定性的函数入参出参，还有模型这一层天生带随机性的输出。所以你得把"工具调用"和"模型调用"当成同一类外部依赖，一起拦截、一起冻结，缺了任何一半，回放都会在半路分叉。

## 录制：把每一次工具 I/O 冻成 fixture

录制的核心，是在工具执行层加一个拦截器，把每次调用的"入参 + 出参"按调用顺序写进一份 trace。顺带把每一步 LLM 的 raw response 也存下来。这样一条完整轨迹就被冻结成了 fixture，可以和代码一起进版本库，谁都能拿去复现，而不用去求"能不能再翻一次那个车"。

```python
class RecordingToolExecutor:
    def __init__(self, real_executor, trace):
        self.real = real_executor
        self.trace = trace          # list，按调用顺序追加

    def call(self, name, args):
        result = self.real.call(name, args)   # 真跑
        self.trace.append({
            "seq": len(self.trace),
            "tool": name,
            "args_hash": sha1(name, args),
            "result": result,
        })
        return result
```

这里有两个容易忽略的点。第一，一定要按 `seq` 顺序记录，而不是只拿 `args_hash` 建字典——同一个工具用同样参数被调两次，返回很可能不同，比如翻页、取号、读时间戳，用字典就会把后一次覆盖前一次。第二，别只录成功结果：超时、报错、空返回同样要录进去，线上翻车往往就翻在这些边角情况上，你偏偏最需要复现它们。

## 回放：拦掉工具层，喂回录好的结果

回放时，把真实的工具执行器换成 `ReplayToolExecutor`：它不碰网络、不调数据库，而是按 `seq` 从 trace 里取出当初的返回值直接吐回去。模型那一层同理，用录好的 raw response 替代真实 API 调用。这样整条轨迹就被钉死了，你可以在本地反复单步、下断点，想跑几遍跑几遍，每一遍都和线上那次分毫不差。

```python
class ReplayToolExecutor:
    def __init__(self, trace):
        self.trace = trace
        self.cursor = 0

    def call(self, name, args):
        step = self.trace[self.cursor]
        assert step["tool"] == name, \
            f"轨迹分叉：期望 {step['tool']}，实际 {name}（第 {self.cursor} 步）"
        self.cursor += 1
        return step["result"]
```

那句 `assert` 是回放的灵魂。如果回放时 Agent 想调的工具和录制时对不上，说明轨迹在这一步分叉了——通常是你刚改的代码或 prompt 让决策变了。这个断言会精确告诉你分叉发生在第几步、本该调什么、实际调了什么，bug 的位置一下就从"某处"收敛到具体一行，而不是让你在整条轨迹里大海捞针。

纯回放能一比一还原现场，但你查 bug 时常常想问一句"如果第五步换个工具会怎样"。这就要用到混合回放：让 Agent 前 N 步严格吃录好的 trace，到第 N 步之后切回真实执行。前半段保证你稳稳走到出问题的现场，后半段则放开手，让你验证改动到底有没有把岔路掰回来，而不用从头一步步重新把 Agent 引到案发地点。

实现上给 `ReplayToolExecutor` 加一个 `live_after` 阈值：`cursor` 小于它就从 trace 取，一旦到了就把调用转发给真实 executor。调试深层 bug 时，你可以把 `live_after` 一步步往后推，像二分查找一样逼近"到底是从哪一步开始跑偏的"。这比通读几百行日志、靠脑补拼状态高效得多，也更不容易冤枉错人。

录制和回放两种模式的职责也要分清，否则很容易在回放时不小心又打了真实接口，或者在录制时误用缓存导致现场失真。下面这张表把边界摊开：

| 维度 | 录制模式 | 回放模式 |
|------|---------|---------|
| 工具是否真跑 | 真调用外部 | 全部从 trace 取 |
| 模型是否真调 | 真请求 API | 用录好的 response |
| 网络 / 花费 | 有 | 零 |
| 非确定性 | 原样保留 | 完全消除 |
| 典型用途 | 线上 / 预发抓现场 | 本地复现、回归测试 |

## 从复现一个 bug 到守住一条防线

录制回放的价值不止于救火，更大的收益在回归测试。你把一条修好的轨迹存成 fixture 钉进 CI，以后每次改 Agent 逻辑，都拿它回放一遍。它比断言"最终答案对不对"细得多：最终答案可能碰巧还对，但中间某步的工具选择已经变了，普通端到端测试根本发现不了，而回放的 `assert` 会在轨迹分叉的那一刻就把 CI 打红。这种"过程级"的回归，恰恰是 Agent 最需要、也最缺的一层保护——因为你改的往往是 prompt 一个词、工具描述一句话，端到端指标毫无波动，行为却已经悄悄变了。

久而久之，你会攒下一整套"疑难杂症轨迹库"：每个历史上出过的诡异 bug，都对应一条被冻结的 trace。它们既是复现现场，也是永不失效的回归用例。新人接手时不必听你讲十遍"当年那个坑"，直接回放一遍，断点走一走，比任何文档都直观。这套录像，慢慢就成了 Agent 最可靠的一道防线。

## 三个绕不开的坑

第一是脱敏。trace 里塞满了真实的 API key、用户数据、内部 URL，直接进版本库就是安全事故。录制时要有一层 scrubber，按字段白名单或正则，把敏感值在落盘前替换成占位符，而且替换要保持稳定映射——同一个值每次换成同一个占位符，否则回放时因为脱敏本身又制造出新的分叉。第二是时间与随机：代码里的 `now()`、`uuid()`、`random()` 同样是非确定性源，回放时要一并 mock 掉，否则轨迹会因为一个时间戳就自己分叉，白折腾半天。

第三是 trace 体积。一条长任务的工具返回可能有好几 MB，几千条轨迹堆起来仓库直接爆。实用做法是给 result 设个大小阈值，超过就单独落到对象存储、trace 里只留一个引用，再配上过期清理策略。别追求录下全宇宙，你要的从来不是完整快照，而是"能复现这个 bug 的最小轨迹"，够用就好。真正进版本库长期保存的，只该是那几条被验证过、能稳定复现问题的精选 trace，其余的采样落盘、定期清掉，别让调试基建自己变成新的负担。

踩坑清单：

- 只按 `args_hash` 建字典 → 同参多次调用的返回被覆盖，一定要带 `seq` 顺序
- 只录成功、不录报错 → 线上真正翻车的边角情况反而复现不出来
- 忘了 mock `now()` / `random()` → 回放自己就分叉，怀疑人生
- trace 明文进 git → 泄露 key 和用户数据，安全和合规双爆
- 不加 `assert` 对齐 → 轨迹早分叉了还以为在复现，查错方向全歪
