## 为什么"从头再来"是奢侈品

你写过那种跑十几分钟、串起七八个工具的 Agent 任务吗？爬一批网页、逐条清洗、再写进库，眼看跑到第 40 步，某个上游 API 超时，整个进程直接崩掉。绝大多数 Agent 的默认行为是——从第一步重新开始。前面攒下的成果全部作废，token 也跟着白烧一遍。

在生产环境里，这种"全量重跑"是奢侈品。一次跑 20 分钟、烧掉几万 token 的任务，重来三次就是一小时加一大笔账单。真正能扛住线上流量的 Agent，必须能从崩溃的那一步接着往下走，而不是每次都从冷启动开始。

这件事的本质，是把 Agent 的执行过程当成一条能"存档读档"的流程，而不是一次性的黑盒。你要能回答一个问题：进程死在半路，重新拉起来时，它凭什么知道自己上次走到哪儿了？

## 续跑的三种粒度，先选档再动手

续跑不是一个开关，而是一条从粗到细的粒度光谱。投入的工程量和恢复的精细度成正比，你得先想清楚要哪一档，别一上来就抡最重的方案。

| 粒度 | 保存什么 | 崩溃后怎么做 | 适用场景 |
|------|----------|--------------|----------|
| 整任务重跑 | 只存输入 | 从头再来一遍 | 步骤少、天然幂等、几秒跑完 |
| 记忆恢复 | 对话历史 + 中间结论 | LLM 读回记忆继续推理 | 纯推理、无强副作用 |
| 步级 checkpoint | 每步的状态与产物 | 跳过已完成步、只补未完成 | 长流程、夹着外部写操作 |

再具体点：最左档只存输入，适合步骤少、天然幂等、几秒钟跑完的活儿；中间档存对话历史和阶段性结论，适合纯推理、没有强副作用的场景；最右档要把每一步的状态和产物都落盘，专门对付那种十几步起、还夹着写库发消息的长流程。选错档的代价是——要么白做工程，要么关键时刻救不回来。

## 用一本 journal 把每一步记下来

步级 checkpoint 最朴素的实现，就是一本 append-only 的日志：每完成一步，就把这步的标识和结果追加一行进去。重新启动时先把日志读回内存，执行到某步前先查——命中就跳过，没命中才真跑。

```python
import json, os

class Journal:
    def __init__(self, path):
        self.path = path
        self.done = {}
        if os.path.exists(path):
            for line in open(path):
                r = json.loads(line)
                self.done[r["step"]] = r["result"]

    def run(self, step, fn):
        if step in self.done:          # 已完成，直接取缓存
            return self.done[step]
        result = fn()                  # 真正执行
        with open(self.path, "a") as f:
            f.write(json.dumps({"step": step, "result": result}) + "\n")
            f.flush()
        self.done[step] = result
        return result
```

用起来是这样，把每个阶段包进 `run` 里，给一个稳定的 step 名字：

```python
j = Journal("run-42.jsonl")
pages = j.run("fetch", lambda: fetch_all(urls))
clean = j.run("clean", lambda: [wash(p) for p in pages])
j.run("save",  lambda: db.write(clean))
```

崩了之后再跑同一个脚本，fetch 和 clean 直接命中缓存秒过，只补跑没写完的 save。逻辑核心就一句话：每一步先查日志，命中就跳过，不命中才执行并落盘。日志格式用 JSON Lines 是个务实选择——天然 append-only、逐行可解析、崩在半行也只丢最后一条，还能直接 grep 排查，一个 jsonl 文件能带你走很远。

还有个常被跳过的环节：恢复时的一致性校验。拉起旧日志之前，先比对当前输入和代码版本的指纹——输入变了、逻辑改了，旧缓存就可能是错的，宁可作废重跑也别将错就错。做法很简单：给日志头写一行 meta，存输入的 hash 和代码版本号，恢复时先验这一行，对不上就当没有旧日志。

## 手写 journal 撑不住了，就换 durable execution

一个 jsonl 文件能带你走很远，但它有天花板。三种情况下你该考虑升级：一是任务要跨机器、跨进程恢复，本地文件就不够了，日志得挪到 Redis、数据库或对象存储这种共享存储里；二是并发跑成百上千个实例，手写的读写和加锁会让你焦头烂额；三是流程本身有复杂的分支、等待和定时，你开始重复造调度器的轮子。

到这一步，值得看看现成的 durable execution 方案。Temporal、Restate、DBOS 这类框架把"每步落盘、崩溃重放、精确一次"做进了运行时，你只管写业务逻辑，续跑是白送的；LangGraph 自带 checkpointer，把图里每个节点的状态存进库，天然支持中断和恢复，做 Agent 尤其顺手。代价是引入依赖和心智负担，所以别一开始就上——先用 jsonl 把问题想清楚，真扛不住了再换重武器。

## 真正的坑在副作用，不在代码

续跑最阴险的坑不在存取代码，而在副作用。读操作重放一百遍都无所谓，写操作重放却会出乱子——重复下单、重复发消息、重复扣款，这类事故追起来能让你怀疑人生。

举个真实的例子：一个发货 Agent，流程是"扣库存 → 生成运单 → 通知用户"，它在生成运单之后崩了。如果没有 checkpoint，重跑会二次扣库存；如果 checkpoint 只存在内存没落盘，重启后照样从头扣。只有把"扣库存"这步的完成状态真正持久化，并给扣减接口加上幂等键，重跑才会安全地跳过它、直接补发运单和通知。

解法有两条，通常要一起上。第一，凡是有外部写的步骤，尽量做成幂等：带唯一业务键的 upsert、先查后写、或者服务端支持的 idempotency-key。第二，把"这步是否已执行"也记进日志，恢复时靠日志判断，而不是靠数据库当前长什么样。

为什么不能只信数据库？因为写库和写日志之间一定有时间差。如果你在"写完库、还没记日志"的缝隙里崩了，下次靠数据库看会以为没做过，靠日志看才知道可能做过——两者结合，再加幂等兜底，才是稳的。

落地时还有个顺序问题值得琢磨：先写外部系统还是先记日志？没有银弹。先记日志，可能记了却没执行成功，恢复时误以为做过而跳过，这叫"幻影完成"；先执行，可能执行了没记上，恢复时重放一遍，又回到幂等问题。工程上更常见的选择是后者加幂等兜底：宁可重放，也不要静默漏做，因为漏做往往更难被发现。

还有一类隐形副作用容易被漏掉：给用户发的中间进度消息、写进监控的埋点、往上递增的计数器。它们看着无害，重放一遍却会污染数据或者刷屏。把它们也当成写操作对待，该记日志记日志，该幂等幂等。

## 什么时候压根不该上 checkpoint

不是所有 Agent 都配得上这套机制。一个三步、全是读操作、十秒钟跑完的任务，加日志纯属过度工程，崩了重来反而更省心、更不容易出 bug。工程的成本要花在真正会疼的地方。

判断标准就两条，占一条就值得做：单次执行足够长，分钟级以上，重跑代价肉疼；或者中间步骤带有不可逆的外部副作用，重放会造成真实世界的损失。两条都不占，老老实实全量重跑。

最后几条用线上事故换来的经验，存下来：

- step 的 key 必须稳定，别用时间戳或随机数，否则重放永远命中不了缓存；循环里带上业务标识，比如 `fetch:{url}` 而不是 `fetch:{i}`
- 日志要 append-only 且逐行 flush，别攒着最后一次性写，那次没写成就全丢
- 别把巨大的中间结果塞进日志，存指针（文件路径、对象存储 key），日志只留元信息
- 恢复前先校验代码版本，逻辑改过就让旧日志作废，别拿新代码套旧缓存
- 幂等键用业务 ID，不要用步骤序号，序号会因为你中途插入新步骤而整体错位

一句话收尾：能续跑的 Agent 和不能续跑的 Agent，差的从来不是模型多聪明，而是工程纪律够不够硬。
