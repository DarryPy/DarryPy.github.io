你训了一个 reward model，对着一道数学题 Best-of-N 采样 64 条，挑分数最高的交上去，正确率却只涨了两三个点。问题通常不在采样数量，而在这个 reward model 只认最终答案：一条推理前面步步跑偏、最后蒙对，它照样给高分。这是 outcome reward model（ORM）的天花板。要突破它，你得让模型学会给推理的每一步单独打分——这就是 process reward model（PRM）。

## 只看答案对错为什么不够

ORM 的训练信号只有一个 bit：整条回答最终对还是错。它把一二十步推理压成一个标量，中间哪一步偷换了条件、哪一步算错又恰好抵消，全都看不见。对数学证明、多步代码这类长链条任务，这个粒度太粗，模型根本拿不到"错在哪里"的反馈。

更糟的是它鼓励 reward hacking。只要最终数字对，过程怎么编都行，ORM 全盘接受。你会看到模型写出一堆似是而非的推导、结论却蒙对——这种样本在 Best-of-N 里反而容易被选中，因为它们"看起来很详细"。信号越稀疏，模型越容易钻这个空子。

举个具体的：一道积分题，模型第二步把换元的上下限写反了，后面又犯了个符号错误，两个错误恰好抵消，最终答案对了。ORM 看到正确答案给满分，这条样本进了训练集，模型学到的是"这种换元写法没问题"。错误就这样被奖励信号固化下来，下次遇到不抵消的情形立刻原形毕露。

PRM 换了个粒度：对每一步输出一个 0 到 1 的分数，代表"走到这里还有没有希望得到正解"。你拿到的不再是一个总分，而是一串分数，能直接定位到崩在第几步。这对两头都有用——训练时信号更密，推理时能按步搜索和剪枝，而不是整条采完再挑。

## 标注数据从哪来

PRM 最贵的从来不是训练，是标注。OpenAI 的 PRM800K 走纯人工路线：标注员逐步判断每一步是正确、错误还是中性，硬堆出 80 万条步级标注。质量确实高，但烧钱烧到没几个团队跟得起，而且模型一迭代，老标注就对不上新输出，得重标。

自动方案是 Math-Shepherd 这类用蒙特卡洛估计的做法：不请人标，从某一步出发让模型继续补全 N 次，数有多少次最终答对，这个比例就当这一步的软标签。走在正道上的步往下容易得到正解，走偏的步基本没救，分数自然拉开。省了人工，代价是采样开销和一定的标签噪声。

软标签的 rollout 数是个超参：太少，估计方差大，正确的步也可能被误判死刑；太多，标注成本直接起飞。常见折中是每步 8 到 16 次，配合温度采样保证多样性。另外要过滤掉"答案对但过程明显错"的 rollout，否则等于把噪声直接喂进标签。

还有一条正在流行的捷径叫 implicit PRM：不单独训打分头，而是直接拿一个训好的 generative verifier 或 DPO 模型的 log-prob 差分，反推出每一步的隐式奖励。好处是彻底省掉步级标注，坏处是这个隐式分数的校准性往往不如显式 PRM，用于精细剪枝时得额外做验证。下面这张表把 ORM 和 PRM 的核心差别摆在一起：

| 维度 | ORM | PRM |
| --- | --- | --- |
| 打分粒度 | 整条回答一个分 | 每一步一个分 |
| 标注成本 | 低，只需答案对错 | 高，人工或大量 rollout |
| 信号密度 | 稀疏 | 密集 |
| 定位错误 | 不能 | 能到具体步 |
| 推理时用法 | Best-of-N 整条挑 | 逐步搜索 / 剪枝 |
| 主要风险 | 过程造假被接受 | 标签噪声、reward hacking 换形态 |

## 怎么训一个 PRM

结构比想象的简单。你在 base model 顶上接一个二分类头，预测每一步末尾那个特殊 token 的"正确概率"，硬标签用交叉熵，软标签用 MSE 或 soft cross-entropy。真正的关键是把每一步的边界用一个占位 token 显式标出来，模型才知道该在哪些位置出分。

训练数据的组织也有讲究：同一道题的正负步要混在一起，别让模型靠题目难度抄近路；学习率比 SFT 再低一档，PRM 很容易过拟合到标注的表面模式上。评估也别只盯步级 accuracy，那个数字很容易虚高——真正该看的是下游指标：把 PRM 接上 Best-of-N，在 held-out 题集上比 ORM 和 majority voting 高多少。步级准、下游不涨的 PRM 多得是，通常是标签分布和真实推理分布对不上。下面是提取每步分数的核心逻辑：

```python
# 每步末尾插入 step tag，只在 tag 位置取 logit
STEP_TAG_ID = tokenizer.convert_tokens_to_ids("<extra_0>")
input_ids = tokenizer(reasoning_with_tags).input_ids
tag_pos = [i for i, t in enumerate(input_ids) if t == STEP_TAG_ID]

logits = model(input_ids).logits                 # [seq, 2]
step_scores = logits[tag_pos].softmax(-1)[:, 1]   # 每步"正确"概率
# 训练: loss = cross_entropy(logits[tag_pos], step_labels)
# 软标签: loss = mse(step_scores, mc_estimate)
```

## 推理时怎么用

训完 PRM，收益主要在推理阶段兑现。最朴素的是 step-level Best-of-N：采多条候选，每条按步打分再聚合成一个总分，挑最高的。聚合方式很关键——取最小值通常比取平均稳，因为 min 惩罚"一步致命错误"，而 mean 会被一堆正确的废话稀释，把真正崩了的那条反而捞上来。

再进一步是 step-level beam search 或 MCTS：每生成一步就用 PRM 打分，砍掉低分分支，只在高分节点继续展开。算力集中花在有希望的路径上，比盲目采几百条整回答高效得多。给定同样的 FLOPs，带 PRM 的搜索通常能顶上大一档模型的 ORM Best-of-N。

实战里 PRM 还常和末端的答案验证器叠着用：PRM 负责在生成过程中剪枝、保证搜索效率，规则验证器（比如把数学答案代回去检验、把代码跑一遍单测）负责在末端做硬过滤。前者快而软，后者慢而硬，两层串起来，既不浪费算力在死分支上，也不会被 PRM 的误判带偏最终结论。

这套逻辑正是 o1、DeepSeek-R1 这类推理模型 test-time scaling 的底层之一：把更多算力投到推理时的搜索与验证，而不是一味堆模型参数。PRM 在这里既是打分器，也是剪枝器，决定了搜索树往哪个方向长。

但别把 PRM 当成通用验证器。它只在训练它的分布里可靠：数学 PRM 拿去评代码、评 agent 轨迹，基本等于瞎猜，因为"一步对不对"的定义完全变了。跨域要用，就得各训各的，或者至少在目标域上重新标一批校准数据，否则分数好看、实际没用。更别指望 PRM 分数能线性反映质量、直接当稠密奖励塞进 PPO/GRPO：实践里它更适合做离散的筛选和剪枝，稠密奖励一硬塞，模型很快学会把分数刷高而推理并没变好，reward hacking 换了个形态又回来了。真要这么用，就加 KL 约束并定期人工抽检。

## 什么时候才值得上 PRM

不是每个任务都值得为 PRM 付账。步级标注和推理时搜索两头都烧钱，如果你的任务链条短、答案又容易直接验证（比如单步分类、有现成单测的代码题），带规则验证器的 ORM 或者干脆 majority voting，性价比往往更高，省下的算力拿去多采几条还更实在。

PRM 真正的主场是另一类：链条长、中间某一步决定全局成败、而且终局验证器拿不到中间信号的推理任务——数学证明、多跳规划、长程 agent 决策。这类任务里一步错步步错，密集的步级信号才有不可替代的价值。先想清楚自己是不是这一类，再决定要不要掏这笔标注和搜索的成本。

**踩坑清单：**

- 聚合用 min 而不是 mean：一步致命错误不该被一堆正确步稀释掉
- Math-Shepherd 的 rollout 数要卡住，太少噪声大、太多烧钱，8~16 次起步
- step 边界 token 必须和训练时完全一致，换了分隔符 PRM 直接失灵
- PRM 自己也会被 hack：模型学会写"看起来每步都对"的废话，拿 held-out 题定期评
- 别指望跨域迁移：数学 PRM 评代码基本没用，各域各训各标
- 当稠密 RL 奖励要谨慎：优先做离散筛选，硬塞进 PPO/GRPO 容易被刷分

一句话收尾：ORM 告诉你答案对不对，PRM 告诉你错在第几步——而能定位错误，才谈得上修正。
