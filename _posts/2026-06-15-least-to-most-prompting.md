你有没有遇到过这种情况：加了 "let's think step by step" 之后，模型在第三步突然跳步，得出一个听起来合理但根本对不上的答案？Chain-of-Thought 确实有效，但它把整个推理链压在一次生成里，面对真正复杂的多跳问题时，长链条很容易在中途漂移——模型没有强制检查点，一旦某一步假设错误，后面全错。

Least-to-Most Prompting（以下简称 L2M）是 Google Research 在 2022 年提出的改进方案。核心洞察很朴素：**先让模型把大问题拆解成从简单到复杂的子问题序列，再依次求解，每步答案作为下一步的 grounding**。就像你学数学时，先搞懂一次方程再去碰二次方程，而不是直接上来就解一元二次不等式组。实验数据里，L2M 在 GSM8K 等数学推理基准上比标准 CoT 准确率提升了 4～8 个百分点，在 SCAN 组合泛化任务上更是从 16% 跳到了 99.7%。这个巨大的跨越不是调参魔法，而是方法论上的根本转变：从"一次性推理"变成"结构化的逐步 grounding"，两者解决的其实是同一个问题，只是后者给模型提供了更多中间检查点，让错误无处遁形。

## 两阶段执行流程

L2M 的每次完整推理分成两个独立的 LLM 调用，中间有一道人工可审查的"防火墙"。这个设计不只是工程技巧，更是让复杂推理变得可调试的关键。

**阶段一：问题分解（Decomposition）**

给模型一个专门的分解 prompt，让它输出子问题列表，而不是急着给答案：

```
你是一个善于拆解问题的助手。
给定下面的题目，把它拆解成必须按顺序解决的子问题列表（JSON 数组）。
从最简单的基础问题开始，最后一个子问题的答案即为原问题的答案。

题目：一列火车从 A 到 B 需要 3 小时，从 B 到 C 需要 2 小时。
      若速度提升 20%，从 A 经 B 到 C 共需多少时间？

只输出 JSON，格式：["子问题1", "子问题2", ...]
```

模型输出：

```json
[
  "设原速度为 v，A 到 B 的距离是多少？",
  "B 到 C 的距离是多少？",
  "速度提升 20% 后的新速度是多少？",
  "提速后 A 到 B 需要多少时间？",
  "提速后 B 到 C 需要多少时间？",
  "提速后 A 经 B 到 C 的总时间是多少？"
]
```

这一步是整个方法的灵魂。好的分解应满足三个条件：子问题之间有明确依赖顺序；每个子问题相对独立，不依赖后续子问题的结论；最后一个子问题直接可以推出原问题答案。如果分解结果不满足这些条件，可以让模型重新分解，或者手动调整后再进入阶段二。

**阶段二：顺序求解（Sequential Solving）**

把子问题逐一抛给模型，每次把已有的 QA 对拼入 context：

```
已知信息：
原问题：火车速度提升 20% 后，A 经 B 到 C 需多少时间？
Q1: 设原速度为 v，A 到 B 的距离是多少？
A1: A 到 B 距离 = v × 3 = 3v

当前子问题：B 到 C 的距离是多少？
```

每步答案成为下一步的 grounding，推理不再悬空。最终答案——提速后总时间 = 3v/1.2v + 2v/1.2v ≈ 4.17 小时——经过 6 个有序子步骤干净地推出来，中间没有任何跳跃。

## 与主流推理方法横向对比

| 方法 | 核心机制 | 最适合场景 | 主要弱点 |
|------|---------|-----------|---------|
| CoT | 一次生成完整推理链 | 中等复杂单跳推理 | 长链条中途漂移 |
| Self-Consistency | 多次采样投票 | 答案分布集中的任务 | 不修复推理路径本身 |
| Tree of Thoughts | 树形搜索 + 评估剪枝 | 需要回溯的创意决策 | 调用次数多、成本高 |
| L2M | 分解后顺序求解 | 多跳依赖、子问题明确 | 分解质量决定上限 |

L2M 在以下场景优势最明显：数学应用题、逻辑推理题、多步骤代码生成（先定接口、再实现、再写测试），以及需要从长文档里递进抽取结构化信息的任务。如果你的任务本质上是"有序依赖的信息处理链"，L2M 几乎是默认首选。

## 用 Python 实现 L2M 框架

```python
import json
from anthropic import Anthropic

client = Anthropic()
MODEL = "claude-opus-4-8"

DECOMPOSE_PROMPT = """把下面的问题拆解成按顺序解决的子问题列表（JSON 数组）。
从最简单的基础问题开始，最后一个子问题的答案就是原问题的答案。
只输出 JSON，格式：["子问题1", "子问题2", ...]

问题：{question}"""

SOLVE_PROMPT = """已知信息：
{context}

当前子问题：{subq}

请给出简洁准确的答案（一两句话即可）。"""


def least_to_most(question: str) -> str:
    # 阶段一：分解
    decomp = client.messages.create(
        model=MODEL,
        max_tokens=512,
        messages=[{"role": "user", "content": DECOMPOSE_PROMPT.format(question=question)}],
    )
    subquestions = json.loads(decomp.content[0].text)

    # 阶段二：顺序求解，每步把上一步 QA 追加进 context
    context_parts = [f"原问题：{question}"]
    for i, subq in enumerate(subquestions):
        prompt = SOLVE_PROMPT.format(
            context="\n".join(context_parts),
            subq=subq,
        )
        ans = client.messages.create(
            model=MODEL,
            max_tokens=256,
            messages=[{"role": "user", "content": prompt}],
        ).content[0].text.strip()
        context_parts.append(f"Q{i+1}: {subq}\nA{i+1}: {ans}")

    return context_parts[-1]  # 最后一步答案即为最终答案
```

`context_parts` 是关键：每步把上一步的 QA 追加进来，让模型在第 5 步仍然"记得"第 2 步的中间结果，而不是凭空推测。注意这里每一步都是独立的 `messages.create` 调用，而不是多轮对话——这样每步的 token 消耗是确定的，方便计费和限速控制。

## L2M 的适用边界

并不是所有任务都适合 L2M。下面两种情况用它反而会帮倒忙。

**适合：** 有明确子问题依赖关系的任务、答案可验证的推理题、需要先定结构再填内容的多步骤代码生成，以及层级式信息抽取（先抽实体、再抽关系、再推断结论）。

**不适合：** 开放性创意写作，拆解会让文章变死板、风格变机械；价值判断或意见类问题，子问题之间没有因果依赖链；简单单跳问答，两次 LLM 调用成本远高于直接 CoT。

一个实用判断标准：如果你能在纸上画出"子问题 A 的结论是子问题 B 的前提"这种有向图，L2M 就适用；如果画不出来，用标准 CoT 或直接 few-shot 更合适。

## 踩坑清单

- **阶段一输出格式必须强约束**：加 `只输出 JSON`，代码里加 `try/except json.loads` 兜底，并在 except 里用正则抽取 `\[.*\]` 做降级解析，因为模型偶尔会在 JSON 外包一层 markdown 代码块。
- **子问题数量控制在 5 个以内**：超过 8 个时，后期子问题容易出现"循环依赖"或重复前面已有结论，既浪费 token，又引入混淆。分解太细的场景建议让模型先做"一级分解"，再对复杂子问题做"二级分解"，而不是一口气列 10 条。
- **context 不要无限累积**：到第 8 步以后 context 会很长。可以只保留最近 3 步 QA 加上原问题，早期子问题的结论已经被后续答案"消化"，没必要全量保留。
- **分解顺序错误比分解不全更致命**：如果子问题 3 依赖子问题 5 的结论，阶段二从第 3 步起就会迷路。关键任务上，在两个阶段之间加一次自动验证——让另一个 LLM 调用检查"子问题序列是否符合拓扑排序"，比直接信任第一次分解结果要稳得多。
- **与 CoT 叠加使用**：阶段二的每个子问题 prompt 里可以追加 `请一步步推理后再给出答案`，让模型对每个子答案也做 CoT，两层结构叠加，复杂推理的准确率会进一步提升。

L2M 不是银弹，但它把"复杂任务的推理失控"这个难以调试的问题，转化成了"分解质量"这个更容易写规则和做验证的问题。推理可以是黑盒，分解不能是。
