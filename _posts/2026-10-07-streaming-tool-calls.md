你点下发送，Agent 卡住三秒，然后结果突然蹦出来——这三秒它在干嘛？多半在等模型把一整段工具调用的 JSON 参数生成完。可这段参数本就是一个 token 一个 token 流出来的，你完全能边收边处理，把黑屏等待换成带反馈的进度。我自己接入后，第一感受不是快了，是"不慌了"。

## 为什么不等整段生成完

非流式下，你得等模型把 function.name 和整个 arguments 的 JSON 全吐完，才拿到一个完整的 tool_call。参数越长等得越久：一个带十来个字段的 search 调用，从首 token 到可用之间能差好几秒，用户只能对着转圈干等。

流式的价值不在"总耗时变短"——模型该生成多久还是多久——而在"反馈提前"。name 一到手，你就能在界面上显示"正在查天气…"，让用户知道它在动，而不是猜它是不是死了。

这在语音 Agent、长参数调用、多步工具链里尤其明显。一条链里每步都黑屏三秒，五步就是十五秒的沉默；把每步的意图提前亮出来，体感完全是两种产品。

还有个常被忽略的点：流式不额外收费。你拿到的 token 数量、花的钱和非流式一模一样，区别只是"分几次给你"。换句话说这是一笔几乎零成本的体验升级，没理由不做——前提是你的累加逻辑别写错。

## delta 是怎么拼起来的

流式返回里，工具调用不是一次给全，而是切成一串 delta。每个 delta 可能只带 name 的一截、或 arguments 字符串的一个片段。你要做的，就是按顺序把这些碎片拼回完整结构。

```python
calls = {}  # index -> {"id", "name", "args"}
for chunk in stream:
    for d in chunk.choices[0].delta.tool_calls or []:
        c = calls.setdefault(d.index, {"id": "", "name": "", "args": ""})
        if d.id:                c["id"]   = d.id
        if d.function.name:     c["name"] = d.function.name
        if d.function.arguments:
            c["args"] += d.function.arguments   # 纯字符串片段，持续追加
# 流结束后再统一解析
for c in calls.values():
    args = json.loads(c["args"])
```

关键点：name 通常在头一两个 delta 里就给全，arguments 则是纯字符串片段持续追加——它在流完之前几乎一定不是合法 JSON。所以拼接用 `+=`，而 `json.loads` 只在最后做一次。中途去解析半截字符串，基本只会收获一堆异常。

进阶一点，你可以边拼边用"宽容解析"预判进度：把当前已拼的字符串补上缺的括号和引号，尝试解析出已经完整的字段。拿到 `query` 字段了就先高亮它，`limit` 还没来就留空。这层只用来驱动 UI，真正的 `json.loads` 仍然等流完那一刻，两者别混为一谈。

## 并行调用：按 index 分桶

模型可以在一次回复里发起多个工具调用，比如同时查天气和查航班。这些调用的 delta 会交错着流出来，靠 `d.index` 区分它属于哪一个。千万别假设只有一个，否则两个调用的参数会被拼成一坨烂字符串。

上面代码里的 `setdefault(d.index, …)` 就是在干这件事：每个 index 一个独立的桶，各拼各的。等流结束，你手里是一个 `{0: …, 1: …}` 的字典，挨个解析再并发执行，这才是并行工具调用真正落地的样子。

还要留意 index 不保证从 0 连续递增，也不保证按顺序到齐。你可能先收到 index=1 的几个片段，中间夹着 index=0 的，再回到 1。用字典按 index 索引而不是用列表下标顺序 append，就是为了扛住这种交错，别图省事用数组。

## 文字和工具调用会混在同一条流里

真实的流里不只有工具调用。模型可能先说一句"我来帮你查一下"，再发起 tool_call，调用完又接着说话。这些内容在同一条 stream 里按 `delta.content`（自然语言）和 `delta.tool_calls`（工具调用）两个字段交替出现。

所以你的循环得同时路由两类 delta：有 content 就往回复文本里追加、实时渲染；有 tool_calls 就进累加器。把这两件事混在一起处理，很容易出现"文字吞了"或"工具参数串进正文"的 bug，各走各的通道最省心。

## 什么时候才能真正开火

默认规则只有一条：等 finish_reason 变成 tool_calls、确认 arguments 是合法 JSON，再执行。想要更早的反馈，可以用容错解析器（比如 partial-json）把已经完整的字段先抠出来更新 UI——但这只限只读和展示类。

| 操作类型 | 参数流动中能做的事 | 必须等参数完整 |
|---------|------------------|--------------|
| 只读查询 | 预热连接 / 显示"查询中" | 真正发起请求 |
| 写操作（下单、删库） | 什么都别做 | 执行 |
| 生成草稿展示 | 边流边渲染预览 | 定稿提交 |

记住这条红线：任何有副作用的操作——下单、删库、发消息——绝不能在参数流完之前执行。流到一半的 `{"amount": 10` 下一截可能是 `00`，你按 10 下单就出事了。早反馈可以，早动手不行。

有个折中技巧：参数刚够解析出工具名和"操作对象"这类稳定字段时，先弹一个确认框让人预览——"准备给账户 X 转账，金额确认中…"。等参数流完、金额落定，用户一点确认再真正执行。既抢了反馈，又把危险动作卡在人工闸门后，两头都顾到了。

## 不同厂商的流式格式有小坑

OpenAI 系把工具调用放在 `delta.tool_calls` 里、带 index；Anthropic 的流式是事件流，`content_block_start` 先给工具的 name 和 id，后续 `input_json_delta` 事件一截截吐 partial_json，你同样是拼字符串。

换句话说两家"概念一致、字段不同"：都是先给元信息、再流参数片段。接入层把这层差异抽象成统一的 `{index, name, args}` 累加器，上层逻辑就不用关心流到底是谁家的了。哪天换模型、或者同时接两家做容灾，改动都锁在这一层，上面的状态机一行都不用动。

## 把累加器做成一个小状态机

当文字、工具调用、结束信号都挤在一条流里，散着用 if 判断很快就乱成一团。更稳的做法是把整条流建模成状态机：idle → 收文字 → 收工具参数 → 等结束，每个 delta 驱动一次状态转移，逻辑一下就清晰了。

状态机真正的好处是异常有地方落。断流了，你能一眼看出当前卡在"收工具参数"态，于是干净地丢弃这个半成品、给用户一句"刚那步没完成，要重试吗"，而不是让半截 JSON 悄悄漏进下游、在三步之后才以一个莫名其妙的报错爆出来。

## 一个真实场景串起来

用户说"帮我把这周三笔最大的订单导出成表格"。流一开，content 先吐出"正在查订单…"，界面立刻有了反馈；紧接着 tool_calls 的 index=0 流出 query_orders 的参数，你显示"查询中"；参数流完、执行、把结果塞回模型。

模型第二轮又发起调用，参数里带着刚查到的订单号，你显示"正在生成表格"，等流完才真正写文件。整个过程用户看着它一步步往前推，而不是盯着一个转圈图标干等三十秒——这就是流式工具调用最朴素、也最值钱的地方。

## 踩坑清单

- 别假设只有一个 tool_call：永远按 `d.index` 分桶累加
- arguments 流完前基本是非法 JSON，中途别 `json.loads`
- 片段可能是空串，拼接前判断真值即可，别让它炸错
- 副作用操作只在 finish_reason=tool_calls 确认后开火
- 断流 / 超时要能丢弃半截的 calls 重来，别拿残参硬跑
- content 和 tool_calls 分两条通道处理，别让工具参数串进正文
- index 可能交错、不连续，用字典按 index 索引，别用数组下标顺序 append
- 调试时把每个 raw delta 原样打出来，分片规律往往和你以为的不一样

说到底，流式工具调用不是什么高深技术，难点全在"分片拼接"和"开火时机"这两处细节上翻车。把累加器写稳、把危险动作卡在流完之后，剩下的就是白捡的体验红利。

一句话：流式工具调用让你"早知道、晚动手"——反馈尽量提前，副作用尽量压后。
