你有没有见过这种场景:Agent 跑了二十几步,日志刷得飞快,你满心期待它快收工了,结果一看,它在第 5 步到第 8 步之间来回打转,同一个搜索关键词查了六遍,每次都拿到一样的空结果,却毫不知情地继续下一轮。token 在烧,时间在走,任务原地踏步。这不是崩溃,是比崩溃更隐蔽的空转。

## 为什么 Agent 会掉进循环

根子在于 LLM 每一步只看当前上下文做局部决策,它没有一个天然的"我刚才试过这个"的全局记忆感。工具返回的错误信息如果一字没变,模型就极度倾向于重复上一次的动作——因为在它眼里,状态看起来和上次一模一样,那当然选一样的解法,人类换成同样的信息也容易犯同样的错。

上下文窗口一旦被压缩或截断,情况更糟。模型"忘了"自己三步前试过什么,于是兴致勃勃地又试一遍。你以为它在推进,其实它在鬼打墙。更麻烦的是,有些框架为了省 token 会把工具返回的长结果做摘要,摘要一旦把"查无结果"和"结果为空"抹成同一句话,模型就更分不清自己到底进展到哪了。

这类失败最讨厌的地方是没有信号。它不抛异常、不返回红字、不触发告警,监控面板一片绿油油,任务状态永远停在"运行中"。真正在流血的是账单、是延迟、是用户那头转了两分钟还没等到结果的耐心。所以死循环不是"要不要处理"的问题,是"必须主动去抓"的问题。

## 三种典型的循环模式

不是所有循环都长一个样。识别之前,先分清它们的形态,才好对症下药:

| 模式 | 表现 | 常见诱因 |
| --- | --- | --- |
| 完全重复 | 同一工具 + 同一参数反复调 | 工具返回空/报错,模型没换策略 |
| 参数微调抖动 | 同工具,参数在几个值之间来回切 | 模型在猜正确参数,始终没命中 |
| 双工具乒乓 | A 调完触发 B,B 又触发 A | 两步互相依赖,状态从没真正推进 |

完全重复最好抓,签名一致就报警。参数抖动要靠归一化后统计频次,因为每次参数都略有不同,单纯比"上一次是不是一样"根本发现不了。乒乓最阴险,单看每个工具都"没重复",得把最近几步当成一个整体序列来看,发现它在两个动作之间画圈,才算真正识别出来。

实战里这三种常常混着出现。比如一个查资料的 Agent,先在 `search` 上参数抖动几轮,拿不到有用结果,又开始 `search` 和 `fetch_page` 之间乒乓,最后彻底躺平成完全重复。所以检测器不能只认一种模式,得几层判断叠着上。

## 检测手段:签名 + 滑动窗口

核心思路很简单:给每次工具调用算一个签名 `hash(tool_name + 归一化参数)`,维护一个最近 N 步的窗口,某个签名在窗口里出现次数超过阈值,就判定为循环。归一化是关键——键的顺序、多余空格、大小写差异都会让"其实一样"的调用算出不同 hash,造成漏判,前功尽弃。

```python
from collections import deque
import hashlib, json

class LoopGuard:
    def __init__(self, window=8, max_repeat=3):
        self.history = deque(maxlen=window)
        self.max_repeat = max_repeat

    def _sig(self, tool, args):
        # 参数归一化后再 hash,避免键顺序/空格造成误判
        norm = json.dumps(args, sort_keys=True, ensure_ascii=False)
        return hashlib.md5(f"{tool}:{norm}".encode()).hexdigest()

    def check(self, tool, args):
        sig = self._sig(tool, args)
        self.history.append(sig)
        if self.history.count(sig) >= self.max_repeat:
            raise LoopDetected(tool, args)   # 打断,交给上层处理
```

窗口大小和阈值要按任务调,不能一套参数走天下。检索类任务重复率天然高,窗口可以开大、阈值放宽;写文件、下订单、发消息这种带副作用的动作,重复两次就该警觉,因为它每错一次都可能在真实世界里留下痕迹。乒乓型循环则再加一层:把最近几步的签名序列本身当作模式去匹配,发现 ABAB 这种交替结构就打断。

这个 guard 放在哪一层也有讲究。最好放在 orchestrator 里、每次真正执行工具之前拦一道,而不是塞进某个具体工具内部——工具内部只看得见自己被调了几次,看不见全局的调用序列,更抓不到跨工具的乒乓。放在中枢,才有完整的上帝视角。

还有一个容易走偏的地方必须在检测层就想清楚:重试不等于循环。一个健壮的 Agent 本来就会重试——网络抖了一下、工具限流返回 429、临时超时,隔几秒用同样参数再调一次,这是对的,不该被打断。如果 guard 一刀切地把所有重复都当循环,你会把系统的容错能力也一起砍掉,反而更脆,治好了空转却治出了误杀。

分界线在于"结果有没有变化、状态有没有推进"。同样的调用,上一次超时、这一次拿到了数据,那是重试成功,健康;连续三次都返回一模一样的空结果或同一句报错,那才是循环,必须干预。所以更聪明的 guard 不只比调用签名,还比返回值的签名:参数一样、结果也一样,才算真正的原地打转。

落地时可以给重试留个白名单——对已知的瞬时错误(超时、限流、5xx)放宽阈值,允许它多试几次并配合指数退避;对"参数错误""查无此项"这类确定性失败则收紧,一旦重复立刻打断,因为再试一百次结果也不会变。区分清楚这两类,既保住容错,又不纵容空转,这是检测器好不好用的分水岭。

## 打断之后,别只是抛异常

检测到循环只是第一步,更重要的是给模型一条出路,否则你只是把死循环换成了硬报错,任务照样死。最有效的做法是往对话里注入一条明确的反馈:"你已经用相同参数调用 `search` 三次且结果一致,请换一种策略或换一批参数,不要重复上一步。" 把这句话当成新的上下文喂回去,模型往往就能自己跳出来。

反馈要具体,别只说"你在循环"。告诉它重复了哪个工具、用了什么参数、结果为什么一样,信息越具体,模型纠偏越准;含糊的一句"请不要重复"往往换来的是它换个说法接着重复。你甚至可以在反馈里给出建议方向,比如"上一批关键词太宽,试试更具体的词",相当于顺手扶它一把,而不是只把它拦下来。如果连续几次注入提示仍不奏效,就该升级:要么把控制权交回给人(human-in-the-loop),让人来判断下一步;要么直接中止并返回已有的部分结果,总比无限空转烧钱强。记住一条原则——检测负责发现,反馈负责纠偏,熔断负责兜底,三层缺一不可。

## 踩坑清单

- 只比工具名不比参数:两次调用参数完全不同也被误判为循环,阈值形同虚设。
- 参数不归一化:`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 算成两个 hash,该抓的没抓到。
- 窗口太小:长任务里正常的周期性调用被误伤,Agent 动不动就被打断。
- 检测到就直接 raise:没给模型反馈,循环变报错,任务同样收不了尾。
- 忽略乒乓型:单工具视角永远发现不了两个动作互相画圈,必须看序列。
- guard 放进工具内部:看不到全局调用链,跨工具循环一个都抓不住。

一句话收尾:Agent 最危险的失败往往不是报错退出,而是笑呵呵地原地转圈——你要做的,是在它转到第三圈之前拍它一下,并且清清楚楚告诉它,该往哪走。
