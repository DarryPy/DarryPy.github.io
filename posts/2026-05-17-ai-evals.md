## 为什么 Eval 是 AI 工程的核心

传统软件 = 输入 + 程序 → 确定性输出，单元测试就够。
AI 应用 = 输入 + 模型 → 概率输出，**单元测试根本检查不出来**。

模型升级了？回归了吗？
Prompt 改了？整体效果上去了还是下来了？
新功能上线？真比旧版本好吗？

**没有 eval = 在闭眼调参**。每次改动都是赌博。

## Eval 的三个层次

### 1. 单元 Eval（针对单个 prompt / 单个工具）

最便宜、最高频。例子：

- 一个分类 prompt 输入 100 条标注数据，看 accuracy
- 一个抽取 prompt 拿 20 个 case，看字段 F1
- 一个工具 schema 改了，看 LLM 还能不能正确调用

工具：直接 Python 脚本就够，不用上 framework。

### 2. 组件 Eval（针对一个 chain / 一个 RAG pipeline）

中等成本。例子：

- RAG 系统：给定 50 个问题 + 标准答案，测召回率（top-K 中是否包含正确文档）+ 回答准确性
- Agent 链：给定任务，测完成率 / 步骤数 / 成本

工具：Ragas（专测 RAG）/ Phoenix / LangSmith / 自建 framework。

### 3. End-to-End Eval（针对完整产品）

最贵、频率最低。例子：

- 上线前跑 500 条线上历史 case，看用户满意度（人评 or LLM-as-judge）
- A/B 测两个版本，看转化率

工具：人工评 + LLM-as-judge 混合。

## LLM-as-Judge：让 AI 评 AI

**用一个强模型评估另一个模型的输出**。最常见模式：

```
[判官 prompt]
你是一个严格的评估官。给定问题、参考答案、候选答案，
给候选答案打分 1-5，说明扣分原因。
不要在意候选答案是否冗长，只看是否准确、完整、相关。

问题：{question}
参考答案：{reference}
候选答案：{candidate}

输出 JSON: {"score": 1-5, "reason": "..."}
```

注意事项：

- **判官要用更强的模型**：用 Opus 评 Sonnet 输出，不要反过来
- **判官 prompt 要有评分细则**：1 分是什么 / 5 分是什么，不要让它自由发挥
- **位置偏差**：如果让判官对比 A 和 B，A 总在前面，结果会偏向 A —— 要随机化顺序
- **校准**：自己拿 50 条样本人评一遍，跟 LLM-as-judge 对比，看一致性
- **打分用整数**：浮点分数（4.7 / 4.3）噪声大，整数更稳定

## 黄金数据集（Golden Dataset）

eval 的基础是一份**人工标注好的 input → expected output** 数据集。

工程实践：

1. 从线上日志里**随机采样 200-500 条真实输入**
2. 让产品 / 业务 / 自己标注期望输出
3. 标注时**多人交叉**，分歧大的 case 单独讨论达成共识
4. 数据集**版本化**：随业务演进周期性更新

没有这份数据集，eval 就是空中楼阁。

## 维度别只看一个

不同任务关注不同维度：

| 任务类型 | 核心指标 |
|---|---|
| 分类 | accuracy / F1 / precision / recall |
| 抽取 | 字段级 F1（每个字段单独算） |
| 问答 / 对话 | 准确性 / 相关性 / 完整性（多维 LLM-as-judge） |
| RAG | retrieval hit rate / answer faithfulness（是否基于检索片段）/ context precision |
| Agent | 任务完成率 / 步骤数 / 工具调用成功率 / 成本 |
| 安全 | refusal rate（该拒的有没有拒）/ leak rate（不该说的有没有说） |

## 持续 Eval：CI 跑、看面板、加门禁

一次 eval 没意义，要做成**像单元测试一样跑**：

- 每次 PR 改 prompt → 自动跑 eval → 看核心指标变化
- 每天/每周 scheduled run，监控线上数据采样的实时指标
- 关键 PR 设门禁：accuracy 不能跌 > 2%

工具上 LangSmith / Phoenix 这种已经做得很顺手，但自己写也不复杂——本质就是"读数据集 → 调模型 → 算指标 → 写报告"。

## 常见反模式

1. **只看"看起来不错的几个 case"** — sample size 太小，统计不显著
2. **只跑成功 case** — 失败 case 才告诉你模型边界
3. **eval 跟生产用不同的 prompt** — 测的不是真东西
4. **LLM-as-judge 用更弱的模型** — 测出来都是假的
5. **没标准答案就开始评** — 没基线就没法比较

## 一个朴素总结

> AI 工程的核心 = eval > prompt > 模型选择 > 其他

eval 跑通了，你才知道**改动是变好还是变坏**。
没 eval 之前，所有"我觉得这版更好"都是错觉。

先建 eval，再开始迭代。
