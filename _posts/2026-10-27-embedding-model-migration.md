## 为什么换 embedding 必须全量重嵌入

你会动 embedding 模型通常是三个原因:新模型召回更准、支持多语言或更长输入、或者单价更便宜能省一大笔推理钱。动机都很硬,但代价常被低估——换模型不是改配置,而是把整个向量库推倒重建。

关键在于不同模型的向量空间互不兼容。维度可能从 1024 变成 1536,即便维度相同,语义方向和相似度分布也完全不是一回事。你把新 query 向量丢进旧库检索,算出来的余弦距离数值上"看着正常",却毫无语义意义,召回会悄悄崩掉。还有个隐蔽差异是归一化:有的模型输出已归一化向量、有的没有,距离度量该用 cosine 还是 dot 也得跟着新模型重新定,配错一样是静默翻车。

这种"静默失败"最坑人。系统不会抛异常,接口照常返回十条结果,只是全是噪声。等你从用户投诉里发现时,脏数据已经跑了好几天。所以换模型第一条铁律:新旧向量绝不能混用,必须整库过一遍新模型重嵌入。

很多团队栽在"以为能平滑热更新"上。索引热更新只处理新增文档的增量写入,前提是模型不变;换模型属于底层向量空间迁移,是两件事。把它们分清楚,是迁移方案能不能落地的第一步。

## 双索引并行:影子写入与灰度切换

零停机的核心是双索引:旧索引继续扛线上检索,新索引在旁边悄悄建,索引名里带上模型版本标签(如 docs_v2_bge)方便区分和回退。代价是迁移期间存储和写入翻倍,这笔账要提前算进预算。

写入侧做"影子写入"——每条新文档同时写旧库(旧模型向量)和新库(新模型向量)。这保证切换那天新库没有数据缺口,不会出现"切过去才发现最近三天的文档没进新库"。务必把所有写入路径都接上,漏一条就是隐患。

读取侧用一个开关控制流量比例。初期 100% 读旧库,新库只接影子读(检索但不返回给用户,只打日志做对比)。等回填完、指标达标,再按 5% → 50% → 100% 灰度放量。任何一档发现召回掉点,立刻把开关拨回旧库,用户全程无感。

```python
def retrieve(query, rollout=0.0):
    # 影子读:新库永远查一次,只记录不返回
    new_hits = new_index.search(embed_new(query), k=10)
    log_shadow(query, new_hits)
    if random() < rollout:          # 灰度比例命中 → 走新库
        return new_hits
    return old_index.search(embed_old(query), k=10)
```

这段逻辑的要害是 embed 函数和索引版本必须绑死:查旧库就用 embed_old,查新库就用 embed_new,一旦交叉就是前面说的静默崩溃。把版本封装成一个对象统一管理,别让它散落在代码各处。

## 回填(backfill)怎么做到不打爆线上

全量重嵌入是迁移里最贵的一步:几百万条文档逐条调 embedding API,既烧钱又占带宽。你要把它当成离线批处理,而不是跟在线检索抢资源的在线任务,最好单独跑在一组隔离的 worker 上。

- 分批:按 1000 条一批拉取,批内并发调 API、批间 sleep 控制 QPS,别把 embedding 服务打到限流
- 断点:每批写完记录游标 last_id 到持久存储,中途挂了从游标续跑,绝不从头浪费已花的 token
- 幂等:重嵌入按文档 id 覆盖写,重复跑同一批不产生脏数据,这样失败重试才安全
- 对账:回填结束比对新旧库文档数,数量不一致说明有漏嵌,按 id diff 定位缺口再补齐
- 成本:先拿 10 万条小样本估算总 token 和费用,提前报预算,别到月底被账单吓一跳

还有个提速技巧:按文档热度排序回填,先嵌入高频被检索的文档。这样即便回填只跑了一半,新库也已经覆盖大部分真实流量,灰度可以提前启动,不必干等全量跑完才敢放量。

## 切换验证:用线上流量做影子对比

别只看离线评测集就敢上线,离线集永远覆盖不全真实用户的刁钻问法。最有效的验证是拿真实线上 query 做影子对比:同一批 query 同时查新旧库,统计两边 top-k 的重叠率、点击位次变化和无结果率。

| 指标 | 旧库基线 | 新库影子 | 判断 |
|---|---|---|---|
| Recall@10 | 0.72 | 0.81 | 新库更优 |
| 无结果率 | 4.1% | 2.3% | 新库更优 |
| P99 延迟 | 80ms | 95ms | 可接受 |
| top3 重叠 | — | 38% | 差异大需抽检 |

重叠率低不一定是坏事——可能是新模型召回了旧库漏掉的好结果。但差异这么大时必须人工抽检一批样本,确认是"更准"而非"跑偏",再往上放量,否则你是在拿线上用户做赌注。

更稳的做法是把指标拆到查询分段看:长尾 query、多语言 query、短 query 往往是新模型收益或翻车最明显的地方。整体 Recall 涨了、某个分段却崩了,这种局部回退只有分段统计才抓得到。

另外给灰度配一道自动护栏:当新库某档的无结果率或 P99 延迟越过阈值,自动回退并告警,别指望人盯着看板。半夜放量出事,自动回退能帮你把损失摁在几分钟内,而不是等早上上班才发现。

## 迁移分几步走:一次只动一个变量

迁移时你会很想"顺便"把 chunk 切小、把 metadata 补全、把 reranker 也换掉。千万别。一次改多个变量,新库指标涨了或跌了你都说不清是谁的功劳,翻车时更无从排查,整个迁移会变成一笔糊涂账。

严格做法是:重嵌入期间保持切分策略、metadata 字段、reranker 和 top-k 全部不变,唯一变量就是 embedding 模型本身。这不仅是方法论洁癖,更是回滚前提——只动一处,出事能精准定位并干净回退;一把梭改五处,回退等于把五个改动全推倒。

在"只动一个变量"的前提下,把迁移拆成清晰阶段、每阶段有明确的进入和退出条件,比"一股脑切过去"稳得多,也方便向上同步进度:

1. 准备:建带版本标签的新索引,确认维度与 schema,打通影子写入的双写路径
2. 回填:离线批量重嵌入存量文档,按热度排序,持续对账直到新旧文档数一致
3. 影子:100% 影子读,积累几天线上 query 对比数据,按分段逐项核对指标
4. 灰度:5% → 50% → 100% 逐档放量,每档观察一到两天,护栏自动兜底回退
5. 收尾:全量稳定运行满一个灰度周期后,再下线旧索引与旧 embed 代码路径

每一步都能回退到上一步,这是零停机的底气。别跳步,尤其别跳过影子阶段直接灰度——影子是你唯一一次"不影响真实用户又能看到真实效果"的机会,跳过它等于蒙眼放量。

## 踩坑清单

- 维度变了忘改索引 schema,写入直接报错——建新索引前先确认 dim 对齐
- 影子写入漏接某条写入路径,切换后新库少数据,表现为偶发性无结果
- 回填期间 embedding API 限流,无脑重试引发风暴把费用翻倍——务必带指数退避
- query 侧还用旧模型 embed、库却是新的,检索全乱——embed 函数必须和索引版本绑死
- 切完立刻删旧库,回退无路可走——至少留一个完整灰度周期确认稳定再下线
- 迁移期双倍存储没报预算,中途被容量告警打断——存储账要和 token 账一起算

一句话:换 embedding 从来不是换配置,而是一次有影子写入、有回填对账、有灰度回退的数据迁移工程。把旧库留到你真正确信新库稳了那天,再动手关掉它。
