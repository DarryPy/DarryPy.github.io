你一定见过这种投诉：用户让模型写一份三千字的方案，写到一半地铁进隧道，网络一断，页面上只剩半截文字。重新进来一看，要么内容全没了，要么只能点“重新生成”，再等一分钟、再花一次 token。对用户来说这是体验事故，对你来说是实打实的成本浪费。

问题的根源很简单：大多数实现把“模型在生成”和“浏览器在接收”绑在同一条 HTTP 连接上。连接一断，后端协程被取消，上游请求跟着中止，已经生成的内容只存在于那条死掉的连接里。断线续传要做的，就是把这两件事拆开。

## 先把生成和连接拆开

核心思路是引入一个中间层：生成任务独立运行，把每个 token 片段写进一条带序号的事件流；浏览器的 SSE 连接只是这条流的一个读者。连接断了，读者没了，但写者还在继续写，内容一个字都不会丢。

我在项目里一般这样分工：接口收到请求后先创建一个 `run_id`，把生成任务丢给后台 worker，立刻返回。前端再用 `run_id` 去订阅事件流。worker 从上游 LLM 读到一个 chunk，就追加一条事件，事件里带上递增的序号和内容。

这里有个容易忽略的前提：worker 必须是真正独立的执行单元，不能只是请求处理协程里 spawn 出来的子任务。否则实例滚动发布时，正在生成的任务跟着进程一起被杀，续传依然无从谈起。我通常用独立的任务队列承载，并把任务状态单独记一份。

这样做还有个附带好处：同一个 `run_id` 可以被多个读者同时订阅。用户在手机上发起、在电脑上打开，两边看到的是同一份实时输出，而不是两次独立生成。客服后台想旁观也只是多挂一个读者。

## 用 Redis Stream 落地事件流

事件流的存储有很多选择，下面这张表是我对比过的几种方案，大多数团队用 Redis Stream 就够了。

| 方案 | 续传能力 | 多实例支持 | 运维成本 | 适合场景 |
| --- | --- | --- | --- | --- |
| 进程内内存 buffer | 只能续同一实例 | 差，需要粘性会话 | 低 | 单机原型 |
| Redis Stream | 按 ID 精确续读 | 好 | 中 | 大多数线上应用 |
| Redis Pub/Sub | 不能回放历史 | 好 | 低 | 只要实时、不要续传 |
| 数据库逐条写入 | 可以，但写放大严重 | 好 | 高 | 强审计要求 |
| Kafka / NATS JetStream | 很强 | 很好 | 高 | 已有消息平台的大厂 |

选型时别只看功能，还要估算写入量。一次长回答可能有上千个 chunk，如果每个 chunk 都单独写一条，Redis 的 QPS 会被放大好几倍。我的做法是在 worker 里按 50 毫秒或 20 个字合并一次再写，用户几乎感觉不到延迟，写入量却能降一个数量级。

Pub/Sub 是最容易踩的坑：它看起来也能推实时消息，但断线期间发出的消息直接丢掉，根本做不了续传。Redis Stream 自带递增 ID 和按 ID 读取，天然就是为这种场景准备的。

下面是一个精简的实现，worker 负责写，SSE 接口负责读，序号直接复用 Redis Stream 的消息 ID：

```python
import json
import redis.asyncio as redis

r = redis.Redis()
TTL_SECONDS = 3600

def stream_key(run_id: str) -> str:
    return "llm:run:" + run_id

async def produce(run_id: str, llm_stream):
    key = stream_key(run_id)
    try:
        async for chunk in llm_stream:
            await r.xadd(key, {"type": "delta", "text": chunk})
        await r.xadd(key, {"type": "done"})
    except Exception as e:
        await r.xadd(key, {"type": "error", "msg": str(e)})
    finally:
        await r.expire(key, TTL_SECONDS)

async def consume(run_id: str, last_event_id: str = "0-0"):
    key = stream_key(run_id)
    cursor = last_event_id
    while True:
        items = await r.xread({key: cursor}, block=15000, count=100)
        if not items:
            yield ": ping\n\n"
            continue
        for msg_id, fields in items[0][1]:
            cursor = msg_id.decode()
            data = {k.decode(): v.decode() for k, v in fields.items()}
            yield f"id: {cursor}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"
            if data["type"] in ("done", "error", "cancelled"):
                return
```

注意 `produce` 里无论成功还是异常，最后都会写一条终止事件并设置过期时间。这一点非常关键：读者完全依赖终止事件来判断何时关闭连接，如果 worker 异常退出却没写，前端就会一直转圈等待，用户只能手动刷新，而刷新之后看到的还是同样的转圈。

## 让浏览器带着断点回来

SSE 协议本身就为续传留了口子：服务端每条事件带上 `id`，浏览器原生的 EventSource 断线重连时会自动在请求头里带上 `Last-Event-ID`。你的接口只要读这个头，把它传给 `consume` 作为起始游标，就能从断点接着推。

但页面刷新不一样，EventSource 对象没了，浏览器不会替你记住断点。所以前端要自己把 `run_id` 和最后收到的事件 ID 存进 localStorage，页面加载时检查有没有未完成的任务，有就带着参数重新订阅，并把之前已渲染的文本先恢复出来。

续读时还要防重复渲染。前端收到事件后先比较 ID，只有比本地记录的游标更新才追加到页面，旧的直接丢弃。这一步看似多余，但在网络抖动、重连和刷新交错发生时，它能保证用户看到的文本始终连续、不重复，也不会出现中间缺一段的情况。

还有一个细节：如果你用 fetch 加 ReadableStream 而不是 EventSource，就没有自动重连，需要自己实现退避重试并手动带上游标。另外记得每隔十几秒发一个注释行心跳，否则中间的 Nginx 或负载均衡会把空闲连接当成死连接掐掉。

移动端还要多考虑一层：应用切到后台后系统可能直接冻结网络连接，回到前台时连接看似还在，实际早已失效。我的经验是监听页面可见性变化，一旦从后台回来就主动关掉旧连接，带着游标重新订阅一次，比等待超时自动重连要快得多，用户几乎察觉不到中断。

## 生命周期：取消、过期和计费

解耦之后，“用户关掉页面”不再等于“停止生成”，这是双刃剑。你需要一个显式的取消接口：用户点“停止”时写一个取消标记，worker 每读一个 chunk 检查一次，发现标记就中止上游请求，再往流里写一条 `cancelled` 事件收尾。

过期策略也要想清楚。事件流不能永久保留，我一般在任务结束后设一小时 TTL，最终全文另外落库到会话表里。如果用户隔天回来，直接从数据库读完整结果，而不是回放事件流。没结束的任务也要有最长运行时间，防止 worker 卡死后流一直挂着。

多实例部署时还要注意：取消标记和事件流一样放在 Redis 里，而不是进程内存。因为用户点停止的请求可能落在实例甲，真正跑生成的 worker 却在实例乙，只有共享存储里的标记才能被对方看到。检查频率不用太高，每个 chunk 查一次已经足够及时。

计费反而变简单了：token 用量只在 worker 侧统计一次，不管前端重连多少次、多少个读者在看，都不会重复扣费。顺手把用量写进 `done` 事件里，前端就能在结束时展示本次消耗，对账也有了统一出处。

## 踩坑清单

- 用 Pub/Sub 代替 Stream：断线期间的消息全丢，续传无从谈起。
- 忘了给 key 设 TTL：每个请求一条流，几天就能把 Redis 内存撑爆。
- 前端没做去重：重连时游标处理不当，同一段文字被渲染两遍。
- 只靠 EventSource 自动重连：页面刷新后断点就没了，必须自己持久化游标。
- 没有心跳：代理层空闲超时一到，长时间思考的推理模型连接必断。
- 取消只断开连接：worker 还在后台跑，用户以为停了，账单照样在涨。
- 每个 token 写一次库：写放大严重，先进 Stream，结束后再一次性落库。

最后提醒一句，上线前一定要专门测试三种场景：生成中途断网再恢复、生成中途刷新页面、生成结束后很久才回来。这三种场景都跑通了，你的续传才算真正可用，否则它只是一个在演示环境里好看的功能。

一句话总结：连接是脆弱的，生成是昂贵的，别让脆弱的东西决定昂贵的东西的生死。
