你有没有碰到过这种场景：一道再简单不过的常识题，模型张口就给一个自信满满的错误答案。问它"高尔夫球的目标是不是尽量多打几杆才算赢"，它很可能一本正经地点头称是。不是模型笨，而是它在没有任何铺垫的情况下，直接把注意力压到了最终答案上，跳过了"关于这个话题我到底知道哪些事实"这一层。Generated Knowledge Prompting 的解法很朴素：先让模型把相关知识吐出来，摆在台面上，再拿这些知识回头去作答。一拆为二，很多离谱错误当场就消失。

## 为什么模型会在常识题上栽跟头

一步到位的 prompt 其实在逼模型同时扛两件事：既要从参数里回忆相关背景，又要立刻拍板下结论。这两个子任务抢的是同一份注意力预算。模型天然倾向走捷径，根据问题表面的高频词先给一个"看起来对"的答案，而把真正相关的事实埋在深处没调出来。于是你看到的，就是逻辑链缺失、语气却笃定的典型幻觉。

更麻烦的是，常识题往往没有外部知识库可查——答案本就该在模型脑子里。这类题目用 RAG 没抓手，因为你根本不知道该去检索什么；用普通 few-shot 又很难把"先回忆"这一步显式逼出来。Generated Knowledge 正好卡在这个缝隙里：它不引入任何外部数据，只是改变模型调用自身知识的顺序，先摊开，再判断。

拿那道高尔夫题走一遍你就懂了。直接问，模型容易被"多打几杆"里的"多"带偏。但如果先让它写知识，它大概率会吐出"高尔夫以最少杆数完成球洞为目标""杆数越少成绩越好"这类事实。有了这两条摆在眼前，第二步再问它赢的条件，答案几乎不可能反着来。知识这一摊，相当于把隐性记忆逼成了显性上下文。

值得一提的是，这招在中等规模模型上收益往往最大。超大模型很多时候一步就能隐式完成回忆与推理，显式生成知识的边际提升有限；而太小的模型连生成出来的知识都错得离谱，拆开反而放大错误。所以别照搬论文里那串漂亮的增益数字，先在你实际要用的那一档模型上做个对照，才知道这笔调用成本花得值不值。

## 核心就两步：先补课，再答题

第一步叫知识生成。给模型几个"问题 → 知识"的示例，让它针对当前问题生成若干条相关陈述。注意这些陈述只负责铺事实，要在指令里明确禁止它提前给答案，否则解耦就失效了。第二步叫知识整合：把上一步生成的知识拼回原问题，作为上下文，再问一次最终结论。

关键全在"解耦"二字。生成知识时，模型的全部注意力放在"关于这个话题我知道什么"；作答时，注意力又集中到"基于这些既定事实，该怎么选"。每个子任务单独看都更简单、更聚焦，错误率自然比硬闯一步低。附带的好处是可解释性：你能把第一步的产物打印出来人工审一眼，出了错也知道是知识错了还是推理错了。

示例怎么挑也有讲究。最好选和目标问题同类型、但内容不相干的例子，让模型学到的是"生成相关知识"这个动作本身，而不是照抄例子里的具体事实。两三个示例通常就够，给太多反而会让模型倾向于模仿示例的措辞和范围，把知识的多样性框死，这和你想要的"尽量铺全"正好相反。

## 一个能跑的最小实现

两段调用，温度策略故意不同：生成知识时调高一点求覆盖面，作答时归零求可复现。

```python
def generate_knowledge(question, k=5):
    prompt = f"""为下面的问题生成 {k} 条相关事实，每条一行，只写事实不要给答案。
示例
问题：企鹅会飞吗？
知识：企鹅是鸟类；企鹅的翅膀演化成了鳍状肢；企鹅擅长游泳但不能飞。

问题：{question}
知识："""
    return llm(prompt, temperature=0.7).splitlines()

def answer_with_knowledge(question, knowledge):
    ctx = "\n".join(f"- {k}" for k in knowledge)
    prompt = f"""已知事实：
{ctx}

请只基于以上事实作答，并说明理由。
问题：{question}
答案："""
    return llm(prompt, temperature=0)

ks  = generate_knowledge(q)          # 第一段：温度高一点，让知识更全
ans = answer_with_knowledge(q, ks)   # 第二段：温度归零，让结论可复现
```

想更稳，就把第一段多采样几轮、取并集去重，再喂给第二段——相当于给模型配了份它自己写的小抄。更激进的玩法是让多个不同模型各生成一批知识再合并，用模型间的差异互相补盲区。代价是多出若干次调用和一截 token，所以别无脑套在所有任务上，先拿小样本量一下收益再决定。

## 它和 RAG、Self-Ask 差在哪

三者都想给模型补上下文，但知识来源和适用面完全不同，混用容易帮倒忙：

| 维度 | Generated Knowledge | RAG | Self-Ask |
|------|------|------|------|
| 知识来源 | 模型参数内部 | 外部检索库 | 模型自问自答 |
| 要外部数据吗 | 不要 | 要 | 不要 |
| 擅长场景 | 常识/推理补全 | 事实/时效查询 | 多跳问题分解 |
| 主要风险 | 生成错误知识 | 检索噪声 | 追问链跑偏 |

一句话区分：问的是模型"本来就会、只是懒得想"的常识，用 Generated Knowledge；问的是模型参数里压根没有的最新或专有事实，老老实实上 RAG；问的是需要层层追问才能拆开的多跳问题，走 Self-Ask。三者并不互斥，比如你可以先生成知识、再用它去检索补充，但别指望任何一个单独包打天下。经验上，它对常识推理、科学常识这类"参数里有、却容易被问法带偏"的任务提升最明显；对纯检索类任务基本无感。

## 怎么用好它：质量控制与踩坑清单

它绝不是银弹。最大的风险是生成的知识本身就是错的，错知识喂回去反而放大幻觉，比直接问还糟。所以第二段 prompt 里"只基于以上事实作答"这句话极其关键，它把模型钉在给定材料上推理，而不是又开始凭空发挥。想进一步降风险，可以让模型给每条知识标个可信度，或在作答时标出到底引用了哪几条，方便你回溯。

上线前，拿这份清单逐条过一遍：

- 第一段只许写事实，一旦让它提前下结论，解耦就白做了
- 知识条数别贪多，5 条上下够用，太多反而稀释重点、引入噪声
- 作答段温度务必归零，否则同一批知识也会给出飘忽不定的答案
- 补一句"若事实不足以判断就回答不确定"，挡住模型的强答冲动
- 时效性、专有、私域事实别指望它，那是 RAG 的活，硬用只会编
- 多一次调用就是多一份延迟和成本，务必先用小样本验证收益再铺开

怎么判断它到底有没有用？别只盯着几个挑出来的漂亮 case，搭一个哪怕只有几十条的小评测集，把"直接问"和"生成知识再问"跑同一批题，对比准确率和稳定性。很多时候你会发现它在某一类题上提升明显、在另一类上纹丝不动甚至倒退，这种分化信息远比一个笼统的平均分有用，能帮你决定到底对哪些流量开这个开关。

说到底，Generated Knowledge Prompting 卖的不是什么魔法，而是一个朴素到容易被忽略的道理：别让模型边回忆边表态，先把它知道的东西摊开在桌上，答案往往就躺在里面。
