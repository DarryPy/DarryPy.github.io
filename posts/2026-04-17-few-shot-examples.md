## Few-shot 的核心 ≠ "多塞示例"

很多人以为 few-shot 是"塞越多越好"。
实际上：

- 加 1 个好示例：准确率 +20%
- 加 3 个好示例：+30%
- 加 10 个好示例：可能只 +35%，还可能掉
- 加 1 个差示例：可能 -15%

收益递减很快，且**一个坏示例能把整组带歪**。

## 怎么选示例

### 1. 选有代表性的"边界 case"

❌ 全是"标准成功 case"
✅ 包含：典型成功、边界、易错的反例

```
示例 1：标准成功（80% 的情况）
示例 2：边界情况（少见但合法）
示例 3：易错的反例（标注：错在哪）
```

模型从中学到的不只是"答案样子"，还有"哪里容易出错"。

### 2. 跟当前任务相似度高

如果你做客服分类，示例就用客服对话，不要拿"今天天气"凑数。
相似度可以用 embedding 衡量——存一份"高质量示例池"，运行时用当前 query 检索 top-3 最相似的示例（动态 few-shot）。

### 3. 多样性比数量重要

5 个相似的示例 < 3 个覆盖不同场景的示例。
**示例之间的差异性**才是真正给模型新信息的部分。

## 放在哪

按效果排序：

1. **system prompt 末尾** — 最常用，稳定，可缓存
2. **user prompt 开头** — 动态 few-shot 场景
3. **多轮对话历史** — 用历史成功对话当示例（隐式 few-shot）

❌ 散落在 prompt 各处 — 模型注意力分散

## 格式很重要

明确分隔输入 / 输出：

```
[示例 1]
输入：今天上海天气怎么样？
输出：{"intent": "query_weather", "city": "上海"}

[示例 2]
输入：你叫什么名字？
输出：{"intent": "ask_identity"}

[当前任务]
输入：{用户问题}
输出：
```

模型一看就知道：**末尾我接的是"输出"那行**。
不要乱用空行或自然语言连接，会增加格式漂移。

## 动态 few-shot

最强的玩法：**根据当前 query 检索最相关的示例**。

```python
# 维护一份高质量示例池
example_pool = load_examples()  # 已 embedding

def get_dynamic_examples(query, k=3):
    query_emb = embed(query)
    return top_k_similar(query_emb, example_pool, k)

# 调 LLM 时拼上
prompt = system + get_dynamic_examples(user_query) + user_query
```

对比固定 few-shot，动态版在多样场景下能多涨 5-15% 准确率。
代价是每次多一次 embedding 查询。

## 常见反模式

| 反模式 | 后果 |
|---|---|
| 示例答案不一致风格 | 模型不知道该按谁的样子学 |
| 示例覆盖不到边界 | 边界 case 上崩 |
| 示例太多（>10）| token 浪费 + 准确率收益消失 |
| 示例之间冲突 | 模型选最近的那个，老示例无效 |
| 示例直接 copy 训练数据 | 过拟合到字面，泛化差 |

## 一份选示例的 checklist

发布 prompt 前过一遍：

- [ ] 示例覆盖至少 3 种情况（典型 / 边界 / 反例）？
- [ ] 示例答案风格完全一致？
- [ ] 示例之间没有冲突？
- [ ] 示例总长度 < 1000 tokens？
- [ ] 测试集上准确率比 zero-shot 高 ≥ 10%？

满足前 4 个再上线，第 5 个用 eval 验证。

---

> Few-shot 是教模型"我要的是这种东西"。
> 选示例像挑教科书——精挑细选 3 个，胜过塞 20 个仓促找的。
