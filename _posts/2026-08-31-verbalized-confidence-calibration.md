你有没有遇到过这种情况：模型信誓旦旦给了个答案，语气笃定得像教科书，结果一查全是编的。问题不在它偶尔答错，而在于它从不告诉你"这题我其实没把握"。让 LLM 显性输出置信度 (confidence)，就是把这层不确定性摊到台面上，让下游能据此决定信不信、要不要复核、要不要转人工。

先划一下适用边界，免得你过度设计。闲聊、创意写作这类没有唯一正确答案的场景，置信度意义不大，硬加反而添乱。真正值得上这套的是有明确对错、且答错代价高的场景：知识问答、信息抽取、代码生成、金融和医疗类判断。这些地方一个"看起来对其实错"的答案，可能直接变成线上事故，把不确定性显性化就是给它们上一道保险。

## 为什么模型天生"过度自信"

先说结论：LLM 默认是 overconfident 的。它的训练目标是预测下一个 token，不是校准概率。经过 RLHF 之后更明显——人类标注者偏爱语气肯定的回答，于是模型学会了"把话说满"。所以你直接看它的措辞去判断可信度，基本等于被它的语气牵着走，和真实正确率对不上。

更麻烦的是 token 概率也不等于答案对错的概率。一个 token 的 logprob 高，只说明它在语言层面顺，不代表事实层面它对。尤其经过对齐的模型，输出分布被压得很尖，logprob 普遍偏高，直接拿来当置信度会系统性高估。所以我们需要专门的手段去"问"出把握，再用数据把它掰回准。

举个我踩过的例子。一个问答系统上线时没做任何置信度处理，抽查发现模型对"它压根不知道"的冷门问题，照样能编出一段结构完整、语气自信的回答。用户根本分不清哪句是真哪句是编的，投诉全集中在"看起来很专业但完全错"。这类幻觉最贵，因为它披着可信的外衣。后来我们做的第一件事不是换模型，而是逼它对每个答案报一个把握值——错答不可怕，可怕的是错得理直气壮还没人拦。

## 三种让模型说出把握的写法

同样是要一个置信度，写法不同，成本和可靠性差很多。下面这张表是我在生产里筛下来的对比：

| 方法 | 怎么做 | 优点 | 坑 |
| --- | --- | --- | --- |
| 数值自评 | 让模型给出 0–100 的分数 | 直接、好比较、能设阈值 | 分数扎堆在 80–95，需要后期校准 |
| 语言档位 | 输出"高/中/低"三档 | 稳、不纠结小数点 | 粒度粗，档位含义要在 prompt 里钉死 |
| Token logprob | 读 API 返回的 logprobs | 不占额外推理、客观 | 只反映语言概率，非事实正确率 |
| 采样一致率 | 同题采 N 次看答案分布 | 经验上和正确率最相关 | 成本 ×N，慢 |

数值自评是性价比最高的起点。关键是把输出格式钉死，别让它把分数写进散文里。一个能直接解析的模板长这样：

```text
回答问题，然后单独给出你对答案的置信度。
置信度定义：假设同样的问题问 100 次，你估计有多少次这个答案是对的。
严格按以下 JSON 输出，不要多余文字：
{"answer": "...", "confidence": <0-100 整数>, "why": "一句话说明不确定来源"}
```

加上那句"why"很有用——它逼模型说出不确定的来源（信息不足 / 有歧义 / 超出知识范围），既能提升分数质量，也给你人工复核时一个抓手。经验上，先让模型输出答案和理由、再回头给分，会比一上来就报分数更准，因为它此时已经把推理链摊开，评估有了依据，而不是凭第一印象拍。

语言档位适合不需要精细阈值的场景。你只要在 prompt 里把每档的含义钉死——比如"高=有据可查、中=推断但合理、低=基本在猜"——模型给档位反而比给小数点稳，因为它不用在 87 还是 89 之间纠结。采样一致率则是另一条路：同一道题用略高的温度采样五到十次，看最终答案的聚集程度，答案越集中说明模型越笃定。它和真实正确率的相关性通常最好，代价是推理成本翻几倍，适合留给高风险、低频次的关键请求，而不是全量铺开。

## 校准：光有分数不够

模型给了 90 分，不代表真的 90% 对。校准 (calibration) 就是检验"它说 90 时，是不是真有九成命中"。工程上最常用的量化指标是 ECE (Expected Calibration Error)：把样本按置信度分桶，比较每桶的平均置信度和实际准确率，差得越多越不准。

```python
def ece(confidences, correct, n_bins=10):
    import numpy as np
    conf = np.array(confidences) / 100.0
    acc = np.array(correct, dtype=float)
    bins = np.linspace(0, 1, n_bins + 1)
    total, err = len(conf), 0.0
    for lo, hi in zip(bins[:-1], bins[1:]):
        m = (conf > lo) & (conf <= hi)
        if m.sum() == 0:
            continue
        # 每桶：|平均置信度 - 实际准确率| 按样本占比加权
        err += m.sum() / total * abs(conf[m].mean() - acc[m].mean())
    return err
```

跑一批带标注的样本，你多半会看到高分桶严重虚高——模型说 95，实际只对 78。补救不用重训：留一份校准集，学一个简单的单调映射（保序回归 isotonic 或 temperature scaling），把原始分数压到真实命中率上。之后线上用的阈值，一律基于校准后的分数来设。

两种映射怎么选，也有讲究。temperature scaling 只调一个参数，把分布整体拉平或收紧，样本少时更稳、不容易过拟合，是我的默认首选。isotonic 更灵活，能纠正非单调的乱象，但需要几百条以上校准数据才靠谱，数据不够时反而会把噪声也学进去。无论哪种，都别忘了画一张 reliability diagram：横轴置信度、纵轴实际准确率，理想是贴着对角线。曲线在对角线下方就是过度自信，上方就是过度保守，一眼就能看出问题出在哪个区间，比只看一个 ECE 数字直观得多。

还有个容易忽略的点：校准集必须和线上分布同源。你拿简单题校准、上线全是难题，那条映射曲线立刻失真。所以校准不是上线前做一次就完事，而要跟着真实流量周期性重采样、重新拟合，尤其在换 prompt、换模型、扩品类之后。

## 落地：把置信度接进流程

有了可信的分数，它才从摆设变成开关。我一般这样用：

- **阈值路由**：高于阈值直接放行，低于阈值不返回原答案，转兜底链路。
- **低置信兜底**：命中低分就触发检索补料、Chain-of-Verification 自查，或直接转人工，而不是硬答。
- **分桶记录**：线上持续采样，画 reliability 曲线，模型或 prompt 一改就重新校准。
- **别跨模型复用阈值**：换底座、换温度，分数分布就变，老阈值直接失效。

成本上也要算清账。数值自评几乎不加成本，加几十个 token 而已，适合全量开；采样一致率贵好几倍，只留给高风险请求；人工复核最贵，务必用校准后的阈值卡住量，别让一半流量都掉进人工队列。一个实用的做法是分层：绝大多数高置信请求直接放行，中间档触发一次自动自查，只有低置信的那一小撮才真正打给人。这样既守住了质量下限，又没让成本失控。

一个反直觉但重要的点：置信度的价值不在"高分"，而在"能可靠地识别出低分"。哪怕整体准确率没变，只要模型能诚实地把没把握的那部分标出来，你的系统就多了一道自动兜底的闸门，线上事故率能实打实往下掉。换句话说，你要优化的不是让模型显得更自信，而是让它的自信更值得信——这两件事方向经常是相反的。

踩坑清单，照着避：

- 别信原始分数，上线前必做一次校准，否则阈值等于拍脑袋。
- 别把 token logprob 当事实置信度，它只懂语言不懂对错。
- 数值别用连续小数，模型给不出稳定的 87.3，整数或档位更靠谱。
- 阈值别写死在代码里，跟着模型版本走，每次换模型重标一遍。
- 置信度和答案分开解析，塞进散文里迟早正则崩给你看。
