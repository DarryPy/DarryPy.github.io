你的向量库里每条 embedding 都是 1536 维,不管这条 query 是简单的关键词匹配还是复杂的语义推理,检索时都要老老实实算完整 1536 维的余弦相似度。文档几千条时你根本不会在意,可当规模冲到千万级,向量计算、内存占用、索引体积全都按满维度线性膨胀,账单和延迟一起劝退。Matryoshka Representation Learning(MRL)给的答案很妙:让同一个向量在前 64、128、256、768 维都能独立可用,像套娃一样层层可裁,一份权重适配多种检索精度。这篇我们把原理、两段式落地和踩坑一次讲透。

## 满维度检索到底浪费在哪

先算一笔账。一条 1536 维 float32 向量占 6KB,一千万条就是 60GB,还没算 HNSW 图结构的额外开销,内存成本直接爆表。而检索时每比较一次都要过完整维度,延迟随维度近似线性增长。真正的问题在于:不是每个 query 都需要 1536 维的分辨率。绝大多数召回场景,前 256 维就足以把相关文档圈进候选集,剩下一千多维只在最后精细排序时才提供那一点点边际收益。可传统做法要么全程满维、白白烧算力,要么为不同精度各训练一个模型、维护成本直接翻倍,两条路都不划算。

更隐蔽的浪费在工程侧。你一旦把维度定死在 1536,整条链路都被绑死:索引结构、缓存布局、下游相似度阈值全按这个维度写死。哪天想给冷数据换个更省的低维表示,得重新 embedding、重建索引、重调阈值,牵一发而动全身。MRL 的价值是把"维度"从一次性决策变成运行时可调的旋钮——同一批向量只存一份,粗筛和精排各取所需,你不必为省内存牺牲精度,也不必为精度全程扛满维。

## 套娃向量为什么能层层可裁

普通 embedding 训练时只优化完整维度这一个整体,你随手砍掉后一半,前一半并不保证还能独立表达语义,切完性能可能断崖式下跌。MRL 的改动在损失函数:训练时对 {64,128,256,512,1024,1536} 这一组嵌套前缀各算一遍对比损失,再加权求和一起回传。模型于是被逼着把最关键的语义信息尽量往前排,越靠前的维度信息密度越高、越不可或缺。最终效果是——取前 k 维直接切片就是一个能用的 embedding,不需要任何降维矩阵、不用重新过一遍模型推理。OpenAI 的 text-embedding-3 系列、Nomic Embed、BGE-M3 都已经原生支持这种截断,拿来即用。

有人担心多目标训练会不会拖累完整维度的表现。实践里几乎不会:嵌套损失相当于一种正则,逼模型把信息按重要性有序排列,满维度性能通常和普通训练持平、甚至略好,而你白赚了所有短前缀的可用性。代价只在训练阶段——每个 batch 要多算几遍前缀损失,推理阶段零额外开销,切片就是一次数组下标操作。这也是它比事后 PCA 降维优雅的地方:PCA 得额外存投影矩阵、还要做一次矩阵乘,MRL 什么都不用,切了就能用。

实操上调用也很简单。OpenAI 接口直接传 dimensions=256 就能拿到截断且已归一化的向量;开源模型如 Nomic、BGE-M3 则自己切前缀、再手动做一次归一化即可。有一点要盯死:同一个库里粗筛向量的维度必须全库统一,别一部分存 256、一部分存 512,否则距离根本没法互相比较,召回会莫名其妙地飘。截断维度也建议挑训练时用过的那几个档位,非嵌套档位虽然能切,但没被专门优化过,效果通常不如标准档。

## 落地:粗筛用短向量,精排用长向量

真正省钱的姿势是两段式检索。第一段用截断到 256 维的短向量做粗召回,快、省内存,一口气拉出 top-200 候选;第二段只对这 200 条,用完整 1536 维重新算一次精确相似度,排出最终 top-10。因为精排只作用在极小的候选集上,满维度那点开销完全可以忽略,你既拿到了短向量的速度,又保住了长向量的精度。

```python
import numpy as np

def truncate(vec, dim):
    v = vec[:dim]                 # 直接切前 dim 维
    return v / np.linalg.norm(v)  # 截断后必须重新 L2 归一化

# 建索引:短向量进 HNSW 做粗筛,长向量留着精排
short_index.add([truncate(v, 256) for v in doc_vecs])

def search(query_vec, k=10):
    q_short = truncate(query_vec, 256)
    cand = short_index.query(q_short, top=200)   # 粗筛:快
    q_full = query_vec / np.linalg.norm(query_vec)
    scores = full_vecs[cand] @ q_full            # 精排:只算 200 条
    return cand[np.argsort(-scores)[:k]]
```

最容易被忽略的细节:截断之后一定要重新归一化,否则前缀向量的模长不再是 1,余弦相似度会整体失真。而候选集大小 top-N 是这套方案里最该调的旋钮。N 太小,粗筛就把正确答案漏在门外,精排再准也救不回来;N 太大,满维精排又开始变贵,两段式的收益被吃掉。经验上先从 top-200 起步,盯着 recall 曲线往下压到收益拐点。若链路里本就有 cross-encoder reranker,还能三段接力:短向量粗筛、长向量中排、reranker 终排,每一级候选集都比上一级小一个量级,算力全花在刀刃上。

## 维度怎么选:recall 和成本的取舍

没有万能维度,得按你的召回容忍度实测。下面是一份通用检索场景下的经验参考,具体数值随模型和数据浮动很大,务必在自己的数据上重跑:

| 截断维度 | 相对内存 | 检索延迟 | recall@10 保留 |
|---|---|---|---|
| 1536(满) | 100% | 1.0x | 100% |
| 768 | 50% | ~0.55x | ≈99% |
| 256 | 17% | ~0.25x | ≈96% |
| 128 | 8% | ~0.15x | ≈90% |
| 64 | 4% | ~0.1x | ≈80% |

经验法则:粗筛阶段选 256 维通常是甜点,内存砍到六分之一、recall 只掉个位数百分点;想再激进就下探到 128,但丢掉的那部分精度必须靠后面的满维精排补回来,否则复杂 query 会明显翻车。还有人会问,这不就是另一种压缩,和 Scalar / Binary / PQ 量化有啥区别?区别在压的东西不同:量化压的是每一维的字节数(float32→int8→1bit),MRL 压的是维度的个数,两者彼此正交、可以叠加。先用 MRL 截断到 256 维,再对这 256 维做 int8 量化,内存能在 6KB 基础上一路砍到几十字节;顺序上建议先截断再量化,因为量化误差在维度更少时更好控制,叠出来的召回损失也更可预期。

更极致的玩法是按 query 自适应选维度。简单的事实型问题用 128 维粗筛就够,复杂的多跳推理才升到 512;你可以拿一个轻量分类器,或直接用 query 长度、意图标签做路由,让便宜的问题走便宜的通道。对超大规模库,还能把 MRL 和 binary 量化叠到底:前 256 维二值化后每条向量只剩 32 字节,用汉明距离粗筛快到极致,再回原始 float 精排,单机扛下十亿级别的候选不再是梦。省的是真金白银,掉的精度靠精排兜底。

## 踩坑清单

- 截断后忘记重新归一化 → 相似度全乱,这是最高频、最隐蔽的坑。
- 只用短向量、跳过精排 → 高维语义细节全丢,复杂 query 直接翻车,粗筛永远不等于终检索。
- 精排还拿短向量的分数排序 → 等于没精排,精排一定要用满维度重新打分再排序。
- 拿非 MRL 训练的模型硬切前缀 → 那些维度压根没被单独优化过,切完性能断崖,先确认模型原生支持 MRL。
- 短、长两套向量来源不一致 → 文档更新时只更了一套,粗筛和精排对不上号,务必同源同批生成。
- 维度靠拍脑袋定 → 一定在自己数据上跑一条 recall 曲线找拐点,别直接照搬别人的甜点值。

一句话总结:Matryoshka 不是让你用更差的向量,而是让同一个向量在"快而糙"和"慢而精"之间自由切换——先用短的把候选圈进来,再用长的把顺序排明白。
