你大概遇到过这种情况：RAG 系统换了三个开源 embedding 模型，召回率始终卡在七成左右，一查失败样例，全是业务黑话、内部产品代号和缩写。这时候再怎么调 chunk 大小都没用，问题出在向量空间本身不懂你的领域。我自己的经验是，几千条高质量的问答对加一次对比学习微调，比折腾检索参数一周带来的提升都大。

但 embedding 模型的训练逻辑和生成模型完全不同。它没有 next-token 预测，也没有 SFT 那套指令格式，核心只有一件事：把语义相近的文本拉近，把不相关的推远。这件事听起来简单，真正决定效果的却是三个互相牵制的变量，损失函数的温度、负样本的难度，以及 batch size 的大小。

## InfoNCE 到底在优化什么

现在主流的 embedding 训练几乎都用 InfoNCE 损失。对每个 query，它有一个正样本 passage，同一个 batch 里其他 query 的正样本自动充当负样本，这叫 in-batch negatives。模型要做的，是在这一堆候选里把唯一正确的那个挑出来，本质上是一个 batch size 路的分类问题。

训练数据的正样本对从哪来，决定了模型最终懂多少业务。最省事的来源是客服工单和搜索日志，用户问题配上最终解决问题的文档，就是天然的正样本对。没有日志时，可以让 LLM 针对每个文档片段反向生成三到五个提问，但要人工抽检，避免生成的问题太直白、和原文逐字重合。

```python
import torch
import torch.nn.functional as F

def info_nce(q_emb, p_emb, temperature=0.05):
    # q_emb: [B, D], p_emb: [B, D]，第 i 个 query 的正样本是第 i 个 passage
    q = F.normalize(q_emb, dim=-1)
    p = F.normalize(p_emb, dim=-1)
    logits = q @ p.T / temperature          # [B, B] 相似度矩阵
    labels = torch.arange(q.size(0), device=q.device)
    return F.cross_entropy(logits, labels)  # 对角线是正样本
```

这里最容易被忽视的是 temperature。它控制 softmax 的锐度，值越小，模型越专注于区分最像正样本的那几个负样本。常见取值在 0.01 到 0.05 之间，设成 1 基本训不出东西，因为余弦相似度被压在 -1 到 1 之间，不缩放的话梯度太平，所有负样本被一视同仁。

## batch size 为什么越大越好

既然负样本来自同一个 batch，batch 越大，每个 query 见到的负样本就越多，分类任务越难，学到的表示也越精细。这也是为什么 E5、BGE 这类模型预训练阶段动辄用几万的 batch size。如果你只有一张卡跑 batch 32，模型每步只需要从 32 个候选里挑一个，难度太低，很快就学饱了。

单卡显存不够时，有两个常用手段。一是跨卡 gather，把所有 GPU 上的 passage 向量收集起来一起当负样本，8 卡 batch 32 就等于 256 路分类。二是 GradCache，先无梯度地算出所有向量，再分块回传梯度，用时间换空间。注意普通的梯度累积在这里不管用，因为它不会扩大单步的负样本池。

## 难负样本才是真正的提分器

in-batch negatives 大多是随机文本，和 query 毫不相干，模型很快就能轻松区分。真正决定上限的是难负样本：那些表面上很像正样本、实际上答非所问的段落。比如 query 问的是退款流程，难负样本可能是讲退货流程或换货流程的文档，关键词高度重合，语义却不对。

挖掘难负样本的常规做法，是先用一个基线模型或 BM25 对每个 query 做检索，从排名靠前的结果里剔除正样本，再随机抽几个当负样本。这里有一个关键细节：不要直接取 top1 到 top5。排得太靠前的结果里，往往混着标注时漏掉的真正正样本，也就是假负样本，把它们当负样本推远，等于在教模型犯错。

| 负样本策略 | 构造成本 | 训练难度 | 主要风险 |
|---|---|---|---|
| 仅 in-batch 随机 | 零 | 低 | 很快学饱，提升有限 |
| BM25 难负样本 | 低 | 中 | 偏向关键词重合，语义多样性不足 |
| 基线模型 top 10-50 采样 | 中 | 高 | 少量假负样本 |
| 直接取 top 1-5 | 中 | 很高 | 假负样本泛滥，效果反降 |
| cross-encoder 过滤后采样 | 高 | 高 | 成本高，但最干净 |

我的建议是从基线检索结果的第 10 到第 50 名之间采样，每个 query 配 3 到 7 个难负样本。如果条件允许，再用一个 cross-encoder 重排模型给这些候选打分，把得分接近正样本的剔掉，剩下的才是干净的难负样本。这一步多花的算力，基本都会在召回指标上还回来。

## 三个变量的互相牵制

温度、难负样本和 batch size 不是独立调的。难负样本加得越多，每个 query 占用的显存越大，能塞进的 batch 就越小。温度设得越低，模型对难负样本越敏感，假负样本造成的伤害也被同步放大。所以一套干净的数据，比一个更大的 batch 重要得多。

实际调参时，我一般先固定温度为 0.02，用基线模型挖好难负样本，然后在显存允许范围内把 batch 尽量开大。学习率比生成模型微调要小，全参数训练常用 1e-5 到 2e-5，训练 1 到 3 个 epoch 就够了。embedding 模型非常容易过拟合，训多了会把通用语义能力一起磨掉，出现领域内召回涨、领域外召回大跌的情况。

另一个常被忽略的点是 query 和 passage 的前缀约定。很多模型训练时会在 query 前加检索指令，在 passage 前加另一套标记，推理时必须保持一致。微调时你沿用了什么格式，上线时就要用什么格式，否则向量空间会错位，效果比不微调还差。

训练过程中，loss 曲线本身信息量有限，因为它和 batch 大小、负样本难度强相关，换一组配置数值就不可比。我更习惯每隔几百步在一个小验证集上跑一次检索，直接看 Recall@10 的走势。如果指标先涨后跌，就说明模型开始过拟合难负样本，应该提前停下，保留表现最好的那个 checkpoint。

还有一个值得顺手做的优化，是 Matryoshka 表示学习。它在训练时同时对向量的前 64、128、256 维等多个前缀计算损失，让短向量也保留大部分语义。上线时你可以按存储预算截断维度，向量库体积减半，召回往往只掉一两个点，对大规模索引非常划算。

## 怎么评估才不自欺欺人

评估集一定要和训练集按文档隔离，而不是按 query 随机切分。如果同一篇文档的不同问题分别进了训练集和测试集，模型等于提前见过答案，指标会虚高。核心看 Recall@10 和 nDCG@10 两个指标，前者衡量能不能捞到，后者衡量排得好不好。

除了领域评估集，还要留一份通用基准，比如从公开检索评测里抽几个子集，用来监控通用能力的退化幅度。如果领域指标涨了八个点，通用指标掉了十五个点，说明训练过头了，应该减少 epoch、降低学习率，或者在训练数据里混入一部分通用问答对做正则。

最后别忘了做线上验证。离线指标只覆盖你想到的问题，真实用户的提问分布往往更长尾。我通常会把新旧两个模型的召回结果并排展示给业务同事盲评几十条，再决定是否全量切换，同时记得整个向量库要用新模型重新编码，新旧向量绝对不能混用。

**踩坑清单**

- 温度保持默认值 1：梯度几乎为零，loss 不降，先检查这个参数。
- 用梯度累积代替大 batch：负样本池没有变大，对比学习效果不会提升。
- 难负样本直接取 top1 到 top5：假负样本把真正的答案推远，召回反而下降。
- query 与 passage 前缀不一致：训练和推理格式错位，向量空间对不齐。
- 评估集按 query 随机切分：同文档泄漏，离线指标漂亮，上线一塌糊涂。
- 训练轮数过多：领域召回涨了，通用能力崩了，记得同时盯通用基准。

一句话总结：embedding 微调的胜负不在模型大小，而在于你给它的负样本有多难、又有多干净。
