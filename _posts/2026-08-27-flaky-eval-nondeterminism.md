你改了一版 prompt，重跑 eval，准确率从 81 涨到 83，截图发群里准备上线。问题来了：把改动全部还原，再跑一遍，你可能还是拿到 82。那两分根本不是 prompt 变好了，是评估本身在抖。分不清这两种"涨分"，你的每次迭代都在和噪声赌博，还赌得心安理得。

## 分数在抖，不是你变强了

大多数人第一次做 eval，默认它像单元测试：同样的输入配同样的输出，跑一百遍结果一致。LLM 的世界不是这样。只要采样链路里留了一点随机，同一套测试集、同一个模型、同一段 prompt，两次跑分就能差出一两个百分点。你以为在比较两版方案，其实在比较两次掷骰子。

更隐蔽的是 LLM-as-judge。就算被测模型稳如老狗，打分的裁判自己还在采样，它今天觉得答案"基本正确"给过，明天觉得"略有瑕疵"给挂，分数照样漂。评估链路里只要有一个环节在采样，最终数字就带不确定性，而这个环节往往是你最容易忽略的那个。

先建立一个概念叫 noise floor（噪声地板）——把同一个版本原封不动重复跑 5 到 10 次，看分数的波动区间。这个区间就是你的测量误差，是一把尺子的最小刻度。任何小于 noise floor 的"提升"，统计上都等于没提升。不先测出这条线，你根本没资格开口说"涨了两分"，因为你连两分是不是噪声都不知道。

## 抖动到底从哪来

抖动来源分两类：能钉死的和钉不死的。把它们拆开，你才知道力气该往哪使，而不是对着一个漂的数字瞎调 prompt。

| 来源 | 说明 | 可控性 |
|---|---|---|
| temperature > 0 | 采样带随机，同一 prompt 生成不同答案 | 完全可控，设 0 |
| top_p / top_k | 截断采样空间，但仍保留随机 | 可控 |
| 未固定 seed | 部分 API 支持传 seed 复现采样路径 | 大多可控 |
| model 版本漂移 | 供应商静默更新权重，昨天的模型不是今天的 | 靠快照锁 |
| judge 自身采样 | LLM 裁判没设 temp=0，打分本身在抖 | 可控 |
| 数据集顺序 / 并发 | 拼 batch 方式变了，边界样本判定跟着变 | 可控 |
| 浮点非确定性 | GPU kernel、batch size、MoE 路由带来微小差异 | 钉不死 |

前六行都是人为疏忽，能一次性消灭，成本几乎为零。最后一行是物理事实：即便 temperature 设成 0，大模型在 GPU 上的前向计算也不是逐位可复现的。batch 拼法不同、请求被路由到不同的专家（MoE）、底层 kernel 走了不同的归约顺序，输出就可能差一个 token，而这一个 token 的偏移会顺着后面的生成连锁放大，最终连判定结果都跟着翻。你能做的不是消灭它，是把它量化。

## 先把能钉死的全钉死

在动任何统计手段之前，先把人为随机压到最低。花俏的 bootstrap 都是后话，第一步永远是删掉不该有的随机源。这是一段最小可复现配置：

```python
# 被测模型
resp = client.chat.completions.create(
    model="claude-opus-4-8",   # 锁死具体版本，别用 latest 别名
    messages=msgs,
    temperature=0,             # 关掉采样随机
    seed=42,                   # 支持则固定 seed
)

# 裁判模型同样待遇，别让评分环节偷偷放水
judge = client.chat.completions.create(
    model="claude-opus-4-8",
    messages=judge_msgs,
    temperature=0,
)

# 每次跑都落盘这些元数据，否则复现无从谈起
run_meta = {
    "model": "claude-opus-4-8",
    "temperature": 0,
    "prompt_hash": sha256(prompt),
    "dataset_hash": sha256(dataset),
    "code_commit": git_rev(),
}
```

关键不是某一行，而是全都记下来。三个月后有人质疑某次结论，你能拿出 prompt_hash、dataset_hash、commit 三件套精确重放，而不是靠"我记得当时大概是这么跑的"。尤其是 model 版本：用 `latest` 这种别名，供应商哪天悄悄换了权重，你的历史结论全部作废还查不出原因，锁死带日期或哈希的具体快照能救你一命。

## 钉不死的部分，用统计兜底

把人为随机清干净后，浮点抖动还在，noise floor 通常会落在 ±0.5 到 ±1.5 个百分点。这个数字每个任务不一样，分类任务小，开放式生成 + LLM judge 的组合能大到吓人。测出你自己任务的 noise floor，是做 eval 的第一课，不是可选项。

做法很朴素：同一版本跑 N 次，算均值和标准差，报一个区间而不是一个孤零零的数。判断新版本是否真的更好，看两个区间是否分离——两个模型分数都是 82±1.2，区间叠得死死的，就别吹"提升"，那是自欺。真要下结论，上配对检验（paired bootstrap 或 McNemar），因为同一批题目在两版之间是配对的，配对检验能抵消掉"这道题本身就难"带来的共同噪声，比独立比较敏感得多，用更小的样本就能识别出真实差异。

举个具体的：你测出 noise floor 是 ±1.0。旧版跑五次是 82.1、81.4、82.8、82.0、81.7，均值 82.0；新版跑五次拿到 83.2、82.9、83.5、82.6、83.3，均值 83.1。看上去涨了 1.1 分，刚好卡在噪声地板边上，单看均值你会犹豫。但配对检验会告诉你：这 1.1 分在每一次配对里都稳定为正——五次全赢，不是三胜两负凑出来的均值，那它就是真信号。反过来，如果新版是 84、80、85、79、86 这种大起大落凑出的 82.8，均值再高也是虚的，方差已经出卖了它。均值骗人，分布不骗人。这一步和样本量强相关：20 条测试集的抖动大到能一口吞掉任何真实改进，那篇《Eval 样本量陷阱》把这笔账算得很清楚，可以配着看。

## 把可复现变成制度

一次性做对不难，难的是每次都做对、每个人都做对。靠自觉守不住，得落成清单挂到 CI 上，让流程替你兜底：

- 锁具体模型版本快照，禁用 `latest`、`stable` 这类会漂的别名
- 被测和裁判一律 `temperature=0`，API 支持 seed 就固定
- 每次 run 落盘 model / 超参 / prompt_hash / dataset_hash / commit
- 上线前先测 noise floor：同版本重复跑 5–10 次拿到波动区间
- 改进幅度 < noise floor 一律判为噪声，不准计入"提升"
- 关键结论用配对检验加置信区间，别拿单次分数直接拍板
- CI 回归里锁死数据集 hash，数据集一变分数就失去可比性

一句话收尾：eval 给你的从来不是一个分数，是一个带误差棒的分数。谁把误差棒忽略了，谁就是在拿噪声当业绩汇报——上线之后，线上流量会一分不差地替你把这笔账算回来。
