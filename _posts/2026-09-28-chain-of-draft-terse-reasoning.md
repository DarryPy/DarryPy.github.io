你让模型开 Chain-of-Thought，准确率上去了，账单也上去了。一道数学题它能写三百字推导，真正有用的可能就两行。你为这些啰嗦的中间步骤付了全额 token 费，还多等了几秒延迟。而你真正要的，其实只有最后那个答案。今天讲的 Chain-of-Draft，就是把这刀砍在最没痛感的地方。

## 为什么 CoT 又准又贵

Chain-of-Thought 的价值在于把推理摊开：模型先列步骤再给结论，复杂问题的准确率能提升一大截。它的代价是输出膨胀——每一步都用完整自然语言描述，一道题动辄几百 token。推理模型还会在这基础上再叠一层思考轨迹，输出量继续翻倍，成本和延迟都难看。

问题的根子在于，我们默认"想得清楚"就等于"写得详细"。可人类打草稿时根本不这样。你算一道题，草稿纸上写的是"20-5=15"，而不是"我们首先设定初始数量，然后根据题意逐步进行计算"。前者三个符号说清的事，后者用了二十个字。Chain-of-Draft 干的，就是把这套草稿习惯教给模型：思路照走，废话不写。

值得强调的是，CoD 不是让模型"少想"。少想会掉准确率，那是偷工减料。它是让模型"想得一样多、写得少得多"——推理的骨架完整保留，只把每一步的表达从散文压成速记。这也是它能做到省 token 却不掉分的根本原因。

这背后有个朴素直觉：模型解题的真本事在于那一步步的计算与推导，而不在于把过程铺陈成通顺的段落。散文式描述是给人看的礼貌，对模型自身的正确率贡献极小。既然中间过程你并不打算展示给用户，那这份礼貌就是纯粹的浪费。CoD 只是把这份浪费识别出来并砍掉，本质上是一次"面向机器读者"的写作风格切换。

## Chain-of-Draft 的核心

CoD 的规则只有一句：每个推理步骤最多写几个词，像草稿而非作文。模型照样一步步推，但每步压到极限——只留关键算式、变量和中间值，砍掉所有连接词和解释性铺垫，最后再给完整答案。原论文里它能把推理 token 砍到 CoT 的两成上下，多数基准上准确率几乎持平。

它和你熟悉的几个技术都不一样，别搞混：

| 技术 | 省在哪 | 主要代价 |
|------|--------|----------|
| Chain-of-Thought | 不省，追准确率 | 输出 token 多、慢 |
| Prompt 压缩 | 输入 token | 可能丢上下文 |
| Thinking Budget | 限制总思考量 | 调太狠会跳步 |
| Chain-of-Draft | 输出 token | 极复杂题略掉分 |

一句话概括区别：Prompt 压缩省进项，CoD 省出项；Thinking Budget 管思考总量，CoD 改每步的表达密度；Skeleton-of-Thought 先列提纲再并行扩写，CoD 恰恰相反——它就是不让你扩写。四者不冲突，甚至能叠着用：输入端压缩，输出端草稿，两头一起省。

## 省了多少，算笔账

抽象的"八成"没感觉，落到钱上就清楚了。假设一个客服意图分类接口，每次调用输入 300 token，CoT 平均输出 250 token，其中推理占 200、答案占 50。换成 CoD 后推理压到 40 token，单次输出降到 90。

```text
CoT:  输入 300 + 输出 250 = 550 token / 次
CoD:  输入 300 + 输出  90 = 390 token / 次
输出 token 省了 (250-90)/250 ≈ 64%
按日均 50 万次、输出单价更贵来算，
每天省下的钱通常是四位数起。
```

别忽略延迟这条隐性收益。输出 token 是逐个自回归生成的，无法并行，砍掉 160 个输出 token，意味着这条请求的生成时间直接缩短一大半。对话类产品里，用户感知到的"变快了"，很多时候不是模型更聪明，而是它不再啰嗦。

吞吐量也跟着受益。同一批 GPU 的显存和算力是固定的，每个请求占用的输出序列越短，单位时间能并发处理的请求就越多。也就是说 CoD 不只降低了单次调用的花费，还顺带抬高了整套服务的天花板——同样的机器能扛更大的流量，这对成本敏感的规模化场景尤其香。

## 什么时候用、什么时候别用

CoD 最适合高频、步骤清晰的推理：数学计算、结构化抽取、规则判断、多步表单校验、意图分类。这些场景每步逻辑明确，压缩表达几乎不损准确率，请求量一大，省下的钱和延迟都非常可观。

有两类场景别硬上。一是需要模型"想深"的开放推理——法律分析、复杂代码 debug、多因素权衡，草稿式会逼它跳步、丢中间约束，准确率明显下滑；二是要把推理过程展示给用户看的产品，五个词的草稿人根本读不懂，反而显得敷衍。这时候老老实实用完整 CoT。

还有个折中办法值得记：线上默认走 CoD，一旦置信度偏低或答案格式异常，就自动回退到完整 CoT 重算一遍。多数请求走便宜快路径，少数难题走贵慢路径，整体成本和准确率兼顾。这种"快慢双档"是把 CoD 用进生产最稳的姿势，比一刀切全量切换安全得多。

判断该走哪档也不复杂：可以用请求的输入长度、任务类型标签，或者上一次同类请求的正确率做路由。简单场景直接钉死用 CoD，模糊地带才交给回退逻辑。工程上无非多一层分支，收益却是实打实的——你既拿到了草稿式的省钱效果，又保住了难题上的准确率下限，两头都不亏。

## 落地与踩坑清单

给个能直接抄的骨架：系统提示写死约束，再配一个 few-shot 草稿示范，模型很快就能对齐节奏。

```text
你在解题时，每个思考步骤最多写 5 个词，
只保留必要算式和中间结果，不写完整句子，
最后用 "####" 分隔，单独给出最终答案。
问：20 个苹果吃 5 个，再买 3 箱每箱 6 个，现在几个？
20 - 5 = 15
3 × 6 = 18
15 + 18 = 33
#### 33
```

- 别只在 system 里写规则却不给示范，模型会偷偷退回长推理——few-shot 草稿才是对齐节奏的关键。
- "最多 N 个词"里的 N 给 5~8 比较稳，压到 1~2 会逼模型跳步、掉分。
- 一定要留明确的答案分隔符（如 "####"），否则你还得再调一次模型去提取，省下的 token 又吐回去了。
- 上线前拿自己的测试集对比 CoD 与 CoT 的准确率差，别信论文平均值，你的任务分布未必一样。
- 草稿推理不适合直接给终端用户看，要展示就另生成一份人话解释，或者干脆用 CoT。

省 token 的技术很多，CoD 的聪明之处是没动输入、没砍能力，只是让模型别把草稿写成作文——而这，恰恰是最没痛感的一刀。
