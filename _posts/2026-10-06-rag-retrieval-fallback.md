你的 RAG 系统在 demo 阶段跑得漂亮,一上线就被用户一句刁钻问题打回原形:检索召回一堆不相关片段,LLM 硬着头皮把它们拼成一个像模像样却完全错误的答案。问题往往不在生成那一端,而是检索这一环从来没人给它兜底。真正能上生产的 RAG,靠的不是召回率再高一个点,而是检索失败那一刻,系统还能不能体面收场。这篇讲的就是检索兜底这件被大多数教程跳过的脏活。

## 检索失败的四种形态

把"检索失败"当成一个笼统概念是第一个坑。它至少分四种,每种对应完全不同的兜底手段,混为一谈只会让你写出一刀切的烂逻辑。空结果:向量库里压根没有相关文档,top-k 返回的全是噪声,分数集体趴在地板上。低分命中:有结果但相似度普遍偏低,说明知识库覆盖不到这个问题,属于"能力边界之外"。

偏题召回更隐蔽:分数不低,但语义漂移了,检索器被查询里的高频词带偏,返回一堆字面相似、意图无关的片段。冲突证据则是召回的多个片段互相矛盾,比如新旧两版文档同时命中,LLM 无从取舍,往往随机挑一个就往下编。先把失败归类,后面的策略才有的放矢;否则一遇到问题就统一拒答,好用户也被你一起赶跑了。

更要命的是,大多数脚手架的默认行为就是灾难:LangChain、LlamaIndex 这类框架默认把 top-k 结果原封不动拼进 prompt,检索好坏一视同仁。你不主动加判断,系统就默认"检索永远成功",于是空结果和偏题召回被当成可靠证据喂给模型,线上的幻觉十有八九就是这么来的,根本不是模型不够聪明。

| 失败形态 | 典型信号 | 兜底手段 |
|---|---|---|
| 空结果 | top-k 全低于阈值 | 查询重写 / 降级通用回答 |
| 低分命中 | 平均分低、方差小 | 扩大召回 / 提示不确定 |
| 偏题召回 | 分数高但答非所问 | 重排 + 相关性二次校验 |
| 冲突证据 | 片段互相矛盾 | 按时间/权威度加权取舍 |

## 第一层防线:检索质量门控

别把检索结果无脑塞给 LLM。在检索和生成之间插一道门控,用相似度分数做第一层过滤。固定阈值是新手做法——不同 embedding 模型、不同查询长度,分数分布差异极大,写死 0.7 换个模型就全盘失效。更稳的是看 top-1 与 top-k 的分数梯度,以及 top-k 的均值和方差,用相对关系判断而非绝对值。

```python
def gate(results, abs_thr=0.35, margin=0.08):
    if not results:
        return "empty"
    top = results[0].score
    if top < abs_thr:                 # 最高分都不够
        return "low_confidence"
    mean = sum(r.score for r in results) / len(results)
    if top - mean < margin:           # 梯度太平,区分度差
        return "ambiguous"
    return "ok"
```

门控输出的不是布尔值,而是一个状态标签,驱动后续走哪条分支。这一步的价值在于:把"要不要相信这次检索"的判断,从 LLM 手里拿回来,用确定性规则兜住,而不是赌模型自己能察觉上下文不靠谱——它大概率察觉不到,还会一本正经地帮你圆谎。

阈值怎么定?别凭感觉。拿一批真实查询离线跑一遍,分别统计有答案和无答案两类请求的分数分布,取能最大化区分度的分位数作为起点,再在灰度环境里微调。embedding 模型升级、知识库扩容之后都要重标一次——阈值是会随数据漂移的活参数,不是一次写死就能吃一年的常量。

## 第二层:查询重写与多路重试

门控判定不理想,先别急着拒答,给检索第二次机会。最有效的是查询重写:让一个小模型把用户口语化、省略主语的问题,改写成检索友好的表达,再重试一轮。多路召回也值得上——原始查询、重写查询、关键词 BM25 三路并发,结果用 RRF 融合,互相补盲区。

举个例子,用户问"这个报错怎么解决",省略了主语,直接拿去向量检索基本召回全是噪声。重写模型结合对话上下文把它补全成"订单支付接口返回 503 错误的排查步骤",检索立刻命中。这类改写对客服、技术支持类 RAG 收益最大,因为真实用户的提问几乎从不规整,充满指代、省略和错别字。

重试要有预算上限,通常一到两轮封顶,否则延迟直接失控,用户等不起。每一轮都复用同一套门控判断是否收敛。关键是重试要"换姿势"而非简单重复:改写查询、切换检索策略、放宽元数据过滤条件,任何一个维度动一下都行;原样再查一遍,只是把同样的坏结果再拿一次,纯浪费 token 和时间。

## 第三层:优雅降级与拒答

重试仍不达标,就进入降级。降级不等于冷冰冰甩一句"我不知道"。好的降级是分层的:能给部分答案就标注置信度给出,并坦白依据不足;只找到相关方向就返回线索、建议用户追问细化;完全没命中才明确拒答,并引导换个问法或转人工。层层递进,体验天差地别。

冲突证据要单独处理:与其让 LLM 盲选,不如在 prompt 里显式把矛盾摊开,附上每个片段的来源和时间戳,让模型按"优先采信最新、最权威来源"的规则取舍,并在答案里主动说明存在版本差异。把取舍逻辑交给规则和元数据,而不是赌模型随机挑中那条对的。

拒答前最好再加一道 grounding 校验:用 NLI 模型或一个轻量判别 prompt,逐条检查草稿答案里的论断能否从检索片段推出,推不出就打回重走降级。宁可少答、不可乱答——在金融、医疗、法务这类场景,一次自信的幻觉造成的信任损失,远大于十次诚实的"这个我暂时查不到"。

## 把失败数据回填知识库

兜底逻辑不是终点,而是一个数据源。全链路埋点,记录每次请求最终走到了哪一层:频繁触发"空结果"的那批查询,恰恰是知识库的覆盖盲区;反复"偏题召回"的查询,暴露的是 chunking 或 embedding 的系统性问题。把这些日志按失败形态聚类,就是一份现成的知识库补全和检索优化优先级清单,比拍脑袋排期靠谱得多。

更进一步,给每条兜底路径配一个告警阈值:当"空结果"占比一周内突然翻倍,大概率是某个新业务上线但文档没跟上,运营和产品该第一时间收到提醒。兜底层由此从被动防御,升级成知识库健康度的实时体检仪,这才是它真正的长期价值所在。

## 落地清单

- 检索与生成之间必须有门控层,别让低质上下文直达 LLM
- 阈值用相对梯度,别写死绝对值,换模型就得重新标定
- 重试设 1-2 轮硬上限,每轮必须换策略,且复用同一门控
- 降级分层:部分答案 > 给线索 > 拒答,别一步跳到底
- 拒答文案要给出路(换问法 / 转人工),而不是死胡同
- 全链路埋点按失败形态聚类,这是优化知识库覆盖的金矿

一句话:RAG 的生产可靠性,不取决于检索最准的时候有多准,而取决于检索最差的时候,摔得有多稳。
