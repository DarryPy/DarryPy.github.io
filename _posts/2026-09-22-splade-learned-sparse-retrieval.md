你上线过 RAG 的话,大概踩过这种尴尬:用户搜"iPhone 15 Pro Max 电池容量",dense 向量把"iPhone 14 续航评测"排到最前——语义确实近,可型号错了。换回 BM25,型号是精确命中了,但用户改口问"这款手机能用多久",关键词对不上,直接零召回。这两类错在生产里天天上演,一个丢精度、一个丢语义,而你常常两头都想要。稠密和稀疏各有死穴,而 SPLADE 代表的学习稀疏检索,恰恰是很多团队一眼扫过、直接跳过的第三条路,今天就把它讲透。

## 稀疏、稠密,各有各的死穴

先把三条路摆清楚。BM25 是词频统计,命中全靠字面重叠,优点是精确、可解释、复用倒排索引,缺点是完全不懂同义——"续航"和"电池"在它眼里是两个毫不相干的词。dense embedding 把整句压成几百维稠密向量,懂语义、抗改写,但代价是把所有信息糊进一个低维空间,专有名词、型号、长尾术语很容易被平均掉,精确匹配能力反而弱。

学习稀疏检索走的是折中路线:用语言模型算出每个词的重要度,输出一个词表维度(三万多维)、但绝大部分为 0 的稀疏向量。它既能像 dense 那样把相关词扩展进来,又像 BM25 那样保留字面权重和可解释性。你可以把它理解成"会自己做同义扩展的 BM25",而扩展规则不是人工同义词表,是模型训练学出来的。

这也是为什么这两年"混合检索"几乎成了 RAG 标配:没有哪条路能单独通吃。而学习稀疏检索的价值在于它把混合的两端往中间拉了一步——你不再必须同时伺候倒排引擎和向量库两套截然不同的基建,一套倒排就能同时承载字面精度和语义扩展,运维复杂度和数据一致性问题都跟着降一档。

## SPLADE 到底在算什么

SPLADE 的巧思是复用 BERT 的 MLM head。它把每个输入 token 投影回整个词表,对序列维度取 max,再套一层 log 饱和,得到覆盖全词表的权重向量。关键在于这个过程天然会"扩展":输入"续航",模型往往顺手激活"电池、耗电、待机、小时"这些相关词,并给出高低不等的权重。字面没出现的词也能带上合理分数,这正是它甩开 BM25 的地方。

```python
import torch
from transformers import AutoTokenizer, AutoModelForMaskedLM

tok = AutoTokenizer.from_pretrained("naver/splade-v3")
model = AutoModelForMaskedLM.from_pretrained("naver/splade-v3").eval()

def encode(text):
    x = tok(text, return_tensors="pt")
    logits = model(**x).logits                      # [1, seq, vocab]
    # ReLU 保留正激活 -> log 饱和压制高频 -> 对序列维取 max
    vec = torch.max(
        torch.log1p(torch.relu(logits)) * x.attention_mask.unsqueeze(-1),
        dim=1,
    ).values.squeeze()
    idx = vec.nonzero().squeeze()
    return {tok.convert_ids_to_tokens(i.item()): round(vec[i].item(), 3)
            for i in idx}

print(encode("iPhone 电池能用多久"))
# {'iphone': 2.1, '电池': 1.8, '续航': 1.2, '待机': 0.7, '手机': 0.6, ...}
```

输出是一份"词:权重"字典,你一眼就能看懂模型把查询扩展成了哪些词、各占多重——这份可解释性是稠密向量永远给不了的,排查 badcase 时尤其值钱。训练阶段 SPLADE 会加一个 FLOPS 正则项,专门惩罚非零项的数量,逼模型只留下真正有用的词。否则激活铺满整个词表,索引直接爆炸,查询也慢到没法用。

顺带说下它的效果到底从哪来。SPLADE 不是把 MLM head 直接拿来用,而是在 MS MARCO 这类检索数据上,拿一个交叉编码器当老师做知识蒸馏训练出来的——老师负责告诉它哪些扩展词真的有助于把相关文档和不相关文档区分开。所以别指望自己随手加载个原始 MLM 就能有 SPLADE 的效果,权重必须是针对检索任务专门训过的 checkpoint,这一步偷不得懒。

## 直接复用倒排索引,省掉向量库

这才是 SPLADE 在工程上最香的一点:它吐出来的是稀疏权重,天然能塞进 Elasticsearch / OpenSearch 的 rank_features 字段,或者 Vespa 的 weightedset。检索就是倒排表上的加权点积,和 BM25 共用同一套引擎,不需要单独维护向量库、不需要调 HNSW、不用担心 ANN 召回损失。对已经在用 ES 的团队来说,接入成本低得惊人。

| 维度 | BM25 | Dense (HNSW) | SPLADE |
|------|------|--------------|--------|
| 语义扩展 | 无 | 强 | 中强 |
| 精确匹配 | 强 | 弱 | 强 |
| 可解释性 | 高 | 低 | 高 |
| 索引基建 | 倒排 | 向量库 / ANN | 倒排(复用) |
| 索引体积 | 小 | 中 | 偏大 |
| 查询延迟 | 低 | 低-中 | 中(长尾词拖累) |

从表里能看出,SPLADE 基本是 BM25 的"语义增强版",还顺带省掉了单独维护一套向量基建的成本。所以很多线上系统的真实选择不是三选一,而是 SPLADE 打底负责主召回,dense 做补充召回,再用 RRF 把两路排名融合——各取所长,召回上限比单跑任何一路都高。

RRF 的融合逻辑简单到几行代码就能落地:每篇文档在稀疏、稠密两路里各拿到一个名次,分数按 1/(k+rank) 累加(k 通常取 60),再按总分重排。它只看名次、不看原始分数,天然绕开了两路打分量纲对不齐的老问题,不用调温度、不用归一化,是目前性价比最高的融合姿势。真要更精细,再在融合结果上挂一个 reranker 做精排即可。

## 什么场景该上、什么先别碰

不是所有 RAG 都值得换 SPLADE。如果你的查询高度依赖专业术语、型号、代码符号、法律条款这类"字面必须对上"的内容,它的收益最大——在保住精确匹配的同时补齐了同义扩展,技术文档、电商商品、代码搜索、合规检索都是它的甜区,往往一上就能看到长尾 query 召回率的明显抬升。

反过来,如果你的语料是闲聊、情感、跨语言这类语义高度发散的场景,dense 依旧是主力,SPLADE 顶多当辅助召回。还有一种情况要冷静:团队压根没有 ES/OpenSearch、纯靠某个托管向量库过日子,那单为 SPLADE 现搭一套倒排引擎未必划算,先把这笔基建账算清楚再动手,别为了新技术硬造需求。

## 上线绕不开的三个坑

第一个坑是查询延迟。SPLADE 会给一条查询扩出几十个 term,其中难免混进高频停用词,对应的倒排拉链极长,点积成本飙升,尾延迟很容易比纯 BM25 高出好几倍。解法是对查询侧做 top-k 剪枝,只保留权重最高的二三十个词,长尾低权重项直接砍掉;再配合引擎的 WAND / block-max 提前终止,延迟能降一大截而召回几乎不掉。

第二个坑是索引膨胀。doc-side 扩展会让每篇文档的 term 数翻好几倍,索引体积普遍是纯 BM25 的两到四倍,写入吞吐也跟着下降。如果存储或写入敏感,可以换成 SPLADE-doc 或 uniCOIL 这类"只在文档侧扩展、查询侧保持原样"的变体,用一点点精度换回可观的体积和写入速度;真上量之前,务必拿全量语料压测一版索引大小和构建耗时,别用小样本估算,容易乐观翻车。

第三个坑是中文。SPLADE 原版基于 WordPiece,直接套中文会把扩展全打散到字级别,权重稀碎、效果大打折扣。中文场景务必换支持中文词表的底座,比如 bge-m3 的稀疏分支,它同时产出稠密和稀疏表示,一套模型就能喂两路检索,省事又对齐。

上线前把这份踩坑清单逐条过一遍:

- 查询侧做 top-k term 剪枝,别让停用词的长拉链拖垮延迟
- 确认用了 FLOPS 正则或官方 checkpoint,把非零项数量压在合理范围
- 中文一律换中文底座(bge-m3 sparse),别硬套英文 WordPiece
- 索引磁盘按 BM25 的 2-4 倍预留,别等写满才发现
- 别指望 SPLADE 单打独斗,和 dense 用 RRF 融合才是召回天花板

一句话总结:当你既嫌 BM25 太笨、又嫌 dense 丢字面时,学习稀疏检索就是那条被长期低估的中间道——它谈不上多神,但实打实把"精确"和"语义"这对老冤家,第一次干净利落地装进了同一套倒排索引里。
