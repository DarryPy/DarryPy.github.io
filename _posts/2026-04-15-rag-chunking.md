## 为什么 chunking 决定 RAG 上限

embedding 模型一次只能 embed 一段文本，所以**长文档必须切**。
切得不对，检索召回再准也救不回来：

- chunk 太大：一个 chunk 里塞了多个主题，向量被平均，啥都不像
- chunk 太小：失去上下文，模型回答支离破碎
- 切错位置：把一个完整论点切成两半

## 6 种主流策略

### 1. 定长切片（Fixed-size chunking）

最简单粗暴：每 512 token 切一刀。

**优点**：实现 5 行代码、可预测、token 数稳定。
**缺点**：切割位置随意，可能在句子中间切断。

**适合**：原型阶段、内容均匀的文档（API 文档、新闻）。

### 2. 按段落 / 标题切（Document-structure chunking）

按 `\n\n` 分段，或按 Markdown `#` `##` 切。

**优点**：尊重作者的语义边界，块内主题相对统一。
**缺点**：段落长短不一，有些 chunk 50 token，有些 5000 token。

**适合**：技术文档、Markdown 笔记。

### 3. 递归切片（Recursive chunking）

LangChain 的 `RecursiveCharacterTextSplitter` 思路：
按 `["\n\n", "\n", "。", " "]` 优先级递归切，直到每块 ≤ 目标长度。

**优点**：尽量在自然边界切，但保证长度上限。
**缺点**：仍然不理解内容含义。

**适合**：通用场景，**生产首选起点**。

### 4. 语义切片（Semantic chunking）

用 embedding 算句子间的相似度，相似度低的地方切——也就是"主题转折点"。

**优点**：真正按语义切，chunk 主题最纯。
**缺点**：贵——每个文档要 embed N 次（N = 句子数）。

**适合**：高质量要求、低更新频率的内容（书、长论文）。

### 5. Late Chunking（晚切）

新潮流：**先 embed 整段长文本**（用长上下文 embedding 模型），再在 token 级别切出每个 chunk 的向量。

**优点**：每个 chunk 的向量带有整段上下文信息。
**缺点**：需要 long-context embedding 模型（如 jina-embeddings-v3、voyage-3）。

**适合**：长文档、跨段引用多的场景。

### 6. 按 Q&A 对切（Query-aware）

把文档预先生成"可能的问答对"，每个问答对作为一个 chunk。
检索的是问题，而不是原文段落。

**优点**：检索准确率最高（query 和 chunk 都是问题）。
**缺点**：预处理贵（要用 LLM 生成 Q&A）。

**适合**：FAQ 场景、产品文档问答。

## 关键参数：chunk_size 和 overlap

| 参数 | 推荐 | 说明 |
|---|---|---|
| `chunk_size` | 256–1024 token | 短：定位精；长：上下文全 |
| `chunk_overlap` | 10–20% of chunk_size | 防止跨块信息丢失 |
| `min_chunk_size` | 50 token | 太短的丢弃 |

**经验值**：技术文档用 512+50；问答 FAQ 用 256+30；长文学/分析用 1024+200。

## 容易被忽略的工程细节

### 1. 保留 metadata

每个 chunk 不仅存 text，还要存：
- 来源（文件名、URL、章节）
- 位置（页码、段落号）
- 时间（创建/更新）

检索时这些 metadata 用于：
- 过滤（"只检索 2025 年之后的文档"）
- 排序（"优先官方文档"）
- 引用（回答时附带来源）

### 2. 标题前置

每个 chunk 在 embed 前，前置加上**它所属章节的标题路径**：

```
[Doc: API Guide > Authentication > OAuth2]
具体段落内容...
```

这能让 embedding 包含"这段在讲哪个主题"的信号，召回准确率涨 5-10%。

### 3. 跨语言一致

中英混排的文档，切片时尽量让一种语言完整在一个 chunk 里。
按句号切的时候，中英文标点都要识别（"。" 和 "."）。

## 决策矩阵

| 场景 | 推荐策略 |
|---|---|
| 通用起步 | 递归切片（512+50） |
| Markdown 文档 | 按标题切 + 递归兜底 |
| 法律 / 合同 | 按章节切（条款单位） |
| 客服 FAQ | Q&A 对切 |
| 长论文 / 书 | 语义切片 或 late chunking |
| 高频更新 | 定长切片（重建成本低） |

## 一个朴素的判断

> 切片不是技术问题，是产品问题。

切片策略要回答："**用户问一个问题时，理想的答案在哪个粒度上？**"
是一段话？一节？一章？答案决定策略。

试错前先想清楚这点，比直接调参省 90% 时间。
