你可能把 LLM 应用的安全想象成「别泄露数据、别说错话」。但有一类攻击既不偷数据也不越权，只是让你的服务一直干活：一个公开的客服 Agent，某个周末被人用脚本反复触发长推理和多轮工具调用，周一早上你看到的不是告警，而是一张比平时贵四十倍的账单。

这就是 Denial of Wallet，OWASP LLM Top 10 里叫 Unbounded Consumption。传统 DoS 打的是可用性，服务挂了用户会立刻发现；成本攻击打的是钱包，服务看起来一切正常，响应也不慢，只是每一次请求都比正常贵很多，直到月底对账才暴露出来。

## 攻击者是怎么让你多花钱的

我把常见手法归成四类。第一类是输出放大：让模型「把这段话逐字重复一千遍」或「列出所有可能的组合」，一次请求就吃满 max_tokens。第二类是推理放大：对 reasoning 模型抛一道看似简单、实则需要大量枚举的题，思考 token 你看不见，但要照样付费。

第三类是工具循环：通过提示注入或构造边界输入，让 Agent 反复调用搜索、重试失败的接口，或者在两个工具之间来回跳，一个任务跑出上百步。第四类是上下文膨胀：上传超长文档、把历史对话刷到上限，让之后的每一轮请求都背着十几万 token 的输入成本。

这四类手法有个共同点：单次请求在内容上完全「合规」，护栏和审核模型都不会拦。它们利用的是你对资源消耗缺少上界，而不是模型的价值观漏洞。所以防御重点不在内容过滤，而在于每个维度都要有明确的硬上限，并且上限要能被及时计量。

还有一种更隐蔽的变体：攻击者并不亲自发请求，而是在网页、邮件或共享文档里埋下指令，等你的 Agent 读到时自己陷入长任务。这类间接触发让限流规则形同虚设，因为请求来自正常用户，只是被借刀消耗了额度。

| 攻击类型 | 放大的资源 | 典型信号 | 第一道防线 |
| --- | --- | --- | --- |
| 输出放大 | 输出 token | 单次输出贴近 max_tokens | 按场景收紧 max_tokens |
| 推理放大 | 思考 token | reasoning token 远高于基线 | 限制 reasoning effort 与预算 |
| 工具循环 | 调用次数与外部 API 费用 | 步数异常、重复同参调用 | 步数上限与循环检测 |
| 上下文膨胀 | 输入 token | 单轮输入持续逼近窗口上限 | 输入截断与历史压缩 |

## 预算要分层，熔断要能落地

只在网关上配一个每分钟请求数限流是不够的。攻击者完全可以每分钟只发两次请求，但每次都让 Agent 跑满五十步。真正有效的单位是 token 和金额，而且要分层：单次调用、单个任务、单个用户每天、整个租户每月，每一层都要有自己的上限和动作。

我的做法是给每个任务挂一个预算对象，每次模型调用和工具调用之前先扣预估，返回后再按实际用量结算。超出任务预算就直接终止，并给用户一句可读的说明；超出用户日预算就降级到便宜模型或排队；超出租户预算才触发人工告警。下面是一个精简版本。

```python
from dataclasses import dataclass, field

class BudgetExceeded(Exception):
    pass

@dataclass
class TaskBudget:
    max_usd: float = 0.50
    max_steps: int = 20
    max_same_call: int = 3
    spent_usd: float = 0.0
    steps: int = 0
    seen_calls: dict = field(default_factory=dict)

    def before_step(self, tool_name: str, args_key: str, est_usd: float):
        self.steps += 1
        if self.steps > self.max_steps:
            raise BudgetExceeded("步数超限: " + str(self.steps))
        sig = tool_name + ":" + args_key
        self.seen_calls[sig] = self.seen_calls.get(sig, 0) + 1
        if self.seen_calls[sig] > self.max_same_call:
            raise BudgetExceeded("疑似循环: " + sig)
        if self.spent_usd + est_usd > self.max_usd:
            raise BudgetExceeded(f"任务预算将超出: {self.spent_usd + est_usd:.3f} USD")

    def settle(self, in_tok: int, out_tok: int, price_in: float, price_out: float):
        self.spent_usd += in_tok / 1e6 * price_in + out_tok / 1e6 * price_out
```

注意「先预估再结算」这一步。很多团队只在调用结束后记账，等发现超额时钱已经花出去了。预估可以很粗糙，用输入 token 数加上 max_tokens 乘以单价就行，宁可高估一点。另外重复调用的签名要对参数做归一化，否则攻击者改一个空格就能绕过检测。

预算耗尽时的用户体验同样要设计。直接抛出异常、返回五百错误，会让正常用户以为系统坏了并反复重试，反而放大消耗。更好的做法是返回已完成的部分结果，说明在哪一步因为什么上限停下，并告诉用户可以缩小问题范围后重新提交。

## 别忘了你看不见的那部分 token

reasoning 模型让成本攻击变得更隐蔽。你在日志里看到的回答可能只有两百字，但背后的思考 token 有两万个。如果你的计量只统计可见输出，那么监控面板上一切正常，账单却在飞涨。所以计费一定要以供应商返回的 usage 字段为准，并且把 reasoning token 单独列一栏。

外部工具也是一样。Agent 调一次网页搜索、一次 OCR、一次地图 API，每一项都有自己的单价，而且常常比模型本身更贵。我建议把工具费用和模型费用放进同一个预算对象，统一折算成金额，而不是各管各的。否则模型预算守住了，第三方 API 的账单却悄悄翻了倍。

还有一个容易漏掉的点是重试。SDK 默认的指数退避重试、你自己写的「解析失败就再问一次」，在正常流量下无伤大雅，但在攻击场景下会把放大倍数再乘一遍。重试本身也要计入预算，并且对同一个输入的重试次数设置上限，超过就直接失败，而不是无限兜底。

缓存是另一道被低估的防线。同一个用户在几分钟内重复提交相同问题，或者大量用户问的是同一类公开信息，完全可以命中语义缓存或前缀缓存，直接返回结果。它省下的不只是正常流量的钱，也让刷同一请求的攻击几乎没有边际成本。

## 上线前先做一次成本压测

Denial of Wallet 应该进你的 Eval 体系，而不是只靠线上监控兜底。做法是准备一组「成本对抗样本」：诱导长输出的、诱导长推理的、诱导工具循环的、超长输入的，各十来条，然后在预发环境跑一遍，记录每条样本的 token、步数、金额和最终结局。

验收标准不是「模型有没有回答」，而是三件事：每条样本的花费是否被限制在任务预算以内；触发熔断时用户是否得到清晰的提示而不是报错堆栈；监控面板是否在一分钟内出现对应的异常信号。任何一项不达标，都说明你的上限只是写在配置里，没有真正生效。

我还会把这组样本接进 CI，和质量回归一起跑。原因很现实：换了一个更强的模型、改了一版系统提示、加了一个新工具，都可能让平均步数悄悄上涨。成本回归和质量回归一样，需要基线和阈值，比如平均单任务成本上涨超过百分之二十就阻断合并，先查清原因再上线。

线上监控则要盯分布而不是平均值。成本攻击往往集中在少数账号或少数会话上，平均单价可能只涨了一点，但百分之九十九分位已经翻了十倍。按用户、按会话、按入口分别画出成本分位曲线，再对单账号的突增设置告警，才能在第一个小时内发现异常。

## 实战清单

- 每次模型调用都显式设置 max_tokens，按场景分档，不要用默认的最大值。
- reasoning 模型限制 effort 或思考预算，计费以 usage 为准并单列思考 token。
- Agent 设步数上限、同参调用上限和总时长上限，三者缺一不可。
- 预算按任务、用户、租户分层，超限动作分别是终止、降级、告警。
- 调用前预估扣费，调用后按实际结算，重试和工具费用一并计入。
- 匿名或免费用户的额度单独核算，注册门槛本身就是一道成本防线。
- 准备成本对抗样本并接进 CI，平均成本超过基线阈值就阻断发布。

一句话总结：内容安全守的是模型说什么，成本安全守的是模型能干多久，后者没有上限的系统，迟早会被人用合法请求打穿。
