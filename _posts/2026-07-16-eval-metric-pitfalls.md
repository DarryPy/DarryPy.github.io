你拿 ROUGE-L 跑了一遍，0.72，不错。GPT-4o-as-judge 平均打了 8.3/10，也漂亮。然后上线，用户投诉"这 AI 废话连篇"——发现了吗？指标和体验之间有一条隐形的鸿沟。

根本原因不是指标本身有问题，而是**你在度量的东西和用户真正在意的东西根本不是同一件事**。ROUGE 量的是词汇重叠，用户在意的是信息密度；LLM-as-judge 量的是"听起来合理"，用户在意的是"用起来有没有帮助"。

这篇文章从实际踩过的坑出发，拆解五种最常见的 Eval 指标陷阱，帮你构建一个不会被数字蒙蔽的评估体系。

## 陷阱一：BLEU / ROUGE 量的是"形似"，不是"质优"

BLEU 和 ROUGE-L 本质上是 n-gram 重叠度计算：你的输出和参考答案用词越相近，分越高。这在 2014 年机器翻译时代是合理的，但放进现代 LLM 评测，问题很多。

第一，同义词替换会让分数下跌，但语义完全等价。"帮我订一张票"改成"帮我买一张票"，ROUGE 认为是坏的，用户感知不到差别。

第二，冗余重复同样词汇可以撑高分数，但答案本身臃肿不堪。一个把参考答案里关键词全部抄进去、再填一大段废话的模型，ROUGE 往往比简洁精准的版本更高。

第三，对话、摘要、代码三类任务用同一套词汇重叠指标，本身就是类别错误——代码生成根本不应该用 ROUGE 评，函数名相同不代表逻辑正确。

**替代方案**：代码生成用执行通过率（pass@k）；摘要任务补充 BERTScore（语义级别的相似度）；对话任务优先用面向任务完成率的指标。

## 陷阱二：LLM-as-judge 有两种系统性偏差

让 GPT-4o 当裁判打分，成本低、扩展性好，已经是行业标配。但它本身携带两类系统性偏差，会让评测结论失真。

**位置偏差（Position Bias）**：在 A/B 对比评测里，排在前面的答案得分会系统性偏高 5-15%，与内容质量无关。这是 LLM 在上下文里的注意力分布导致的，和具体模型版本关系不大。

**奉承偏差（Sycophancy Bias）**：judge 倾向于认为语气更自信、格式更漂亮的答案更好，哪怕内容有明显事实错误。一个答案如果用了加粗标题、清晰列表，哪怕内容平庸，也能多拿 0.5-1 分。

解决方法：每个 pair 翻转顺序做两次评测，取平均消除位置偏差；在 judge prompt 里显式要求"优先看事实准确性，忽略排版格式"；高风险任务另外抽样做人工核查。

## 陷阱三：Accuracy 不告诉你模型在哪里错

分类任务里，整体准确率 92% 听起来很好。但如果数据集正负样本是 92:8，那"全预测为正类"也能拿到 92% Accuracy，模型学到了什么都没学。

更隐蔽的版本出现在 LLM 场景里：模型在常见问题上表现完美，在边缘 case 上一塌糊涂，而边缘 case 恰好是生产环境最容易翻车的地方。整体 Accuracy 高，遮蔽了真正危险的失效模式。

解决方法：按难度和类别拆分测试集，分别报告各子集的 F1 和错误率；明确标记哪些是 hard case，把它们的通过率当作质量门槛，而不是整体平均值。

## 陷阱四：Faithfulness 高不代表 RAG 有用

RAG 评估里，Faithfulness 看的是"答案有没有超出 context 范围乱说"。这是必要条件，但不是充分条件。

一个只会回答"根据提供的文档，无法回答此问题"的模型，Faithfulness = 1.0，因为它确实没有乱说——但 Answer Relevance = 0，用户什么有价值的东西也没得到。

很多团队上线 RAG 后只看 Faithfulness，觉得"不幻觉了就是好的"，结果用户体验依然很差，根因是相关性完全没评。

**完整的 RAG 评估三角**：Context Precision（检索回来的有没有用）+ Faithfulness（生成有没有超范围）+ Answer Relevance（答案有没有真的回答问题）。三个都高才算合格，缺一不可。

## 陷阱五：Human Eval 的标注员不是你的用户

雇外包标注员做人工评估，看起来是金标准，实际上藏着一个隐患：标注员按任务说明行事，不是真实用户在真实场景下做决策。

常见失真：长答案因为"看起来全面"被偏好，短而精准的答案反而评分低；领域专业任务（医疗、法律、代码审查）如果标注员没有背景知识，评分可信度接近随机；标注员知道自己在评 AI，会带入"AI 应该这样说"的先入印象，而不是"我作为用户需要这个"。

解决方法：标注员尽量从目标用户群体招募，或者让产品团队和核心用户直接参与抽样评审；盲测（不告知是 AI 生成还是人工生成）比知情评测更可信。

## 对比一览：各指标的度量边界

| 指标 | 真正在量什么 | 典型失效场景 |
|------|------------|------------|
| ROUGE-L / BLEU | 词汇 n-gram 重叠 | 同义改写、冗余填充 |
| LLM-as-judge | 语言质量的感知评分 | 位置偏差、奉承偏差 |
| Accuracy | 整体标签正确率 | 类别不平衡、边缘失效 |
| Faithfulness | 输出是否超出 context | 高分但拒绝回答 |
| Human Eval | 标注员的主观判断 | 非目标用户、领域外标注 |

## 构建"不被骗"的 Eval 体系

好的评估体系不是找一个完美指标，而是**多指标交叉约束，让它们互相拆台**。

**配对互制**：Faithfulness + Answer Relevance 同时高才放行；Accuracy + 分类别 F1 同时上报，防止整体数字掩盖局部崩塌。单一指标通过就放行，是最常见的自我欺骗。

**拆分难度集**：把测试集分为 easy / hard 两档。easy 集确认基础能力没有退化；hard 集（边缘 case、对抗输入、领域冷门问题）才是真正的质量门槛，上线前 hard 集通过率必须达标。

**用户对齐校验**：每隔一段时间，从真实用户交互里随机抽 50-100 条，和产品团队一起做盲评，与自动化指标对比。如果两者方向不一致，自动化指标就已经失效了，需要重新设计。

**绑定业务数据**：最终的真相是业务指标：用户续问率、任务完成率、人工修正频率。把 LLM eval 分数和这些业务指标做长期相关性分析，找到真正有预测力的 eval 维度，淘汰没有预测力的。

**版本间相对变化优先**："ROUGE 0.72 好不好"没有意义；"这次比上次 ROUGE 降了 0.03，但 LLM-judge 提升了 0.5"才是可以决策的信息。绝对分数参考价值有限，趋势和回归才是关键。

## 踩坑清单

- [ ] 上线前跑了至少两种互补指标，没有靠单一分数拍板
- [ ] LLM-as-judge 评测翻转了 A/B 顺序，抵消位置偏差
- [ ] Accuracy 任务额外输出了各类别 F1，不只看整体准确率
- [ ] RAG 流程同时评了 Faithfulness 和 Answer Relevance，两个都达标
- [ ] 测试集包含边缘 case 和对抗样本，hard 集单独设了通过率门槛
- [ ] 做过至少一次自动指标 vs 真实用户反馈的对齐校验
- [ ] Human Eval 标注员的领域背景和目标用户基本一致

**一句总结**：Eval 指标是探照灯，不是裁判席——它帮你找到该看的地方，但说了算的永远是用户。
