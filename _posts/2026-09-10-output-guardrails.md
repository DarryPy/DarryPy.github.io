你把 Prompt Injection 防住了，输入侧的过滤器也上了，可上线第二周还是出事：模型在一次看起来完全正常的对话里，把另一个用户的订单号原样吐了出来。攻击者什么都没干——是模型自己在拼答案时"想多了"，顺手带出了 context 里不该暴露的字段。这类事故的共同点是，它们绕过了你所有的输入防御，因为问题根本不在输入。

输入护栏管的是"别让脏东西进来"，输出护栏管的是"别让不该出去的东西出去"。这是两道彼此独立的闸门：输入干净不代表输出安全，输出检查也补不回输入的漏洞。很多团队只做了前者，以为把用户管住就万事大吉，结果最危险的泄露恰恰来自模型的正常输出。今天只聊输出这一侧——它更隐蔽，也更容易在上线后半夜把你叫醒。

## 护栏到底在拦什么

输出侧的风险不是一类，而是四类，混在一起谈一定会漏。第一类是敏感信息泄露：PII、内部工号、别的用户的数据，模型在组织语言时顺手带出。第二类是越权或违规内容：暴力、违法指引、明显歧视，哪怕用户压根没这么要求，模型也可能自己"发挥"出来。第三类是格式违约：你要一段严格 JSON，它回你一段带寒暄和解释的 Markdown，下游解析直接崩。第四类是事实性风险：一本正经地编造 API、编造数字、编造引用。

这四类的检测手段几乎没有交集。PII 靠模式匹配，违规内容靠语义分类，格式违约靠 schema 校验，事实性靠检索比对或 LLM 复核。你不可能用一个正则、一个模型把四类全兜住。护栏设计的第一步，是先把你的业务到底怕哪几类想清楚——大多数 to C 产品最怕前两类，而 to B 的 API 服务最怕第三类，选型完全不同，别照抄别人的方案。

举个最容易被低估的例子：模型没有直接吐出手机号，而是说"尾号 8341 的那位客户，住在你上次提到的小区"。单看每个字段都不算 PII，正则一个都命不中，可拼起来足以定位到具体的人。这就是为什么规则层永远只是底线——真正危险的泄露往往是跨字段、语义级的，需要更上层的手段才拦得住。你先得承认单靠正则兜不住，才不会在事故复盘时才发现护栏形同虚设。

## 三层拦截：规则、分类器、LLM 裁判

一条好的护栏是流水线，不是单点：越靠前越便宜，越靠后越准，请求应该尽量在前面就被解决掉。规则层——正则、关键词表、JSON schema 校验——几乎零延迟零成本，天生适合抓 PII 和格式违约。分类器层用一个小模型给 toxicity、语义 PII 打分，几十毫秒能覆盖规则抓不到的语义风险。裁判层用 LLM-as-Judge，最贵，但只有它能判断"这段话放在这个上下文里到底算不算越权"。原则很简单：能用规则解决的绝不上模型，能用小模型的绝不上大模型。

| 层级 | 手段 | 延迟 | 成本 | 擅长 |
|---|---|---|---|---|
| 规则层 | 正则 / schema / 关键词 | <1ms | 几乎为零 | PII、格式违约 |
| 分类器层 | 小模型打分 | 10–50ms | 低 | toxicity、语义 PII |
| 裁判层 | LLM-as-Judge | 300ms+ | 高 | 上下文相关的越权判断 |

这张表的用法不是"三层全上"，而是按你的风险画像裁剪：纯内部工具可能只要规则层，面向公众的对话产品才值得把裁判层加上。层数越多越安全，但也越慢越贵，别一上来就堆满。

## 一个最小可用的输出护栏

先把便宜的挡在最前面。下面这段代码把 PII 正则和 schema 校验串起来，任何一层不过就拦截，绝不把原文返回：

```python
import re, json

PII_PATTERNS = {
    "email": r"[\w.-]+@[\w.-]+\.\w+",
    "phone": r"1[3-9]\d{9}",
    "id_card": r"\d{17}[\dXx]",
}

def guard(output: str, need_json: bool = False) -> dict:
    # 1. 规则层：PII 扫描
    for name, pat in PII_PATTERNS.items():
        if re.search(pat, output):
            return {"blocked": True, "reason": f"PII:{name}"}
    # 2. 规则层：结构校验
    if need_json:
        try:
            json.loads(output)
        except json.JSONDecodeError:
            return {"blocked": True, "reason": "format:not_json"}
    # 3. 通过，交给下一层（分类器 / 裁判）
    return {"blocked": False, "output": output}
```

这段代码看着简单，但两个细节最容易被忽略。第一，拦截后返回的是一句兜底话术，不是原文——把命中 PII 的原文回给用户，等于护栏白做。第二，每次命中都要把样本落日志：这些真实的违规样本，就是你下一版分类器和裁判 Prompt 的训练与调优数据，丢了就等于每次都从零开始。

还有一个部署位置的选择常被忽视：护栏应该同步阻塞在返回链路上，而不是异步事后审计。异步审计能帮你统计和复盘，但拦不住已经发出去的那一条——用户早就看到了。对真正会造成泄露或合规风险的类别，必须让护栏卡在 output 和用户之间，宁可多几十毫秒，也不能让脏内容先出门再报警。至于哪些类别值得同步阻塞、哪些走异步就够，同样要按风险画像分级，别一刀切。

## 别把护栏做成延迟黑洞

护栏最常翻车的地方不是准确率，是延迟。如果每个 output 都串一次 LLM 裁判，首 token 还没出，用户已经干等了半秒，再安全的产品也会被嫌慢。有三个务实的办法。一是分层短路：规则层拦住就立刻返回，不再往后走，大部分正常请求根本碰不到裁判层。二是流式增量检查：在 streaming 场景边生成边扫，发现违规立刻掐断，而不是等全文生成完再一次性判。三是采样裁判：不是每条都过 LLM，按风险等级或按比例抽样，高风险场景全过、低风险场景抽查。

安全和体验永远在互相拉扯。你要的从来不是"零风险"，而是"在可接受延迟内够用的安全"——这条线画在哪，是产品决策，不是纯技术问题，得让业务一起拍板。

## 护栏本身也要被评估

很讽刺：护栏往往是整个系统里最没人测的一段代码，因为它"看起来只是几个 if"。但它有两个必须盯的指标——漏放率（该拦的没拦）和误杀率（不该拦的拦了）。误杀比漏放更隐蔽：用户不会投诉"我本该看到的内容没看到"，他只会默默觉得这产品很笨，然后流失，你连数据都收不到。

所以给护栏也建一个小 golden set，正例负例都要，每次改规则或改裁判 Prompt 都跑一遍回归，盯住这两个数字有没有恶化。护栏没有 eval，它就只是又一个凭感觉的黑盒，和你想防的那个不可控模型没有本质区别，只是这次黑盒是你自己写的。

golden set 也不是建一次就完事。攻击手法在变，业务话术在变，你上个月觉得安全的输出，这个月可能就成了新的泄露口。最好的补样来源就是线上真实拦截日志——把误杀和漏放的 case 定期回捞进 golden set，让它跟着业务一起长。护栏是活的，评估也得是活的，一套三个月不更新的测试集，给你的只是一种"还安全"的错觉。

**最后，一份踩坑清单，照着自查：**

- 只做输入护栏、不做输出护栏：模型自曝数据这条路一直开着
- 拦截后把原文一并返回：等于没拦
- 全量上 LLM 裁判：延迟和账单一起爆
- 只测漏放、不测误杀：是安全了，但产品悄悄变蠢没人知道
- 护栏规则硬编码、命中不留日志：真实违规样本白白流失，迭代无依据
- 把 PII 正则当万能：跨字段拼出来的隐私，单条正则根本看不见

一句话记住：输入护栏防的是攻击者，输出护栏防的是模型自己——而后者，才是上线后真正让你半夜爬起来的那一个。
