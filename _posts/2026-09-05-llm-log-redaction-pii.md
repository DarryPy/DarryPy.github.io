你排查一个线上 bug，翻开日志，随手就能看到用户完整的对话内容、邮箱、甚至上游返回里夹带的 API Key。这在 LLM 应用里太常见了。prompt 里拼满业务数据，response 又长又杂，图省事整段打进日志，等到某天被监控平台、下游系统、外包同事看到，隐私就这么漏了出去。这篇把该脱敏什么、在哪一层做、脱敏后又怎么排障，一次讲清楚。

## 日志为什么是重灾区

LLM 应用的输入输出天生是大段自然语言，你很难像传统接口那样只记几个结构化字段。prompt 里可能拼进了用户订单、聊天记录、身份证号，response 里可能带回模型复述的隐私内容。再叠加排障时"先全量打日志再说"的惯性，日志就成了整个系统隐私密度最高的地方，比数据库还危险。数据库好歹有行级权限和审计，日志往往是全组可见、还会被采集到第三方平台长期留存。

更麻烦的是泄露路径隐蔽。你以为日志只躺在服务器上，实际上它会流进 ELK、流进 APM、流进告警消息、甚至被打进异常上报的 SaaS。任何一个环节的权限没收紧，全量 prompt 就暴露了。很多合规事故不是黑客攻进来，而是内部一条链路的日志被越权访问。所以脱敏不是锦上添花，而是 LLM 应用上线前的硬门槛，得在写第一行 `logger.info` 之前就想清楚。

## 到底哪些东西要脱敏

先分清两类：一类是用户隐私 PII，一类是系统凭据 secrets。很多人只盯着邮箱手机号，其实凭据泄露的危害更直接更致命，一个 key 泄露可能意味着整个账户被盗刷。下面这张表是我踩过坑后固定下来的清单，照着落地基本不会漏：

| 类别 | 典型字段 | 处理方式 |
| --- | --- | --- |
| PII | 邮箱、手机、身份证、地址、姓名 | 掩码保留首尾，如 `a***@x.com` |
| 凭据 | API Key、Bearer Token、Cookie | 整体替换为 `***` |
| 业务敏感 | 订单号、余额、病历、合同 | 按需哈希或截断 |
| 大字段 | 完整 prompt / response | 采样加截断，只留长度和 hash |

凭据这一栏尤其要警惕上游穿透。你调外部 API 拿回的报错体里，经常原样带着请求头或签名串；模型在 tool 调用里也可能把 key 复述进 response。这些不是你主动打的，却照样会进日志，所以脱敏规则必须覆盖"响应内容"而不只是"请求参数"。另外别忘了 metadata：user_agent、referer、cookie 这些看似无害的字段，拼起来一样能定位到具体的人，脱敏清单要把它们也纳进来。

还有个容易被忽略的维度是分级。不是所有敏感字段都一刀切打成 `***`，你得区分"完全屏蔽"和"部分可见"。凭据必须全屏，因为留任何一位都没意义；邮箱手机则保留首尾方便人工比对，既能确认是不是同一个用户，又不暴露完整值。把这套分级写进配置而不是散在代码里，后面加字段、调策略才不用满仓库改正则。

## 脱敏应该做在哪一层

最稳的做法是双层防御。源头做白名单，只把明确需要的字段结构化写入；出口再挂一个兜底的 redactor，作为最后一道防线，防止某个同事图快直接 `logger.info(prompt)` 把整段捅出去。兜底层用日志框架的 filter 实现最省心，它对所有日志生效，谁都跑不掉：

```python
import re, logging

PATTERNS = [
    (re.compile(r'sk-[A-Za-z0-9]{20,}'), '***KEY***'),
    (re.compile(r'Bearer\s+[A-Za-z0-9._\-]+'), 'Bearer ***'),
    (re.compile(r'(\w)[\w.+-]*(@\w+\.\w+)'), r'\1***\2'),
    (re.compile(r'1[3-9]\d{9}'), '***PHONE***'),
]

def redact(text: str) -> str:
    for pat, repl in PATTERNS:
        text = pat.sub(repl, text)
    return text

class RedactFilter(logging.Filter):
    def filter(self, record):
        record.msg = redact(str(record.msg))
        return True

logging.getLogger().addFilter(RedactFilter())
```

正则兜底不是万能的，它会漏掉没有固定格式的隐私，比如自由文本里的人名和地址。所以别把它当唯一手段，真正的隐私控制在源头：能不打的原文就不打，要打就先过结构化提取，只留业务需要的最小字段。兜底层负责接住漏网之鱼，而不是承担全部责任。两层各司其职，源头减量、出口兜底，才不会顾此失彼。

## 性能和误伤怎么权衡

脱敏是有成本的。每条日志都跑一遍多个正则，在高 QPS 下 CPU 开销不容忽视，尤其 response 动辄几千 token，正则回溯还可能拖慢主链路。实战里我一般把重脱敏放到异步日志管道，主线程只做轻量的凭据替换，PII 掩码交给 sink 侧的 worker 批量处理，避免阻塞请求。真的扛不住，就先在源头把大字段截断，别指望出口层去啃整段长文本。

另一个坑是误脱敏。正则太激进会把正常内容也打码，比如把订单号里恰好像手机号的一段替换掉，排障时就看不出真实值了。所以正则要收紧边界、加锚点，宁可少抓一点、由源头白名单补位，也别让日志被打得面目全非。上线前拿真实流量样本回放一遍，统计脱敏命中率和误伤率，心里才有数。

这套规则还得纳入回归测试。每次改正则、加字段，都跑一遍固定的样例集，断言凭据一定被屏蔽、正常内容一定不被误伤。脱敏逻辑一旦上线就很难验证是否退化，只有用例把它钉死，你才敢放心迭代，而不是每次改动都提心吊胆地怕漏掉一类隐私。

## 脱敏之后还怎么排障

脱敏最大的顾虑是"删干净了还怎么定位问题"。答案是用可关联的替身。给每个请求生成 request_id，把原文的 hash、长度、token 数一起记下来。排障时你看到的是 `hash=8f3a len=1204`，虽然读不到内容，但能确认是不是同一段输入、有没有被截断、复现时比对 hash 就知道命中的是不是同一条，绝大多数问题不需要真的看到原文就能定位。

真要看原文时，走单独的审计通道：短 TTL、强权限、独立存储，和普通日志物理隔离。需要深挖某个 case 就带工单去申请调阅，用完即焚。这样既满足了合规的可追溯，又不会让明文隐私常态化地散落在人人可见的日志里。日常可观测性和敏感原文调阅，本就该是两套权限、两条链路，别图省事混成一摊。

保留期同样是脱敏的一部分。就算脱过敏，`hash` 和 metadata 攒久了也能被拼图还原，所以普通日志设 7 到 30 天自动过期，审计原文压到 24 小时甚至更短。个人信息保护法和 GDPR 都要求"最小必要"和"限期删除"，把 TTL 写进采集配置由系统强制执行，比靠人记得清理靠谱得多。合规审计真来查的时候，你能拿出一条自动化的删除策略，远比一句"我们会定期清"有说服力。

## 踩坑清单

- 只脱请求不脱响应：模型复述和上游报错会把隐私从 response 带回来，规则要双向覆盖。
- 异常栈里漏光：`repr(exception)` 常把整个 payload 拼进堆栈，异常上报前必须再过一遍 redactor。
- 采样把敏感样本留全文：调试采样很方便，但采样命中的那几条同样要脱敏，别开后门。
- 正则当万能药：自由文本的人名地址正则抓不住，源头白名单才是主力。
- 脱敏在应用层做完转发 sink 又还原：确认 ELK / APM 采集的是脱敏后的流，别让中间件绕过你的 filter。

一句话：日志里能看到的东西，就是未来某天可能泄露的东西。上线前把它当敏感数据管，用双层防御守住、用审计通道兜底、用保留期收口，而不是等出事了再回头补，那时候数据早就散出去了。
