你大概率在代码里写过 `top_k=5`，然后再也没动过它。问「年假几天」这种单点问题，5 段里只有 1 段有用，剩下 4 段是噪声，LLM 还可能被其中一段旧制度带偏；问「对比三个版本的退款政策」，5 段又明显不够，答案缺一角。固定条数的本质，是假设所有问题需要的信息量一样，而这个假设几乎从不成立。

我在一个内部知识库项目里统计过：把 top_k 从固定 5 改成按分数动态截断后，平均上下文 token 降了 38%，引用错误率降了接近一半。这篇就讲怎么做到这件事，以及中间那些容易踩的坑。

## 为什么固定 Top-K 会坑你

固定 Top-K 有两种失败模式。第一种是「凑数」：库里真正相关的只有 1 段，但系统硬要返回 5 段，于是相似度 0.42 的无关段落也被塞进 prompt，LLM 很难判断哪段该信，最后编出一个缝合答案。第二种是「截肢」：问题需要汇总多处信息，相关段落有 9 段，你只给了 5 段，模型拿着残缺证据作答，还写得很自信。

更隐蔽的问题是成本。上下文越长，推理延迟和 token 费用线性上涨，长上下文里中间位置的信息还会被模型忽略。你用 reranker 精排过的结果，如果后半截全是低分噪声，等于花钱给模型增加干扰。动态 Top-K 要解决的，就是让返回条数由「相关性」决定，而不是由一个拍脑袋的常量决定。

还有一个反直觉的现象：很多团队发现答案质量差，第一反应是把 top_k 调大，觉得多给点上下文总没坏处。实际评测下来，调大之后召回率确实上去了，但答案的忠实度反而下降，因为模型面对更多相互矛盾的段落时，更容易挑错依据。问题不在给得多还是少，而在给的是不是对的。

## 三种截断策略对比

常见的动态截断方法有三类：绝对阈值、相对阈值和断崖检测。绝对阈值最直观，分数低于某个值就丢弃；相对阈值以第一名为基准，只保留分数不低于最高分某个比例的结果；断崖检测则看相邻分数的落差，在落差最大的位置切一刀。三者各有适用场景，实际项目里往往组合使用。

| 策略 | 规则示例 | 优点 | 缺点 | 适合场景 |
|------|----------|------|------|----------|
| 绝对阈值 | score ≥ 0.55 | 简单、可解释 | 分数分布随 query 漂移 | reranker 分数已校准 |
| 相对阈值 | score ≥ top1 × 0.8 | 自适应 query 难度 | top1 本身低时会放进噪声 | 向量相似度原始分 |
| 断崖检测 | 相邻落差 > 0.15 处截断 | 贴合真实分布 | 分数平缓时找不到断点 | 结果条数波动大 |
| 组合策略 | 绝对下限 + 断崖 + 上下限 | 稳健 | 参数多，需要标定 | 生产环境 |

关键前提是：这些规则都依赖分数「有意义」。原始 cosine 相似度在不同 embedding 模型下分布差异很大，有的模型所有结果都挤在 0.7 到 0.85 之间，阈值几乎没有区分度。所以生产里我更推荐在 reranker 之后做截断，cross-encoder 的输出经过 sigmoid 后更接近概率含义。

如果你暂时没有 reranker，也可以先用相对阈值顶上，它对分数的绝对尺度不敏感，只关心和第一名的差距。但要额外加一条保护：第一名分数本身也要过一个最低线，否则当整个库都没有相关内容时，相对阈值会把一堆同样无关的结果原样放进来。

## 组合截断的代码实现

下面是我在项目里用的组合策略：先用绝对下限过滤明显无关的结果，再在剩余结果里找最大落差做断崖截断，最后用 min_k 和 max_k 兜住两端。min_k 防止截到 0 条导致模型无据可依，max_k 防止宽泛问题把上下文撑爆。

```python
import math

def sigmoid(x):
    return 1 / (1 + math.exp(-x))

def adaptive_cut(results, floor=0.35, gap=0.15, min_k=1, max_k=8):
    # results: [(doc_id, raw_logit), ...]，已按 reranker 分数降序
    scored = [(d, sigmoid(s)) for d, s in results]
    kept = [r for r in scored if r[1] >= floor]
    if not kept:
        # 全部低于下限：交给兜底逻辑，而不是硬塞低分段落
        return [], "no_relevant"
    cut = len(kept)
    for i in range(1, len(kept)):
        if kept[i - 1][1] - kept[i][1] > gap:
            cut = i
            break
    cut = max(min_k, min(cut, max_k))
    return kept[:cut], "ok"

hits = [("a", 3.1), ("b", 2.8), ("c", 0.2), ("d", -0.5), ("e", -1.9)]
docs, status = adaptive_cut(hits)
print(status, [(d, round(s, 2)) for d, s in docs])
# ok [('a', 0.96), ('b', 0.94)]
```

注意 `no_relevant` 这个返回状态。动态截断最大的价值之一，是让系统第一次有能力说「我没找到」。当所有结果都低于下限时，你应该走兜底话术或者触发 query 改写重试，而不是把三段低分噪声交给 LLM 让它硬编。

参数含义也说一下。floor 是绝对下限，决定什么算「相关」；gap 是断崖灵敏度，越小切得越激进；min_k 和 max_k 是安全边界。我一般先把 gap 设成 0.15，再用标注集微调。另外断崖只找第一个大落差，是有意为之：第一个断点之后的结果，即使内部还有小簇，通常也已经是次要信息了。

## 阈值怎么标定，而不是怎么拍

阈值不能靠感觉定，要用标注集标定。做法是准备 200 到 500 条真实 query，每条人工标出相关段落，然后跑一遍检索加 rerank，把每个候选的分数和是否相关的标签存下来。这样你就有了一张分数与相关性的对照表，可以画出不同阈值下的 precision 和 recall 曲线，选一个业务能接受的平衡点。

如果 reranker 的分数和真实相关概率偏差较大，可以再做一层校准，比如用 Platt scaling 或 isotonic regression，把分数映射成「这段相关的概率」。校准后的好处是阈值有了统一语义，0.6 就代表六成把握，换模型时只需要重新拟合映射，下游的截断逻辑和配置都不用改。

我的经验是：客服、制度问答这类对准确性敏感的场景，优先保 precision，下限可以设高一点，宁可少给也别给错；研究、汇总类场景优先保 recall，下限放低，同时把 max_k 放大。还有一点常被忽略，就是阈值要按 query 类型分组标定。短关键词 query 和长自然语言 query 的分数分布往往不同，用同一个阈值，一类会过严，另一类会过松。

标定完不是终点。embedding 模型、reranker 版本或者文档库结构一变，分数分布就会漂移，原来的阈值可能突然失效。建议在线上记录每次检索的截断条数分布和 `no_relevant` 比例，一旦这两个指标出现明显跳变，就说明需要重新标定了。

我还会把 `no_relevant` 的 query 单独收集起来，每周抽样看一遍。这里面通常混着两类问题：一类是库里确实没有答案，属于知识缺口，应该推给内容团队补文档；另一类是库里有答案但没检索到，说明 query 改写或 chunking 出了问题。这个分桶本身，就是动态截断带来的额外收益。

## 上线前的实战清单

动态 Top-K 改动小、收益大，但它改变的是「喂给模型多少证据」这件根本的事，上线前一定要对照检查。下面这份清单是我踩过坑后整理的，每一条都对应过一次真实事故或者回滚，建议你逐项过一遍再切流量。

- **先 rerank 再截断**：原始向量相似度分布太挤，直接设阈值几乎等于没设。
- **保留 min_k 兜底**：但当最高分都低于下限时，要走「没找到」分支，别让 min_k 把噪声硬塞进去。
- **max_k 按上下文预算算**：用 token 预算反推条数上限，而不是随手写个 10。
- **阈值随模型版本绑定**：换 embedding 或 reranker 后，旧阈值一律作废，重新标定。
- **按 query 类型分组**：关键词、问句、对比类问题分别统计分数分布。
- **监控截断分布**：平均条数和 `no_relevant` 比例都要上看板，漂移就报警。
- **A/B 看答案质量**：只看 token 降了多少是不够的，要同时看准确率和引用正确率。

一句话总结：top_k 不该是一个常量，而该是一次判断。让分数告诉你该给几段，比你替所有问题拍一个数字靠谱得多。
