你给团队做了一个内部 Agent，能查工单、改 Jira 状态、发 Slack 消息。上线第一周大家都很满意，直到有个实习生问它「帮我看看 CEO 上周的日程」，它真的查出来了。原因很简单：后端所有工具都用同一个管理员服务账号调用，Agent 根本不知道「谁在问」。

这类问题和沙箱、护栏不是一回事。沙箱管的是代码能不能碰宿主机，护栏管的是输入输出内容是否越界，而这里的核心是身份：工具调用时代表的是哪个人，这个人本来能做什么，Agent 又被允许替他做多少。

## 三种身份模型，各有各的坑

我见过的 Agent 工具鉴权，大致落在三种模型里。第一种是共享服务账号，最省事，但等于把所有用户的权限并集交给了模型；第二种是直接透传用户令牌，权限天然对齐，却让一个高权限长令牌在多步任务里四处流转。

第三种是令牌交换：用户登录后，网关在每次工具调用前用用户身份换一个短期、窄范围的下游令牌，只给这一个工具、这一类操作用。它实现成本最高，但也是唯一能同时做到「权限对齐」和「影响面可控」的方案。

选型时别只看实现难度，还要看你的下游系统支持什么。如果下游只认静态 API Key，令牌交换就无从谈起，这时至少要在网关层按用户做一次权限映射，把「谁能调什么」的判断收回到自己手里，而不是交给下游的一把万能钥匙。

| 模型 | 权限是否对齐用户 | 令牌泄露影响面 | 审计能否追到人 | 实现成本 |
| --- | --- | --- | --- | --- |
| 共享服务账号 | 否，是所有人的并集 | 极大，等于后台全开 | 只能看到服务账号 | 低 |
| 透传用户令牌 | 是 | 大，长期有效且范围宽 | 能 | 中 |
| 令牌交换（短期窄权限） | 是，且可再收窄 | 小，几分钟内过期 | 能，还能关联任务 | 高 |

如果你的 Agent 只读公开数据，服务账号完全够用；一旦涉及「某个人的」数据或写操作，至少要做到透传，最好走交换。别因为 MVP 阶段图快，把服务账号方案一路带进生产。

## 凭证永远不要进上下文

最常见的错误，是把 access token 当成工具参数让模型填。写法看起来很自然：schema 里加一个 `token` 字段，系统提示里塞上用户令牌。结果令牌进了上下文、进了日志、进了 trace，还可能被提示注入骗着原样输出到聊天窗口。

正确做法是让模型完全看不到凭证。模型只决定「调哪个工具、传什么业务参数」，鉴权由工具执行层在调用前注入。执行层从会话里拿到用户身份，再去换下游令牌，模型侧的 schema 里压根没有任何和认证相关的字段。

```python
import time

class ToolExecutor:
    def __init__(self, token_broker, audit_log):
        self.broker = token_broker
        self.audit = audit_log

    def call(self, session, tool, args):
        # 1. 身份来自会话，不来自模型输出
        user = session.user_id
        # 2. 按工具声明的最小 scope 换短期令牌
        scope = tool.required_scope(args)
        if scope not in session.granted_scopes:
            return {"error": "permission_denied",
                    "hint": "需要用户授权: " + scope}
        token = self.broker.exchange(user, scope, ttl=300)
        # 3. 执行并审计，令牌本身不写日志
        started = time.time()
        result = tool.run(args, auth=token)
        self.audit.write(user=user, task=session.task_id,
                         tool=tool.name, scope=scope,
                         cost_ms=int((time.time() - started) * 1000))
        return result
```

注意权限不足时返回的是结构化错误，而不是抛异常让整条链路崩掉。模型拿到 `permission_denied` 后，可以转而告诉用户需要授权什么，这比悄悄失败或换个工具硬绕过去要安全得多。

还有一个细节：执行层返回给模型的结果里，也要过滤掉下游接口带回来的凭证信息。有些接口会在响应头或响应体里回显会话 ID、签名链接，这些内容一旦原样喂回上下文，前面所有隔离就白做了，记得在结果处理阶段统一脱敏。

## scope 要按任务收窄，而不是按用户给满

透传用户身份只解决了一半问题。用户本人有删库权限，不代表他让 Agent「帮我整理一下本周工单」时，Agent 也该拿着删库权限去干活。这一点在提示注入面前尤其关键：一段被污染的工单描述，可能诱导模型去调用删除接口。

所以授权要按任务来，不按人来。会话开始时根据意图推导出一个最小 scope 集合，例如「只读工单、可改状态、不可删除」，写操作额外要求用户点一次确认。任务结束 scope 就作废，下一个任务重新申请，别让权限在长会话里一路累积。

实操上，我会给每个工具在注册时声明两样东西：读写级别和所需 scope 模板。像 `delete_ticket` 这种不可逆操作，scope 永远不进默认授权集合，只能由用户在界面上单独批准，并且批准后几分钟就过期，不跨任务复用。

读操作也不能完全放开。「只读」听起来很安全，但读取范围过宽同样会出事，比如一个只读的全文搜索工具，能搜到整个公司的薪酬表。读工具的 scope 同样要带资源边界，例如只能读当前用户所在项目，或者只能读用户显式指定的那几个文档。

## 多 Agent 与异步任务里的身份链

单 Agent 还好办，麻烦在于多 Agent 和后台任务。主 Agent 把子任务派给检索 Agent、写作 Agent 时，身份应该怎么传？我的原则是只能降级不能升级：子 Agent 拿到的 scope 必须是父任务 scope 的子集，并且在令牌里记录完整的委托链。

异步任务更容易出事。用户晚上布置了一个「明早帮我汇总并发邮件」的任务，第二天执行时他的登录态早已过期。很多团队的偷懒做法是存一个长期 refresh token 到任务表里，等于把用户的钥匙复印了一份放在数据库，任何能读表的人都能冒用。

更稳的方式是让用户在创建任务时显式授予一个绑定该任务 ID 的离线授权，范围只覆盖这个任务要用的工具，到期或任务完成后自动吊销。审计日志里同时记录「谁授权的、哪个任务用的、哪个 Agent 调的」，出了问题才能顺着链路追回去。

最后别忘了吊销。用户离职、改密码、手动退出登录时，所有挂在他名下的 Agent 任务和交换出来的下游令牌都要能一键作废。我建议在令牌代理里维护一张按用户索引的活跃授权表，吊销时直接按用户清空，而不是等令牌自然过期。

测试环节也要单独覆盖鉴权路径。准备几个权限各不相同的测试账号，让同一个 Agent 用同一句指令分别跑一遍，检查低权限账号是否被正确拒绝、拒绝信息是否友好、审计日志是否完整。这类用例比功能用例更容易被遗漏，却最能挡住越权事故。

## 上线前的踩坑清单

- 工具 schema 里出现 token、password、cookie 字段，说明凭证已经暴露给模型，立刻改成执行层注入。
- 所有工具共用一个服务账号，又要处理「某个人的」数据，这是越权事故的标准起点。
- 用户令牌直接塞进系统提示，日志和 trace 里全是明文，一次导出就全部泄露。
- 权限不足时直接抛异常，模型会换别的工具硬绕，应返回结构化的拒绝原因。
- 长会话里 scope 只增不减，任务结束不回收，最终退化成全权限 Agent。
- 子 Agent 继承父 Agent 全部权限，没有降级，也没有委托链记录。
- 异步任务存长期 refresh token，没有绑定任务、没有过期时间、没有吊销入口。
- 审计只记了工具名，没记用户、任务和 scope，出事后无法定位到人。

一句话总结：模型负责决定做什么，执行层负责决定能不能做，凭证永远只在执行层手里，而且越短越窄越好。
