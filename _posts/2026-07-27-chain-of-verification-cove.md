你让 LLM 列"1990 年代拿过诺贝尔物理学奖的五位美国科学家"，它会流畅地报出五个名字、五个年份，语气笃定得像从维基百科抄来。可你逐个去查，发现两个人根本不是美国籍，还有一个拿的是化学奖。这就是幻觉最阴险的地方：它不是留白，而是用高置信度把空白填满，让你懒得去核对。Chain-of-Verification（CoVe）正是冲着这个场景来的——不指望模型一次答对，而是让它答完之后自己出一套核验题，逐条独立比对，把编造的部分揪出来。它不需要外部知识库，只用几次额外调用，就能明显压低事实类回答的幻觉率。

## 幻觉为什么总是理直气壮

自回归生成的本质是"接下一个最可能的 token"，模型优化的目标是流畅度而非真值。开头几个 token 一旦走上错误轨道，后面就会自我强化，越编越顺、越编越像真的。这不是模型"想骗你"，而是它的解码机制天然偏向连贯，而连贯和正确从来就不是一回事。

更麻烦的是一次性生成长答案时，模型没有回头检查的机会。它写第五个名字时，早忘了第一个对不对；写结论时，也不会重新审视前提是否成立。人写完报告会通读一遍反复核对，而 LLM 默认"一遍过"，写完即终，没有内建的复查回路。

还有一层容易被忽略：模型的错误往往是"局部自洽"的。它给错误人名配上看似合理的年份和国籍，整段读起来毫无破绽。正因为错得体面，肉眼抽查很难发现，你需要的是一套能把答案逐项拆开、单独盘问的机制——这正是 CoVe 要补的那个洞。

## CoVe 的四步流水线

CoVe 把"生成"和"核验"彻底拆开，四步依次是：先生成基线答案 baseline；再让模型针对答案里的每个事实规划一批核验问题 plan；然后逐个回答这些核验问题 execute；最后综合核验结果重写出修正版 final。四步单看平平无奇，真正的杀招藏在第三步执行阶段。

执行核验时，关键是不给模型看原答案。如果你把 baseline 塞进上下文再问"这里对不对"，模型会本能地维护自己刚说过的话，核验就成了走过场。只有让每个核验问题在一段干净上下文里独立作答，才可能暴露它与原答案之间的矛盾。隔离语境，正是 CoVe 区别于普通"自我反思"的分水岭。

拿那道诺贝尔题走一遍：baseline 列出五个人，plan 就该生成"某人是美国籍吗""某人拿的是物理奖还是化学奖""获奖年份是不是落在 1990 年代"这类原子问题。execute 阶段在不看原答案的前提下逐题作答，一旦某题答出"化学奖"，final 阶段就能据此删掉那一项。矛盾是被独立追问逼出来的，而不是被原文自证的。

原论文其实给了四种变体：joint 把规划和执行塞进一次调用，最省钱但效果最差；two-step 拆成两次；factored 让每个核验问题各自独立回答，效果最好；factor+revise 再加一步专门比对交叉核对。规律很清晰——拆得越碎、上下文越干净，幻觉压得越狠，代价就是调用次数越多。真正落地时，优先选 factored。

有一点反直觉，值得单独点出：让模型在同一段对话里"反思一下有没有错"，效果往往聊胜于无，因为它读得到自己的原话，天然倾向于确认而非推翻。CoVe 的增益几乎全部来自这种"失忆式核验"——把核验问题从原答案里剥离出来，模型失去了自我背书的锚点，才会老老实实按事实作答。这也顺带解释了为什么 joint 变体最弱：它等于又把核验拽回了原文语境里。

## 一个能跑的最小实现

别把四步塞进一个 prompt，那等于退回最差的 joint 变体。要用多次独立调用，execute 阶段每道核验题都开一段干净上下文：

```python
def cove(question, llm):
    baseline = llm(f"回答：{question}")
    plan = llm(
        f"针对下面的回答，列出核验用的事实性问题，每行一个：\n{baseline}"
    )
    verified = []
    for q in plan.splitlines():
        if not q.strip():
            continue
        # 关键：干净上下文，绝不把 baseline 塞进来
        ans = llm(f"简短准确地回答：{q}")
        verified.append(f"Q: {q}\nA: {ans}")
    checks = "\n".join(verified)
    final = llm(
        f"原问题：{question}\n"
        f"初版回答：{baseline}\n"
        f"独立核验结果：\n{checks}\n"
        f"根据核验结果修正矛盾，删掉存疑项，输出最终答案。"
    )
    return final
```

execute 阶段的独立调用是整套方法的精髓。合并成一次多轮对话就会失效——模型看得见自己刚说过什么，自然倾向自圆其说，核验也就名存实亡。这段代码刻意没做并发，真上生产时 execute 的 N 道题彼此独立，完全可以并行发出，把翻几倍的延迟摊平回接近一次调用的水平。

## 什么时候值得用，什么时候是浪费

CoVe 不免费，它把一次调用变成 3+N 次，N 是核验问题数，延迟和成本都翻几倍。它真正擅长的是"可核验的离散事实"——人名、日期、数字、清单这类能逐条判真假的内容；而对开放式创作、主观分析、依赖实时外部数据的场景，它几乎无效，甚至会把本来不错的答案越改越差。

| 场景 | 用 CoVe | 原因 |
|------|---------|------|
| 实体列表、传记事实 | 值得 | 每项可独立核验 |
| 多步数值计算 | 部分值得 | 核验中间量优于核验最终结论 |
| 主观评价、创意写作 | 不值 | 没有客观真值可比对 |
| 需实时或外部数据 | 换 RAG | 核验凭的也是记忆，会一起错 |

想让它更狠，记三个调优点。其一，核验问题必须原子化，一题只问一个事实；笼统地问"这段有没有问题"几乎拿不到有用信号，拆成"某人是美国籍吗""某奖是哪一年颁的"才能逼出明确的真假判断。其二，给核验数量封顶，长答案能被规划出几十个问题，N 不设上限成本会直接失控，按事实密度取 5 到 10 个通常够用。

其三，final 阶段的指令要偏保守——发现矛盾时明确要求"删除存疑项"，而不是"把它改对"。模型很可能并不知道正确答案，硬改只会用一个新幻觉替换旧幻觉。一个务实的折中是别对整段答案跑 CoVe，只挑高风险字段——报告里的关键数字、直接甩给用户的结论——单独核验，把有限预算花在最容易出错也最伤人的地方。

再往前一步，CoVe 和 RAG 并不互斥，反而是绝配：用检索为每个核验问题挂上外部证据，execute 阶段就从"凭记忆自答"升级成"拿证据对质"，连模型本就不知道的知识盲区也能一并修正。纯 CoVe 治的是"知道却写错"，叠上检索才治得了"根本不知道"，两者合起来，覆盖面才算完整。

## 踩坑清单

- execute 阶段务必用干净上下文，塞进 baseline 等于让模型自我背书，核验形同虚设
- 核验问题要原子化，一题一个事实；笼统地问"有没有错"拿不到可用信号
- 别指望 CoVe 修正模型压根不知道的知识——它核验的也是自己的记忆，该错还是错，这时候要上 RAG
- 核验数量一定要封顶，否则长答案能把成本和延迟拖垮，execute 记得并发发出
- final 阶段偏保守，宁可删存疑项也别硬改，避免新幻觉顶替旧幻觉

一句话：CoVe 不是让模型变聪明，而是逼它把"一遍过"的自信，拆成"多遍查"的谨慎。
