你的 RAG 系统接了五个知识库:产品文档、代码仓库、工单记录、财报、HR 制度。用户问一句话,你把它同时打到五个库里检索,再把三十条结果一股脑塞进 context——又慢、又贵、还召回一堆噪声。Query Routing 要做的事其实很朴素:先判断这个问题该去哪个库,再检索。

## 为什么"一个大池子"会崩

最直觉的做法是把所有文档塞进同一个 index,靠向量相似度一把捞。库小的时候确实没问题,库一多就露馅:用户问产品功能,财报里语义相近的句子照样被召回到前排,reranker 再强也只是在给噪声做二次排序,召回阶段的预算早浪费掉了。

问题的根子在于,不同数据源的检索形态天生不同。代码要按符号和调用关系找,工单要带时间和状态过滤,财报要先解析表格再切块,HR 制度则更看重章节层级。硬塞进同一套 embedding 和 chunk 策略,等于逼所有库去迁就最不适配的那一个,谁都别想检索准。

还有一笔账是延迟和成本。五路并发检索就是五倍的向量计算加五倍的 rerank,而端到端延迟只会按最慢那一路算。Routing 的作用是先把问题收敛到一两个真正相关的库,检索范围小了,响应时间和 token 账单自然一起降下来。

更隐蔽的代价是权限和多租户。企业场景里,财报和 HR 制度往往只对特定角色开放,全塞一个池子意味着每次检索都得在召回之后再补一遍行级过滤,既慢又容易漏。按库路由天然带上了访问边界:先判定用户有没有资格进这个库,不合规的库压根不进检索,安全和性能一起照顾到了。

## 三种路由策略,按复杂度选

Routing 的本质是个分类器:输入一个问题,输出它该走哪一个或哪几个库。落地时常见三种做法,复杂度和准确率各有取舍。

| 策略 | 原理 | 延迟 | 适用场景 |
|---|---|---|---|
| Rule Router | 关键词 / 正则 / 元数据命中 | 极低 | 意图边界清晰(带订单号→工单库) |
| Embedding Router | 问题向量与各库描述向量比相似度 | 低 | 库多、主题语义可分 |
| LLM Router | 模型读库描述,用 function call 选库 | 高 | 意图复杂、需要拆分或多选 |

Rule Router 最快也最脆。它适合意图边界清晰的场景,比如问题里带订单号就直接走工单库,提到"薪资""考勤"就走 HR 库。零延迟、可解释,但规则是死的,覆盖不到的问题只能漏给下一层去兜。

Embedding Router 是性价比之王。给每个库写一段描述,离线算好描述向量;线上把用户问题也编码成向量,和各库描述比余弦相似度,取最高的一两个。它比 LLM 便宜两个数量级,库越多越划算,唯一前提是各库主题在语义上确实可分。

LLM Router 最灵活。把库的用途写成 description 丢给模型,让它用一次受限的 function call 选库。它能处理"这个功能为什么被改"这类需要跨库、甚至需要先拆解的复杂意图,代价是多一次模型调用的延迟和费用。

我自己的经验是三层叠着用:先用 Rule 兜掉能一眼判定的,剩下的交给 Embedding 粗筛,只有粗筛置信度不够高时才升级到 LLM。这样九成以上的流量根本不花大模型的钱,准确率却不塌。

分层的好处不只是省钱。每一层的错误都有下一层兜着:Rule 漏了 Embedding 补,Embedding 拿不准 LLM 定夺,系统整体的鲁棒性比任何单层都高。工程上也更好维护——新增一个库,先把它加进 enum 和描述向量,跑一批线上真实问题看错分率,再决定要不要专门为它补规则。

## LLM Router 怎么落地

LLM Router 写起来其实最省心。核心就两件事:把每个库的用途讲清楚,再用一个带 enum 约束的 function call 把输出锁死。路由是典型的高频、低难度任务,用 Haiku 这类又快又便宜的模型完全够用,没必要上 Opus。

```python
import anthropic

client = anthropic.Anthropic()
ROUTES = ["product_docs", "codebase", "tickets", "finance", "hr_policy"]

def route(question: str) -> list[str]:
    resp = client.messages.create(
        model="claude-haiku-4-5",          # 路由高频,选快而便宜的模型
        max_tokens=256,
        system="你是检索路由器。只选真正相关的库,拿不准就多选,别漏。",
        tools=[{
            "name": "pick_indexes",
            "description": "选出回答该问题最相关的一个或多个知识库",
            "input_schema": {
                "type": "object",
                "properties": {
                    "indexes": {
                        "type": "array",
                        "items": {"type": "string", "enum": ROUTES},
                    }
                },
                "required": ["indexes"],
            },
        }],
        tool_choice={"type": "tool", "name": "pick_indexes"},  # 强制走路由工具
        messages=[{"role": "user", "content": question}],
    )
    block = next(b for b in resp.content if b.type == "tool_use")
    return block.input["indexes"]
```

这段代码里有三个关键点。tool_choice 强制模型必须调用路由工具,它就不会跟你闲聊或解释;enum 把输出锁在合法库名集合内,省掉一层"模型是不是瞎编了个库名"的校验;而每个库 description 写得好不好,直接决定准确率——边界描述越含糊,模型越容易投错票。

值得强调的是那句 system prompt:让它"拿不准就多选"。因为在 RAG 里,路由错分导致的漏检,代价通常比多查一个库更高——多查最多费点 token,漏查直接答错。把召回的天平往高 recall 那边压一点,几乎总是划算的。

## Embedding Router:便宜且够用的中间层

如果说 LLM Router 是重武器,Embedding Router 就是日常主力。它的思路简单到几乎不像 AI:为每个库写一段能概括其内容的描述文本,离线用 embedding 模型编码成向量存好;线上来了问题,同样编码,再和这几个库向量逐一算余弦相似度,排序取前一两名。

这里最容易被忽略的,是"库描述"本身的质量。很多人图省事直接拿库名当描述,结果 finance 这种词的向量和用户口语化的提问差得很远,相似度全都偏低,路由自然乱。更好的做法是用一段自然语言:比如财报库写成"公司季度与年度财务报表、营收利润、现金流与关键财务指标",语义覆盖面立刻宽出一大截。

还有一个进阶技巧叫 routing by examples:与其描述库"是什么",不如给每个库挂几条典型问题当锚点。把这些样例问题也编码进向量库,线上拿用户问题去检索最相似的样例,再看它归属哪个库。这比抽象描述更贴近真实提问的分布,尤其适合口语化、长尾的用户输入。

至于阈值,别只取 Top-1。设一个相似度门槛,凡是超过门槛的库都召回;都不过门槛就走兜底大库。这一步把"硬选一个"变成"按需多选",能挡掉相当一部分边界模糊问题的错分。

## 别让路由变成新的瓶颈

Routing 在链路里加了一跳,用不好反而拖后腿。下面几条是踩过坑后总结的守则:

- **允许多选**:大量真实问题天生跨库,Router 要返回数组而不是单值,硬逼它二选一往往两头都不讨好。
- **永远留一个兜底库**:模型或规则都拿不准时,回退到全局大库,别让它在错误选项里硬挑一个。
- **给路由加观测**:记录每次路由的输入、选中的库、最终有没有命中,离线专门复盘错分样本,description 才有依据迭代。
- **设置置信度阈值**:低置信度的问题直接多召几个库,让后面的 rerank 去兜底,别把宝全押在单库上。
- **给高频问题加缓存**:相同或高度相似的问题反复进来时,把路由结果缓存住,省掉重复的模型调用和向量计算,长尾之外的流量几乎零成本。
- **算清楚该不该上**:库少于三个、或各库主题高度重叠时,直接全召回加 rerank 往往更简单也更准,别为了架构好看硬加一层。

说到底,路由是笔投入产出的权衡:它省下的是无关库的检索开销和噪声,付出的是一跳判定的延迟加一层要长期维护的逻辑。只有当前者稳稳盖过后者,这层分流才值得存在。

一句话:Query Routing 不是拿来炫技的,它的全部价值是把有限的检索预算花在对的库上。库不够多、边界不够清时,那多出来的一跳延迟,盖不过它省下的噪声。
