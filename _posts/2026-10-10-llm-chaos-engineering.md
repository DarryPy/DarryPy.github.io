你给 LLM 应用加了重试、熔断、超时、降级,配置写得漂亮,review 也过了,但你真的在上游崩掉的那一刻验证过它们吗?大多数团队没有。等到某天 provider 真抖动,才发现熔断阈值配反了、降级分支从上线起就没走通过、超时参数被某次重构悄悄改没了。混沌工程的思路很直白:不等故障自己找上门,你主动在可控范围内把它造出来,先炸一遍给自己看。

## 为什么 LLM 应用格外需要

传统后端的依赖相对稳定,而 LLM 的上游天然不可靠:限流随时触发、长尾延迟动辄几十秒、模型偶尔返回空内容或半截坏 JSON。这些在别的系统里算异常边界,在 LLM 这儿是日常。你写的容错代码会被高频触发,也因此更容易藏着没人发现的 bug。

更麻烦的是降级路径的"冷启动"问题。很多兜底逻辑平时根本不执行,只有真出事才第一次运行,而那恰恰是最不能出错的时刻。一段三个月没跑过的 fallback 代码,和没写过几乎没区别。混沌工程把顺序反过来——在你精力充沛、监控齐全、能随时叫停的工作时间,故意让 provider"挂"给你看。走通了你才真有底;走不通,你在白天从容地修,而不是凌晨被 oncall 电话惊醒后边打瞌睡边改。

我见过最典型的一次:某团队的 fallback 模型配置里写错了一个字段名,代码就这么静静躺了两个月,直到主模型限流那天才被第一次调用,结果 fallback 自己也抛异常,两条路一起断,用户端直接白屏一片。而这个 bug,用混沌工程在上线当天花十分钟就能照出来——代价差了几个量级。

## 该注入哪些故障

别一上来就拔网线。LLM 场景的故障有它特定的形状,建议按影响面从小到大逐个来,每一种都对应你代码里一条本该生效的保护:

| 故障类型 | 模拟方式 | 验证什么 |
|---|---|---|
| 延迟注入 | 请求前 sleep 随机秒数 | 超时预算、deadline 层层传递 |
| 限流 429 | 直接抛 RateLimitError | 退避重试、多 Key 轮换 |
| 服务 5xx | 返回伪造的 500 | 熔断阈值、fallback 模型 |
| 坏输出 | 返回空串或非法 JSON | 结构化校验、重解析逻辑 |
| 连接中断 | 流到一半 close 掉 | 流式超时、半截响应处理 |

注入的目的从来不是"看它报错"——那太容易了。真正要看的是报错之后,系统有没有安静地按设计走到正确分支:该退避的退避了,该切 Key 的切了,该降到小模型的降了,用户端拿到的是一个可接受的结果,而不是一个白屏 500。

## 一个最小可用的注入中间件

不需要一上来就搬 Chaos Mesh 这种重家伙。包一层 client,用配置控制每种故障的概率,就足够验证绝大多数降级逻辑了:

```python
import random, time
from myapp.errors import RateLimitError

class ChaosClient:
    def __init__(self, real, cfg):
        self.real = real
        self.cfg = cfg  # {"latency": 0.1, "rate_limit": 0.05, "bad_json": 0.05}

    def chat(self, **kw):
        c = self.cfg
        if random.random() < c.get("latency", 0):
            time.sleep(random.uniform(3, 8))      # 戳长尾延迟
        if random.random() < c.get("rate_limit", 0):
            raise RateLimitError("chaos: injected 429")
        if random.random() < c.get("bad_json", 0):
            return {"content": "{not valid json"}  # 戳输出校验
        return self.real.chat(**kw)
```

关键有三点:概率可调、按环境隔离、日志里统一打上 `chaos:` 前缀。前缀是为了事后能把注入的噪声和真实故障干净地区分开。先在 staging 把概率拉到 20% 跑一整轮,确认每条降级都走通,再考虑往生产放小剂量。

还要留意一个坑:注入的故障必须是幂等安全的。延迟、429 这类重试友好的故障随便造,但如果你的 chat 调用带副作用——扣费、写库、发消息——那么在注入 5xx 之前,先确认重试逻辑不会导致重复执行,否则你是在用混沌测试给自己制造真实的数据脏乱,得不偿失。

## 怎么把演练跑起来:从控爆炸半径到形成常态

生产演练的核心只有一个词:爆炸半径(blast radius)可控。三条硬规矩不能破。一是先圈人群,只对内部账号或 1% 流量注入,绝不碰真实付费用户;二是必须有一键总开关,改个配置就能秒停,别指望靠重新部署来灭火;三是演练期间死盯核心指标——成功率、P99 延迟、降级命中率,任何一项越线立即回滚,不犹豫。

还有一点最容易被忽略:注入故障的同时,要顺便验证告警真的会响。很多团队演练只看系统扛没扛住,却没发现监控其实是哑的。把"故意制造一次 500,确认 oncall 五分钟内收到告警"直接写进演练脚本——这一条的价值,一点不比容错代码本身低。演练结束别急着散,把每条触发了的降级路径、每个慢半拍的告警都记下来,这份清单就是你下次迭代的待办。

控住了半径,就该往深里走了。单点随机注入能验证单条保护,但真实事故几乎都是连锁的。一次 provider 的区域性故障,往往同时带来飙升的延迟、密集的 429 和偶发的 5xx;更糟的是你的重试还会反过来放大流量,把本就紧张的限流踩得更狠。只测单点,等于默认故障永远礼貌地排着队一个一个来——现实里它们是一拥而上的。

更进一步的玩法是场景化:把几种故障按真实事故的剧本编排起来。比如"延迟先涨两倍,30 秒后叠加 10% 的 429,再过一分钟升级成区域性 5xx"。这时你常会突然看见,平时各自都没问题的保护凑在一起却互相打架:重试加剧了限流,限流触发了熔断,熔断又把 fallback 的配额瞬间打满,最后整条链一起躺平。这种耦合问题,随机的单点注入一辈子也测不出来,只有把它们放进同一条时间线里才会暴露。

最后,再好的演练也怕"只做一次"。很多团队的混沌工程都死在"搞过一次、拍了照、再也没有第二次"。一次性的演练只能证明那一天没炸,证明不了下次还扛得住——代码天天在变,配置也在漂。真正有价值的,是把它变成例行动作。

最低成本的做法,是在 CI 里加一组"故障用例":每次发布前自动用 ChaosClient 跑一遍关键路径,断言降级分支仍然返回可接受的结果。这等于给你的容错代码也配上了回归测试,改坏了当场就红,而不是等到生产才暴露。再往上一层,是定期的生产演练——比如每月固定一个"故障日",提前周知、限定时段、限定流量,由固定的人盯着指标复盘。节奏比强度更重要:一次温和但长期坚持的演练,远胜于一次惊天动地、之后谁都不敢再碰的实验。最终目标,是让"上游随时会挂"长成团队的肌肉记忆,而不是每次出事都当成头一回。

## 踩坑清单

- 只注入不观测:没有 dashboard 和告警的混沌等于裸奔,先建好观测再开枪。
- 概率写死在代码里:一定要配置化、能热关,否则真出事时你只能干瞪眼等部署。
- 只测"挂了"不测"慢了":长尾延迟比直接报错更难缠,别漏掉延迟注入这一项。
- 把 chaos 流量算进真实 SLO:注入的失败要能被过滤掉,否则你的错误率报表全是假数据。
- 一次注入太多种故障:信号会互相污染,单点验证时一次只测一条降级路径,定位才清楚。
- 演练完不复盘:注入本身不产生价值,把暴露的问题变成修复项才算闭环,否则只是一场热闹。

容错代码不是写完就自动有效的,它和任何功能一样,需要被执行、被验证。你不主动触发,那它的第一次执行权,就等于交给了深夜的线上事故。
