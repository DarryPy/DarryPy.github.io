你有没有遇到过这种情况：Agent 的编排逻辑写得挺漂亮，工具也注册齐了，一跑起来却总在 function call 上翻车。LLM 把 user_id 填成字符串、把必填的 amount 漏了、在枚举字段里编了个根本不存在的 urgent_high。工具函数收到脏参数直接抛异常，整条链就断在这里。更糟的是有些脏参数不抛异常，而是被工具默默当成默认值处理，最后结果全错还查不出原因。今天聊的就是怎么在参数进入工具之前拦住它，再让 Agent 自己把错的地方改回来。

## 参数出错的三种典型形态

先认清敌人。LLM 生成的工具参数出错，绝大多数落在三类里，每一类的修复策略都不一样，别想着用一套逻辑硬扛过去。

第一类是结构缺失。必填字段没给，或者嵌套对象少了一层，再或者该是数组的地方给了单个对象。这类最好抓，schema 一跑就现形，把缺的补上模型通常一次就对。它多发生在字段多、层级深的复杂工具上，模型顾此失彼漏了几个。

第二类是类型错配。amount 该是 number 却给了 "100元"，timestamp 该是整数却塞了自然语言的"明天下午三点"。这类根源在于模型把"给人看的表达"和"给机器用的值"搞混了，光提示"类型错了"没用，得告诉它期望的确切格式和一个样例。

第三类最阴险：值越界或纯幻觉。字段结构和类型都合法，但值是模型凭空编的——枚举里不存在的选项、超出上限的分页大小、数据库里根本没这条记录的 ID。这类能骗过所有基础 schema 校验，只能靠业务规则和真实数据去兜底，也是最容易漏到线上的一类。

| 出错形态 | 校验手段 | 修复难度 |
|---------|---------|---------|
| 结构缺失 | JSON Schema required | 低，补字段即可 |
| 类型错配 | 类型 + 格式校验 | 中，需给样例 |
| 值越界/幻觉 | 枚举 + 业务规则 | 高，需喂回合法集合 |

## 第一道闸：执行前做结构化校验

别信任 LLM 的输出，也别让工具函数当第一道防线——工具内部抛出的异常栈对模型毫无帮助，它读不懂 Traceback。正确做法是在调用工具之前插一层独立的校验，把脏参数挡在门外，让工具函数只处理干净数据。

```python
from pydantic import BaseModel, field_validator, ValidationError

class TransferArgs(BaseModel):
    user_id: int
    amount: float
    priority: str  # 只允许 low/normal/high

    @field_validator("amount")
    @classmethod
    def amount_positive(cls, v):
        if v <= 0:
            raise ValueError("amount 必须大于 0")
        return v

    @field_validator("priority")
    @classmethod
    def priority_enum(cls, v):
        allowed = {"low", "normal", "high"}
        if v not in allowed:
            raise ValueError(f"priority 只能是 {allowed}，你给了 '{v}'")
        return v

def validate(raw: dict):
    try:
        return TransferArgs(**raw), None
    except ValidationError as e:
        # 把 pydantic 的报错压成一行行人话
        msgs = [f"字段 {err['loc'][0]}: {err['msg']}" for err in e.errors()]
        return None, "; ".join(msgs)
```

关键点在于 validate 返回的不是异常，而是一段能读的错误文本。这段文本待会要原样喂回给模型，所以它的质量直接决定了修复成不成。校验层还有个隐藏好处：它把"参数对不对"和"工具怎么执行"彻底解耦，工具函数从此可以假设入参永远合法，逻辑清爽很多。

## 自我修复循环：把报错喂回给模型

有了校验层，修复循环就水到渠成：调模型拿参数，校验，通过就执行，失败就把错误当成一条新消息追加进上下文，让模型带着报错重试一次。

```python
def call_tool_with_repair(llm, messages, tool_name, max_retries=3):
    last_raw = None
    for attempt in range(max_retries):
        raw = llm.get_tool_args(messages, tool_name)
        if raw == last_raw:           # 两次填的一样，回灌没用，别再烧 token
            break
        last_raw = raw
        args, err = validate(raw)
        if err is None:
            return execute_tool(tool_name, args)   # 校验通过才真正执行
        messages.append({"role": "assistant", "content": f"我调用了 {raw}"})
        messages.append({"role": "user",
                         "content": f"参数校验失败：{err}。请只修正错误字段后重试。"})
    raise RuntimeError(f"{tool_name} 参数修复 {max_retries} 次仍失败")
```

实测下来，绝大多数参数错误在第一次回灌后就修对了。原因很朴素：模型不是不会填，而是第一遍没拿到足够约束——你把它撞墙的确切位置精确告诉它，它自己就绕过去了。这比在系统提示里堆一大段"务必注意字段类型"要有效得多，因为反馈是精准的、针对当前这次错误的，而不是泛泛的事前叮嘱。

还有一点容易忽略：回灌的那两条消息用完最好清理掉，别让它们长期堆在上下文里。修复只是一次性纠偏，一旦参数校验通过、工具执行成功，把中间的错误对话折叠成一条简短记录即可，否则多跑几轮 Agent，光是历次修复的废话就能把上下文窗口撑爆，反过来又降低后续调用的准确率。

## 让报错信息对 LLM 友好

修复循环成不成，七成看错误信息写得好不好。同样一个越界错误，两种写法效果天差地别，这一步偷懒，前面的架子搭得再好也白搭。

差的写法是 "ValidationError: invalid value"。模型看完一头雾水，不知道是哪个字段、也不知道该改成什么，只能瞎猜，大概率原地打转甚至越改越错，白白耗掉宝贵的重试次数。

好的写法是 "priority 只能是 low/normal/high，你给了 'urgent_high'"。既点了字段名、又给了合法集合、还回显了它填错的值。模型几乎不用思考就能把 urgent_high 映射到 high，一次修复到位。

三个必备要素记牢：一是点名具体字段，别让模型猜是哪个错了；二是给出合法取值范围或格式样例，让它有明确靶子；三是回显它这次填错的值，形成"你填了 X，但应该是 Y 集合里的"的直接对照。做到这三点，实测修复成功率能从五成拉到九成以上。

时间类字段尤其值得单独给样例。你只说"timestamp 要整数"，模型可能给个毫秒又可能给个秒；你直接写"timestamp 需要 Unix 秒级整数，例如 1753776000"，它照着填几乎不会错。样例是最省字又最有效的约束，能配样例的字段就别只写类型。

## 修复不是万能：知道何时放弃、何时刹车

自我修复很香，但它有边界。硬把不该修的错拿去循环，只会浪费 token 还拖慢响应，识别出下面三种情况要果断跳出。

一是参数越界背后是任务本身不可行。模型想给一个不存在的用户转账，你再怎么校验回灌，它也变不出这个用户。这时该做的是把"资源不存在"作为结果返回，让上层 Agent 重新规划，而不是在参数层死磕。

二是工具 schema 本身有歧义。如果同一个字段模型反复填错、换着法子错，八成不是模型笨，而是字段命名或描述让它误解了。这种要回头改工具定义，把字段名、描述、样例写清楚，从源头减少出错，修复循环治标不治本。

三是错误其实需要人来拍板。涉及金额、删除、对外发送这类高风险操作，参数即使校验通过也别急着执行，插一道人工确认。修复循环负责保证参数合法，但"要不要做"这件事，超出了它的职责范围。

识别出该放弃的情况之后，剩下能修的错也得装好刹车。自我修复最大的坑是变成死循环——模型反复填同一个错值，每轮都在烧钱烧延迟。必须装好刹车再上路。

硬性重试上限是底线，一般 3 次足够，超过就说明这压根不是参数问题。原值对比是第二道保险：如果这次的参数和上次完全一样，直接跳出，回灌显然没起作用，再试也是白试。最后是降级路径，修复失败绝不能静默吞掉，要么抛给上层换工具或重新规划，要么转人工，把错误历史一并带出去别丢上下文。

踩坑清单，拿走即用：

- 校验层返回人话错误，别把工具的异常栈直接甩给模型
- 错误信息三要素缺一不可：点名字段、给合法集合、回显错误值
- 重试上限设 3 次，并检测"两次参数相同"提前退出
- 幻觉枚举值单独处理，把完整合法列表塞进提示里
- 任务不可行、schema 有歧义、需人拍板——这三种别硬修
- 每次修复都记 log，反复被填错的工具往往是 schema 该重写的信号
