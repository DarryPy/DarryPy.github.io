你的 LLM 网关前面挂着一层缓存,命中率 85%,看起来很美。直到某个热门问题缓存过期的那一瞬间——几百个用户同时问同一句话,全部 miss,全部穿透到上游,同一个 prompt 被原样打了几百次。这就是缓存击穿,在 LLM 场景里它不只是慢,而是真金白银:每一次重复调用都在烧 token、烧配额、占并发。single-flight 就是来堵这个洞的,而且代价小到不可思议。

## 缓存击穿在 LLM 场景有多贵

传统 Web 里缓存击穿顶多多打几次数据库,DB 一般扛得住,慢一点而已。LLM 完全是另一个量级:一次调用几秒钟、几分钱,还占着上游宝贵的并发配额。慢和贵在这里是同一件事。

假设一个爆款问题 QPS 50、响应 3 秒,缓存刚好过期,那 3 秒内就有 150 个请求同时在途,它们算的是一模一样的东西。你为同一个答案付了 150 份钱,还把并发池占满,把其他正常请求挤到排队甚至被限流直接拒掉。

更难受的是它的触发时机:越热门的问题缓存越容易被频繁访问,也就越容易在某个高峰点集中过期。击穿往往不是随机发生,而是精准地挑你流量最大的时候爆发,雪上加霜。

很多人第一反应是给缓存加随机过期时间、或者后台定时续期来缓解,这些手段能降低击穿概率,却堵不住并发那一刻的重复——哪怕过期只持续几百毫秒,高 QPS 下照样能挤进几十个相同请求。真正要治本,得从"同一时刻的并发去重"这个角度下手,这正是 single-flight 的战场。

## single-flight:在途请求只放一个出去

single-flight 的思路很朴素:给每个请求算一个 key,维护一张"正在执行"的表。第一个请求进来,发现表里没有,真正去调上游,同时把自己的 future 塞进表。

后面同 key 的请求进来,发现已经有在途的,直接 await 那个 future,不再发新调用。上游返回后,所有等待者共享同一份结果,然后把 key 从表里清掉。N 个并发请求,上游只承担 1 次,其余 N-1 次凭空省下。

它和缓存最大的区别在于时机:缓存复用的是"过去已经算完的结果",single-flight 合并的是"此刻正在算、还没出结果的并发请求"。前者管历史,后者管当下这一瞬间,正好补上缓存管不到的那个真空窗口。

注意上面那把锁只保护"查表和塞 future"这一小段,绝不能把真正的上游调用也包进锁里——否则并发全被串行化,比不合并还慢。锁要足够细、持有时间足够短,这是这段代码最容易写错、也最该 code review 的地方。

```python
import asyncio

class SingleFlight:
    def __init__(self):
        self._inflight: dict[str, asyncio.Future] = {}
        self._lock = asyncio.Lock()

    async def do(self, key: str, fn):
        async with self._lock:
            fut = self._inflight.get(key)
            if fut is None:
                fut = asyncio.ensure_future(self._run(key, fn))
                self._inflight[key] = fut
        return await fut   # 共享同一个 future,异常也一起抛

    async def _run(self, key, fn):
        try:
            return await fn()
        finally:
            async with self._lock:
                self._inflight.pop(key, None)   # 无论成败都要清掉

sf = SingleFlight()
# 100 个并发走到这里,上游只被真正调用 1 次
answer = await sf.do(cache_key, lambda: call_llm(prompt))
```

接进现有网关几乎零成本:把原来"查缓存 miss 后直接 call_llm"的那一行,换成"查缓存 miss 后走 sf.do"即可。顺序是缓存在前、single-flight 在中、真实调用在最里层,三者各守一道。

省下来的到底是多少?拿前面那个 QPS 50、响应 3 秒的爆款问题算笔账。没有 single-flight 时,缓存过期的 3 秒窗口里 150 个请求全部穿透,上游被调 150 次。

加上 single-flight,这 150 个请求里只有第 1 个真正发出,其余 149 个 await 同一个 future,上游只被调 1 次。省掉的 149 次调用,按一次几分钱算,单次击穿就是实打实的几块到几十块。

一天里这样的热点过期发生几十次,叠加起来就是一个月好几千的无谓支出。而这些钱省得毫无代价——答案完全一样,用户甚至感知不到,延迟还因为少占并发而更稳。这类"零负作用的纯收益"优化,在工程里并不多见,遇到了就别犹豫。

## 用对地方:key 设计与适用边界

key 太粗会把不该合并的请求揉一起——比如忽略了 user_id,导致 A 的个性化答案被发给了 B,这是会出线上事故的严重错误;key 太细又等于没合并,白加一层。

实战里 key 应该覆盖所有影响输出的输入:归一化后的 prompt、model、temperature、system prompt 版本号、以及任何注入上下文(RAG 片段、用户画像)的 hash。少算一个维度,就可能把语义不同的请求错误合并。

temperature>0 的随机生成要特别小心,用户可能就想要每次不一样的结果,这种场景干脆别合并。single-flight 只适合确定性输出,或业务上可以接受"同一瞬间大家拿到同一个答案"的请求,这个判断要提前和产品对齐。

key 对了,还要想清楚边界——single-flight 不是万灵药,有三类场景要主动绕开。第一种是低并发场景:如果相同请求几乎不会同时在途,这层表的维护和加锁纯属开销,合并率常年为零,不如直接去掉。

第二种是长耗时任务:一个请求要跑 60 秒,后来者全被绑在同一个 future 上等,万一第一个失败,所有人白等一分钟再一起失败,体验比各自跑还差。这种更适合用异步任务 + 轮询,而不是在线合并。

第三种是带副作用的调用:如果 fn 里除了拿答案还会写库、扣费、发消息,合并会让这些副作用只发生一次,而业务可能期望每个请求都触发。single-flight 只适合纯读、幂等、无副作用的调用,这条红线不能破。

## 和缓存、幂等、限流各管一段

别把这几个机制搞混,它们解决的是不同维度的问题,串在一起才完整。缓存管"算过的存起来复用",single-flight 管"此刻同时在算的合并",幂等管"同一个写操作重试不重做"。

请求的完整路径是:进来先查缓存,miss 则进 single-flight,真正调用后再回写缓存。限流站在最外层保护上游,而 single-flight 恰好能大幅降低到达限流器的真实调用量,相当于给限流器减负。

| 机制 | 解决的问题 | 触发条件 |
|------|-----------|---------|
| 缓存 | 时间上的重复 | 之前算过 |
| single-flight | 并发中的重复 | 此刻正在算 |
| 幂等 | 写操作重试去重 | 带相同幂等键重试 |
| 限流 | 保护上游不被打垮 | 超过配额阈值 |

## 踩坑清单

- 异常也要共享:上游报错时,所有等待者应一起收到这个错,而不是各自重试又把上游打爆;但留个开关,某些瞬时错误(超时、503)允许后来者快速重试一次。
- 别忘了超时:future 挂住了,所有等待者一起挂。给 await 加 deadline,超时后让后来者能另起一次调用,而不是陪着第一个请求一起死。
- 分布式失效:进程内的 single-flight 只在单实例有效,多副本部署下每个副本各放一次。真要全局去重得上 Redis 分布式锁,但那又引入新的延迟和故障点,先评估单实例合并够不够,大多数时候已经够。
- 流式响应要特殊处理:SSE 场景没法简单共享一个 future,得用广播把同一份 token 流 fan-out 给所有等待者,实现复杂度明显上升,上线前务必压测。
- 监控合并率:上报"被合并掉的请求数 / 总请求数",这个指标直接告诉你省了多少钱,也能反过来暴露你的 key 设计是不是出了问题。

一句话:缓存管昨天,single-flight 管此刻。把这层加在网关里,热点问题的账单能瞬间降一个数量级——而你只需要几十行代码和一次认真的 key 设计。
