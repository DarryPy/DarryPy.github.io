你最怕的从来不是 Agent 干错事，而是它悄无声息地把生产库的一张表清空了，等你发现时数据早没了，你连拦一下的机会都没有。读操作错了可以重来，写操作发出去就收不回来。

删除、转账、发邮件、改线上配置，全是一锤定音的动作。给这些工具加一层 dry-run，就是让 Agent 先把"我准备干什么、会动到什么"摊开给你看，确认无误再真正落地。这一步不复杂，却是你能拦下事故的唯一窗口。

## 读操作随便跑，写操作必须先预演

先把工具分成两类。读类工具——查询、检索、列目录——错了大不了再查一次，放心让 Agent 自由调用，硬加确认反而拖慢节奏，还会淹没真正重要的提示。

写类工具才是 dry-run 的目标：任何会改变外部状态的动作都算。判断标准很简单，这次调用如果连着重复十遍会不会出问题？会，它就是写操作，就该有预演模式，重复不出问题的才可以豁免。

别被动词骗了。有些看起来是"读"的调用其实有副作用：会计费的搜索、消耗配额的接口、带埋点的查询。判定标准只看两件事——它是否改变外部状态、是否花钱，跟叫 GET 还是 POST 无关。

别一刀切给所有工具都套确认。人对高频弹窗的本能反应是习惯性无脑点"是"，护栏套得越密，真正致命那一次反而越容易被随手点过去。把预演的仪式感，留给少数真正不可逆的动作。

## 给工具加一个 dry_run 开关

实现的核心只有一句话：预演和真跑走同一段代码，只在最后落地那一下分叉。绝不能为预演单独写一套逻辑，否则预演说能删、真跑却因权限失败，这份预演就成了骗人的假报告。

```python
def delete_users(ids: list[int], dry_run: bool = True):
    rows = db.query(
        "SELECT id, name FROM users WHERE id = ANY(%s)", ids)
    if dry_run:
        return {"would_delete": rows, "count": len(rows)}
    db.execute("DELETE FROM users WHERE id = ANY(%s)", ids)
    return {"deleted": rows, "count": len(rows)}
```

关键在于 `dry_run` 默认为 `True`。Agent 第一次调用只拿到"会删掉哪 3 行、分别是谁"，它把这份结果讲给你、或喂回自己复核，确认没问题后，才带 `dry_run=False` 再调一次真正执行。

别让每个工具各写各的开关。更稳的做法是在工具框架层统一处理：用一个装饰器或中间件拦住所有写操作，自动注入 `dry_run` 语义，谁也别想漏掉。统一注入，比指望每个作者都记得靠谱。

预演也不是免费的。每个写操作都要多跑一次查询来算影响面，高频调用叠加起来延迟和成本都不小。折中办法是只对高风险工具强制预演，低风险的按阈值动态开启，或把预演结果短暂缓存复用。

默认安全，比默认危险靠谱得多。哪怕框架某天漏传了参数、或是 LLM 忘了带上这个字段，兜底行为也是"什么都没删"，而不是"默默删光"。一张安全网的默认状态，必须是张开的。

## 预演要讲清"影响面"，而不是"我要做 X"

很多人把 dry-run 写成一句"即将删除用户"，这等于没预演。这种话 Agent 自己脑补都说得出来，没给任何可核对的信息，人和模型都无从判断到底该不该放行。

有用的预演要给出具体影响：命中哪几条记录、关键字段前后对比、涉及多少行、有没有级联删除、会不会触发下游 webhook。信息越具体，超纲的操作就越藏不住，红灯才亮得及时。

对比就一目了然：坏预演说"将更新配置"，好预演说"将把 `max_conn` 从 100 改成 10000，影响 3 个服务的连接池"。前者你只能闭眼点头，后者你一眼看出这数值离谱，当场喊停。差别不在措辞，在有没有把可核对的事实端上来。

预演结果尽量返回结构化数据，而不是一段自然语言。固定字段的 JSON 能让 Agent 程序化地比对阈值、自动判断要不要转人工，也方便你把它直接渲染成一张确认卡片，而不是让模型每次重新解析散文。

把这份 diff 摆给 LLM 看，它才判断得出这次是不是失控。比如你只想删一个测试账号，预演却显示会连带清掉 2000 条订单，异常立刻暴露，Agent 会自己收手而不是硬着头皮执行。

这份结构化预演还能反过来当测试工具。在 CI 里对着预演输出写断言，比如"这批参数只该动到 test_ 开头的表"，上线前就能拦下越权的批量操作，比等生产报警强得多。

含糊的预演比不预演更危险，因为它给了你虚假的安全感。你以为看过了、确认过了，其实那句话什么都没告诉你。预演的全部价值，都压在这份"账单"够不够细上。

## 哪些工具值得上 dry-run，谁来点头

不是所有写操作都值得预演。一次性、影响小、可回滚的动作，加 dry-run 反而啰嗦；高风险、不可逆、批量的操作，省这一步就是拿生产环境赌命。用一张表划清界线。

| 工具类型 | 要不要 dry-run | 预演给什么 |
|---|---|---|
| 删库 / 批量删除 | 必须 | 命中行数 + 样本记录 |
| 转账 / 支付 | 必须 | 金额、收款方、余额变化 |
| 发邮件 / 群发 | 必须 | 收件人列表 + 正文预览 |
| 改线上配置 | 必须 | 配置项前后 diff |
| 写单条业务日志 | 不必 | — |
| 幂等的 upsert | 可选 | 新增 / 更新条数 |

怎么让 Agent 老老实实先预演再执行？靠系统提示写规则不够牢，最好在框架层强制：写工具首次调用一律当预演，真跑必须带上预演返回的令牌。令牌绑定这批参数，中途偷改参数就作废，堵死"预演一套、真跑另一套"的漏洞。

预演产出后，按风险分三条路放行。低风险的，Agent 核对影响面在阈值内就直接执行；中风险的，把预演摘要发给人等一句确认；高风险的，强制人工二次确认并留痕审计，出了事能查到是谁点的头。

阈值要量化才有意义：删除超过 100 行、转账超过 500 元、群发超过 50 人，一律转人工。把"确认"用在刀刃上，人才会认真看每一条，而不是条件反射地点通过，让确认沦为走过场。

## 收尾：一份踩坑清单

这些坑全是用生产事故换来的，上线前逐条对一遍：

- `dry_run` 默认给了 `False`：一行默认值写反，整张安全网当场作废
- 预演和真跑走两套代码：预演能过、真跑翻车，这份预演就是假的
- 预演阶段带了副作用：预演时就先占了库存、发了请求，那还叫预演吗
- 只报"要做什么"不报"影响多大"：Agent 和人都没法判断，等于没预演
- 两次调用之间状态变了：预演时 3 行、真跑时变 5 行，落地前要复核数量或加乐观锁

最后别把 dry-run 当成万能药。它只管事前拦截，幂等设计防的是重试重复，回滚兜的是事后翻车，三道防线各守一段，缺谁都补不上另一个的窟窿。预演拦住的是"根本不该做"，另两层管的是"做了之后怎么收场"。

dry-run 的本质不是多写一个开关，而是把"不可逆"拆成"可预览 + 可确认 + 可执行"三步。多花这一步，你才真正握着拦下事故的那一秒钟。
