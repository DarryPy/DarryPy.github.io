你有没有遇到过这种情况：同一套 Chain-of-Thought 模板，在数学题上表现惊艳，换到逻辑谜题或多步规划就频频翻车。问题往往不在模型笨，而在你替它把"该怎么想"这件事提前定死了。

Self-Discover 换了个思路。它不给固定套路，而是让模型面对每一类任务，先自己挑选并拼装出一套推理结构，再照着这套结构逐题求解。相当于开考前，先让模型给自己写一份专属解题提纲，然后照纲答题。

## 为什么套死一种模板会碰壁

CoT、ToT、Plan-and-Solve 本质都是固定的推理脚手架。你选定其中一种，就等于默认所有任务都适合同一条思考路径。可现实里，规划任务要分解步骤，归纳任务要找规律，因果任务要排查变量，拿一把锤子敲所有钉子，总有敲不动的那颗。

few-shot 还藏着另一个陷阱：示例会把模型的思路锚死在你给的样例风格上，任务稍一变形，示例反而成了误导。你想覆盖所有情况，就得堆一大堆模板，维护成本越滚越大，还未必对得上真实分布。

还有个容易被忽略的代价：为了让一个万能模板尽量通用，你往往得往 system prompt 里塞进一长串"如果是 A 就这样、如果是 B 就那样"的分支说明。每道题都带着这坨长指令跑，token 白白烧掉不说，模型还得先在一堆分支里找到适用的那条，反而更容易分神。

Self-Discover 的出发点，就是把"选哪种推理方式"这件决策交还给模型自己。人不再预设唯一路径，而是提供一批可组合的思考零件，让模型按任务特征临场搭出最合适的那条链路。灵活性从此不靠你手写模板堆出来。

## Self-Discover 的两阶段：先组装蓝图，再逐题求解

它分两步走。Stage 1 是自我发现：模型面对一类任务，从一个通用的推理模块库里挑选、改写、再拼装出一套专属推理结构，输出成一份结构化蓝图。这一步关心的是"这类问题该按什么框架想"，而不是某道题的具体答案。

Stage 1 内部其实还能再细分三小步：先 SELECT，从模块库里圈出跟任务相关的几个原子；再 ADAPT，把这些通用原子改写成贴合当前任务的具体描述；最后 IMPLEMENT，把它们排成一份可执行的有序结构。你不必真拆成三次调用，但在 prompt 里点明这三步，蓝图质量会明显更稳。

Stage 2 是求解：对每一道具体题目，模型照着上一步的蓝图逐格填空，一步步产出中间结果，最后收敛到答案。蓝图在这里扮演硬约束，把模型的注意力钉在"当前该做哪一步"，而不是任由它自由发挥、东想西想。

妙处在于蓝图只需生成一次，就能复用到同类的成百上千道题上。所谓推理模块，是一批被抽象出来的思考原子，比如把问题拆成子问题、先列已知量、换角度重述、逐步演算并自检。模型要做的不是发明方法，而是从原子里挑合适的、按任务重排组合。

## 走一个具体例子

假设你要批量解一类"多条件排班"应用题。Stage 1 里，模型可能从模块库挑出三块拼成蓝图：先抽取全部硬约束、再逐个人排入可行时段、最后回查是否有冲突。它把这三块写成一份有序 JSON：

```json
{
  "step_1": "抽取题面里全部硬约束（人数、时段、禁排规则）",
  "step_2": "逐个人排入满足约束的可行时段",
  "step_3": "回查整张排班表，标出任何冲突并回退重排"
}
```

到了 Stage 2，每来一道新排班题，你只把题面和这份蓝图一起喂进去，模型就照着 constraints → assign → verify 的顺序推进。你会发现它很少再漏掉"回查冲突"这一步，因为蓝图里白纸黑字列着，而不是指望它每次都自觉想起来。

对比一下没蓝图时的情形：模型每道题都自己临场决定先做什么，遇到约束多的题就容易急着排班、把"回查"抛在脑后，错了还找不到是哪一步漏的。有了固定蓝图，出错时你能精确定位到是 step_2 排错还是 step_3 没查出来，调试从"重抽一次卡"变成"改哪一格"。

## 一个可复用的实现骨架

落地并不复杂，核心就是两次调用加一个模块库。第一次调用生成蓝图并缓存，之后所有同类题目共用它。下面这段伪代码勾出最小骨架：

```python
MODULES = [
    "把问题拆成更小的子问题",
    "列出所有已知条件与约束",
    "先估算量级，再精确计算",
    "换一种表述重新理解问题",
    "逐步推演并在每一步自检",
]

def discover_structure(task_examples):
    # Stage 1：只跑一次，生成可复用蓝图
    return llm(f"从模块库中挑选并改写，拼成解决这类任务的推理结构，"
               f"输出有序 JSON。\n模块库：{MODULES}\n样例：{task_examples}")

def solve(structure, question):
    # Stage 2：每道题按蓝图逐格求解
    return llm(f"严格按此推理结构解题：\n{structure}\n题目：{question}")
```

缓存的粒度值得琢磨：蓝图应该按"任务大类"而不是"单道题"来存。你可以给每类任务起个 key，比如 scheduling、causal_qa、code_review，命中就直接取蓝图，没命中才触发一次 Stage 1。这样新任务类型第一次慢一点，之后全走缓存，总调用量几乎只比原来多了任务种类那么多次。

蓝图也不一定非得是 JSON。对开放式任务，一段有编号的自然语言步骤同样能用，关键是"有序、可逐条对照"这两点。JSON 的好处是下游好解析、好做程序化校验；自然语言的好处是模型改写起来更自由。按你后续要不要机器读取来选就行。

真正上线时，你可以在两阶段之间插一道人工审核：Stage 1 生成的蓝图先让人扫一眼，缺了关键步骤就补回模块库，多余的步骤就删掉。审核只做一次，成本极低，却能挡掉大部分"蓝图本身就错"的连锁翻车。

## 什么时候值得用，什么时候别用

| 场景 | 更适合的做法 |
| --- | --- |
| 同类任务量大、可摊薄蓝图成本 | Self-Discover |
| 多步推理、路径因任务而异 | Self-Discover |
| 单次一次性问答 | 直接零样本 CoT |
| 需要并行探索多条候选路径 | ToT |
| 任务极简、一步即可作答 | 零样本直答 |

省钱逻辑一句话：一次发现、多次复用。任务批量越大、结构越稳定，摊薄到每道题上的那次蓝图调用就越划算。反过来，如果你只问一次，或者每道题解法都天差地别，生成蓝图那次调用就是纯浪费。

和 ToT 的区别也值得说清：ToT 是在同一种推理里横向铺开多条候选枝、再剪枝，解决的是搜索广度；Self-Discover 是纵向决定"用哪一种"推理骨架，解决的是路径选型。两者甚至能叠用——先让 Self-Discover 定框架，再在某个需要探索的步骤内部套 ToT。

所以别把它当银弹。它擅长的是"同一大类、需要多步推理、路径又因任务而异"的批量场景；碰到一步能答的简单问题，或者需要并行铺开多条候选路径的开放搜索，直接上零样本直答或 ToT 反而更省心。

**上线前的踩坑清单**

- 模块库别贪多：几十个原子模块会让模型挑花眼，精选 10 个左右通常就够覆盖常见任务
- 蓝图务必固化缓存：Stage 1 结果存下来复用，别每道题都重新发现一遍，否则成本优势归零
- Stage 2 别留自由发挥空间：把蓝图当硬约束喂进去，模型一旦开始即兴联想就前功尽弃
- 按大类切分蓝图：不同类任务配不同蓝图，硬套同一份跟当初套死 CoT 没有本质区别
- 关键业务加人审：让模型自己给自己出考纲，也得有人先验一遍纲对不对，再放它上线

说到底，Self-Discover 不是又一个更玄的 prompt 咒语，而是把"选方法"这一步显式外包给模型——你负责备好零件、把住验收，它负责临场组装。备好零件的人，永远比背好模板的人走得远。
