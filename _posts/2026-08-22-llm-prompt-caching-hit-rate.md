你给 agent 塞了一个两万 token 的 system prompt，接了工具、灌了检索文档，本以为开了缓存账单能砍一大截。结果一周下来，成本和没缓存时几乎一样。问题几乎从来不在你"忘了开缓存"，而在缓存根本没命中——你在某个不起眼的地方，每次请求都往前缀里塞了一个会变的字节。这篇就把命中规律、断点放法和验证手段一次讲透。

## 别把它和 Semantic Cache 搞混

先划清边界，这是最常见的概念混淆。Semantic cache 缓存的是"相似问题的答案"，靠 embedding 相似度判断命中，省的是重复问答的整次模型调用，命中与否是个概率判断。Prompt caching 完全不同：它缓存的是"请求前缀那部分的 prefill 算力"，靠字节级完全一致来命中，省的是每次都要重新处理长上下文的钱，命中是个确定性结果。

两者不冲突，也不解决同一个问题。你的长 system prompt、固定工具定义、检索进来的大段文档，这些每次请求都一模一样又特别烧钱的部分，正是 prompt caching 的主场。而 semantic cache 更适合挡在最前面，直接拦掉高频重复的整个 query。真实系统里两层可以叠着用，但这篇只聊后端这层确定性的 prompt caching。

一个直观的对照：同样是"用户又问了一次天气"，semantic cache 会判断这句话和历史某条问题够像，直接把旧答案吐回去，模型压根不跑；prompt caching 不管你问什么，只要你的前缀(系统提示、工具、历史)和上次逐字节相同，就复用那段已经算好的 prefill，模型照跑但便宜九成。前者省的是"要不要调"，后者省的是"调用里最重的那段计算"。搞混这两者，你会在错误的层做优化，然后奇怪为什么账单纹丝不动。

## 唯一铁律：前缀是字节级匹配

记住一句话就够用大半：prompt caching 是前缀匹配，前缀里任何一处字节变化，都会让它之后的全部缓存失效。渲染顺序是固定的 `tools` → `system` → `messages`，缓存 key 由渲染后的字节从头算起。所以位置越靠前的内容越"贵重"：工具定义在最前面(位置 0)，动一个工具、改个顺序，整条缓存从头作废；system 次之；messages 最后。

但也别过度恐慌，不是任何改动都全废。API 其实分三层缓存，改动只影响它所在的层级及之后：

| 改动 | tools 缓存 | system 缓存 | messages 缓存 |
|---|:---:|:---:|:---:|
| 增删/重排工具、切换 model | 废 | 废 | 废 |
| 改 system 内容 | 保 | 废 | 废 |
| 改消息内容 | 保 | 保 | 废 |
| 切 tool_choice、开关 thinking | 保 | 保 | 保 |

这张表的意思是：你可以每轮切 `tool_choice`、临时开关 thinking，而不丢掉 tools+system 那层大缓存。真正需要盯死的，只有工具定义和 model 这两个会让前缀从头重建的改动。

最常见的翻车，是有人把 `当前时间: {now()}` 拼进了 system prompt 开头。你自己看日志觉得内容"差不多没变"，但字节层面每次都不一样，后面几万 token 的缓存全部作废，账单纹丝不动。同类的隐形杀手还有：请求里带 UUID 或自增 id、没排序的 `json.dumps` 让 key 顺序漂移、按 Python set 遍历生成的工具列表顺序不稳定。这些都不会报错，只会让你的命中率静默归零，所以定位它们全靠事后 diff。

## 断点放哪：稳定在前，易变在后

`cache_control: {"type": "ephemeral"}` 就是断点，每个请求最多放 4 个。原则只有一句：把断点压在"稳定内容的末尾"，让易变内容落到它之后。

- **长 system prompt**：断点打在最后一个 system block 上，工具和 system 会被一起缓存。
- **多轮对话**：断点打在最新一轮的最后一个 content block，后续请求整段历史前缀都能复用，命中随对话增长而累积。
- **共享前缀 + 变化提问**：断点打在共享段末尾，绝不要打在整条 prompt 结尾——否则每次都在写新缓存却从不读取，纯付钱不省钱。

还有两个隐蔽约束常年坑人。一是最小可缓存前缀：Opus 4.8 要 4096 token 起，Sonnet 4.6 是 2048，不够长会静默不缓存，加了 marker 也白搭。所以一个三千 token 的提示在 Sonnet 上能缓存，搬到 Opus 上却悄悄失效，排查时很容易被这条门槛差异误导。二是 20-block 回看窗口：一个断点最多往前找 20 个 content block，agentic loop 里 tool_use/tool_result 成对堆积，一轮很容易超过 20 个，下一次的断点就找不到上一次的缓存了。对策是长轮次里每 15 个 block 补一个中间断点，把命中链接续起来。

## 架构纪律比 marker 更重要

真正决定命中率的不是你打了几个 marker，而是几条架构习惯。这几条比断点位置重要得多，要先修。

第一，冻结 system prompt。别往里拼 `当前时间: {now()}`、`用户: {name}`、`模式: {mode}`，这些坐在前缀最前端，会把后面几万 token 全部拖下水。动态上下文一律往后放，塞进 messages 里——后期支持的 model 可以用 mid-conversation 的 system 消息，否则就作为某轮 user 消息的内容。位置在第 5 轮的东西，不会让第 5 轮之前的任何缓存失效。

第二，别中途换工具或换 model。工具在位置 0，增删重排直接全废；缓存也是按 model 隔离的，切模型等于从零开始。要做"模式切换"，别去换工具集，而是给模型一个记录模式的工具，或者把模式当消息内容传进去。序列化工具时按 name 排序，保证字节稳定。

第三，fork 操作要复刻父请求的前缀。做摘要、compaction、子 agent 这类旁路调用时，很多人会另起一次请求重新拼 `system`/`tools`，只要有一点不同就完全错过父缓存。正确做法是原样拷贝父请求的 system、tools、model，再在末尾追加 fork 专属内容。

还有个并发时序的坑值得一提：缓存要等第一个响应"开始流式返回"之后才可读。你同时并发发出 N 个前缀相同的请求，谁都读不到别人还在写的缓存，结果 N 个全付全价。想扇出跑一批，正确姿势是先发 1 个、等它吐出第一个 token，再发剩下的 N-1 个，它们就能读到刚写好的缓存。对延迟敏感的交互场景，也可以在启动时发一个 `max_tokens: 0` 的请求预热缓存，把首个真实请求的冷启动延迟提前吃掉；但流量本来就连续的服务不必这么做，第一个真实请求自己就会把缓存焐热。

## 算清账、验证命中与踩坑

价格上，cache read 大约是基础输入价的 0.1×，cache write 是 1.25×(5 分钟 TTL)或 2×(1 小时 TTL)。5 分钟 TTL 下同一前缀请求两次就回本(1.25 + 0.1 低于不缓存的 2×)；1 小时 TTL 写入更贵，得三次以上才划算。流量连续用默认 5 分钟，只有那种长间隔的突发流量才值得上 1 小时。

但配置对不对不能靠猜，一定要看 `usage` 三个字段来验证：

```python
resp = client.messages.create(...)
print(resp.usage.cache_creation_input_tokens)  # 本次写入缓存，付 1.25×
print(resp.usage.cache_read_input_tokens)      # 本次从缓存读，付 0.1×
print(resp.usage.input_tokens)                 # 未缓存部分，全价
```

相同前缀连发几次，`cache_read_input_tokens` 却始终是 0，那必有静默失效源。最快排查法：把两次请求渲染后的 prompt 字节 diff 一下，第一个不同点就是元凶。收尾一份踩坑清单，照着自查：

- system prompt 里禁止 `now()`、UUID、session id 等每次都变的东西。
- `json.dumps` 记得 `sort_keys=True`，工具列表按 name 排序，别用 set 遍历。
- 不中途增删工具或切 model；要多模式就用工具或消息表达。
- 断点别无脑打在最末尾，共享前缀场景打在共享段结尾。
- 短于最小前缀(Opus 4.8 是 4096 token)不会缓存，别浪费那 1.25× 写入费。
- 上线第一件事就是盯 `cache_read_input_tokens`，不看这个数，你永远不知道缓存到底开没开。

一句话收尾：prompt caching 不是加个参数就生效的开关，而是"稳定的排前面、易变的排后面"这条架构纪律。前缀设计对了缓存自动命中，设计错了再多 marker 也救不回来。
