你手里有一个 1B 的模型，学习率扫了 8 个点，找到最优值 3e-3，信心满满地把同样的配置搬到 7B 上。结果 loss 前一千步就开始抖，降到 1e-3 才稳住，最后效果还比预期差一截。你只能再扫一轮，可 7B 跑一次就是几天的卡时，扫 8 个点根本扫不起。

这不是你运气差，而是标准参数化（Standard Parametrization，下文简称 SP）的天然缺陷：模型变宽，最优学习率就会漂移。μP（Maximal Update Parametrization）要解决的就是这件事——让最优超参在不同宽度之间保持不变，小模型上扫出来的值可以直接搬到大模型上用。

它和 Scaling Laws 解决的不是同一个问题。Scaling Laws 告诉你给定算力该训多大的模型、喂多少 token，μP 则告诉你这个模型的学习率、初始化该怎么定。前者管预算分配，后者管训练能不能一次跑对，两者配合使用效果最好。

## 为什么最优学习率会随宽度漂移

先看问题根源。SP 下你用 1/fan_in 的方差初始化权重，前向时激活值的尺度是稳的，这一点没错。但更新量不稳：Adam 给每个坐标的更新幅度差不多都是学习率那么大，一个宽度为 n 的隐藏层，n 个输入坐标的更新会在输出上叠加，叠出来的变化量大约随 n 线性增长。

于是宽度翻倍，同样的学习率在隐藏层上造成的激活变化也翻倍。小模型上刚好的步长，到大模型上就成了大步乱跳，你只能把学习率往下压。压多少没有公式可依，只能重新扫，这就是你在 7B 上踩到的坑。

很多人会想当然地按参数量开方去缩学习率，这种经验公式偶尔能蒙对，但它没有区分不同层：embedding、隐藏层和输出层对宽度的敏感程度完全不同，用一个全局系数去压，总有几层被压得过头，另外几层又压得不够。

更麻烦的是，输出层 logits 在 SP 下也会随宽度膨胀，训练早期 softmax 很容易饱和。很多团队靠 z-loss、更小的初始化去兜底，本质上都是在给 SP 打补丁。

还有一个经常被忽视的现象：在 SP 下把模型做得足够宽，它会逐渐退化成「懒惰训练」状态，隐藏层的特征几乎不动，只剩最后一层在学。理论上这对应 NTK 极限，实际表现就是大模型的特征学习能力被浪费，参数多了效果却没按比例提升。

## μP 到底改了什么

μP 的核心思路来自 Greg Yang 的 Tensor Programs 系列论文：给每一类参数单独设定初始化方差、学习率和前向乘子，使得宽度趋于无穷时，每一层的激活、更新量都保持 O(1) 量级，同时每一层仍在充分学习特征。下面这张表是 Adam 优化器下最常用的版本，m 表示宽度倍数，即当前宽度除以 base 宽度。

| 参数类型 | SP 做法 | μP 做法（Adam） |
|---|---|---|
| 输入 embedding | 学习率 η，init 固定 | 不变，学习率 η |
| 隐藏层矩阵 | 学习率 η | 学习率 η / m，init 方差 1/fan_in |
| 输出层 logits | 直接矩阵乘 | 前向乘以 1/m，或 init 置零 |
| attention 缩放 | 1/√d_head | 1/d_head |
| bias、LayerNorm | 学习率 η | 学习率 η，不缩放 |

注意 attention 那一行：从 1/√d 改成 1/d，是因为训练后 q 和 k 会产生相关性，点积随维度线性增长而不是开方增长。这一条最容易漏，漏了以后 head 维度一变，迁移就失效。

表里的规则看起来零碎，其实只有一个目标：让每一层每一步的激活变化量都和宽度无关。隐藏层的 fan_in 随宽度变大，所以学习率要除以 m 抵消累加；输入 embedding 的 fan_in 是词表大小，不随宽度变，所以学习率保持不变；输出层把宽维度收缩到词表，所以要额外乘一个 1/m 防止 logits 膨胀。想明白这一点，换别的结构你也能自己推出缩放规则。

## 落到代码上就三处改动

实际改起来比读论文轻松得多。你不一定要引入微软的 mup 库，自己在 optimizer 参数分组和前向里改三处就够。我在项目里一般会写成下面这样：

```python
import math
import torch

base_width = 256
width = 2048
m = width / base_width  # 宽度倍数

def build_param_groups(model, lr):
    groups = []
    for name, p in model.named_parameters():
        if p.ndim == 2 and "embed" not in name and "lm_head" not in name:
            groups.append(dict(params=[p], lr=lr / m))   # 隐藏层矩阵
        else:
            groups.append(dict(params=[p], lr=lr))       # embedding、bias、norm
    return groups

class MuPAttention(torch.nn.Module):
    def scores(self, q, k):
        d = q.shape[-1]
        return q @ k.transpose(-2, -1) / d               # 1/d 而不是 1/sqrt(d)

class MuPHead(torch.nn.Module):
    def __init__(self, width, vocab):
        super().__init__()
        self.proj = torch.nn.Linear(width, vocab, bias=False)
        torch.nn.init.zeros_(self.proj.weight)            # readout 零初始化
    def forward(self, h):
        return self.proj(h) / m                          # 输出乘子 1/m

opt = torch.optim.AdamW(build_param_groups(model, lr=3e-3), weight_decay=0.1)
```

改完以后务必先跑 coordinate check：取 4 个不同宽度，各训 10 步，画出每层激活的平均绝对值随宽度的变化。μP 正确时这些曲线是水平的；如果某层随宽度上翘，说明那层的参数分组写错了。这个检查只花十几分钟，却能省掉后面几天的白跑。

还有一个实践细节：base 宽度只是一个参考坐标，不必真的去训练它。你在 base 宽度为 256 时扫出最优学习率 3e-3，那么所有宽度的模型都把 3e-3 写进配置，参数分组会自动帮你按 m 缩放到各层，你在配置文件里看到的永远是同一个数字。这让超参管理变得干净很多，不同规模的实验也能直接放在一起对比。

## μTransfer 的实战流程

参数化改对了，真正的收益来自 μTransfer：用一个很窄的代理模型扫超参，再把结果搬到目标宽度。我的流程一般是这样：

- 定 base 宽度：比如 256，代理模型深度、词表、序列长度、batch size 与目标模型保持一致，只缩宽度。
- 扫三个核心超参：学习率、初始化标准差、输出乘子，用随机搜索各取几十个点，每个点只训几千步。
- 验证迁移：在 512、1024 两个宽度上复跑 top-3 配置，确认最优点不随宽度漂移，再上目标模型。
- 只迁移宽度：μP 保证的是宽度方向的迁移，深度、batch size、训练步数变化时仍要单独验证，深度方向可以参考 Depth-μP 或 CompleteP。

Cerebras-GPT 用这套方法在 40M 的代理模型上扫参，搬到 13B 后 loss 比 SP 基线更低；MiniCPM 也把同一思路当作「风洞实验」，用小模型定下学习率再放大。代理模型的总成本通常不到目标训练的百分之一，比在大模型上盲扫划算太多。

我自己的经验是，扫参阶段最好把随机种子也纳入考虑，每个配置至少跑两个 seed。代理模型小，单次结果的方差相对大，只跑一个 seed 很容易把噪声当成最优点。另外，扫参时 loss 要看训练末段的平滑值，而不是最后一步的瞬时值，否则排序会被偶然的波动打乱，选出来的配置在大模型上未必站得住。

## 踩坑清单

μP 原理不复杂，但实现细节一处错，迁移就会悄悄失效，而且不会报错，只会表现为大模型效果莫名差一截。下面是我和同事真实踩过的坑：

- 用了 tied embedding：输入 embedding 和输出层共享权重时两者的缩放规则冲突，要么解绑，要么按 mup 库的方式单独处理乘子。
- weight decay 不随 m 调整：AdamW 的有效衰减是 lr 乘以 wd，隐藏层 lr 除了 m，wd 的实际强度也跟着变了，需要用解耦写法或对应放大 wd。
- 忘了改 attention 缩放：仍用 1/√d，coordinate check 能过，换了 head 维度就不行。
- 拿 dropout 和 wd 做迁移：正则类超参和数据量强相关，μP 不保证它们可以迁移，需要在目标规模上单独确认。
- 代理模型太小：base 宽度低于 128 时噪声大，最优点本身就不稳，搬过去也没意义。
- 中途切换参数化：已经用 SP 训了一半的 checkpoint 不能直接改成 μP 续训，各层的有效步长会突变，loss 大概率当场跳起来。

如果你接手的是已有的 SP 训练代码，建议先在小规模上同时跑 SP 和 μP 两个版本，确认 μP 版本在 base 宽度下的 loss 不比 SP 差，再逐步放大宽度验证迁移效果。这样出了问题能快速定位是参数化本身写错，还是迁移范围超出了 μP 的保证。

一句话总结：SP 下你是在每个规模上重新碰运气，μP 下你只需在小模型上把运气碰对一次。
