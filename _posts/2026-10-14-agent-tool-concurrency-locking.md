你给 Agent 开了并行工具调用，延迟立刻掉下来，爽。直到某天两个子任务同时给同一个账户扣款、余额算错了，你才反应过来：并行不是免费的午餐。LLM 不懂事务，也不懂锁，它只会把能并行的调用一股脑丢出去。并发安全这件事，得你在工具层和编排层替它兜住，指望模型自觉是不现实的。

## 并行不是免费的午餐

最经典的翻车是 read-modify-write。工具 A 读到余额 100，工具 B 几乎同时也读到 100，两个各自减 30 再写回 70，本该是 40 的结果凭空多出 30。LLM 看到的是两次成功，日志一片绿，数据却悄悄错了。这种账面对不上的 bug，往往要等对账时才暴露，追查起来血压直接拉满。

另一类是重复副作用。Agent 判断"订单还没创建"，于是两个并行分支都跑去创建，下游冒出两张单；或者一次框架重试叠加一次并行，把通知发了两遍。根因都一样：工具调用之间共享了状态，却没有任何协调机制。你以为并行只是提速，其实它把单线程里根本不存在的问题，悄悄塞了进来。

更麻烦的是，这类 bug 在单元测试里几乎碰不到。测试通常串行跑，时序固定，竞态窗口压根不会出现；只有线上高并发时才偶发，且每次复现的时序都不一样。你盯着日志翻来覆去看，每一步都"对"，合起来却错，这种无从下手的感觉最磨人。所以别等它上线作妖，设计阶段就得把并发安全当成默认约束，而不是事后补丁。

动手加锁之前，先给工具分三类。纯函数类（查汇率、算哈希、格式化）天然无副作用，放心并行，它们怎么重入都不会坏数据。只读类（查余额、拉订单详情）可以并行，但要接受"读到的可能是旧值"，别拿它当强一致的依据去做写决策。

真正要盯紧的是写操作类（扣款、下单、发消息）。它们有副作用、会改共享状态，是所有竞态的发源地。一个实用的原则：先把工具按"读/写/纯"打标签，让编排层心里有数——读的随便并行，写的严格管控。很多团队出事，就是因为把写操作也当读操作一样无脑并发出去了。更隐蔽的是那种"看着像读、其实会写"的调用，比如一个查询接口顺手更新了最近访问时间，这种藏在读里的写，最容易漏标签、最容易翻车。

## 三种加锁思路，先看对比

应对并发，主流就三条路：悲观锁、乐观锁、串行化。选哪条，取决于冲突有多频繁、工具能不能安全重试、以及你愿意为吞吐牺牲多少。别上来就无脑加全局锁，那等于把并行的收益亲手还回去。

| 方案 | 核心做法 | 适用场景 | 主要代价 |
| --- | --- | --- | --- |
| 悲观锁 | 改之前先抢锁 | 冲突频繁、必须强一致 | 吞吐下降、易死锁 |
| 乐观锁 | 带版本号提交，冲突就重试 | 冲突少、读多写少 | 高冲突时重试风暴 |
| 串行化 | 写操作排队单线程跑 | 写少、顺序敏感 | 写吞吐受限 |

对 Agent 场景，乐观锁通常是甜点区：多数工具调用是读，真正的写冲突并不密集，带版本号重试的代价远低于全程持锁，也不用担心锁没释放把整条链路卡死。

## 乐观锁实战：比盲目加锁更合身

乐观锁的核心是 compare-and-set：读的时候连版本号一起拿走，写的时候带上版本号，只有版本没变才允许提交，变了就说明有人先改过，回头重读重算。

```python
def deduct(account_id, amount, max_retry=3):
    for _ in range(max_retry):
        row = db.read(account_id)          # 拿到 balance 和 version
        if row.balance < amount:
            return {"ok": False, "reason": "insufficient"}
        ok = db.update(
            account_id,
            new_balance=row.balance - amount,
            expect_version=row.version,     # 版本没变才成功
        )
        if ok:
            return {"ok": True, "balance": row.balance - amount}
    return {"ok": False, "reason": "conflict, retry later"}
```

关键有两点。一是把重试次数设上限，别让它无限循环；二是把"冲突"作为结构化结果返回给 Agent，而不是抛异常让它瞎猜。Agent 拿到 conflict，可以选择稍后重试或改走串行通道，而不是把半截状态当成成功继续往下走。把失败语义讲清楚，模型才有机会做对决策。

但加锁不是银弹，用不好还会带来一批更隐蔽的新坑，反而比竞态更难查。悲观锁最怕死锁：两个分支各持一把锁、又互相等对方那把，整条链路卡死。规避办法是给锁定个全局顺序，所有写操作一律按同一顺序申请锁，外加超时自动释放，宁可失败重来也别永久挂起。

乐观锁的反面是重试风暴：冲突一高，大家都在重读重试，CPU 空转、冲突更密，雪崩式恶化。应对是给重试加指数退避加随机抖动（jitter），把重试错峰开；冲突持续偏高，就说明这条路选错了，该把这个写操作直接降级到串行通道，而不是硬扛。

## 真正的防线在编排层

光靠工具内部加锁还不够，很多竞态发生在 Agent 的决策层。更稳的做法是在编排层分流：读操作继续放开并行，所有会改状态的写操作收进一个单写者（single-writer）队列串行执行。读写分离之后，你要加锁的面积一下子小了一大圈，推理和排查也简单得多。

再给每个写操作配一个幂等键（idempotency key），下游用它去重，就算 Agent 手抖、框架重试、并行分支各发一次，下游也只认第一次。幂等键要用"业务维度 + 操作意图"生成，比如扣款用订单号加用户加金额哈希，千万别用随机 UUID——随机键在重试时会变，去重也就彻底失效了。幂等加单写者这两道，才是真正托底的保险。

## 并发安全怎么测

前面说竞态在串行测试里测不出来，那就得主动制造并发。最简单是并发压测：开几十个协程同时打同一个账户扣款，跑完对账，余额对不上就说明有竞态漏网。进阶做法是故障注入，在工具的读和写之间人为插入延迟，把竞态窗口硬生生放大，让偶发问题变成必现问题，调试起来就踏实多了。

更讲究的团队会上确定性调度测试：固定随机种子、控制协程的切换时点，让每次跑的时序完全一致，竞态一旦复现就能稳定重放。不管用哪种，核心思路都一样——别指望线上帮你测并发，自己先把时序掰开揉碎地打一遍，把能想到的交错顺序都过一遍。

## 踩坑清单

- 别指望 LLM 自己避让并发，它没有事务概念，协调必须由你兜底。
- 先给工具打标签：读/写/纯，读的随便并行，写的严格管控。
- 凡是有副作用的工具都要幂等，并行默认当成"可能重入"。
- 幂等键用业务语义生成，不要随机，否则重试即失效。
- 乐观锁设重试上限 + 指数退避，否则高冲突会变重试风暴。
- 悲观锁按固定顺序申请 + 超时释放，避免互等死锁。
- 把"冲突"做成结构化返回值，别抛异常，让 Agent 能据此决策。
- 用并发压测加故障注入主动制造竞态，别把测试这步留给线上。

一句话：并行工具调用提速是真的，数据改坏也是真的。这俩本来就是一体两面，收益越大，裸奔的代价也越大。在你给 Agent 松开并发这根绳子之前，先把幂等和重试这两道保险扣好。
