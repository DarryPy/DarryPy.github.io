你有没有遇到过这种情况：chunk 切得不大不小，embedding 也换成了最好的那个，可检索召回的段落还是半句相关、半句噪声，LLM 读完一脸懵？问题常常不在模型，而在检索的"颗粒度"。命题化检索（proposition-based indexing）换了个思路——不按固定长度切片，而是把文档拆成一个个自洽的原子命题，让每条进入检索的单元只讲一件事。

这套方法来自 "Dense X Retrieval" 的研究，但真正落地时，拆分质量、回填策略和成本控制才是决定成败的三道坎。下面逐个拆开讲。

## 为什么 chunk 不是最优检索单元

传统 RAG 用固定 token 或句子窗口切片，天生带着矛盾。切大了，一个 chunk 混进好几个主题，query 的信号被无关内容稀释；切小了，代词和上下文又丢了，"它""该功能"到底指谁说不清。你把 chunk size 调到头，也只是在稀释和断裂之间找平衡，没从根上解决问题。

更隐蔽的问题在 embedding 层。一个 chunk 的向量是对内部所有 token 的某种聚合，只要段落里混进一句跑题的话，整段向量就被带偏，相似度打分跟着失真。这不是换一个更强的 embedding 模型能救回来的，病根在检索单元本身不够"纯"。

举个例子：一段讲"某 API 限流策略"的文字里，顺带提了一句"该服务 2023 年迁移到了 Kubernetes"。用户问限流，这句迁移史就是纯噪声，却照样被编进这个 chunk 的向量里，拉低了它和限流 query 的相关度。命题化会把这两件事拆成各自独立的单元，查限流时那句迁移史根本不会浮上来。

## 命题是什么，怎么拆

命题（proposition）是能独立成立的最小事实单元：主语完整、不含未解析指代、只表达一个意思。"Dense X Retrieval" 这篇工作的核心结论是——用命题当检索单元，召回精度和下游答案质量都优于句子与段落，尤其在需要精确事实的问答里，差距相当明显。

拆分通常交给 LLM：把原文段落喂进去，让它改写成一组自洽陈述句，并补全被省略的主语、时间、数值限定。prompt 的约束比模型选型更关键，宁可啰嗦也别留歧义。

```python
PROP_PROMPT = """把下面的段落拆成一组原子命题。要求：
1. 每条命题独立成立，不含"它/这/该"等未解析指代
2. 补全缺失的主语、时间和数值限定，从上下文还原
3. 一条命题只表达一个事实，不合并、不遗漏
以 JSON 数组返回。

段落：{chunk}"""

def to_propositions(chunk, llm):
    raw = llm.complete(PROP_PROMPT.format(chunk=chunk))
    return json.loads(raw)   # ["命题1", "命题2", ...]
```

拆分的直观效果长这样。原文"它在 v2 版本引入了批量接口，吞吐提升了约三倍"，拆完会变成两条自洽命题："某服务在 v2 版本引入了批量接口""某服务的批量接口使吞吐提升约三倍"。主语补全、指代消除，每条单独拎出来都读得懂——这正是检索需要的形态。

拆分质量参差是常态，别指望一把过。建议对拆出的命题做一轮轻量校验：长度异常、含残留指代、或和原文事实对不上的，打回重拆或直接丢弃。离线阶段多花点算力换一套干净索引，比上线后反复救火划算得多。

## 检索命题，回填原文上下文

光检索命题有个坑：命题太短，直接喂给 LLM 反而缺背景，生成的答案没头没尾。实战里的标准解法是 small-to-big 的变体——索引命题的向量，但给每条命题挂一个指向所属原始 chunk 的 parent_id，命题负责"找得准"，父 chunk 负责"讲得全"。

检索时用命题去匹配 query，命中后不把命题本身给 LLM，而是回填它的父 chunk，再做一次父级去重。这样既吃到命题带来的高召回精度，又保住了生成所需的完整上下文，两头的好处都占得上。

父单元用多大也有讲究。父 chunk 太大，回填后又把当初拆掉的噪声请了回来，等于白拆一场；太小，上下文仍然不够。实践中让父单元落在原始段落或一个小的 sentence window 上比较稳，既覆盖命题所需的背景，又不至于喧宾夺主。

| 检索单元 | 召回精度 | 上下文完整度 | 索引成本 |
|---|---|---|---|
| 段落 chunk | 中 | 高 | 低 |
| 句子 sentence | 中高 | 低 | 中 |
| 命题 proposition | 高 | 需回填 parent | 高（LLM 拆分）|

实现上有个细节容易漏：多条命题可能指向同一个父 chunk，回填时要按 parent_id 去重，否则同一段原文会在 context 里重复出现，既浪费 token，又可能让 LLM 过度偏信这段。去重之后，按命中命题的最高相似度给父 chunk 排序，再截断到你的 context 预算。

## 和 reranker、hybrid 怎么搭

命题化解决的是"检索单元纯不纯"，和其他 RAG 技巧不冲突，反而能叠加。你可以在命题层做 hybrid search——BM25 抓关键词、向量抓语义，两路召回的命题用 RRF 融合，再统一回填父 chunk，关键词和语义的漏网都能互相兜住。

reranker 也值得接上。命题短、语义集中，cross-encoder 给它打分比给长段落打分更稳，噪声少、信号强。常见链路是：命题召回 top 50 → reranker 精排 top 8 → 按 parent 去重回填 → 交给 LLM 生成。每一环都在为"喂进模型的上下文更干净"这一件事服务。

不过别一上来就堆全家桶。命题、hybrid、reranker 每加一层都增加延迟和运维复杂度，先用最朴素的命题召回跑出一个 baseline，再按 eval 结果决定到底加哪一层、值不值，比盲目叠加靠谱得多。

## 成本与适用边界

命题化不是免费午餐。拆分要为每段多调一次 LLM，离线索引时间被拉长；命题数量通常是原 chunk 的 3-5 倍，向量库的存储、写入和检索开销都跟着涨。上线前先把这笔账算清楚，别等账单来了才后悔。

所以它适合问答精度优先、知识库相对稳定的场景：产品文档、法规条款、医疗与金融 FAQ。不适合海量日志、高频更新的流式数据——那种场景反复重建命题的代价会把你拖垮。我的做法是分层：只对高价值、改动少的文档命题化，其余走普通 chunk，检索层做混合召回。

如果全量命题化还是太贵，有个折中叫双索引：原始 chunk 照常建一套向量，另给高价值文档额外建一套命题向量，检索时两套都查、结果融合。贵的那套只覆盖最该覆盖的文档，整体成本压得住，又拿到了命题在关键问答上的精度红利，不至于一刀切。

还有一步别省：上线前用自己的 eval set 做 A/B，对比命题化前后的 retrieval recall、context precision 和最终答案准确率，三个指标一起看。有些文档本身就写得很"命题化"，一句一个事实，再拆收益寥寥，纯属白烧 token；还有些结构性很强的表格和代码，硬拆反而破坏语义。数据会诚实地告诉你，哪类文档值得这么干、哪类该放过。

踩坑清单：

- LLM 拆分会漏信息或"脑补"出原文没有的事实，加约束并抽样人工核对，别全盘信任
- 命题丢了时间、数值、条件限定词就会退化成错误事实，prompt 里强制补全
- 别拿命题直接喂 LLM，一定回填 parent chunk，否则答案缺头少尾
- 索引膨胀 3-5 倍，先算清存储和 embedding 账单再定命题化的文档范围
- 增量更新时父 chunk 一改，挂在它下面的所有命题都要重拆重建，级联逻辑提前设计好
