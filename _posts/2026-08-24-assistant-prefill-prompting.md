你有没有遇到过这种情况：反复在 system prompt 里写"只返回 JSON、不要解释、不要加代码块"，模型却还是先来一句"好的，这是你要的结果："，然后才进入正题。你删掉它的废话，下一次它换个说法照样加。与其一遍遍求它改口，不如直接替它把话头开好。预填充(prefill)就是这么一招——你在请求里塞进一段助手回复的开头，模型只能顺着往下续写，而不是从零自由发挥。这篇讲清楚它怎么用、为什么灵、以及哪些坑别踩。

## 预填充到底改了什么

大多数 Chat API 的请求是一串消息，角色 user 和 assistant 轮流出现。常规调用里最后一条是你的 user 消息，模型负责生成一整条 assistant 回复，从第一个字到最后一个字都由它自己决定，你只能事后收拾。

预填充的做法是：你自己再追加一条 assistant 消息，但只写开头，故意不写完。模型接到的任务，就从"写一条回复"变成了"把这条没写完的回复续下去"。开头由你定，模型的自由度被你提前收走了一大半。

代码上几乎没有额外成本，用 Anthropic Messages 风格演示一下：

```python
messages = [
    {"role": "user", "content": "把这段话抽成 JSON: 张三,28,工程师"},
    {"role": "assistant", "content": "{\n  \"name\": \""}  # 这就是预填充
]
# 模型从 `{"name": "` 往下续，天然吐出合法 JSON，不会有客套前言
```

这个能力并不是所有平台都开放。Anthropic 的 Messages API 原生支持——你只要让消息数组的最后一条是 assistant 角色，它就会当作预填充往下续写。部分开源模型的推理框架也提供类似的续写补全模式；而一些闭源接口出于安全考虑做了限制。所以真正上手前，先确认你的目标平台认不认这条 assistant 尾消息，别拿一个不生效的技巧白忙一场。

那它凭什么比 system prompt 更硬？关键差别在约束的性质。system prompt 是"请你这么做"的软约束，模型可以理解，也可以打折执行；尤其在长对话里，早期的指令很容易被稀释，被后面几十轮内容一点点盖过去，格式就飘了。

预填充则是把回复的第一个 token 直接钉死。LLM 是自回归模型，每生成一个新 token 都要和前面已有的内容保持连贯，你写的开头就成了它绕不开的既成事实。开头越具体，它往下跑偏的空间就越小。

换句话说，system prompt 影响的是模型"想怎么说"，预填充直接决定了它"已经说了什么"。前者是建议，后者是既定事实，两者的硬度根本不在一个量级上。

## 三个立竿见影的用法

第一，锁定 JSON 输出。用 `{` 或 `{"key": "` 起头，模型没有机会先说"好的"，直接进结构体。你还能借开头钉死第一个字段名，顺带定死键的顺序，省去后处理里用正则从一堆文字里抠 JSON 的脏活。

第二，跳过客套前言。让它写代码时预填充三个反引号加语言名，回复直接从代码块开始；要它做判断时预填充"结论："，它就先给结论再补理由，省掉"让我们一步步分析"那种口水铺垫，也让下游程序更好截取想要的字段。

第三，锁定角色与语气。做角色扮演时预填充"[医生]"，能明显降低模型跳戏、自曝"作为一个 AI"的概率；要固定分点格式，预填充"1. "即可让它从有序列表开头，而不是先写一段没人会看的导语。

三种用法的共性是：你不是在描述你要什么，而是把"要什么"的样板直接摆到模型嘴边。它顺着接比凭空理解你的要求，出错率低得多，这也是 prefill 在生产里越用越顺手的原因。

## 进阶：和停止序列打配合

预填充管开头，停止序列(stop sequence)管结尾，两个配一对特别顺手。你用 `{` 预填充逼它进 JSON，再把某个固定标记设成 stop，模型吐完你要的结构就自动刹车，不会画蛇添足再续一段解释。

抽单个字段时更明显。预填充"答案是："，同时把换行符设成 stop，模型给完一行答案就停，你拿到的就是干干净净一行，不用再切割。做分类、打标签这类短输出任务，这一招能省下大把清洗代码。

要留意 stop 序列本身通常不会出现在返回里，所以如果你拿闭合符当 stop，记得自己把它补回去再解析；和预填充那段开头一起拼，才是完整合法的字符串。

## 预填充 vs 其他控制手段

| 手段 | 约束强度 | 额外成本 | 适用场景 |
|------|---------|---------|---------|
| System prompt 叮嘱 | 弱，可被无视 | 低 | 泛化风格引导 |
| Few-shot 示例 | 中 | 占 token | 复杂格式示范 |
| 预填充 prefill | 强，钉死开头 | 几乎为零 | 卡死起始格式 |
| 约束解码 / JSON mode | 最强 | 需引擎支持 | 严格 schema |

预填充的性价比在这张表里最突出：不烧额外 token，不依赖特殊推理引擎，只要 API 允许最后一条是 assistant 消息就能用。它和约束解码也不冲突——先用 prefill 钉开头，再叠 JSON mode 兜底，等于上了双保险。真正严格的 schema 场景，两者配合远比单靠提示词稳。

## 边界、翻车与上手清单

先说一个真实会踩的例子。你想让模型输出数组，于是预填充了 `[`，然后在代码里直接把接口返回值丢进 `json.loads`，结果永远解析失败，排查半天以为模型抽风。其实模型老实续了，问题在你少接了那个 `[`——接口返回的只是"续写部分"，预填充的开头得你手动拼回去。养成 `full = 预填充 + 返回值` 的习惯，这个 bug 就不会再找上你。

另一种翻车是预填充写太满。有人把大半个答案都填进去，只留模型补几个字，结果它被逼着照抄，反而失去判断力，连你开头写错的地方也不敢纠正。记住 prefill 是起手式，不是替身，把方向定住就收手。

也不是所有场景都适合把话头堵死。开放式创作、头脑风暴、需要模型自由发挥的任务，预填充反而会框住它的思路，让输出变得单调，你拿到的是被你开头带偏的答案，而不是模型真正想给的最优解。这类任务，把嘴堵上等于自废武功。

需要模型先思考再作答的推理任务也要小心。如果你预填充"答案是："，等于逼它跳过中间推理直接报结果，正确率往往会掉一截。这种时候要么别预填充，要么先把思维链的容器留出来，比如预填充"我先分析一下："，引导它展开而不是抄近路。

还要记住，预填充是一次性的，只作用于当前这一轮回复，不会改变模型后续的行为习惯。如果每轮都要同一种格式，靠预填充逐轮补太累，不如把格式要求写进 system prompt 当长期基线，再用预填充在关键轮次加固，两者分工，各管一段。

最后收几条上手时最容易忘的注意事项：

- 结尾别留多余空格或换行，"结论："比"结论： "更稳，尾随空格偶尔让模型多打一个空格
- OpenAI 系接口对 assistant 结尾消息的支持有限，跨厂商迁移前先实测一遍，别默认通用
- 别用 prefill 硬塞模型本该拒答的内容，既不可靠，也踩安全红线，不是它的正经用途

一句话总结：system prompt 是跟模型商量，预填充是直接替它开口。凡是能钉死开头的地方，就别浪费口舌去反复求它。
