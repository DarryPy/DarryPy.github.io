## 20 条测试集为什么会骗你

你上线前跑新版 Prompt，在 20 条测试集上准确率从 70% 冲到 85%，兴冲冲就合并了，三天后线上投诉翻倍。你第一反应是模型退化，其实问题出在样本量。20 条里差 3 条，很可能只是随机波动。小样本下准确率的方差极大，你看到的那个"提升"多半是掷硬币掷出来的运气，换一批测试集，结论立刻翻转，而你已经把锅甩给了模型和 Prompt。

把评测想成抛硬币会更清醒：每条样本要么对要么错，是一次伯努利试验，整份测试集就是一串抛硬币的结果。20 次里正面朝上 17 次是 85%，14 次是 70%，看着差了 3 个，但两组数据的置信区间几乎完全重叠。也就是说，即便模型真实水平根本没动，你也有相当大的概率随机抽出这样一组"看起来变好了"的数字。

样本越小，这种幻觉就越强。真正危险的地方在于，它给了你一种"我做了实验、有数据支撑"的踏实感，于是你反而更敢拍板。数据不会主动告诉你它有多不靠谱，除非你自己给每个数字都算一遍误差范围，否则你永远分不清眼前是真进步还是一次好运。

## 给准确率加上误差棒:置信区间与样本量

任何单个准确率数字，不带误差范围就等于没说。判断它可不可信，先算 95% 置信区间，二项分布下半宽约等于 1.96×√(p(1-p)/n)。p=0.8、n=20 时，这个半宽高达 ±0.175，真实准确率可能在 62% 到 98% 之间乱飘。你拿着一个"80%"去做上线决策，手里其实握着的是一整段区间，而不是一个干净利落的点。

反过来，先定好你能容忍多大误差，就能直接反推最少要测多少条：

```python
import math

def sample_size(p=0.5, margin=0.05, z=1.96):
    # p=0.5 是最保守估计,此时方差最大
    return math.ceil((z**2 * p * (1 - p)) / margin**2)

print(sample_size(margin=0.10))  # 97
print(sample_size(margin=0.05))  # 385
print(sample_size(margin=0.03))  # 1068
```

数字很不给面子：想要 ±5% 的可信度，最少 385 条；想压到 ±3%，得上千条。而当准确率贴近 0 或 1（比如越狱率这种极端值）时，上面这个基于正态近似的粗公式会失真，区间甚至会算出负数，这时该换成 Wilson score 区间。20 条能给你的，只是一个方向模糊的暗示，绝对不是能写进上线报告里的结论。不同精度对应的样本量差距，一张表就看明白：

| 目标误差 | 最少样本 (p=0.5) | 适用场景 |
|---|---|---|
| ±10% | 97 | 快速冒烟,选方向 |
| ±5% | 385 | 上线前 gate |
| ±3% | 1068 | 版本对比定论 |
| ±1% | 9604 | 安全红线指标 |

顺带提醒一句：样本量只是可信度的一半，另一半是代表性。你测了一万条，但全来自同一类简单问题，得到的漂亮区间也只对那类问题成立，一遇到长尾输入照样翻车。样本量解决的是"抽得够不够多"，分布覆盖解决的是"抽得对不对"，两者缺一不可，别用前者的统计严谨去掩盖后者的选样偷懒。

## A/B 比较盯的是差值区间,不是谁数字高

更常见的场景是 A/B 两版 Prompt 比高低。这时你真正要问的不是"B 是不是 85%"，而是"B 减 A 的差值，它的置信区间有没有越过 0"。如果差值区间落在 [-2%, +12%]，那就跨过了 0，统计上你根本无法断言 B 更好，哪怕 B 的点估计确实更高一截。很多团队恰恰在这一步栽跟头：看见 B 数字大就发版，本质上是在追逐噪声，还美其名曰数据驱动。

省样本的关键技巧是成对评测：同一条输入同时喂给两版，只记录谁赢、谁输、还是打平。配对能消掉题目本身难易带来的公共噪声，你比较的是每题的差异，而不是两个各自带着方差的绝对分数，因此能用更少的样本更早达到显著。这就像同一批学生做两套卷子对比，而不是拿两个班的平均分硬比，后者的干扰因素多得多。

落到工具上，成对结果对应的检验是 McNemar，或者干脆对差值做 bootstrap 重采样：把测试集有放回地抽上几千次，每次都算一遍 B 减 A，最后直接把差值的分布和它的置信区间画出来。这比脑补一个 p 值直观得多，也让非统计背景的同事一眼就能看懂"这次到底赢没赢"。

## 安全指标为什么要多测一个数量级

普通准确率错几个点顶多是体验差，安全指标错判则是直接出事故。而偏偏是越狱率、数据外泄率这类指标最难测准，因为它们本质是稀有事件：真实越狱可能几百条里才触发一次。你拿 100 条红队样本测出"0 次越狱"，很容易自我安慰成"很安全"，但 0/100 的 95% 置信区间上界接近 3.6%，放到百万级流量上就是几万次可能成功的攻击。

稀有事件的正确姿势有两条路。要么老老实实按 ±1% 精度把样本量往上堆，参考上表就是近万条的量级；要么做对抗采样，主动构造更容易触发问题的极端输入，人为抬高事件密度，再对统计结果加权还原到真实分布。无论走哪条，都切忌拿一次偶然的"0 次"当护身符。安全这条线，宁可测得慢一点、贵一点，也绝不能测得糊里糊涂就放行。

一个能落地的折中办法是分层：日常回归用几百条固定安全集守住基本盘，快速发现明显退化；发大版本或改核心 Prompt 时，再动用近万条的大集加对抗样本做一次深测。别每次都上全量，那样成本扛不住；也别永远只跑那几百条，那样迟早被没覆盖到的攻击面偷袭。把测试成本花在刀刃上，本身就是评估工程的一部分。

## 显著不等于重要,以及一份踩坑清单

最后一个反直觉的点：统计显著并不代表值得改。样本量一旦堆到几万，连 0.3% 的差距都能算出"显著"，可为这点提升去加一层复杂逻辑、多养一个分支，往往得不偿失。显著性回答的是"差异是不是真的存在"，效应量 (effect size) 回答的是"差异大到值不值得你动手"，上线决策必须两个一起看，缺任何一个都会把团队带进无效优化的泥潭。

还有个隐形杀手叫多重比较。你在同一份固定测试集上反复调 Prompt、反复刷分数，测得越多，纯靠运气蒙到一次"显著提升"的概率就越高，跟彩票买得多总会中一次是一个道理。对策要么每次大改后就换一批新样本，要么用 Bonferroni 之类的方法收紧显著性门槛，别把一次次偷看测试集攒出来的偶然，误当成真实的进步。

- 报准确率必带样本量和置信区间，单独甩一个百分比等于没说
- 冒烟阶段用小集快速筛方向，上线 gate 至少 300+ 条起步
- A/B 比较用成对评测加差值区间，别拿两个孤立数字硬比
- 安全指标（越狱、外泄）按 ±1% 精度或对抗采样，别信偶然的"0 次"
- 测试集定期换血，固定 20 条跑久了就是在过拟合你自己
- 显著性和效应量分开看：能测出来 ≠ 值得改

一句话：20 条测试集得出的结论，和抛 20 次硬币就断言硬币不公平，是同一个可信度。评估的第一性原理从来不是"你跑了没"，而是"这个数字，到底扛得住多大的误差"。
