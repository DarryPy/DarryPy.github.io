你给 Agent 挂了 30 个工具，结果它每次都调错，或者干脆不调——这不是模型的问题，是你的工具工程出了问题。

工具数量和选择准确率之间存在明显的负相关。当可用工具超过 20 个时，选错率在某些任务上会上升 15%-30%。原因并不神秘：模型需要在同一个上下文窗口里读完所有工具描述，再在生成阶段做多分类决策。工具越多，注意力越分散；描述越相似，语义边界越模糊；工具参数越繁琐，填错的概率越高。这三件事同时发生，就会导致 Agent 要么选错工具、要么用正确的工具传错参数、要么面对高度相似的两个工具时陷入僵局直接放弃调用。

更让人沮丧的是，这个问题往往在早期测试时发现不了。你用 5 个工具测试，一切正常；业务扩展到 30 个工具之后，准确率悄悄掉了 20 个百分点，而你没有监控，完全不知道。等到用户投诉才开始排查，发现问题早就埋下了。

问题是可以系统性解决的，不需要等更好的模型。下面六种策略从不同角度切入，可以单独用，也可以叠加用。

## 工具描述是第一道防线

`description` 字段不是注释，是 LLM 在推理时唯一可以参考的"工具说明书"。很多团队写工具描述像写变量注释——能看懂是什么，但不知道该什么时候用、不该什么时候用。这两个信息才是模型真正需要的。

差的描述：

```json
{
  "name": "search_orders",
  "description": "搜索订单"
}
```

好的描述：

```json
{
  "name": "search_orders",
  "description": "按订单号、用户 ID 或时间段检索订单列表，返回最多 50 条结果，含状态、金额、创建时间。适合用户问'我的订单在哪'或'帮我查一下 ORD-2025-xxxx'。如果只需要查单条订单的完整详情，请改用 get_order_detail，它返回的字段更全。"
}
```

关键差异有三点：说清楚**何时用**、**返回什么格式**，以及**何时不用（与相邻工具的边界在哪里）**。最后一点尤其重要——相似工具最容易造成混淆，在各自的 description 里互相指向对方，是最低成本的修正方式。加上一两个触发场景短语，模型在推理阶段可以直接做语义匹配，不必靠模糊的语感来猜。

参数级别也同样重要。`parameters` 里每个字段都该有 `description`，说清楚格式期望、可选值范围、默认行为。模型在填参数时和选工具时用的是同一套注意力机制——给的信息越具体，填错的概率越低。

## 工具分组与路由层

超过 15 个工具时，单层 tool list 就该考虑拆成两层了。先用一个轻量路由模型判断用哪个**工具组**，再让执行模型在小集合里选具体工具。

```
用户请求
  → 路由 Agent（工具：[order_tools, payment_tools, logistics_tools]）
    → 执行 Agent（只收到 order_tools 的 5 个具体函数）
```

路由层可以用更小、更快的模型处理，成本低、延迟短。执行层拿到的工具集从 30 个缩减到 5-8 个，选择准确率显著回升。这种架构的额外好处是横向扩展时只需要在路由层加一条，不需要修改执行层的 prompt 模板，也不会随着工具增加让整体 prompt 越来越臃肿。

工具组的划分粒度建议按照业务领域或用户意图类别，而不是按技术实现。用户说"我想退货"，路由层判断的是"售后意图"，而不是"需要调 HTTP 接口还是 gRPC"。

## Few-shot 示例注入

在 system prompt 里放 2-3 个已解决的完整工具调用示例，比冗长的文字说明更有效。大模型是从大量示例中学会推理的，提供具体的输入-输出对，它能直接类比，而不是从抽象描述推导。

```
【工具调用示例】
- 用户说"帮我查快递" → 调用 track_shipment(order_id=...) ，不要用 search_orders
- 用户说"修改收货地址" → 调用 update_shipping_address(order_id=..., address=...)
- 用户说"退款进度怎么样" → 调用 get_refund_status(order_id=...)，注意是 refund_status 而不是 order_status
```

注意：示例要覆盖**容易混淆的工具对**，不要只演示最简单、最明显的情况。如果线上已经出现过两个工具被混用的情况，专门为这对工具写一条区分示例，效果往往立竿见影。示例条数不宜超过 5 条，否则 prompt 变长反而引入噪音。

## 动态工具裁剪

不是每轮对话都需要全量工具。根据对话状态动态裁剪工具列表，是成本和准确率的双赢策略，也是扩展性最强的一种方案。

| 对话阶段 | 挂载工具集 | 工具数量 |
|---------|-----------|---------|
| 用户未登录 | auth_tools | 3 个 |
| 浏览商品阶段 | product_tools | 6 个 |
| 下单阶段 | order_tools + payment_tools | 8 个 |
| 售后阶段 | support_tools + refund_tools | 5 个 |

实现上不需要改模型，只需要在每次调 LLM API 前，根据 session state 或上一步工具的返回结果，过滤 `tools` 数组再传入。裁剪后的工具集更小，token 消耗下降，上下文更干净，准确率自然提升。这是工具工程里性价比最高的改进手段之一，尤其适合多轮对话场景。

极端情况下可以做到"工具按需注入"：Agent 在某一步调用了 `get_order_detail` 并拿到了订单信息，下一轮再根据订单状态决定注入哪几个处理工具，而不是从一开始就把所有工具都塞进去。

## 工具命名的语义一致性

`get_user` 和 `fetch_customer` 做同一件事，`query_orders` 和 `search_orders` 也做同一件事——这种命名混乱会让模型在两个候选之间反复横跳，或者随机选一个，都不是你想要的结果。

约定统一的动词前缀，并在整个工具集里严格执行：

- 查询单条记录：`get_`
- 查询列表/搜索：`search_` 或 `list_`
- 创建资源：`create_`
- 修改资源：`update_`
- 删除资源：`delete_`
- 触发异步动作：`send_` / `trigger_` / `dispatch_`

命名规范的底层原因是：大模型在预训练中见过大量遵循 REST 风格和 SDK 风格命名约定的代码，一致的命名能激活它对这类模式的"直觉"，降低生成时的歧义。修改命名不需要重新训练任何东西，成本几乎为零，但收益往往比反复调整 description 还明显。

## 工具调用日志与反馈闭环

线上部署后，把"这一轮调用了哪个工具"和"任务是否最终成功"记录下来。不成功的 case 里找出模型选错的工具，反查根因：是 description 写得模糊、命名有冲突、缺少 few-shot 示例，还是某个场景下工具集没有及时裁剪？

这套流程不需要 fine-tune，不需要大批量标注，只需要每周拿出一两个小时看错误样本，然后针对性地修改 schema。通常 2-3 轮调整之后，准确率就能稳定在高位。工具工程的本质是**持续运营**，把 schema 文件当产品文档来对待——它不是配置，是你和模型之间的沟通协议，需要随着业务变化持续迭代。

## 踩坑清单

- [ ] description 别以"该工具用于..."开头，直接说用途，省字且更直接
- [ ] 别把可选参数堆进 `required`，模型遇到填不上的必填项会直接放弃调用整个工具
- [ ] 相似工具必须在各自 description 里互相指向，明确边界
- [ ] 工具数量超过 20 个立刻考虑路由分层，别等到准确率崩了再重构
- [ ] 动态裁剪优先于堆 few-shot，前者从根本上减少选择空间，后者只是引导偏好
- [ ] 每个参数的 `description` 不能空着，尤其是 enum 类型的参数，必须列出所有合法值
- [ ] 线上一定要记工具调用日志，没有数据就没有迭代依据

工具选错，99% 不是模型笨，是你给的信息不够好。把 schema 当产品文档来写，Agent 自然选得准。
