你有没有遇到这种情况：把十段参考资料喂给模型，明明第五段里有答案，模型却信誓旦旦地答错了，或者直接说"资料中没有相关信息"？多轮排查后发现，答案明明就在那里，模型只是……没仔细看。

这不是随机失误，也不是偶发幻觉。研究者把这个现象称为 **Lost in the Middle**：当关键信息出现在长上下文的中间位置时，模型的回答质量会系统性地下降。理解它、绕过它，能在不改一行模型权重的情况下，让你的 RAG 系统准确率提升 10–20%。

## 为什么会"丢失在中间"

Transformer 的注意力机制在处理长序列时，对首尾 token 的关注度天然高于中间部分。这和人类阅读长文章有些相似——开头建立框架、抓住注意力，结尾给出结论、留下最后印象，中间段落容易被快读甚至跳过。LLM 的这个倾向更系统、更可量化。

Liu et al.（2023）做了一个干净的控制实验：固定文档内容，只改变"包含正确答案的那段文档"在上下文中的位置，统计多个主流模型的问答准确率。结果呈现出清晰的 **U 形曲线**：

- 关键文档放在第一位：准确率约 **75%**
- 关键文档放在最后一位：准确率约 **72%**
- 关键文档放在中间（第 10–15 位）：准确率跌至约 **55%**

这不是某个模型的特有缺陷——GPT-3.5、GPT-4、Claude 2 等当时的主流模型全部呈现相同的 U 形走势。上下文越长，"中间坑"越深，首尾与中间的准确率差距越大。

现代模型（GPT-4o、Claude 3.5、Gemini 1.5 等）通过架构优化缩小了这个差距，但没有消除它。不要因为用了"支持 128k token"的模型就认为问题消失了——**能读入和真正均匀推理，是两回事**。

## 策略一：首尾重排，把重要内容挪出中间

最直接的应对方案，成本几乎为零。在把检索结果拼成 prompt 之前，做一次"首尾优先"的重排：相关度最高的文档放第一位，相关度第二的文档放最后一位，其余文档按原顺序填充中间。

这个操作和检索系统的默认排序是反着来的，需要一个轻量的后处理步骤：

```python
def reorder_for_attention(docs: list[dict]) -> list[dict]:
    """
    输入：按相关度降序排列的文档列表
    输出：首位=最相关，末位=次相关，中间=其余文档
    """
    if len(docs) <= 2:
        return docs
    return [docs[0]] + docs[2:] + [docs[1]]
```

这个改动在多个内部基准评测中能带来 5–8% 的准确率提升。背后的逻辑很直接：利用模型天然对首尾的高注意力，把最有价值的信息放到模型最容易"看进去"的位置。

适用场景：文档数量在 15 段以内、每段长度适中的标准 RAG 流程，直接使用这个策略即可。

## 策略二：显式扫描指令，强制模型逐段审查

"中间盲区"的部分成因是模型没有被明确要求仔细检查每一段。在生成回答前，模型会对"哪些部分值得关注"做一次隐式规划，而这个规划本身就容易偏向首尾。加一条显式扫描指令，可以打断这个偏向：

```python
# 效果较差：没有引导扫描行为
system_prompt = "根据提供的文档回答用户问题。"

# 效果更好：显式要求逐段审查
system_prompt = """根据提供的文档回答用户问题。
请逐一审查每个文档片段，不要因为某段"看起来无关"就跳过。
确认已排查过所有片段后，再给出最终答案。"""
```

这种策略在文档数量为 5–15 段时效果最明显，能额外带来 3–5% 的准确率提升。超过 20 段之后，单靠指令收益递减，因为模型的"意愿"弥补不了注意力机制本身的局限，此时需要配合策略三。

两条策略可以叠加使用：先做首尾重排，再加扫描指令，效果叠加并不会互相抵消。

## 策略三：Map-Reduce 分批推理

当文档数量超出有效注意力范围——经验阈值是普通问答约 8–12 段、多跳推理约 4–6 段——与其把所有文档一次性送入，不如分批处理再聚合。每批上下文更短，模型注意力更集中；批次间信息独立，"中间坑"问题在每个批次内都更浅。

```python
async def map_reduce_qa(docs: list[str], query: str, llm) -> str:
    chunk_size = 6
    partial_answers = []

    # Map 阶段：每批独立回答，找不到就明确说
    for i in range(0, len(docs), chunk_size):
        batch = docs[i : i + chunk_size]
        answer = await llm.ask(
            context="\n---\n".join(batch),
            question=(
                f"{query}\n"
                "如果这批文档里没有直接答案，请明确回复"本批无相关信息"，"
                "不要猜测或补充批次外的内容。"
            ),
        )
        partial_answers.append(answer)

    # Reduce 阶段：基于局部结论给出最终答案
    return await llm.ask(
        context="\n".join(f"- {a}" for a in partial_answers),
        question=f"综合以上局部回答，给出最终简洁答案：{query}",
    )
```

Map-Reduce 的代价是调用次数增加，整体 latency 和 token 成本会上升。在高准确率要求的关键业务场景（客服知识库、合规审查、技术文档问答）下，这个代价通常是合理的。对 latency 敏感的场景可以用 `asyncio.gather` 把 Map 阶段并发执行，把多次串行调用压缩成一次并行。

## 四种场景的策略选择

| 场景 | 文档规模 | 推荐策略 |
|------|---------|---------|
| 轻量 RAG 问答 | ≤ 8 段 | 首尾重排即可，问题不显著 |
| 标准 RAG 问答 | 8–15 段 | 首尾重排 + 扫描指令 |
| 大规模文档召回 | > 15 段 | Map-Reduce 分批，Map 内仍做重排 |
| 超长对话历史 | > 20 轮 | 压缩早期历史，关键约束在 system prompt 首行重申 |

模型对比方面，Gemini 1.5 Pro 因为在长序列上的针对性训练，U 形曲线相对其他模型更平坦，但并非消失。Claude 3.5 系列在 32k 以内的上下文里表现相当稳定；超过 64k 后仍建议配合上述策略。

## 踩坑清单

- **更大的上下文窗口不等于更均匀的注意力**：128k token 不是 128k 的平坦有效推理，中间区域始终是洼地，只是近年来稍浅了些。
- **检索分数高不等于可以随意放位置**：不要把检索结果直接降序拼接，排名第一放首位、排名第二放末位，这一步重排不能省。
- **system prompt 也是上下文，也有中间盲区**：关键角色设定、安全规则、输出格式约束必须写在 system prompt 的最开头，别埋在第三屏。
- **模型不说"没找到"≠ 找到了**：中间位置的信息更容易被静默忽略，而不是主动报告"我没看到这段"——缺失答案不总等于缺失信息。
- **Map-Reduce 质量瓶颈在 Map**：如果每批文档里本来就没有答案，Reduce 阶段无法凭空合成正确结论，先保证检索召回率，再优化位置策略。
