你的 Agent 跑到第七步崩了。前六步里，它开了台云主机、发了封邮件、往数据库插了三条记录、还调支付接口扣了钱。重试？会把这些再做一遍。断点续跑？可上一次的半成品还躺在系统里没人收拾。这时候你要的不是往前走，而是把已经造成的副作用一件件撤回去——这就是补偿（compensation），也是很多 Agent 编排框架里最容易被跳过、上线后又最疼的一环。

## 先分清：重试、续跑、回滚是三件事

很多人以为工具做成幂等就万事大吉。幂等解决的是"同一个动作重复执行不出乱子"，它管不了"一串动作做到一半要不要全撤"。断点续跑更是反方向：它假设你想把剩下的做完。可现实里大量场景恰恰相反——中途失败意味着整笔操作作废，扣的钱得退、建的资源得删、发出去的工单得关，往前续跑只会让脏数据越滚越大。

数据库把这套语义叫事务，一个 ROLLBACK 就全回去了。Agent 世界里没有 BEGIN/COMMIT，跨的还是云主机、邮件、支付这些互不相干的外部系统，没有谁能帮你统一回滚。想要"要么全成、要么全撤"，只能自己在编排层把它搭出来——这就是分布式事务里的 Saga 模式落到 Agent 上的样子：没有全局锁，靠一串正向动作配一串补偿动作，把一致性一步步凑齐。

## 补偿栈：每个动作配一个反动作

思路很朴素：每成功执行一个有副作用的工具，就往一个栈里压入它的"反动作"。一旦后面某步失败，从栈顶开始逐个弹出执行——顺序天然是逆序的，最后做的最先撤，依赖关系自动对上。栈这个结构在这里几乎是白送的正确性。

```python
class CompensationStack:
    def __init__(self):
        self._stack = []

    def do(self, action, undo):
        result = action()            # 执行正向动作
        self._stack.append(undo)     # 成功后立刻登记撤销方式
        return result

    def rollback(self):
        while self._stack:
            undo = self._stack.pop()
            try:
                undo()               # 逆序补偿
            except Exception as e:
                log.error(f"补偿失败: {e}")  # 别中断，继续撤剩下的
```

用起来是这样：`saga.do(lambda: create_vm(), lambda: delete_vm(vm_id))`。有个细节能救命——undo 必须在 do 成功后立刻登记，而且要用闭包捕获**真实返回的 id**，不能等失败时再回头猜刚才到底建了什么。很多回滚 bug 就死在"撤的不是刚建的那台"，删错资源比不删更可怕。

## 落到一次真实编排：开通服务三件套

设想一个开通流程：建云主机 → 绑域名 → 扣月费。三步都有副作用，任何一步失败都要整单作废。把它写进补偿栈，正向和反向就成对出现：

```python
saga = CompensationStack()
vm = saga.do(lambda: create_vm(spec),
             lambda: delete_vm(vm.id))
saga.do(lambda: bind_domain(vm.id, domain),
        lambda: unbind_domain(domain))
try:
    saga.do(lambda: charge(user, price), lambda: refund(user, price))
except Exception:
    saga.rollback()      # 逆序：先解绑域名，再删主机
    raise
```

注意逆序的意义：绑域名依赖主机存在，撤的时候必须先解绑再删主机，反过来就会因为"主机不存在"而解绑失败。补偿栈天生按压栈顺序倒着弹，正好符合依赖方向，你不用手写任何顺序判断——这也是为什么值得用栈而不是普通列表顺序执行。

## 补偿本身也会失败，得留后手

最疼的一课：回滚代码同样会翻车——删主机时网络抖了、退款接口正好限流。所以补偿不能只 try/catch 打个日志就算完。三个兜底：一是每个 undo 也做成幂等，撤一半再撤一次不出问题；二是实在撤不掉的操作丢进死信队列（DLQ），转人工或延迟重试；三是全程记账，哪些补了、哪些没补一目了然，别让残留静悄悄躺着变成对不上的账。

| 正向动作 | 补偿动作 | 是否幂等 | 能否自动补偿 |
| --- | --- | --- | --- |
| create_vm | delete_vm(id) | 是 | 能 |
| charge(¥) | refund(¥) | 需幂等键 | 能 |
| insert_row | delete_row(id) / 软删 | 是 | 能 |
| send_email | 撤不回，补发更正邮件 | 否 | 半自动 |

表里最扎眼的是 send_email：邮件一旦送达就没有真正的 undo，你能做的只是补发一封更正。这类不可逆动作，能往整个流程后面挪就往后挪——把"点火"放在所有可回滚步骤都成功之后执行，失败面自然就小了，这是编排顺序层面几乎零成本的容错。

补偿最好别只靠内存里的栈，因为进程一崩栈就没了，残留反而彻底失联。稳妥做法是把每步的正向结果和对应补偿指令落库，做成一张 saga 状态表：每条记录带 `step / status / undo_payload` 三列，正向成功写 done、补偿成功写 compensated。这样即便 Agent 整个挂掉，重启后也能扫出所有 done 但整单失败的记录，照着 undo_payload 补撤一遍。补偿的 refund 之类还要带幂等键，避免重启重放时把钱退两次——记账和幂等键，是让补偿在崩溃场景下依然可靠的两根柱子。

## 并行分支会打破逆序假设

补偿栈的逆序正确性，建立在"动作是一条线顺序执行"的前提上。可 Agent 常常并行开火——同时建三台主机、同时发两个渠道的通知。这时候单纯按压栈顺序倒弹就不再等于真实依赖顺序，谁先完成谁后完成是不确定的，逆序反而可能撤错。

处理并行补偿有两条路：一是给每个动作显式声明依赖，回滚时按依赖图拓扑逆序而不是按时间栈；二是把并行的一组动作打包成一个"补偿单元"，组内无依赖可任意顺序甚至并行撤销，组间才讲究先后。别偷懒直接对并行结果套用 LIFO 栈——它在串行时是免费的正确，在并行时是免费的 bug。真正并发的编排，值得单独画一张依赖图再决定回滚顺序。

## 什么时候干脆别写补偿

补偿不是免费的，它让每个工具都得配一套反向逻辑，代码量和测试量都翻倍，还得维护两条永远要保持一致的路径。三种情况我会直接放弃自动补偿：副作用本就无法逆转（短信已发、货已出库）、失败后果轻到可以忽略（临时缓存文件残留）、或者操作设计成可覆盖（每次全量重写而非增量累加）。

后两种更省心的做法是"标脏 + 下次清理"：失败就把这条记录打上未完成标记，下一轮运行前先扫一遍脏状态统一收拾，而不是在失败瞬间硬凑一套回滚逻辑。把补偿的复杂度只留给真正"钱和资源会漏"的关键路径，其余交给幂等重试和定期对账，整体反而更稳、更好维护。

几条用血换的教训：

- undo 一定闭包捕获真实 id，别在失败时现推断刚才建了什么
- 补偿严格逆序执行，顺序反了会踩依赖（先删网卡再删主机就废了）
- 回滚路径也要写测试，它是最少被跑到、最容易烂掉的代码
- 不可逆的副作用尽量排到流程最后，缩小失败爆炸半径
- 分不清该重试还是该回滚时，先问一句：这步失败，整笔还算不算数——算，就往前续；不算，就往回撤。
