你花了大力气调 reranker、调 chunk size，检索出来的 top-5 片段条条相关，可最终答案还是漏掉了关键信息。别急着怪模型笨——问题很可能出在你把最相关的那条，恰好塞进了 prompt 的正中间。检索质量只决定捞到了什么，拼接顺序决定模型愿不愿意看，而后者常被彻底忽视。

## 中间位置的信息，模型会"看不见"

2023 年 Stanford 的 Liu 等人做过一个经典实验：在多文档问答里，把标准答案藏到上下文的不同位置，逐一测模型的召回准确率。结果画出来是一条清晰的 U 形曲线——信息在开头时准确率最高，挪到结尾也不错，可一旦落到中段就断崖式下跌，最惨时比只喂一半上下文还差。这个现象后来被命名为 Lost in the Middle。

更扎心的是，它和 context window 大小几乎无关。哪怕你用的是号称支持 128K 甚至上百万 token 的模型，只要有效信息压在中段，召回率照样掉。很多人误以为把窗口开大、多塞点文档就万事大吉，实际上塞得越多、中段越长，被埋没的关键片段就越多，反而是负优化。

对 RAG 系统而言这是个极隐蔽的杀手。你的 embedding、rerank、chunk 策略可能都调到了最优，检索命中率的离线指标很漂亮，可线上答案质量就是上不去。排查半天查不出原因，因为 bug 根本不在检索环节，而在你把结果拼进 prompt 的那一行代码里。更糟的是它不会报错、不会抛异常，只是安静地让答案少了一块，你甚至意识不到本该有的信息被吞掉了。

## 为什么会 Lost in the Middle

根子在 attention 的分布规律。Decoder-only 架构里，靠前的 token 会被后续每一个位置反复 attend，天然累积起更高的注意力权重；而结尾 token 离生成位置最近，recency 效应又让它格外醒目。夹在中间的内容两头都不沾光，注意力被严重稀释。

位置编码也在推波助澜。RoPE 这类相对位置编码，训练时见过的长距离依赖样本本就稀疏，外推到超长序列时，中段的位置信号衰减得更厉害。模型对隔得很远的中间那段，既没充分训练、编码信号又弱，自然容易略过。

还有一层来自数据先验。人类写作习惯把结论放段首、把总结放段尾，训练语料里重要信息集中在两端的模式被模型学了个透。于是它形成了一种根深蒂固的偏见：默认中间是过渡、是铺垫，可以粗读甚至跳读。三重因素叠加，中段就成了信息黑洞。

## 重排实战：把王牌放在头和尾

解法出奇简单：检索加 rerank 拿到有序结果后，别按相关性从高到低直接拼进 prompt，而是做一次折叠重排——把最相关的放到最前和最后，次相关的往中间塞。LlamaIndex 的 `LongContextReorder` 就是干这个的，原理一目了然，手写也就几行：

```python
def head_tail_first(chunks):
    # chunks 已按相关性降序排列，rank-1 在最前
    res = [None] * len(chunks)
    left, right = 0, len(chunks) - 1
    for i, c in enumerate(chunks):
        if i % 2 == 0:
            res[left] = c; left += 1     # 偶数序 -> 从头往中间填
        else:
            res[right] = c; right -= 1   # 奇数序 -> 从尾往中间填
    return res

# [A,B,C,D,E] -> [A,C,E,D,B]
# rank-1 的 A 占开头，rank-2 的 B 占结尾，最弱的 E 被压到正中间
```

这样 rank-1 牢牢占住开头、rank-2 占住结尾，最弱的证据被挤到没人细看的正中间，恰好卡在 U 形曲线的两个高点上。改动只有一个函数、零额外延迟、不调用任何模型，是性价比极高的一步。但别当成银弹：它的前提是你的相关性排序本身足够准，否则只是把烂结果更均匀地撒开而已。

上线前务必做一版 A/B：同一批 query，重排前后对比答案的 groundedness（有据可依程度）和关键事实命中率，用数据说话，别凭感觉拍板。经验上，当上下文里塞了 5 条以上片段时，重排带来的收益才明显；片段太少反而没必要折腾。除了 LlamaIndex，LangChain 的 `LongContextReorder` 和 Haystack 里也有等价组件，接入通常只是在检索链末尾加一个节点，几乎无侵入。

## 不止重排：从源头减轻中段压力

重排是治标，真正的上策是让中段根本不堆那么多东西。第一招是狠心截断：rerank 之后只保留分数明显偏高的 top-k，与其塞 15 条稀释注意力，不如精拼 5 条放对位置，多数场景下答案质量不降反升。判断阈值不用玄学，看 rerank 分数的自然断层即可——分数从某一条开始骤降，那条之后的基本都是噪声，果断砍掉。

第二招是 query-aware 压缩，用 LLMLingua 一类工具把每个片段里与问题无关的句子先删掉再拼接，等于变相缩短了中段长度。第三招是结构化提示：给每个片段加上明确的序号和来源标签，用显式结构对抗模型对中段的忽视，让它更容易定位证据。这三招可以叠加使用，效果比单靠重排更稳。

## 怎么确认你踩了这个坑

别停留在理论，给自己的技术栈跑一次 needle-in-haystack 测试：构造一批已知答案的 query，把那条答案 chunk 分别放到上下文的开头、中间、结尾，其余位置塞满干扰片段，然后对比三种摆放下的命中率。整个过程几十行脚本就能跑完，成本极低。

把结果画成一条曲线，你就能看清自己这套模型加 prompt 组合的 U 形到底有多深、掉点最狠的区间落在哪里。有了这条基线，重排前后的收益才能被量化，安全的 top-k 上限也能顺手定出来，不用再拍脑袋猜。更重要的是，每次换模型、换 prompt 模板，这条曲线都值得重跑一遍，因为它会实实在在地变。

## 排序策略对比与选型

| 策略 | 拼接顺序 | 适用场景 | 主要风险 |
| --- | --- | --- | --- |
| relevance 直接降序 | 最相关在最前 | 上下文短（≤3 chunk） | 中段信息被忽略 |
| head-tail 折叠重排 | 两端优先 | top-5~10 长上下文 | 依赖 rerank 质量 |
| 原文档顺序 | 按 source 位置 | 强时序/叙事文档 | 相关性信号丢失 |
| 分段摘要后拼接 | 中段先压缩 | 超长（>20 chunk） | 摘要引入误差 |

选型的核心判断其实只有一个：你的有效上下文到底有多长。三条以内压根没有中间可言，直接降序最省事；一旦进入 top-5 以上的长上下文，折叠重排几乎是零成本的免费午餐；文档本身有强时序（如日志、会议纪要、代码调用链）就老实按原顺序，别为了排序破坏语义连贯，那样得不偿失。

## 踩坑清单

- chunk 数 ≤3 时别折腾重排——三条以内没有中间，纯属过度工程。
- 重排是 rerank 之后的最后一步，顺序不能颠倒：先选对，再排好。
- 折叠重排依赖 rank 准确，rerank 模型不行的话，重排只会把烂结果均匀撒开。
- 评测别只盯 BLEU/ROUGE，要专门测关键事实是否命中，这才是 Lost in the Middle 真正影响的维度。
- 长上下文不等于万能：与其塞 20 条让模型自己挑，不如 rerank 后精拼 5 条、放对位置。
- 换模型要重测：不同模型的 U 形曲线深浅不一，老模型的最佳片段数不一定适用于新模型。
- 别只在中文场景验证：多语种检索里，跨语言片段更容易被当成噪声甩到中段，问题会被放大。

一句话收尾：检索决定你捞到了什么，排序决定模型愿不愿意看。这是一条投入产出比极高的优化——几行代码、零延迟、无需重训，却能把埋在中段的关键证据重新推到模型眼前。省掉这最后一步拼接，前面所有的检索优化都可能被一个糟糕的顺序悄悄抵消，实在太可惜。
