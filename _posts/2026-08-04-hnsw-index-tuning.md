你换了更贵的 embedding 模型，召回却没涨；你加了更多机器，P99 延迟还是抖。多数时候问题不在模型也不在硬件，而在向量索引本身的参数。HNSW 是当下 pgvector、Qdrant、Milvus、Weaviate 默认的近邻索引，它有三个决定命运的旋钮：M、ef_construction、ef_search。拧错任何一个，你要么召回低得可怕，要么延迟高得没法上线。这篇把三个参数拆开讲清楚，再给出一套可以照抄的调参顺序，让你不再靠运气填数。

## HNSW 到底在做什么

先建立直觉。HNSW 是一张分层的邻接图，最上层节点稀疏、跨度大，越往下层节点越稠密。查询时算法从顶层随机入口出发，在当前层贪心地走向离目标更近的邻居，走不动了就下沉一层，直到底层锁定最近邻。这种"先粗定位再精搜"的结构，让它在千万级向量上也能亚毫秒返回。理解这点你就明白：图连得好不好、搜得广不广，直接决定召回，而这两件事分别由建图参数和查询参数控制。

正因为是近似最近邻，HNSW 永远不保证百分百找到真正的 top-k。它用召回率来衡量准不准，recall@10 等于返回的前十里有几个是真正的最近邻。你的所有调参动作，本质都是在同一份数据上，用更多内存或更多查询时间去换更高的 recall。没有免费的召回，只有你愿意付多少成本。想清楚这句话，后面的取舍就都有了标尺。

## 三个旋钮各管什么

M 决定每个节点在图里连多少条边。边越多，节点之间的路径越通畅，贪心搜索越不容易走进死胡同，召回自然越高；但每条边都要占内存，M 翻倍内存也接近翻倍，建图时间同样上涨。M 是建索引时定死的，事后改不了，所以它决定了你召回的天花板在哪。

ef_construction 是建图阶段每个节点维护的候选邻居队列长度。它越大，算法在挑选邻居时看得越全，建出来的图质量越高、召回上限越高，代价是构建耗时显著变长。注意它只影响建图那一次，不影响任何查询，所以离线建索引时可以给得慷慨些，用一次性的时间换长期的质量。

ef_search 是查询阶段的候选队列长度。它越大，搜索时探索的节点越多，召回越高、延迟也越高，且近似线性。最关键的一点：ef_search 是查询期参数，上线后可以随时改，甚至按 query 动态调整。记住这句话——M 和 ef_construction 建索引时定，ef_search 查询时定，这条界线决定了你调参的先后。

三者的关系可以这样记：M 和 ef_construction 一起决定图的质量，也就是召回能到多高的上限；ef_search 决定你在查询这一刻愿意花多少时间去逼近那个上限。上限由建图时的两个参数封死，逼近程度由查询参数实时控制。所以健康的做法永远是先把上限建高、再动态逼近，而不是上限没建够就拼命加 ef_search 硬撑，那只会白白付出延迟。

## 参数取舍与实战配置

三个参数并非各自独立，它们共同决定你落在召回-延迟-内存三角里的哪个点。下表是千万级 768 维向量上的经验区间，具体数值随数据分布浮动，但趋势稳定可靠，可以直接当起点。

| 参数 | 调大的收益 | 调大的代价 | 常用区间 | 何时定 |
|------|-----------|-----------|---------|--------|
| M | 召回上升、图更稳 | 内存增加、构建变慢 | 16–48 | 建索引 |
| ef_construction | 图质量更好、召回上限更高 | 构建时间显著变长 | 100–400 | 建索引 |
| ef_search | 查询召回上升 | 查询延迟线性上升 | 40–200 | 查询期 |

核心洞察是：ef_search 是你上线后唯一能实时拧的旋钮，所以要先把 M 和 ef_construction 建得足够好，把召回天花板抬高，再靠 ef_search 在线做召回和延迟的精细权衡。M 建小了，事后无论怎么加大 ef_search 都补不回丢掉的召回，唯一补救是重建整个索引，那是最贵的操作。落地时各库参数名略有差异但语义完全一致：

```sql
-- pgvector：建索引时定 m 和 ef_construction
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops)
  WITH (m = 32, ef_construction = 200);

-- 查询前按需临时调大 ef_search（会话级，不用重建）
SET hnsw.ef_search = 100;
SELECT id FROM docs ORDER BY embedding <=> :q LIMIT 10;
```

```python
# Qdrant：hnsw_config 建图，search 时用 hnsw_ef 覆盖
client.create_collection(
    "docs",
    vectors_config=VectorParams(size=768, distance=Distance.COSINE),
    hnsw_config=HnswConfigDiff(m=32, ef_construct=200),
)
client.search("docs", query_vector=q, limit=10,
              search_params=SearchParams(hnsw_ef=100))
```

一个实用技巧：给不同场景配不同的 ef_search。用户实时问答走小 ef_search 保延迟，离线批量评测或高价值查询走大 ef_search 保召回，同一份索引服务两种诉求，不用建两套，也不用重复占内存。

上线前一定要算内存账，别等 OOM 才后悔。HNSW 的图部分开销大致等于向量条数乘以 M 再乘以每条边的字节数，加上向量本身占用，M 越大这块越重。千万级向量把 M 从 16 提到 48，图内存可能翻三倍，这在小样本压测里完全看不出来，只有用真实规模跑一遍才知道机器扛不扛得住，所以定 M 之前先按公式估一遍量级。

## 调参与排查顺序

别拍脑袋填数，按目标倒推。先准备一份几百条 query 的评测集，标好每条对应的正确文档，用它来算 recall@10，没有这份集合后面全是玄学。有了尺子，才谈得上优化。

第一步固定 M=32、ef_construction=200 建一版索引，这是绝大多数场景的安全起点，先跑通再说。第二步只扫 ef_search，从 40 起每次翻倍，记录每一档的 recall 和 P99 延迟。你会看到一条清晰的曲线：召回先陡升后走平，出现一个明显拐点，越过它 recall 几乎不涨、延迟却继续爬。取拐点略靠右的值，就是你的上线配置。

第三步只有当拐点处 recall 仍够不着目标时，才回头把 M 提到 48 重建索引，把天花板抬高，再重复第二步。这个顺序的意义是：先把免费的查询期参数榨干，再动昂贵的重建，绝不反过来。多数团队折腾半天，其实一步都没走对。

如果参数都扫过召回还是上不去，先别换模型。第一查距离度量是否对齐：建索引用 cosine、查询却按 L2，或者向量入库前没归一化，这类不匹配会让召回莫名其妙地烂，且怎么调 ef 都没用，是最高频最隐蔽的坑。第二查评测集本身可不可信，标注有噪声或 query 与文档不在同一语义空间，那 recall 再低也不代表索引有问题，你只是拿错了尺子。确认度量对齐、评测集可信，再回到参数上，才不会在错误方向上反复空转。

最后说重建的时机。HNSW 支持增量插入，但大量删除和高频更新会让图逐渐退化，被删节点留下的空洞让路径变绕，召回悄悄下滑却不报错。经验做法是给索引设一个健康指标，比如累计写入量或删除比例超过阈值就触发一次离线重建，用一份干净的图换回召回。别把重建当成救火手段，而要当成周期性维护排进计划，这样你的召回曲线才能长期稳住，而不是上线三个月后莫名其妙变差还查不出原因。

## 踩坑清单

- ef_search 必须大于返回的 top_k，否则队列装不下就悄悄丢召回，常见于 ef_search=10 却要 LIMIT 10。
- 别用整库平均延迟骗自己，盯 P99，HNSW 的尾延迟往往是均值的三到四倍。
- M 翻倍内存也几乎翻倍，上线前务必用真实规模压测内存，别在小样本上定 M。
- 数据大量增删后老图会退化，写入太猛时定期重建，别指望它自愈。
- 调参一定要配评测集，没有 recall 数字的调参都是在换一种方式抖延迟，不是优化。
